# T-10 证据：agent 套件里一条既有的间歇红（只登记，不修）

对应 `change.md` 的 **D-27** 与 **Q-07**。原始转录：`evidence/task-10-flake.out`。

被测用例：`tests/test_sidecar_entry.py::SigtermTests::test_a_request_in_flight_when_the_signal_arrives_is_waited_for`
（断言原文见 `test_sidecar_entry.py:348-375`）。它红一次的形态是：**有一个请求还压着连接，进程却照样退了**
——即「有请求在飞时退出必须被拖着」这条性质当场不成立。

这条红**不是本 CHG 引入的**：本 CHG 对 agent 侧的改动只有 `config_online/` 的两个文件与
`tests/test_config_shipping.py`，都不在被测路径上；量测也是在**未跑过本 CHG agent 改动**的树上做的。

## 1. 现象与分母

| 量测 | 读数 | 说明 |
|---|---|---|
| 原树（当前树，revert 掉本 CHG 的 agent 改动后同样跑） | **1 / 20** | 两次独立量测都是 1/20 ⇒ 这条红**稳定地存在**（约 5%），不是幻觉 |
| 关闭门禁时首次撞见 | —— | 门禁跑 agent 套件时撞上，是本 CHG 发现它的场合 |

5% 的量级意味着：任何一次「跑一遍套件全绿」都**必然**经常看到绿，这正是它此前从未被记录的原因。

## 2. 判别实验：想证什么，以及它反而证出了什么

**假设**（不是结论）：「SIGTERM 可能赶在连接被 `accept`、其处理线程登记**之前**到达，
于是那一刻确实没有请求在飞，退出便不拖」——若成立，只要在请求行发出后**多等一会儿**再发信号，
窗口就关上了。

判别实验的做法：一次性探针（`tests/zz_t10_race_probe.py`，**不提交、用完即删**）复用同一套
`_start`/`_sigterm` 夹具，只加一个旋钮 `PROBE_WAIT` = 「请求行发出后、SIGTERM 之前等多久」。

| 臂 | 旋钮 | 读数 |
|---|---|---|
| P（真实例） | —— | **1 / 20** |
| A（探针，不等） | `PROBE_WAIT=0` | **6 / 40**（15%）；更早一次同臂是 **2 / 40** |
| B（探针，等 0.3s） | `PROBE_WAIT=0.3` | **11 / 40**（27.5%） |

**方向与假设相反**：多等 0.3s 不但没关掉窗口，红得更多。更早一轮的 15 次小样本曾读出
「不等 2/15、等 0.3s 0/15」这个与假设一致的方向；**40 次样本把它翻了过来**。

**但翻转本身也算不上证据**，三件事把它压住：

1. **同臂两次就能差 3 倍**：A 臂先 2/40、后 6/40。Fisher 精确检验双尾 **p ≈ 0.53**——
   同一个臂、同一个旋钮，两次跑的差就已经不显著，这给「15～40 次样本能分辨什么」定了个下界。
2. **A 与 B 的差也不显著**：6/40 vs 11/40，双尾 **p ≈ 0.55**。
3. **块序混杂**：三臂是**块状**跑的（P 全跑完再 A，A 全跑完再 B），不是交错随机化。
   于是「B 比 A 差」与机器负载、残留句柄、块序混在一起，这次量测**分不开旋钮与顺序**。

**另外**：探针与真实例在名义相同的场景下（都不等）红得不一样（6/40 vs 1/20，p ≈ 0.81），
说明探针**不是**真实例的忠实替身——这也是不能拿它的方向去推真实例机制的理由。

## 3. 结论：不宣称机制，不用一个 `sleep` 糊过去

- **机制未定**。假设既没被证实，也被那 40 次的方向顶了一下；而块序混杂使得连这个「顶」都还不足以下判断。
- **因此不修**。加一个 `sleep` 恰好是「凭一次跑通接受显然的一行修法」：它会把窗口从视野里藏起来，
  而窗口还在。按本 CHG 自己的规矩（先红要真红、否定结论要报分母），**登记**才是这里的正确动作。
- 处置方向留 **Q-07（未裁定）**：该改测试（用例的断言假定了不该假定的时序）还是该改实现
  （`serve()` 的停机顺序是生产问题）。
- **它影响一个措辞**：在 Q-07 关闭之前，「agent 套件全绿」这句话**不成立**——
  LEDGER、AC-11 与 `evidence/test-summary.md` 都按这个口径写。它也会随机打红后续任何一次门禁，
  登记在此，免得下一个人以为是自己的改动造成的。

## 4. 未取得的读数与作废的记录（如实登记）

- 更早一轮 15 次小样本（不等 2/15、等 0.3s 0/15）：**不足以支撑方向判断**，已在 §2 说明它被什么推翻。
- 一个跑 40×2 的后台任务：命令本身 exit 0，但**输出文件是 0 字节**（日志没被捕获），读数**丢失**，不作数。
- 另一次 40 次重跑：因超时被移到后台后被**重复执行**，两个循环同时往同一个文件写，
  只保住 A 臂那一行（2/40）；**B 臂那一轮没有拿到**，记为未取得。此后改用
  单进程串行 + 每次迭代 20s 上限的驱动（`/tmp/t10-flake-driver.py`，一次性，不在仓内）。

## 5. 这份证据证不到什么

- 证不到机制。上面所有数字加起来只够说「这条红是真的、量级约 5%～15%、且本次没能定位」。
- 证不到「实现没问题」。红的是用例，但**根因可能在实现**（Q-07 的另一半），本次没有分开这两者。
- 证不到它不影响生产：`daemon_threads` / `shutdown()` 的时序本身已在 T-03 落过盘
  （`evidence/task-03-exit.md`），但这条红与那套改动**是否同源**，本次没有验证。
