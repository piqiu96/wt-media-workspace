T0.2　注入机制验证（关键：必须先证明锁真能挡住写入）
----------------------------------------------------------------
用 `SELECT id FROM materials FOR UPDATE` 取锁后，第二会话执行

  START TRANSACTION; SELECT id FROM materials WHERE id=999999999 FOR UPDATE NOWAIT; ROLLBACK;

→ 无冲突。**该探针无效**：间隙锁之间互不冲突，加锁读不能用来探测插入是否被阻塞。
表锁实测显示：PRIMARY 上 146 个 `X,REC_NOT_GAP`，而 `uq_materials_source_content` 上另有
147 个 next-key 锁（含 `supremum pseudo-record`）——即唯一二级索引的间隙确实被锁住。

改用**真实 INSERT 探针**（同形语句 + ROLLBACK，无副作用）：

  SET SESSION innodb_lock_wait_timeout=2;
  START TRANSACTION;
  INSERT INTO materials (<id 以外全部列>) SELECT <同列> FROM materials WHERE id=1;
  ROLLBACK;

→ `ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction`
→ 结论：写入确被阻塞。复核 `SELECT COUNT(*) FROM materials` = 146（ROLLBACK 无残留）。
   同一探针在 T1 释放锁后改报 `ERROR 1062 Duplicate entry '84' for key
   'uomaterials.uq_materials_source_content'`（真到达唯一键校验），反向确认阻塞已消失。
