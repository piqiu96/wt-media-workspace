## 修改

**执行过程记录（需求 6）**

- `migrations/20261016_064_compose_task_attempt_steps.sql`：新增 `compose_task_attempts.steps_json JSON NULL`（可空，不依赖表达式默认值；既有 INSERT 与扫描端都不用改）。
- `internal/modules/production/model/task.go`：`ComposeTaskAttemptStep`、6 个步骤常量与中文 `ComposeStepLabel` 表、metrics 四键白名单（`size_bytes`/`sha256`/`output_duration_ms`/`output_id`）；`ComposeTaskAttempt.Steps`。
- `internal/modules/production/model/task_json.go`：attempt 改为**重建式投影**——未知 step 丢弃，`label`/`error_label` 一律用服务端表重算（不信列里的字符串），metrics 逐项合法性检查，`Steps == nil` 输出 `[]`。
- `internal/modules/production/repository/task_lifecycle_mysql.go`：单语句原子追加 `JSON_ARRAY_APPEND(COALESCE(a.steps_json, JSON_ARRAY()), '$', CAST(? AS JSON))`，守卫与其余生命周期写一致（仍持租约、节点/attempt 匹配、`outcome='running'`）；收尾步骤写在提交事务**内部**，否则终态写完守卫就把日志关了；人工重试的 `ON DUPLICATE KEY UPDATE` 不含 `steps_json`。
- `internal/modules/production/repository/task_mysql.go`：attempts 查询补 `steps_json`，按既有 `[]byte` 手法扫，NULL 归一成 `[]`。
- `internal/modules/production/service/execution.go`：6 个既有阶段点各追加一条「完成」步骤；`validate_input` 只在失败时记；三条失败助手先记失败条目**再**写终态。
- `contracts/cloud-api/v1/content-production.openapi.yaml`：`ComposeTaskAttempt` 加 `steps`，新增 `ComposeTaskAttemptStep` 与 metrics schema（`additionalProperties: false`）。

**任务名称（需求 7）**

## 验收期发现（本轮内已修）

1. **失败原因不变红**：规则写的是 `var(--wt-status-error)`，页面字符串断言全绿，但实机计算色是 `rgb(15, 23, 42)`。根因不是 scoped 样式，而是 `--wt-status-error` 在运行时不解析——语义表 `web/src/shared/styles/tokens.css` **从未被任何入口引入**（`git log -S 'tokens.css'` 全历史零命中，`apps/cloud/main.ts`、`apps/desktop/main.ts` 只引入 `design-token.css`、`layout.css`、`resource-module.css`）。同页既有的 `.compose-detail__attempt-err`（同一个变量）也一直没生效，属存量问题。
   修法：三处失败态改用已加载且与失败徽标同色的 `var(--wt-danger)`；**没有**顺手把 `tokens.css` 接进入口——那会连带把 `--td-success-color` 从 TDesign 自带的 `#2ba471` 改成 `#00a870`，等于全站换色，超出本轮范围（登记为待裁定）。
   同时补了一条会失败的测试：`ComposeTasksPage.test.js` 的「only uses CSS variables the loaded stylesheets define」——从两个应用入口真正 `import` 的样式表里取定义，放行 `--td-*`。变异验证：把规则改回 `--wt-status-error` → 该用例红（`unresolved = ['--wt-status-error']`），改回即绿。
2. **计划措辞与实际不符**：计划写「多条按 items 顺序，也就是选素材的顺序」，实测**不是点击顺序**——已选列表与提交的 `items` 都按候选（我的素材）列表顺序，所以序号跟着运营看到的那张列表走。计划文本按此修正登记，代码未动。

## 探针假阴性（记一笔，避免后人把它当缺陷）

只读核对脚本曾在任务 250 上读到「失败原因格 = 无」。追查后确认是**探针顺序**造成的：该格在「任务信息」tab 内，脚本先点了「执行记录」tab，非活动面板不在 DOM 里，`count()` 于是为 0。单独复测（不切 tab，300/800/1400/2400/3600 ms 五次采样）该格恒为 1 且文本为 `源文件缺失`。产品无此缺陷。
