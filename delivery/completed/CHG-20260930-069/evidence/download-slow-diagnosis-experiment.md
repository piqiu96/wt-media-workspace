## 结论

**瓶颈是「本机 → 对象存储」这条路径对单条 TCP 流的速度限制（实测 ~112–160 KB/s/流），不是带宽，也不是本机出口。**
并行连接下聚合速率随连接数**线性增长**，一直到 64 条连接撞到线路本身的上限：

| 连接数 N | 聚合速率（中位数） | 折算 | 相对 N=1 | 每流速率 |
| --- | --- | --- | --- | --- |
| 1 | **112,623 B/s** | 0.90 Mbps | 1.00× | 112.6 KB/s |
| 4 | **473,430 B/s** | 3.8 Mbps | **4.20×** | 118.4 KB/s |
| 8 | **950,956 B/s**（另一轮 1,138,968） | 7.6 Mbps | **8.44×** | 118.9 KB/s |
| 16 | **2,483,958 B/s** | 19.9 Mbps | 22.1× | 155.2 KB/s |
| 32 | **5,041,238 B/s**（另一轮 5,085,060） | 40.3 Mbps | 44.8× | 157.5 KB/s |
| 64 | **10,001,775 B/s** | **80.0 Mbps** | **88.8×** | 156.3 KB/s |

**按计划判据（C ≥ 5×A）**：8 条连接就到 **8.44×**（另一轮 10.11×），远超阈值，且到 64 条仍在涨——
→ **单流受限成立，并行分片下载是解**；「按 IP 硬限」这一支被**排除**（至少到 64 流没有出现）。

**当前单流下载只用掉线路的 ~0.9%**（112.6 KB/s vs 64 流实测 80 Mbps）。

## 实测方法

- 对象：素材 30 的源视频，`SIZE = 48,511,909 B`（46.3 MiB），由 `GET /api/v1/materials/30/video-url` 取到尺寸后固定。
- 地址：经**生产同一条 presign 路径**（`storage.Initialize` + `PresignGet`）签发的直连对象存储 GET，只写入 `0600` 文件、**全程不打印**（地址即凭据）。
- 每臂固定 **20 秒墙钟窗口**，`curl --range` 各起 N 条并行连接抢同一对象的互不重叠起点，`-w` 收每条连接的 `size_download` 与 `http_code`；输出到 `/dev/null`，不落盘。
- **交错跑**（A,B,C,A,B,C,A,B,C 再补一次 A 做书挡），不是块状跑——块状跑分不开「旋钮」与「时间漂移」。
- 每个连接**全部回 206**（Partial Content），不是 403/200——这是本实验能作数的前提（见下「踩到的坑」）。

### 书挡与重复性

- 书挡 A 臂 = 112,213 B/s，与三轮 A（113,033 / 111,396 / 116,311）同档 → 实验期间基线未漂。
- N=32 在两个独立时段各测一次：5,041,238 / 5,085,060 B/s，**相差 0.9%**。
- **唯一不稳的点是 N=8**：第一时段 950,956 B/s，第二时段 1,138,968 B/s（**+20%**）。这是**轮间离散**，不是阶梯断点——引用 8 流收益时应按 ~8–10× 报，不要报成精确的 8.44×。

## 对照与分母（全部本次现测）

| 量 | 读数 | 对照 | 分母 |
| --- | --- | --- | --- |
| 本机出口基线 | mirrors.aliyun.com **20.9 / 29.3 / 35.0 MB/s** | Cloudflare 2.67 / 3.36 MB/s | 3 次 |
| 到对象存储 RTT | **61.1 ms**（110.42.63.230） | www.aliyun.com 12.5 ms、mirrors.aliyun.com 10.3 ms、223.5.5.5 15.3 ms | 各 100 包 |
| 到对象存储丢包 | **6.0%**（56 B 与 1400 B 载荷各 6/100，与包长无关） | 上述三个对照全 **0%** | 100 / 60 / 25 / 25 |
| 真实下载速率（Agent 实跑） | **94,628 B/s** 均值（分窗 104,857 / 78,643 / 104,857） | 同刻 A 臂 HTTP 裸测 112,623 B/s | part 文件 15:23:58→15:34:13 |

出口基线 20.9–35.0 MB/s（≈167–280 Mbps）说明**线路不是限制**；61 ms RTT 在国内目标是异常值（对照 10–15 ms），traceroute 走 221.179/221.183（中国移动）→ 110.94.0.249 → 61.175.22.58（浙江），指向跨网互联的固定绕远路径。

**两条独立读数互证**：按丢包 + RTT 用 Mathis 模型（MSS 1460 / RTT 61.1 ms / p=6%）算单流上限 = **97.5 KB/s**，实测单流 94.6–112.6 KB/s，同量级。这条同时回答了一个反质疑——「6% 的 ICMP 丢包会不会只是控制面限速的假象」：若丢包只存在于 ICMP，TCP 单流应显著跑高，而它没有。

## 机制：只报测到的，不替它认领原因

两条候选机制都能产生「每流恒定、聚合线性」：

1. **按流限速**（运营商或对象存储侧的 per-flow shaping）；
2. **路径丢包把单流拥塞窗口压死**（Mathis 已给出同量级的单流上限）。

本实验**没有**把这两者分开。有一点与「纯拥塞丢包」不符：若丢包来自自身流量造成的拥塞，连接数上升应让每流速率**下降**，实测却是每流从 112.6 缓升到 ~157 KB/s 后持平在 ~157（N=16/32/64 三点相差 <2%）。

**但这对决策无影响**：两种机制下「更多流 = 更多总吞吐」都成立，判据指向同一个动作。

## 字节路径（代码核实，本次未改）

Cloud 不在数据路径上，也不做任何限速：Cloud 用 MinIO presign 签一个**直连对象存储**的 GET，写进租约交给 Agent（`wt-media-cloud/internal/infra/storage/minio.go:101-105`、`internal/filetransfer/service/service.go:850-865`），Agent 直接拉。界面显示的速率就是 Agent 的 ~2 秒窗口速率原样存回（`wt-media-agent/src/wt_media_agent/executors/material_download.py:732-737` → `filetransfer/service/service.go:611-618`），**不是前端算的、也不是显示失真**。

**Range 可用**：全程 206，服务端（错误 XML 自称 `<Region>garage</Region>`）支持按字节区间取——**分片下载不需要动基建**。

## 次生因素（不是本次瓶颈，但会压住「改完并行之后」的上限，登记备查）

- 单 TCP 连接、严格串行，一次只领一条任务（`runner/transfer.py:64`）；
- 每 256 KiB 一块，每块 `mkdir` + `open`/`close`（`storage/download_sink.py:258-263`）；
- 读循环里**内联阻塞**的 progress POST 与 SQLite 写（`material_download.py:530, 740-765, 748`）；
- commit 时对整份文件 `fsync`（`download_sink.py:295-299`）；
- 续传前把已下前缀**整份重读重算 sha256**（`material_download.py:468-470`）；
- **签名 URL 默认只有 15 分钟**（`internal/config/config.go:115` `PresignTTL`、`:321` 校验、`internal/config/config_test.go:124` 断言默认 15m；`internal/infra/storage/registry.go:43,52` 把它放进交给 Agent 的租约）。按实测 94.6 KB/s，**15 分钟 ≈ 85 MB 上限**；素材 30（46.3 MiB）余量 ~1.8×，但 100 MB 以上的源会在下载中途过期。此条是**算术推演，未做跨 15 分钟的实拖**。并行分片后同一文件约 1 分钟下完，这个风险顺带消失。

裸 HTTP 相比 Agent 实跑（112.6 vs 94.6 KB/s）多出 ~16%：那是 Agent 侧上述机器开销。速率放大 8–45 倍后，这些开销会从「不显著」变成「咬人」，改并行时要一并处理。

## 被证伪 / 未排除（如实登记）

- **MTU 假设：已证伪**。`ping -s 1472 -D` 打对象存储 100% 丢包，看着像 PMTU 黑洞；但**同一命令打 mirrors.aliyun.com 也是 100% 丢包**（带不带 `-D` 都一样）——那是「这些主机不回大 ICMP」，不是 MTU 证据。
- **按 IP 限速：已排除**（至少到 64 流）——聚合到 64 流仍线性，若按 IP 限速会在某个 N 上出现平台。
- **对象存储侧聚合上限：未测到**。N=64 时曲线尚未见拐点，10 MB/s 只是「64 × 156 KB/s」的落点，不是被证明的天花板；要探到真上限需要 128+ 连接，已超出实用分片数，没有继续测。**注意**：出口对国内镜像能跑 20.9–35.0 MB/s，所以 10 MB/s 不是线路墙。

## 附带发现（与本反馈不同的一件事，需用户裁定）

`GET /api/v1/materials/:id/video-url`（任务 2 落地）返回的是**无签名的稳定对象地址**（实测 `url_len=119`、`query_keys=[]`），而本机桶**拒绝匿名访问**，实测回：

```
403  <Code>AccessDenied</Code>  Forbidden: Garage does not support anonymous access yet
```

即任务 2 的验收项「云端视频 URL 实际可访问性」在**当前开发环境不成立**。这**不影响下载**（下载走的是另一条带签名的租约地址，实测 206），影响的是「在浏览器里打开该素材视频」这条路径。是「桶应放开匿名读」还是「该端点应改为签发 presign」，属于产品/安全取向，未自行推断。

## 踩到的坑（影响本次读数可信度，登记）

第一版脚本从 `GET /materials/30/video-url` 直接取地址，每连接回的是 `287 (403)`——**403 的响应体也被算进了字节数**，如果不看 `http_code`，这一臂会"测出"一个荒谬的低速率并被当成数据。改为经生产 presign 路径签发地址后全部回 206。**教训：这类实验必须逐连接校验状态码，否则读数是错误页面的长度。**
