# Milestone 业务闭环

本目录保存每个 M 由人工确认的业务闭环基线。

尚未确认的拆分必须显式标注 DRAFT，不能作为已批准的实现依据。

当前 M3 闭环见 [M3 内容挖掘 V2](M3-content-discovery-v2.md)：**M3 已于 2026-09-23 通过 E3 综合验收并由用户签收，状态为 `DONE`**（验收矩阵第 1～7 项全部通过，无 FAIL、无 NOT VERIFIED）。A～E1 有真实证据；C2/E2（博主搜索与作者策略）已于 2026-09-23 暂停并移出本期范围；逐阶段状态见该文件第 2.1 节，签收记录见第 2.2 节。M3 产品事实源为 [PRD 第四章：内容挖掘](../../docs/product/prd/详细文档/第四章_内容挖掘.md)。旧 M3-content-discovery.md 与 CHG-037～043 为 SUPERSEDED。M2 仍保持已验收 DONE。

M4-M5 于 2026-09-24 按用户确认方向完成闭环重划。M4 于 2026-09-26 进入 `IN_PROGRESS`；用户 2026-10-14 暂缓 M4-H2 人工走查，要求先执行 M5，M5 进入 `IN_PROGRESS`：

- [M4 Cloud 内容生产闭环](M4-content-production.md)：素材库 → 我的素材 → 人工 `compose_task` → Cloud Worker + FFmpeg → 我的成片 → 下载；
- [M5 策略自动生产与 Worker 资源控制](M5-automatic-production.md)：`compose_strategy.schedule` → Scheduler → Worker Pool → 自动成片。

两者共同依据 ADR-0017；不再使用本地/Cloud Agent 合成、`production_rule`、`compose_pool_item`、成片池或成片领取对象。M4-A 的 `CHG-20260924-061` 已于 2026-09-27 关闭归档为 `DONE`（归档记录见 [`../completed/CHG-20260924-061/change.md`](../completed/CHG-20260924-061/change.md)）。M4 与 M5 于 2026-10-28 经用户统一走查签收，均进入 `DONE`（签收记录见 [CHG-20261015-098](../completed/CHG-20261015-098/change.md)）；两者各 CHG 的机器验收已逐项完成。

Milestone 不替代 Product、Engineering、MASTER PLAN、AI Spec、CHG 或 Evidence。它只回答：用户按什么顺序操作，以及哪些业务结果和真实外部效果必须同时成立，才能认为该 M 的一段闭环完成。

每张闭环卡只包含：

- 用户目标；
- 前置条件；
- 用户操作顺序；
- 系统与外部动作；
- 成功必须同时满足的事实；
- 失败时禁止出现的假成功；
- 对应 CHG。

CHG 必须引用一张闭环卡，只描述本次差距、修改范围、任务和验证方法，不重复维护完整业务流程。

## 事实与交付分别维护

稳定产品决策直接回写 PRD；工程技术选择进入 Engineering Spec，重大架构取舍按现有规则记录 Decision。Milestone 保存本阶段的业务交付与验收边界，CHG 保存具体实施范围与实际验证结果，不等整个 Milestone 结束才回写已确认的长期规则。

| 变化 | 写入位置 |
| --- | --- |
| 已确认且长期有效的产品规则、页面动作或异常处理 | 对应 PRD；Milestone 引用并调整交付边界 |
| 工程实现、安全或三端职责选择 | 对应 Engineering Spec，必要时 Decision；同步受影响交付边界 |
| 本阶段用户能完成什么、前置能力和验收条件 | 对应 Milestone；变化后重新核对候选 CHG |
| 本次具体修改、进展与验证结果 | 当前 CHG；必要时保留 evidence，不复制整套产品规则 |
| 不改变既定规则的实现缺陷 | 当前 CHG，不重复修改 PRD 或 Milestone |

未决建议显式标注，不能写成已批准需求。简短交接、正式回写及渐进加载遵循 `AGENT-INDEX.md` §4、§7；本目录不另建任务状态。

## 页面实施与验收基线

PRD 负责产品规则，Engineering Spec 负责技术方案，Cloud `web/example/proto/publishing-design/` 中已验收原型负责页面布局、交互和视觉基线。各发布 Milestone 列出本阶段原型入口及公共前端规范，不复制截图、CSS 或完整交互规范。

- 正式页面 CHG 必须在 References 引用本阶段的具体原型入口、相关源码位置、Cloud 原型 commit SHA 及公共前端规范，不能只写“参考原型”。实施与验收均固定到该 SHA，不随 main 漂移；预览使用服务启动输出中的实际访问地址与本阶段业务路由，不固定主机和端口。
- 验收使用实际页面与同一原型基线逐项对照，覆盖布局、操作路径、状态反馈、返回上下文、公共组件及视觉；记录核对的 Cloud 原型 commit SHA、实际实现版本、结果及差异，不以原型通过代替正式服务验收。
- AI 不得绕开原型重新设计界面、交互流程或视觉样式。确需调整时先说明差异和原因，由产品负责人裁定后再修改原型及其对应正式来源，最后据此实施并验证；不能将自行偏离的实现当成新基线。
- M10 在安装版回归时继续引用四个发布 Milestone 的原型入口，不另建页面基线或复制原型资料。

## Milestone 关闭检查

- 目标、用户路径、成功条件和验收矩阵已闭环，没有未解释的失败或遗漏。
- 没有遗留的 Active CHG、未收口阻塞或“只登记未处理”的当前事项。
- 下一 Milestone 的范围、依赖和未决事项清楚；没有把下一阶段内容混进当前闭环卡。
- 闭环卡只保留当前业务事实和验收结论，不写开发流水账、过程报告或临时分析。
- 已经稳定的产品事实已回写 PRD；执行过程记录按历史处置规则退出默认上下文。
