# M2 账号与运行环境业务闭环

本文件是 M2-A～E 唯一业务闭环基线。Product 定义产品规则，Engineering 和 Decisions 定义跨端实现原则，AI Spec 和 Reports 只作为分析材料，CHG 只实现本文件中的一个闭环或更小纵向切片。

## 1. Milestone目标

### 目标描述

完成运营账号从用户授权、Desktop与BitBrowser环境可信、Profile管理、代理绑定、账号登录与Cookie回填，到可进入发布和互动预检的完整闭环。

### 完成后能力

- 管理员可以管理用户、运营分组和游戏范围；
- 普通运营只能操作本人且在授权游戏内的数据，高级运营管理同组且在授权游戏内的Cloud业务数据；
- Web可以管理Cloud数据，Desktop可以通过Tauri与Local Agent操作当前电脑的BitBrowser；
- 用户可以同步、创建、分配和管理真实Browser Profile；
- 代理可以导入、检测、分配到Profile并从BitBrowser读回；
- 账号可以通过CK、接码链接、人工验证码或人工接管完成登录并同步真实身份与Cookie；
- 未绑定Profile的账号可以作为台账存在，但明确不可执行本地任务；
- 原业务页面展示完整过程和处理操作，普通运营可通过Desktop顶部“本机执行”抽屉获得跨业务提醒和快速跳转；
- 用户可以看到单项和批量操作的最终结果、失败原因及恢复入口。

## 2. Milestone范围

### 包含范围

- M2-A 用户、运营分组、游戏权限、会话和本地身份环境；
- M2-B 浏览器窗口、Profile Diff、媒体账号台账、绑定与检查；
- M2-C 代理资源、统一窗口配额、推荐、写入与读回；
- M2-D CK、接码、人工验证码、人工接管、Cookie读取和账号回填；
- M2-E Desktop安全桥、Agent生命周期、恢复和M2综合验收。

### 不包含范围

- 自定义角色、组织树、多级分组、审批和复杂账号交接；
- 远程删除BitBrowser本地Profile；
- Cookie历史版本、快照和独立凭证资产系统；
- 代理采购、续费和结算；
- M3～M10的内容、生产、发布、互动和统计业务；
- 面向未来全部模块重新建设通用任务平台。

### 横切执行规则

```text
纯Cloud数据
→ Web或Desktop直接调用Cloud

单项短BitBrowser操作
→ Cloud预检
→ Tauri调用Local Agent
→ Agent同步调用BitBrowser并读回
→ Cloud验证并保存正式结果
→ 页面展示最终结果

批量或等待人工流程
→ Cloud保存专用batch/item
→ Agent逐项同步调用BitBrowser
→ 持续回写单项和批次结果

发布、互动、合成等长流程
→ 后续Milestone使用正式异步task
```

HTTP成功、请求已接受、任务已创建或Agent已调用接口都不等于业务成功。外部修改必须读回；无法确认时进入结果待确认，不得盲目重试。

## 3. 子阶段拆分

## M2-A 用户、权限、会话与运行环境可信闭环

### 用户目标

管理员可以创建和管理用户、运营分组和游戏范围；普通运营可以安全登录 Desktop，并绑定正确的 BitBrowser 主账号树，为后续本地操作建立可信身份和环境。管理员和高级运营只使用 Cloud Web 做管理与查看，不进入 Desktop 本机执行环境。

### 前置条件

- M1 Cloud、Desktop、Local Agent最小任务和会话基础可用；
- Cloud真实MySQL可用；
- Desktop、Local Agent和BitBrowser可连接。

### 核心流程

```text
管理员创建运营分组
→ 创建游戏分类
→ 创建用户并设置角色、分组、游戏和新密码
→ 用户登录
→ 有旧会话时确认是否替换
→ 普通运营进入Desktop检测Cloud、Agent和BitBrowser
→ 读取并确认当前BitBrowser主账号身份
→ 用户确认绑定main_user_id
→ 后续操作持续检查身份匹配
```

### 系统要求

- `users.id`使用自增主键并作为页面UID；
- 角色固定为管理员、高级运营、普通运营；
- 管理员不属于分组，查看全部Cloud数据；
- 高级运营范围为所属分组与授权游戏交集；普通运营范围为本人资源与授权游戏交集；
- Desktop本机执行环境只允许普通运营登录和发起本地浏览器操作；管理员和高级运营登录Desktop时必须被阻止，并提示使用Cloud Web；
- 普通运营和高级运营必须属于一个分组，分组不提供停用；空且无历史数据的分组可删除；
- 分组被用户或业务历史引用时不能删除，必须先转移用户或处理引用；
- Cloud系统管理分为“用户管理”“运营分组”“游戏管理”，不把三类管理混在一个页面；
- 所有管理类列表默认具备搜索、筛选、列表和分页，不需要后续逐项单独声明；
- 游戏范围来自Cloud游戏字典，创建或编辑用户时只能选择已启用游戏，不能手工输入自由文本；
- 创建或重置密码后可查看、复制本次新密码，关闭后不能查询原文；
- 用户管理支持列表、搜索、筛选、分页、角色/分组/游戏修改、密码重置、停用和重新启用；有历史数据的用户不物理删除；
- 运营分组支持独立列表、搜索、分页、新建、重命名、删除空分组，并展示用户数量；
- 游戏管理支持独立列表、搜索、状态筛选、分页、新建、编辑、启用和停用；
- 游戏被用户或业务历史引用时不能停用或删除，必须先调整用户游戏范围或处理引用；
- 新登录只有在用户确认后才替换旧会话；旧Agent停止领取新的本地浏览器操作；
- 首次绑定只读取和确认当前BitBrowser主账号`main_user_id`，不读取完整Profile列表，不校验`profile_user_id`，不创建或更新正式Profile；Profile扫描、Diff和授权同步归M2-B；
- 已绑定用户刷新本机状态时只允许当前BitBrowser主账号与用户已绑定`bit_main_user_id`一致；不一致必须阻断，不能静默从账号A改绑到账号B；
- 本机可信绑定不要求当前BitBrowser中的所有窗口都已存在于Cloud；绑定阶段只确认主账号身份和本机节点可信，未知窗口通过M2-B扫描Diff处理；
- 如系统故障导致绑定错误，由管理员在Cloud用户管理中解除目标用户的BitBrowser账号绑定；解除不会删除已有Profile镜像、媒体账号、代理关系或历史记录；目标用户再在自己的Desktop重新绑定正确账号；
- M2-A只检测Cloud、Local Agent、BitBrowser和主账号匹配，不检测FFmpeg或管理本地业务目录。
- 用户登录后的工作台展示当前绑定的BitBrowser环境、环境可用性和本人媒体账号摘要，不在工作台复制账号管理功能。

### 完成标准

- 三角色创建、登录、密码、修改、禁用和数据保留流程在真实MySQL通过；
- 管理员和高级运营不能进入Desktop业务页面；普通运营可以进入Desktop并继续完成本机环境可信检测；
- 用户管理、运营分组和游戏管理三个Cloud页面均具备搜索、筛选/查询、列表和分页；
- 创建用户失败时页面显示可理解原因，例如密码过短、未选分组、未选游戏、用户名重复或游戏不可用；
- 页面、API、batch/item创建和Agent执行入口使用一致权限结果；越权零数据泄漏、零外部副作用；
- 用户转组后新数据使用新分组，历史数据保留原分组；
- 用户取消会话替换时旧会话不受影响；确认后旧Web、Desktop和Agent不能继续发起新操作；
- Web明确不能直接操作本机；Desktop显示真实Agent、BitBrowser和身份匹配结果；
- 主账号绑定来自真实BitBrowser身份读取，不能手填；不匹配时所有本地浏览器操作被阻止；
- 关键用户、权限、会话和绑定操作可追溯且不记录密码、Cookie和代理密码。

### 异常与恢复

- 用户、分组或游戏无效时不创建用户；
- 游戏被停用后不能再分配给新用户或更新为用户授权范围，历史授权和历史业务数据保留；
- 修改角色、分组、游戏、密码或禁用后当前会话失效；
- 旧Agent在途外部结果无法确认时进入待确认；
- 无法读取当前BitBrowser主账号身份时禁止绑定；
- 重新启用用户后必须重新登录并重新验证Desktop与BitBrowser环境。

### 不允许情况

- 不保留原`technician`作为第四角色；
- 不让管理员分组影响权限；
- 不允许管理员或高级运营通过Desktop直接操作普通运营本机BitBrowser资源；
- 不通过前端隐藏代替Cloud授权；
- 不用“Desktop已发送命令”代替环境正常；
- 不在M2-A应用Profile同步结果。

### 依据与关联CHG

- Product：第三章3.2、3.4.2～3.4.4、3.7；
- Decisions：ADR-0003、0004、0009；
- Completed：`CHG-20260723-024`，M2-A 已人工验收通过。

## M2-B 浏览器窗口与媒体账号真实闭环

### 用户目标

普通运营可以同步和管理自己的BitBrowser窗口，创建媒体账号台账，将账号绑定到正确窗口并通过真实检查获得平台身份与登录状态。

### 前置条件

- M2-A完成；
- 当前Desktop节点、Local Agent、BitBrowser和`main_user_id`匹配；
- 本机可信绑定应在同一用户、同一电脑、同一Local Agent节点、同一BitBrowser主账号下稳定保持；只有切换系统用户、替换登录会话、切换BitBrowser主账号、更换本机节点或管理员注销旧绑定时，才需要重新绑定；
- 目标Profile没有其他本地浏览器操作占用。

### 核心流程

```text
Desktop登录后扫描Profile
→ 生成Diff但不应用
→ 用户接受BitBrowser变化或恢复Cloud配置
→ 单个或批量创建窗口并读回
→ 管理员分配未授权窗口
→ 普通运营创建媒体账号台账
→ 绑定或换绑窗口
→ 单个或批量账号检查
→ 回填平台UID、名称、头像和登录状态
```

### 系统要求

- 页面使用“浏览器窗口”，代码和数据库使用`browser_profile`；
- Cloud Web没有本机Agent执行环境，只展示Cloud已保存的浏览器窗口和媒体账号基本信息，不提供扫描、Diff、读回、打开、关闭、创建、更新等依赖BitBrowser或Local Agent的操作入口；
- Desktop是所有依赖BitBrowser和Local Agent能力的用户入口；Desktop Vue必须通过Tauri/Rust调用Local Agent，不得直接访问Local Agent动态端口或持有动态凭据；
- Cloud Web与Desktop展示功能必须分层：

| 功能 | Cloud Web | Desktop |
|---|---|---|
| 浏览器窗口列表 | 展示Cloud已保存镜像、授权用户、绑定账号摘要、最近同步时间 | 展示Cloud镜像，并额外展示本机环境状态、扫描状态和本机读回结果 |
| 浏览器窗口详情 | 展示Cloud基本信息、授权关系、绑定账号摘要、历史同步/检查记录 | 展示Cloud基本信息，并提供打开窗口、读回、扫描、检查等本机操作入口 |
| BitBrowser扫描 | 不展示入口，不触发扫描 | 展示入口，通过Tauri/Rust调用Local Agent同步读取BitBrowser |
| Diff结果 | 不展示依赖本机实时读回的Diff处理入口；可查看已保存的历史同步摘要 | 展示本次扫描Diff、无差异结果、失败原因和后续处理入口 |
| 打开/关闭/创建/更新窗口 | 不展示入口，不调用Agent，不创建本机副作用 | 可操作，但必须同步调用Agent并读回验证 |
| 接受本地变化/恢复Cloud配置 | 不在Cloud Web处理 | 在Desktop处理；接受本地变化更新Cloud镜像，恢复Cloud配置必须写BitBrowser并读回 |
| 媒体账号绑定与检查 | 可查看Cloud台账和历史结果；不触发本机检查 | 可触发绑定、换绑和账号检查，并通过Agent读回真实结果 |

- 单Profile创建、编辑、打开、关闭、检查和扫描同步调用Agent；批量创建使用专用批次逐项执行；
- 打开/关闭窗口是Desktop本机同步操作，不创建Cloud异步任务：Desktop Vue通过Tauri/Rust调用Local Agent，Local Agent调用BitBrowser打开/关闭接口，打开成功后返回可用于后续窗口操作的连接信息或失败原因；
- 新建窗口必须按BitBrowser Profile字段建模；分组需要读取BitBrowser分组并选择真实分组ID后调用BitBrowser创建，创建成功后读回Profile并更新Cloud镜像，不能只创建Cloud记录；
- 扫描只生成新增、名称、分组、代理、缺失、运行状态和已绑账号影响Diff；
- 浏览器窗口列表和详情至少展示系统记录ID、BitBrowser Profile ID、比特序号、名称、分组、代理摘要、比特备注、比特标签、Cloud备注、授权运营、Cloud镜像状态、本机运行状态和最近同步时间；
- 浏览器窗口列表必须支持搜索、筛选和分页；搜索至少覆盖系统记录ID、BitBrowser Profile ID、名称、分组、备注和标签；
- 浏览器窗口系统记录ID使用数据库自增主键；BitBrowser Profile ID只作为外部系统ID展示和关联，不作为业务主键；
- 用户绑定的BitBrowser主账号信息属于Cloud已保存的账号环境摘要，可在用户管理或浏览器窗口相关详情中以只读方式展示给有权限的管理员和当前用户；展示内容只包括绑定状态、绑定时间、最近验证时间和脱敏主账号标识，不展示Agent凭据、本地端口、Token或完整本机诊断信息。具体入口和表格列在M2-B窗口同步/详情CHG中统一设计，不在M2-A本机状态修复中单独补页面。
- 接受本地变化更新Cloud镜像；恢复Cloud配置必须写BitBrowser并读回；
- “取消变更”只放弃本次扫描Diff，不修改Cloud镜像，也不写入BitBrowser；“关闭”只关闭当前弹窗/抽屉，不代表接受、取消或恢复，未处理Diff仍保持待处理状态；
- “恢复Cloud配置”用于用户确认以Cloud保存配置为准并覆盖本机BitBrowser差异的场景；它必须通过Desktop写回BitBrowser并读回验证，不允许只改Cloud状态或只提示成功；
- Cloud授权用户、账号绑定、游戏、标签、备注、Cookie和业务状态不能被扫描覆盖；
- 一个Profile只授权一个系统用户；共享`main_user_id`不共享Cloud授权；
- 一个账号最多绑定一个Profile；一个Profile可绑定多个不同平台账号，同平台最多一个；
- 账号可暂不绑定Profile，但标记不可执行；
- 账号台账覆盖多游戏关联、标签、用户级去重、重复标记、备注以及业务/登录双状态；账号系统记录ID使用数据库自增主键，平台账号ID作为平台身份字段单独保存；
- P0平台为哔哩哔哩和百家号；新增账号入口命名为“新增账号”，绑定窗口选择项必须能让用户识别系统记录ID、窗口名称和BitBrowser Profile ID；
- 新增账号时可以先不绑定游戏；账号启用、上号完成进入可执行状态、发布或互动预检前必须至少绑定一个游戏；一个账号可以绑定多个游戏；
- 媒体账号业务状态包括`draft`、`enabled`、`disabled`、`abnormal`、`retired`；`retired`账号从可执行资源池剔除；
- 媒体账号登录状态包括`unchecked`、`logged_in`、`not_logged_in`、`expired`、`mismatch`、`check_failed`；
- 媒体账号操作栏至少包含详情、编辑、绑定/更换窗口、打开窗口、关闭窗口、检查/同步账号信息、启用/停用；打开窗口默认跳转到平台对应主页或创作入口，平台URL由平台配置提供；
- 自动登录或Cookie上号失败后，允许用户在BitBrowser窗口中人工登录，再回到Desktop点击“检查/同步账号信息”，由Agent读取当前窗口真实平台身份并回填平台UID、昵称、头像、登录状态和最近检查时间；
- P0不保存平台密码以外的第二套账号事实；
- 手工补录不能授予执行资格；真实检查串行执行并以平台读取结果为准。

### 完成标准

- 单个和批量窗口真实创建、逐项读回、部分成功和失败项重试成立；
- 自动与手工扫描均只产生Diff，用户可以接受或恢复且读回一致；
- 浏览器窗口不做真实删除BitBrowser Profile；窗口"退役"通过业务状态（启用/停用）管理——停用仅影响社媒账号匹配/执行资格（不可参与账号匹配、不可打开/关闭），窗口存在性仍以扫描为准；窗口已从BitBrowser删除且已停用时，可同步删除该Cloud镜像记录；不删除账号历史和本机BitBrowser数据；
- 管理员可分配未授权Profile；高级运营只查看同组授权范围的Cloud状态，不操作他人本地窗口；
- 账号可创建、编辑、绑定、解绑、换绑、加减标签和筛选；
- 账号台账页面支持列表、详情、搜索、平台/游戏/标签/业务状态/登录状态筛选、分页和备注维护；
- 单个/批量账号检查真实回填平台身份、头像、登录状态和最近检查时间；
- 页面、Cloud镜像、Agent读回和BitBrowser实际状态一致。
- Cloud Web与Desktop页面边界清晰：Cloud Web只能查看Cloud基本信息，Desktop才能展示和处理依赖本机BitBrowser读回的扫描Diff和执行结果。

### 异常与恢复

- BitBrowser创建成功但读回失败时进入结果待确认，重试前先扫描真实Profile；
- Diff未确认时不修改Cloud正式镜像；正在执行本地浏览器操作的Profile不应用扫描变化；
- 换绑后登录状态变为`unknown`并必须重新检查；
- 新窗口已经登录其他同平台账号时阻止换绑；
- 实际账号与Cloud记录不一致时不自动覆盖，由用户选择更新或重新登录；重复UID使用已有账号并避免第二条正式记录。

### 不允许情况

- 不远程删除BitBrowser本地窗口；
- 不把浏览器窗口“停用/归档”包装成真实删除；真实删除BitBrowser Profile不属于M2-B范围；
- 不用“已创建任务”代替Profile真实结果；
- 不让高级运营或管理员绕过目标用户Desktop操作本地资源；
- 不在Cloud Web提供依赖BitBrowser或Local Agent的扫描、Diff处理和本机执行入口；
- M2-B只完成“只换绑”，不清理原窗口Cookie。

### 依据与候选CHG

- Product：第三章3.3、3.4；
- Decisions：ADR-0002、0003、0004、0008、0009；
- 候选：B1窗口扫描与Diff只读、B2接受本地变化/恢复Cloud配置/窗口生命周期与授权、B3账号台账与绑定、B4账号检查。

## M2-C 代理资源与窗口真实绑定闭环

### 用户目标

普通运营可以新增或批量导入代理，真实检测可用性，按统一窗口配额获得推荐方案，并将代理写入授权Profile后读回验证。

### 前置条件

- M2-A完成；正式绑定依赖M2-B的Profile身份和授权；
- 代理导入和检测可在Profile绑定前准备；
- 当前Desktop本地环境可用。

### 核心流程

```text
新增或上传代理
→ 解析、逐行预览和修正
→ 用户确认后入库
→ 单个或批量真实检测
→ 设置max_profile_count
→ 系统生成窗口分配建议
→ 用户调整并确认
→ Agent同步写入BitBrowser
→ 读回代理配置
→ Cloud更新正式关系和配额
```

### 系统要求

- 支持Excel、CSV、TXT和多行粘贴；预览阶段零副作用；
- 代理记录协议、Host、Port、用户名、密码、地区、出口IP、供应商、到期时间、状态、检测结果、刷新URL、标签和备注；
- 一个Profile同时最多使用一个代理；一个代理可绑定多个Profile但不超过`max_profile_count`；不再按平台配额；
- 单代理检测、写入、更换、解绑和读回同步调用Agent；批量操作使用批次逐项执行；
- 推荐只使用已启用、检测正常、未到期且有剩余配额的代理；确认前不占用配额；
- 更换时新代理读回成功后才释放旧配额；解绑时读回无代理后才清除Cloud关系；
- BitBrowser外部代理变化进入Profile Diff；未知代理生成待补充记录，补齐并检测前不参与推荐；
- 刷新URL调用后重新检测出口，不自动修改Profile绑定。

### 完成标准

- 单个新增和真实检测成功；批量解析、预览、修正、重复提示和部分成功成立；
- 推荐方案、人工调整和统一窗口配额计算正确；
- 代理写入、更换和解绑均在BitBrowser读回一致后更新Cloud；
- 目标Profile能使用写入后的代理打开；
- 外部代理变化可通过Diff确认并正确影响Cloud关系；
- 页面展示已绑定窗口、已用/剩余配额、检测、到期和失败重试结果。

### 异常与恢复

- 写入或读回失败不更新正式绑定或占用配额；
- 超时且无法确认时先读回Profile，不能重复写入；
- 停用代理不自动清空现有Profile，页面提示仍在使用的窗口；
- 未绑定且无历史的误建代理可删除，已有历史的代理只能停用。

### 不允许情况

- 预览不能提前入库；
- 前端建议不能冒充正式分配；
- 密码不在普通列表、日志和Evidence中展示；
- 高级运营只查看同组授权状态，不修改他人窗口代理。

### 依据与候选CHG

- Product：第三章3.5；
- Decisions：ADR-0004、0008、0009；
- 候选：C1代理台账与无副作用导入、C2真实检测与配额、C3推荐与Profile写入读回、C4外部变化与生命周期。

## M2-D 账号上号与Cookie闭环

### 用户目标

普通运营可以从媒体账号发起CK、接码链接或人工验证码上号，查看批次和单项进度；自动化失败后可在BitBrowser人工登录，再同步真实账号资料与Cookie。

### 前置条件

- M2-A～C完成；
- 账号、窗口、代理和当前`main_user_id`通过预检；
- P0平台为哔哩哔哩和百家号。

### 核心流程

```text
选择独立上号方式
→ 输入账号、手机号、密码、接码链接或CK
→ 预览账号、窗口和代理，确认前零副作用
→ 用户确认后创建media_account和account_login_batch/item
→ Agent逐项检查窗口当前登录账号
→ 创建/绑定窗口并写入代理
→ 执行CK、接码或人工验证码登录
→ 检查平台UID、名称、头像和登录状态
→ 读取当前真实Cookie
→ 更新media_account和batch/item
```

自动化失败人工接管：

```text
自动上号失败
→ 保留并打开对应BitBrowser窗口
→ 用户人工完成登录
→ 返回系统点击“同步账号信息”
→ Agent同步读取真实身份和Cookie
→ Cloud回填media_account
→ item完成
```

### 系统要求

- `media_account`保存`login_username`、`login_phone`、`login_password`、`sms_receive_url`、`sms_receive_expires_at`、`original_cookie`和`active_cookie`；
- CK、接码、人工验证码使用独立批次，不混入同一队列；
- `account_login_batch/item`只保存过程，长期账号事实只写`media_account`；
- 单账号Cookie读写和检查同步调用Agent；批量上号由item串行编排，同时只执行一个主要窗口；
- 上号前识别窗口现有账号：已是目标账号则读取并计成功；是其他账号则停止且不暴力退出；
- 接码支持发送、轮询、到期、更新链接和重试；人工验证码支持等待输入、重发、错误、过期、取消和继续；
- 管理员和账号所有者可查看、复制登录密码和完整Cookie；高级运营只看已配置状态；
- 原始Cookie长期保留；真实Cookie必须从窗口读取，失败不得以原始Cookie冒充；
- 自动或人工登录成功具有相同使用资格；记录完成方式；
- 实际账号不一致时不自动覆盖，用户选择更新当前记录或重新登录；发现当前用户下相同平台UID时使用已有账号，避免重复正式记录；
- “换绑并清理”只清除原窗口目标平台Cookie，读回成功后才更新绑定，不影响其他平台。
- 上号批次详情是完整业务执行页面，展示批次统计、账号执行列表、单项步骤时间线、等待人工原因和业务执行记录；验证码、接码链接、账号冲突、更换窗口、跳过、取消和失败项重试均在该页面处理。

### 完成标准

- 三种上号方式都有独立入口、批次、单项状态和真实成功样例；
- 预览零副作用，确认后才创建正式资源；
- 批次支持部分成功、等待人工、冲突、取消、结果待确认和失败项精确重试；
- 自动失败后，用户可人工登录并一键同步平台UID、名称、头像、登录状态和真实Cookie；
- 账号冲突不自动覆盖；用户选择后的去重结果正确；
- 用户可分别查看/导出原始Cookie和当前真实Cookie，批量导出逐项反馈；
- 上号成功后账号业务状态为`enabled`、登录状态为`normal`，且Profile和代理预检通过，可进入发布/互动预检；
- Cloud账号、批次/item、Agent读回、BitBrowser和页面最终状态一致。

### 异常与恢复

- 未开始item取消后不创建资源；已产生外部效果时先读回，再判成功、失败或结果待确认；
- 已成功项不回滚；已创建Profile和代理绑定默认保留；上号失败不自动关闭窗口；
- Desktop或Agent重启后读取未完成item并检查实际窗口状态：已成功补写、明确未执行继续、无法判断待确认；
- 结果待确认不能自动重复写CK、重新发码或再次登录；
- 接码链接过期保留记录并阻止继续使用，更新后可重试。

### 不允许情况

- 创建`media_account`不能称为上号成功；
- 不因为存在Cookie判定登录正常；
- 不在列表、普通日志、错误和Evidence中泄露密码、Cookie和验证码；
- 不让批量失败回滚成功账号；
- 不用通用task替代上号batch/item业务状态。

### 依据与候选CHG

- Product：第三章3.3.7～3.3.10、3.6、3.7；
- Decisions：ADR-0004、0008、0009；
- 候选：D1凭据与Cookie台账、D2批量CK、D3接码、D4人工验证码与人工接管、D5导出和换绑清理、D6批次恢复。

## M2-E Desktop本地执行投影与安全收口闭环

### 用户目标

普通运营可以通过真实Desktop壳安全执行M2-A～D本地操作；完整业务过程留在原业务页面，Desktop只提供环境状态、跨业务提醒、恢复和安全收口。

### 前置条件

- M2-A～D分别完成；
- 真实MySQL、Desktop、Local Agent、BitBrowser、代理及适用账号资源可用。

### 核心流程

```text
用户打开Desktop
→ 自动启动并检测Local Agent与BitBrowser
→ 用户在浏览器窗口、代理、媒体账号或上号页面发起操作
→ Cloud完成权限、环境和互斥预检
→ Tauri调用Local Agent
→ Agent同步操作BitBrowser并读回
→ 原业务页面展示完整进度、人工处理和最终结果
→ Desktop顶部“本机执行”抽屉提供跨业务提醒与跳转
→ 中断后先读取真实状态再恢复或重试
```

### 系统要求

- Tauri管理Sidecar生命周期和本地安全桥；Vue不持有动态Agent凭据，不直接访问Agent端口；
- M2-E不建设第二套Profile、代理、账号、上号详情、通用任务中心、通用工作流平台或独立本机任务业务模型；
- 完整批次、步骤、业务日志、验证码、账号冲突、参数调整、取消和重试由M2-B～D原业务页面负责；
- Desktop提供“环境状态”页面，展示Cloud、Local Agent、BitBrowser、`main_user_id`和当前节点可执行状态，并提供重新检测、启动/重启Agent、打开BitBrowser及恢复提示；
- Desktop顶部提供“本机执行”入口和右侧抽屉，仅普通运营可见，只展示当前电脑的正在执行、等待人工、结果待确认和最近失败摘要；
- “本机执行”不创建任务、不编辑业务配置、不复制业务表单，只允许查看摘要、打开窗口、重新检测、重新读取、查看脱敏日志摘要和跳转原业务页面；
- 顶部关注数量只统计执行中、等待人工和结果待确认；最近失败不计入红色数量；
- 最近失败只作为当前电脑的轻量便捷提醒，不作为长期业务历史或M2-E核心退出条件；
- 单项短操作不创建异步`task`，执行期间可由Tauri/Agent实时事件临时投影，完成后以原业务对象为准；
- 批量及等待人工过程以对应业务`batch/item`为过程事实；发布、互动、合成等后续长流程才使用Cloud异步`task`，且不属于M2验收；
- 本地执行进度不上传为另一套Cloud任务历史；Cloud仍保存业务`batch/item`和原业务对象最终结果；
- Agent只保存最小未完成操作标记，用于中断恢复，包含操作ID、类型、业务对象ID、阶段、可能副作用和待回传结果；正常完成立即清理，不形成运营可管理的本地历史；
- 同步操作超时或中断后必须先读回；能够证明成功则补写业务结果，明确未执行才允许重做，无法判断则进入结果待确认；
- 用户不能通过点击直接确认业务成功，必须由重新扫描或读取的真实结果证明；
- 同一个Profile同时只能执行一个本地浏览器操作，同一个媒体账号同时只能执行一个账号本地操作；用户手工发起冲突操作时直接阻止并提供当前执行入口；
- 普通运营不查看Agent端口、Token、SQLite、Contract版本和技术堆栈；本地只展示脱敏日志摘要，需要排障时由用户主动导出诊断信息；
- Desktop无执行中操作时停止Agent并退出；存在本地浏览器操作时提示返回业务页面处理或安全停止，已产生但无法确认的副作用进入结果待确认；首版Desktop关闭后Agent不长期后台运行。

### 完成标准

- Sidecar启动、健康、状态、停止、重启和清理在真实打包环境通过；
- 环境状态能让用户理解当前电脑是否可执行、为什么不可执行以及如何恢复；
- Web只能做Cloud操作，Desktop本地短操作和批量流程边界正确；
- 单项短操作同步执行、读回并更新原业务对象，不出现“已创建任务”或“命令已发送”即成功；
- 批量创建、批量检查、批量Cookie和上号过程均有对应业务详情页，本机执行抽屉只投影摘要并准确跳转；
- 验证码、账号冲突、代理调整、Cookie修改和批量重试均返回原业务页面处理；
- Cloud、Desktop、Agent、BitBrowser中断恢复不产生重复外部副作用；本地未完成标记正常完成后清理；
- Profile和媒体账号互斥规则对所有本地浏览器操作入口一致生效；
- PRD—Milestone—CHG—Evidence追踪矩阵、三角色UI/API矩阵、真实依赖矩阵、跨仓库回归和人工验收全部通过；
- M2-A～D可以在真实Desktop、Local Agent和BitBrowser环境完整演示。

### 异常与恢复

- 执行前失败零外部副作用；执行中断后先检查实际状态；
- Cloud不可达时不丢失已发生结果；恢复后幂等回写；
- Desktop或Agent重启后读取本地未完成标记和当前节点相关`batch/item`，再检查BitBrowser实际状态；
- 明确未执行的操作在原业务页面重新发起；无法判断的高风险操作保持结果待确认；
- Desktop或Agent退出时释放安全可释放资源，不删除恢复所需数据；
- BitBrowser结果无法确认时不自动重试。

### 不允许情况

- 不使用开发fallback、Mock-only路径或单纯任务详情代替真实Desktop业务链路；
- 不把“本机执行”建设为侧边栏复杂页面、第二套业务详情或第二套任务中心；
- 不让高级运营或管理员远程查看普通运营本机执行记录；管理员只能在自己的Desktop查看环境状态并完成被授权的本机确认；
- 不把本地执行过程同步成另一套Cloud历史；
- 不并发操作同一Profile或同一账号的本地浏览器资源；
- 不因代码、接口或自动测试存在而判定M2完成。

### 依据与候选CHG

- Engineering：Desktop、Agent、通信、测试和发布章节；
- Decisions：ADR-0003、0004、0008；
- 候选：E1 Sidecar、环境状态与同步安全桥，E2本机执行抽屉与本地恢复，E3互斥、安全退出与综合真实验收。

## 4. M2完整纵向业务流程

```text
管理员创建运营分组和用户
→ 分配角色、分组和游戏范围
→ 普通运营登录Desktop并确认会话
→ 绑定正确的BitBrowser主账号树
→ 扫描、确认或创建浏览器窗口
→ 导入和检测代理
→ 将代理写入窗口并读回
→ 创建媒体账号并绑定窗口
→ 选择CK、接码链接或人工验证码上号
→ 自动执行或人工接管完成登录
→ 同步平台UID、名称、头像、登录状态和当前Cookie
→ 账号通过Profile、代理和登录预检
→ 账号具备进入后续发布和互动的条件
```

该流程中，原业务页面承担完整过程和处理操作；Desktop环境状态负责可执行性说明；本机执行抽屉只负责当前电脑的跨业务提醒和快速跳转。

## 5. Milestone完成判定

### 业务验收

- M2-A～E全部闭环；
- 用户能够从可信身份和环境开始，完成Profile、代理、账号登录与真实信息回填；
- 页面不存在“请求成功但业务未发生”的假成功。

### 技术验收

- Cloud正式事实、Desktop安全桥、Agent执行与BitBrowser读回一致；
- 单项同步、批次/item和长流程异步task边界符合ADR-0008；
- 权限、互斥、幂等、取消、重试和结果待确认行为通过。

### 真实依赖验收

- 使用真实MySQL、Desktop、Local Agent、BitBrowser、代理、Cookie以及适用的接码/验证码资源；
- Mock只证明确定性逻辑，不能替代真实依赖退出条件。

### 安全与恢复验收

- 密码、Cookie、代理密码和验证码不进入普通列表、日志、错误和Evidence；
- 四端中断恢复不重复外部副作用，不丢失正式结果。

### 人工最终验收

M2只有在全部追踪项和真实Evidence通过，并由用户完成人工整体验收后，才能在Master Plan中标记`DONE`。
