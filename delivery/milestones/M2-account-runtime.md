# M2 账号运行环境业务闭环

M2 的最终目标是：运营人员能够在正确权限范围内，将账号资源配置到真实 BitBrowser 运行环境，完成验证并获得可供后续发布、互动使用的媒体账号。

本文件是 M2-A～E 的唯一业务闭环基线。详细分析和技术方案继续引用 Product、Engineering、Contracts、Decisions 与 AI Spec。

## M2-A

### 用户与权限可信闭环

**用户目标：** 管理员可以创建和管理运营用户；运营用户只能访问获授权的游戏、账号和运行环境，并能看到关键敏感操作的审计结果。

**前置条件：** M1 登录、会话、任务领取和审计基础可用；管理员已登录。

**用户操作：** 创建用户 → 分配角色和游戏范围 → 用户登录 → 执行业务查询与敏感操作 → 管理员修改权限、重置密码或停用用户 → 查看审计记录。

**系统与外部动作：** Cloud 在每个 M2 业务入口校验角色与游戏范围；新登录替换旧会话；失效 Agent 会话停止领取新任务并安全处理在途敏感任务；BitBrowser 首次绑定与重新绑定产生脱敏审计事件。

**成功必须同时满足：** 三类角色的页面与 API 权限一致；越权请求被拒绝且无数据泄漏；权限修改和停用即时生效；旧会话不能继续领取任务；关键操作可审计；自动化与人工角色矩阵均通过。

**失败时不得发生：** 不能只隐藏页面而允许 API 越权；不能在会话失效后继续领取任务；不能把敏感凭据写入日志或 Evidence；不能用接口存在代替角色链路验收。

**涉及 CHG：** `CHG-20260721-020` 的已验证基础工作；其余缺口由后续独立 CHG 承接。

## M2-B

### 媒体账号与 Profile 真实闭环

**用户目标：** 运营人员可以绑定自己的 BitBrowser 主账号树，管理获授权 Profile，将媒体账号绑定到真实 Profile，并通过账号检查看到真实身份和登录状态。

**前置条件：** M2-A 权限闭环通过；Desktop、Local Agent 和 BitBrowser 可连接；存在可使用的测试 Profile。

**用户操作：** 确认主账号绑定 → 扫描 Profile → 查看完整 Diff → 接受本地变化或恢复系统配置 → 创建或导入媒体账号 → 选择并绑定 Profile → 打开 Profile → 单个或批量检查账号 → 查看结果。

**系统与外部动作：** Agent 校验 `main_user_id`、`profile_user_id`、节点和 Profile 可见性；执行扫描、创建、更新、打开、关闭和检查；Cloud 保护运营字段，接收经验证的 Agent 结果并更新正式事实；恢复系统配置必须写入 BitBrowser 后读回。

**成功必须同时满足：** Cloud 与 BitBrowser 的 Profile 身份和配置可核对；同一 Profile 可绑定多个不同平台账号、同平台最多一个；账号检查回填平台账号 ID、名称、头像和登录状态；页面展示最终结果与失败原因；重试保留历史尝试。

**失败时不得发生：** 扫描不能覆盖 Cloud 运营字段；创建任务不能显示为业务成功；身份不匹配或 Profile 不可见时不能执行敏感操作；无法读回时不能更新正式成功状态。

**涉及 CHG：** 在 M2-A 完成后创建独立 M2-B CHG。

## M2-C

### 代理到 Profile 的真实绑定闭环

**用户目标：** 运营人员可以导入、检测和分配代理，并确认目标 Profile 实际使用经过验证的代理。

**前置条件：** M2-B Profile 身份与授权闭环通过；存在真实代理和专用测试 Profile。

**用户操作：** 导入文本、TXT、CSV 或 Excel → 查看解析预览与逐行错误 → 确认入库 → 执行真实检测 → 设置平台默认和单代理配额 → 查看自动分配预览 → 人工调整并确认 → 打开 Profile 验证。

**系统与外部动作：** Cloud 在确认前不产生导入或分配副作用；Agent 执行协议与连通性检测；Cloud 校验状态、到期、检测结果、平台配额和实际占用；确认后创建敏感任务；Agent 将代理写入 BitBrowser 并强制读回；Cloud 只在读回一致后记录正式绑定。

**成功必须同时满足：** 代理记录、检测结果和配额有效；BitBrowser Profile 中的代理与分配结果一致；目标 Profile 能通过该代理打开；页面显示正式绑定、逐项结果和可精确重试的失败项。

**失败时不得发生：** 解析预览不能提前入库；前端预览不能冒充正式分配；禁用、过期、检测失败或超配额代理不能分配；写入失败或读回不一致不能产生 Cloud 正式绑定。

**涉及 CHG：** 在 M2-B 完成后创建独立 M2-C CHG。

## M2-D

### Cookie 与账号开户闭环

**用户目标：** 运营人员可以通过批量 Cookie、接码链接或人工验证码，将账号资源变成已绑定 Profile、代理和真实登录身份的可运营媒体账号。

**前置条件：** M2-B Profile 闭环和 M2-C 代理闭环通过；真实 Cookie、代理、接码或人工验证码资源可用。

**用户操作：** 选择开户方式、平台和游戏 → 导入 Cookie 或接码资源 → 查看 Profile 与代理分配预览 → 调整并确认 → 逐条查看代理写入、Cookie 写入、浏览器打开和账号检查结果 → 对失败或安全可重试项精确重试 → 导出经授权的原始或真实 Cookie。

**系统与外部动作：** Cloud 创建批次和逐项任务并预检容量；Agent 逐条创建或选择 Profile、写入并读回代理、写入并读回 Cookie、打开平台、检查真实身份；Cloud 保留 `original_cookie`，将读回结果写入 `active_cookie`，回填账号资料和登录状态；接码凭据与一次性验证码仅临时使用。

**成功必须同时满足：** 三种适用开户路径各有真实成功样例；Cookie 在 BitBrowser 写入并读回；账号 ID、名称、头像、登录状态和 `active_cookie` 正确回填；成功项保持提交；批次展示部分成功、逐项失败原因和精确重试；成功账号可进入后续发布或互动预检。

**失败时不得发生：** 创建 `media_account` 记录不能称为开户成功；代理预览不能冒充分配；Cookie 或验证码不能出现在普通响应、日志或 Evidence；外部结果不确定时不能自动重试或标记成功。

**涉及 CHG：** 在 M2-C 完成后创建独立 M2-D CHG。

## M2-E

### Desktop、安全、恢复与综合验收闭环

**用户目标：** 用户可以通过真实 Desktop 壳启动和管理 Local Agent，完成 M2 本地操作，看到进度、错误和恢复状态，并最终确认整个账号运行环境可用。

**前置条件：** M2-A～D 分别完成；真实 MySQL、BitBrowser、代理、Cookie、接码或人工验证码以及 Desktop Sidecar 验收环境可用。

**用户操作：** 启动 Desktop → 启动或连接 Local Agent → 登录 Cloud → 查看本地环境状态 → 执行账号、Profile、代理和开户操作 → 查看任务进度与错误 → 中断并恢复 Cloud、Agent、Desktop 或 BitBrowser → 完成最终人工验收。

**系统与外部动作：** Tauri 管理 Sidecar 生命周期和本地安全桥；Vue 不持有动态 Agent 凭据；Desktop 不读取 Agent SQLite；Cloud 与 Agent 保存检查点、租约、待回传结果和重试历史；同一 Profile 的敏感任务被拒绝或串行；综合验收运行自动化、三角色 UI、真实依赖、安全和恢复矩阵。

**成功必须同时满足：** Desktop 的启动、健康、状态、事件、停止、重启和清理真实可用；用户从业务页面看到最终结果；中断后状态可恢复且无重复外部副作用；64 项 M2 矩阵、跨仓库回归和真实依赖 Evidence 全部通过；最终由用户人工确认 M2 完成。

**失败时不得发生：** 不能用开发 fallback、Mock-only 路径或任务详情页代替真实 Desktop 业务链路；不能并发执行同一 Profile 的敏感任务；不能因代码存在或局部自动测试通过而将 M2 标记为 `DONE`。

**涉及 CHG：** 在 M2-D 完成后创建独立 M2-E CHG；最终人工验收前 M2 最多进入 `VERIFYING`。
