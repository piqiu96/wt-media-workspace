### 认证读回能力与跨工程合同（待裁定）

V3 要求标记托管配置与比特实际配置的认证差异，应用成功还须有真实读回。当前 Agent 的 `BitProfile` 和 Cloud 的窗口快照刻意排除认证字段；代理写入的 `readback` 仅比较协议、地址、端口，Cloud 据此确认正式关系。因此不能从现有数据判断认证一致，也不能把现有 `readback` 解读为认证已核实。只读现场探测证实当前比特列表样本包含认证字段，但尚未证明所有比特版本都返回可比较原值。窗口详情先明确显示认证“待核实”，这不是完整实现。

推荐方案：保持凭据不进入通用窗口快照、浏览器前端和日志；由 Cloud 在授权和本人窗口校验后，向 Local Agent 发起针对单窗口、单目标配置的受保护核对。Agent 在本机瞬时比较比特读回值，仅返回认证 `一致 / 不一致 / 不可核实` 和观察时间，不返回认证原文或可复用摘要。写入确认和未知结果恢复必须分别处理不一致、缺失字段、掩码或读取失败，不把不可核实当成功；Cloud 仍是正式关系与额度事实中心。旧 Agent 缺少能力时按不可核实处理，并明确升级要求，禁止以默认值推断一致。是否保存核对结果、其失效条件、幂等与并发占额、具体接口及混合版本兼容须在正式合同中逐项定义并验证，不能仅靠页面改变。

备选方案：将认证值加入普通扫描快照便于比较，但会扩大敏感数据传播面，不推荐；继续只比较协议和地址改写提示，安全但不能满足完整业务要求，只可作为当前过渡状态。此项涉及 Agent、Cloud 和可能的 Desktop 桥/合同，超出现有已批准工程范围；按[change.md](change.md)中“未审批的……Contract/Ownership变化须先回到Workspace裁定”，记录为待裁定，不直接改动合同或 Agent。用户确认后须先更新 CHG、正式合同与仓库范围，再实施和做秘密泄露、混合版本、未知结果恢复及真实比特读回验证。
