## 独立目标与范围

用户从 DMG 原生应用报出内容池两处呈现问题，并追问「desktop 和 web 是同一套视觉，为啥差别会这么大」：

1. 当前内容池前端风格错乱；
2. 封面图片无法正常加载。

本 CHG 的独立目标是**回答这一问并修掉被证实的根因**。两处现象经实测归结为**两条互相独立的根因**：
一条 Desktop 独有（CSP 未放行图片），一条两端共有（标题省略号规则漏了渲染分支）。
「两端视觉是不是同一套」本身也被独立证否/证实，见 `evidence/20260923-fix-and-verification.md` 第一节。

本 CHG 后续由用户在 DMG 实机复核中**追加**了三批现象，均归入本 CHG：

- 根因 **E**：桌面端菜单栏图标全空（远程 sprite 被 CSP 拦掉）——已修，用户实机确认恢复。
- 根因 **F**：「内容」列只剩封面；挖掘任务的「任务名称/任务来源/发现结果」被压得不可读——已修。
- 呈现与时间列：三页时间列收窄到 150px 且**去秒**；「互动/发现结果/最近效果」的数字由 `·` 串行改为**竖排一行一项**（用户裁定）。

不含于本 CHG：不新增 Cloud 图片代理端点、不精简内容池列集、
不标 M3 DONE、不修 CHG-054 已登记的 D1～D10/S-1。

> **修订记录（2026-09-23，根因 F 轮次）**：上文原写「不动 `scroll.x`」。该决定**已被取代**——
> 三张表的 `scroll.x` 现改为由列宽推导，断言写死 `2060px` 的那条测试也一并改写。
> 取代理由与根因 B 的证否**无关**（B 仍成立：固定列是 `position: sticky`，与 `scroll.x` 无关）：
> 一是写死的值与列宽合计无关、是个漂移源；二是全列定宽后，列宽合计才第一次成为**真实地板**。
> 事实核对：写死的 `2060px` 从未生效（TDesign 取列宽合计，实测滚动容器 `scrollWidth=2378`）。

### 根因 F 的证否过程与一条方法学教训

F 曾被**误判为不复现**（见 `evidence/20260923-symptom-f-not-reproduced.md`，该文已作废）。
原因单一且明确：那次量测全程用**无头 Chrome**，而 **Chrome 的 fixed 布局认 `minWidth`、WebKit 不认**
（Chrome 里内层表宽 2378 = 含 minWidth 的列宽合计，读数恒为 340；WebKit 同产物实测 91.5）。

**教训：模拟台的引擎与宿主不一致时，它能把真实 bug 判成不复现。**
「窗口开大开小」此前也被这条误导——`tauri.conf.json` 的窗口恰是 1280×800，
**等于模拟台的测试尺寸**，所以尺寸从来不是变量，是引擎。

因此本轮改用**用户实机截图逐列量测**（PNG 解码后按表头左边界间距反推列宽，DPR=2）。
并新增静态闸门 `ListPageConventions.test.js`：断言五张表每列都声明 `width`、写死列数作分母，
**已做阳性对照**（临时改回 minWidth-only → 测试立即失败并指名该列，随后按 SHA 还原）。
**Chrome 模拟台只用于证明「无回归」，不再用于判断 F 是否修好**——它对本类 bug 结构性失明。

### 行高的真实构成（修正推断）

修后行高**统一 85px**（此前 87～153 不等）。逐件实测：
`85 = td padding 8 + max(内容格 64, 来源格 68) + td padding 8 + 边框 1`。
**驱动者是「来源」列而非标题列**——来源格 68 = 链接 22 + gap 2 + `<small>` 44（长标识符折成 2 行）。
`resource-module.css` 的 `tr { height: 56px }` 对本表**本来就不可达**：88×56 的封面加 16px 单元格内边距
已经给出 80px 下界。这是既有基线，不是本次引入，故不改；行高现已由内容稳定决定，视觉一致。

> **修订（2026-09-23，根因 F 轮次）**：上文的 85px 是 **WebKit** 读数，仍然有效。
> 但「互动」列的数字改为**竖排一行一项**后，该列由 1 行变 3 行（3×16 + 2×2 = 52px，未超 56px 下界），
> 「发现结果」（5 项 → 88px）、「最近效果」（4 项 → 70px）**会超过 56px 下界而把行撑高**——这是用户裁定竖排时接受的代价。
> 本轮模拟台（Chrome）对**已嵌入 DMG 的那份产物**读到行高 81px；Chrome 与 WebKit 的字形度量不同，
> **两者不可直接比较**，WebKit 的实际行高需由用户截图重读后回写本节。
