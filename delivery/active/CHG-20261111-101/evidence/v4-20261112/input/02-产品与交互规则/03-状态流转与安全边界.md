# 状态流转与执行边界

## 正常链路
`待执行 --执行校验成功--> 排队中 --调度领取--> 执行中 --平台接收--> 平台审核中 --审核通过且公开--> 已发布`

执行中如取得公开发布的明确证据，可直接进入已发布。

## 人工/异常链路
`执行中 --需要登录/验证--> 等待人工 --去处理完成且确定未手动提交--> 执行中(同一次尝试)`

`等待人工 --人工可能投稿--> 结果待确认`

`执行中 --平台提交不明确--> 结果待确认 --人工核实--> 已发布 / 平台审核中 / 发布失败 / 结果待确认`

`执行中 --确认执行结束且未成功--> 发布失败 --重试且安全检查通过--> 排队中(新尝试)`

`待执行 / 排队中(成功撤队) / 执行中(可安全终止) / 等待人工(可安全终止) --取消--> 已取消`

`已取消 --既有安全资源释放机制完成--> 已放弃`：**仅表示对已有状态的解读，不授权开发新增入口或更改资源占用规则。**

## 实现强制项
1. 所有改变状态的操作由后端核验当前状态和操作者权限，防止并发竞态及重复提交。
2. 执行、重试以及人工完成后的恢复过程均应设计幂等性；重试必须新增 attempt，保留历史尝试、内容快照和审计记录。
3. 发出取消请求≠取消成功；撤队要确认执行器未领取。已经触达平台且结果不明时不能直接释放资源，必须留在未知结果核实路径。
4. 人工接管只做外部平台验证动作，不在业务弹窗中存储账号密码或验证码。未知投稿立即阻断上传。
5. 核实结论必须附本次 attempt 的证据；失败结论要求「已结束+未发布」，已发布结论要求作品身份与可信成功证据，审核中要求平台已接收的证据。
6. 发布成功后应按平台和作品唯一标识去重关联作品管理；不可因重复核实重复创建作品实体。
7. UI 状态、操作只根据服务端真实结果刷新；不要在点击时提前变为已发布/已取消/排队中。
