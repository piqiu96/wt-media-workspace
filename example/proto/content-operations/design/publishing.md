### 先明确：发布计划、发布批次、发布任务的职责

**本轮推荐，待确认：计划管编排规则，批次管本次确认范围，任务管单条执行结果；当前不强制建成三个独立对象。** 上一轮提出的发布批次用于稳定找回一次发布，不应因此再给现有计划增加一个职责重复的执行容器。

| 概念 | 负责什么 | 边界 |
| --- | --- | --- |
| 发布计划 | 内容范围、平台与账号分配、每日条数与时段等编排规则，以及这些规则生成的安排预览 | 多平台、指定未来时间或跨日不单独构成独立长期计划的理由；是否独立取决于规则是否需要持续生成多次发布 |
| 发布批次 | 一次确认的有限任务范围；整体进度、前后检查汇总、人工处理入口及范围内的控制 | 支持当天或跨日完成；本次需哪些账号窗口不改变批次身份；状态和数量从原任务汇总，不替代单条结果 |
| 发布任务 | 一条成片在一个平台、一个账号上的发布安排、字段、执行过程与结果 | 同账号多条对应多任务并串行；重试是原任务的新尝试，不另建任务或批次 |

**当前场景推荐两层执行关系：**

```text
新建发布：单平台、多账号、多成片 ──┐
                                  ├→ 一次发布批次 → 多条发布任务
按计划编排：平台、条数、时段等规则 ─┘
```

当前原型的计划从选定的有限成片一次生成完整安排，因此推荐将编排规则保存在该次发布范围中，与普通发布共用批次进度和任务工作区；不再同时创建一个计划总控和一个一对一的批次总控，分别维护相同进度、暂停和收尾。界面仍可称“发布计划”、保留现有三步入口；这是按规则编排的同一份发布范围，不是第二份执行对象。下文计划列表／详情在此方案下是同一范围的入口或类型视图，页面归并待评审，不直接删除原型现有入口。

“一次确认”指首次创建该次发布。后续调整未开始项、明确授权追加内容或重试失败项，保留原范围与任务关联，记录范围变化，不因再次保存生成新批次；复制后重新确认另一轮发布才形成新范围。批量修改操作本身也不是发布批次。

**仅当以后确实需要同一组规则持续接收新内容、反复产生独立发布范围时，才拆成可选的“计划 → 多个批次 → 多条任务”。** 届时计划负责后续生成规则和授权边界，各批次保留本次实际内容、安排与结果；停止后续生成不等于取消已生成任务。不能按自然日、每 5 个窗口或每次进入页面机械创建批次，本轮不提前实现循环派发或定时产出联动。

当前 5 个浏览器窗口只是原任务的处理集合，不增加第四层业务对象。任务不因窗口切换或重试换归属，批次结束不代表全部成功；整体和平台检查复用任务证据，不在“计划”和“批次”重复确认。以上对象合并与页面组织属于本轮建议，未成为正式模型或已实施能力。

### 运营如何选择与操作

**推荐待确认：围绕运营目的提供入口，不要求先在计划、批次、任务三个对象中选择。** 发布管理以“新建发布”为主入口，“按规则编排”为次入口（对应现有新建发布计划），不增加“新建批次”。默认查看每次发布的总览，提供任务明细切换、需我处理和草稿入口。

| 运营目的 | 选择与操作 |
| --- | --- |
| 将这批成片发到一个平台，立即或指定未来时间 | 新建发布；也可从成片勾选“去发布”带入。选平台、多个账号和成片，核对分配与时间后确认 |
| 希望按每号每日条数、时段分配，或统一编排多个平台 | 按规则编排；三步配置并预览完整安排，再确认排期。单平台也可使用，不要求跨日 |
| 已有安排需要登录、微调、核对或修复 | 从原发布记录或“需我处理”进入，沿原任务继续；不重新创建发布 |
| 只想改未开始项的时间、顺序或账号 | 在原发布范围内调整，展示影响清单，保留任务与结果；不因修改再建一个计划或批次 |

当天还是跨日不决定入口；指定一个未来时间仍可用普通发布。批次在确认创建后自动形成，运营无须另外选择归属或先起名；总览可用平台、内容数量和创建时间自动摘要，按需修改显示名称。

**发布前是否需要人工检查，是独立于入口的执行要求。** 默认自动执行；主动需要真实平台页面微调时，开启“发布前人工检查”。系统完成可执行任务的浏览器准备后等待人工，不自动越过该检查最终提交。已知技术条件只能人工最终提交的任务则提前说明数量与原因，不能伪装成可全自动。表单“逐条检查”核对的是安排和字段；可选的运行时人工检查用于真实页面微调，两者不要求所有任务重复执行。

确认后的路径为“本次发布进度 → 按需进入当前窗口处理 → 逐条核验结果”。全自动任务直接按安排推进；人工检查场景保持当前窗口集合稳定，完成微调后提交已核对项，明确结果后“准备下一组”。只取符合执行时间的任务，不因准备窗口提前发布未来安排。浏览器数量按可用条件决定，同账号多条仍串行；两种入口共用该处理区。

总览每行表达一次发布，显示平台、内容／任务与账号数、安排时间范围、进度、状态和独立操作列；“查看进度”用于跟踪，“处理 N 条”用于定位具体人工事项。跨日未完成项持续可查，离开再进入保留原范围和状态；失败修复或结果未明都从原记录处理。发布成功后可去作品查看，后续互动结果独立跟踪。

**沿用的已确认边界：**
- 成片勾选“去发布”和任务页“新建发布任务”共用一个弹窗，只差是否带入所选成片；成片行内不重复放发布按钮。
- 用户明确的常见创建场景为单平台、多个账号、多个成片，并提出同时打开 5 个浏览器窗口微调后发布。发布批次与窗口处理方式的具体方案见 §1、§3、§5，仍按建议评审，不将窗口数当作发布任务数量限制。
- 普通发布可包含多条内容、多个账号，也可指定未来时间。发布计划已有按每日条数、时段持续安排的用途；普通发布的平台范围与计划的补充用途按 §3、§4 本轮建议评审，不将此前 AI 提出的普通发布多平台当作用户已确认要求。
- 确认“立即发布／确认排期”后按安排执行，不再要求逐条开始或再次启动计划。保存草稿不授权执行；历史未启动项不被自动执行。
- 前期浏览器自动完成优先；技术不足时才人工最终提交，后期按平台条件接入 API，允许不同平台混用。常规检查自动推进，异常或特殊要求才需人工。
- 通常当天完成是主要场景，不是技术限制。跨日、等待预约时间和回执均保留，零点不改变任务结果。
- 内容生产、发布、作品、互动各自负责；定时产出不是普通发布的前提，产出成功不自动授权发布。

## 1. 列表放什么

### 发布任务列表

**推荐：任务明细中，一行仍是一条视频在一个平台、一个账号上的发布任务；增加按本次创建查看的“发布批次”。** 批次自动归集一次确认创建的任务，帮助运营找回整批进度与处理现场，不要求额外创建、命名或维护“短期计划”。按计划编排时保留对应规则与来源，按前述关系建议共用同一执行范围，不再复制一组任务或总控对象。

**批次与任务两个视图，推荐待确认：** 发布任务页优先按发布批次查看，提供“任务明细”切换，用于跨批次查单条异常。批次行显示批次标识、平台、创建时间／创建人、内容与实际账号数、任务数、进度、状态、操作；状态与操作继续分列。“查看进度／进入处理”打开该批次的执行工作区，查看不等于重新启动。未具备真实创建关联的历史任务仍可在明细中查找，不按相近时间或同名内容猜测归批。

若采用本轮对象关系建议，总览以“直接发布／按计划编排”区分类型；原计划列表可作为按计划编排的筛选入口，同一次发布不作为两份独立记录统计。入口“新建发布任务”可简化为“新建发布”，另保留“新建发布计划”作为规则编排入口，避免一次创建被误解为只能生成一条任务；命名待评审。

| 区域 | 具体内容 |
| --- | --- |
| 页面操作 | 推荐主按钮“新建发布”；次入口“按规则编排”（现新建发布计划）、“发布草稿（N）”；入口名称随对象关系一起评审 |
| 常用筛选 | ID／标题搜索、平台、账号标签、账号、状态 |
| 高级筛选 | 来源（直接／计划／复刻）、发布批次、关联计划、安排时间、实际发布时间、执行方式、通道；有管理权限时增加负责人 |
| 快捷范围 | 全部任务、需我处理；后者汇集需要当前用户采取动作的任务，正常等待不混入 |
| 任务明细表格列 | 发布 ID；发布内容（封面＋标题）；平台／账号；安排时间；状态；来源；实际发布时间；操作 |
| 详情补充 | 完整发布字段、来源成片、负责人、实际通道、过程与检查记录、作品结果、发布后动作 |

状态列只显示状态；“去登录、查看进度、核对结果”等按钮放操作列。当前阶段、原因和处理说明放详情或人工处理区，不拼接到状态名称里。技术通道不占首要列，详情可查，高级筛选可找。

列表默认展示全部有效任务，不用“今天”隐藏跨日未完成项。提交成功后定位本次真实任务，可一键返回全部；筛选、分页、跨页选择和详情返回保持上下文。草稿独立找回。

任务明细中的批量动作只提供当前适用的操作，例如取消待执行任务、重试明确失败项；显示可处理数量与不适用原因。恢复错过排期的任务先确认补发或改期，不瞬间追发全部历史任务。取消常规“批量开始”，人工处理按所选范围连续进入。

## 2. 状态有哪些，分别能做什么

**推荐：任务收敛为六个互斥主状态。** 准备文件、填写内容、上传、提交、等待自动核验与正在核验均属于“执行中”的阶段；登录异常、错过排期、需补链接等作为原因，不另增顶层状态。

| 任务状态 | 用户看到的解释 | 可执行动作 |
| --- | --- | --- |
| 待执行 | 等待指定时间或账号队列；到时自动推进 | 查看安排、编辑未开始项、取消任务 |
| 执行中 | 系统正在处理，包括提交后等待或核验平台结果 | 查看进度、查看提交记录；浏览器通道可查看对应窗口，不重复提交 |
| 待人工处理 | 当前需人登录、微调／最终提交、核对发布结果、补必要记录或完成特殊检查 | 按原因提供去登录、打开窗口、核对结果、补链接等操作，完成后回原阶段 |
| 已发布 | 有可追溯的发布结果 | 查看作品、查看详情与后续动作 |
| 失败 | 本次尝试已明确结束且未发布，显示原因 | 修正后重试原任务、取消任务 |
| 已取消 | 待执行任务已取消，或失败后明确不再执行；保留原记录与尝试历史 | 查看详情 |

草稿是未生效配置，不混入执行状态。正常等待平台结果保持执行中，确实需要人核对或补必要结果时才转待人工处理。无法判断不等于失败或成功；人工确认未发且旧执行结束后才允许重新准备。正常人工最终提交不计为故障。

计划状态描述是否还在执行；发布结果单独显示“全部成功／有失败／有取消”等数量。**已结束不等于全部发布成功。** 部分平台暂停或需要人工时，其他平台仍可执行，不能用一个状态掩盖组内差异。

批次总览同样由其实际任务归并进度和运行情况，保留失败、取消及未决数量，不新增一套独立执行状态。当前 5 个窗口处理结束不代表整批结束；仍有排队、自动核验或需人工任务时，批次继续保留相应进度与待办。

控制动作按对象明确命名：

| 动作 | 影响 |
| --- | --- |
| 暂停计划／暂停本平台 | 阻止对应范围内新任务及尚未发生的最终提交；已提交结果继续核验，不撤回作品 |
| 继续计划／继续本平台 | 重新检查对应范围，沿原阶段恢复；错过原时间的任务先确认补发或改期 |
| 取消任务（任务行／所选任务） | 取消明确未发布的待执行或失败任务；执行中、结果不明和已发布任务不提供此动作 |
| 取消未执行任务（计划／平台） | 取消该计划或平台内尚未开始的任务；确认框显示范围和条数，已经开始、已提交或已发布任务继续按实际状态处理 |

例如计划有 20 条任务，12 条已发布、2 条执行中、6 条未开始，取消时说明“取消本计划尚未开始的 6 条任务？12 条已发布结果保留，2 条执行中任务继续处理。”离开页面、关闭详情或返回列表是普通导航，不作为发布业务按钮，不改变任务状态；再次进入仍展示真实进度与待办，依赖本机在线时明确展示设备条件。

**推荐示例：** 正常等待回执、自动核验归执行中；登录问题、必须人工核对结果归待人工处理，具体原因放详情／人工处理区。详情业务操作只放 Footer；同一区域一个主要操作，同一行可用操作不超过 5 个时平铺。

## 3. 新建发布任务如何组织

**已确认：共用两步弹窗——内容与安排 → 逐条检查。**

**本轮推荐，待确认：普通发布维持单平台。** 用户提出普通发布更像单平台操作；结合现有原型，推荐一次选择一个平台，支持多条视频、多个账号、立即或指定时间执行。平台字段、账号与执行方式集中在当前平台，不增加平台页签。此前将单平台本身列为原型缺口的判断撤回；跨平台扩展需要实际效率收益支持，不作为本轮必改项。

普通发布解决“把这批内容发到这个平台”；按计划编排解决规则分配与节奏安排，两条入口复用同一批次执行模型和相同粒度的任务。单平台不等于单视频、单账号，也不限制当日完成；采用独立长期计划的条件见前述对象关系，不因进入三步编排就强制增加第三层总控。

**一次创建与 5 个窗口的关系，推荐待确认：** 一次确认创建自动关联为一个发布批次，例如 20 条视频分给 8 个账号，产生同一批次内的 20 条任务。当前准备的最多 5 个账号窗口只是从该批次取出的工作集合，不另生成一个业务批次，也不改变任务 ID。窗口处理完可以继续取后续任务；同账号仍串行。全自动任务正常按安排执行，人工微调作为明确采用的协同方式或异常接管路径，不把所有发布默认改为人工。

### 第一步：内容与安排

按下面顺序组织，明确当前平台和内容，再配置该平台账号与字段，最后设置时间和可选动作。

| 分区 | 内容与交互 |
| --- | --- |
| ① 发布内容 | 选择成片／本地视频；带入成片可增删，无需重选。选择器支持类目、平台、搜索、分页和跨页保留，说明已安排／已发布与不可用原因 |
| ② 发布平台 | 本次只选择一个平台，展示该平台可用视频数；适用平台范围不等于自动选入。平台选择纳入共用弹窗，避免前置选择后重复设置 |
| ③ 账号与发布设置 | 在当前平台选择账号、账号标签与分配方式，设置公共标题／简介／标签／封面等平台字段，无需平台页签 |
| ④ 执行时间 | 立即／指定时间。立即项按账号依次执行；指定时间可在未来，检查同账号时间冲突，不强迫创建持续计划 |
| 连续发布节奏 | 同账号相邻发布的最小提交间隔，默认继承已配置的平台／团队规则并展示采用值，按权限调整；不虚构平台“安全间隔”。同账号跨批次、跨计划统一排队，不同账号可并行 |
| 执行要求 | 默认自动执行；可选“发布前人工检查”，用于真实平台页面微调并在最终提交前等待确认。提前展示已知必须人工最终提交的任务数与条件；平台通道由能力适配，不要求运营先选浏览器或 API |
| ⑤ 可选后续动作 | 引导评论、初始互动等默认收起，开启后配置；发布成功后衔接，结果单独跟踪 |

多个视频默认轮流分配到所选账号；一条视频在本平台分配一个账号，不展开“视频×账号”全组合。同一成片／平台的占用沿用现有原型基线，跨平台独立判断。

**账号与视频的数量关系，推荐待确认：允许一个账号在本次发布中顺序发布多条，不限制为每账号一条。** 一条发布任务仍对应“一条视频＋一个平台＋一个账号”；一次创建可以生成同账号的多条任务。选择 1 个账号和 5 条视频即生成该账号的 5 条任务；12 条视频分给 4 个账号，默认每号 3 条，共 12 条任务。

同账号任务按确认顺序串行，不同时占用该账号提交多个视频；不同账号可按执行资源并行。立即发布表示开始处理队列，不代表所有任务同一时刻提交。逐条检查支持按账号查看分配结果、调整账号和未开始项的顺序；人工调整不被重新分配静默覆盖。明确指定单条时间时继续检查同账号冲突，正常串行排队本身不算时间冲突或错过排期。

**创建需要什么，推荐待确认：** 运营明确成片／视频文件、目标平台、账号、平台要求的发布字段，以及立即或未来安排。分配方式、发布间隔、自动执行设置可继承默认值，确认前展示实际采用值；可选运行时人工检查和发布后互动。平台不要求的简介、标签、封面等不强制填写。涉及本地文件／浏览器时明确执行设备与窗口归属及可用条件；任务 ID、批次关联、创建人和实际通道由系统生成或匹配，不让运营手填。只创建一条也能直接用任务 ID 找回，不要求先理解批次。

间隔推荐按同账号两次实际提交发布的最小间隔定义，以上次已核实的提交时间计算；下一条还必须满足自身安排时间、上条结果已明确及平台限制。缺少可信提交时间时不猜测放行，间隔已过也不能覆盖未决提交现场。等待展示“等待账号／等待间隔／平台限流”和可确定的预计时间；正常等待不是失败或待人工处理。准备下一组同样遵守这些约束；本稿不预设统一分钟数。

执行默认自动，平台配置中说明已核实的可用方式；浏览器／API 按能力和授权适配，在详情可查。保留人工辅助路径，已知不能自动最终提交时提前显示“预计需人工提交 N 条”，不等执行时才告知。静态演示能力不能作为真实平台支持承诺。

本地视频显示文件名、当前设备及待校验／可用情况，不伪造成片或上传成功。设备无法访问时支持重新选择。切换平台或方式保留有效输入，失配项给出原因，不静默换账号或文件。

### 第二步：逐条检查

| 区域 | 内容与交互 |
| --- | --- |
| 顶部摘要 | 不同视频数、任务数、实际／候选账号数、立即／定时条数、需修正项 |
| 检查清单 | 视频 → 平台／账号 → 文案与封面 → 时间 → 后续动作；每页 20 条，可逐条修改并跨页保留 |
| 批量调整 | 明确作用于所选行还是全部，区分填默认值与覆盖已有值；重新分配保留仍有效的人工修改 |
| 问题定位 | 按平台和具体行列出账号失效、文件占用、时间冲突、字段缺失；可修正，或明确移出问题项并保留草稿 |
| Footer | 上一步、保存草稿、一个主要提交按钮；默认立即项为“立即发布”，未来安排为“确认排期”。主动开启立即任务的发前人工检查时推荐“开始准备”，并明确“准备完成后等待你确认发布”；混合安排逐项说明检查要求。文案变化随该执行要求一起评审，不另加常规二次启动 |

普通发布数量示例：12 条视频发到 B站，选用 4 个账号轮流分配，产生 **12 条任务**，不是 12×4 条。多平台计划中 B站安排 12 条、百度安排 8 条，则共 20 条任务；各层分别统计不同视频数与实际发布任务数。

确认后按安排执行，定位本次发布批次及其任务，不再点开始；人工微调方式进入该批次处理区，全自动方式以进度与异常为主。混有立即与定时项时确认区明确各自数量与时间。草稿不创建有效任务、不授权执行、不占用视频用途；关闭或返回保留有效输入。

提交时重新校验；部分创建成功时保留成功任务，失败项保留输入，重试只补失败项并归回原次创建范围。预计任务数、实际创建数和未创建项分别表达，未创建项不能当作已排队任务计数。重复点击、切换入口和响应丢失恢复不能重复创建任务或批次、不能重复发布。已提交结果不明先核对。

## 4. 新建发布计划如何组织

**已确认：发布计划用于持续安排，三步完成；普通一次发布无需先建计划。** 通常当天完成不影响跨日能力，也不要求将定时产出绑进来。

**本轮补充建议，待确认：保留“新建发布计划”作为按规则编排的入口。** 可承接当天多个平台的统一分配，单平台需要每日条数和时段规则时也可使用。当前针对已选有限成片生成一次完整安排，推荐与普通发布共用一个批次执行范围；规则与安排保存在本次范围内，不另创建一对一的计划和批次总控。“持续安排”不等于已确认无限循环、自动补入内容或每日生成新批次。

若采用上述补充，当天统一发布可直接按当前批次安排执行；只有需要按规则分配时才配置每日条数和时段。不能因为进入计划，就强迫用户设置长周期或定时产出。以下三步继续保留，执行节奏的必填条件随计划用途一起收敛；确认后的计划详情复用同一批次的进度、检查、任务与人工处理，不重复显示两套暂停、取消或完成状态。

| 步骤 | 怎么组织 | 本步产出 |
| --- | --- | --- |
| ① 内容与目标平台 | 选择类目、候选成片、目标平台和开始日期；展示每个平台可用量与缺口 | 明确计划内容范围，各平台可用不同子集 |
| ② 分平台配置 | 按“内容范围 → 账号与分配 → 每日条数与时段 → 发布字段 → 可选后续动作”组织；复用普通发布字段与选择器 | 每个平台有独立节奏和字段，公共默认与覆盖来源可见 |
| ③ 全部安排预览 | 全部平台／单平台、全部／需处理；逐条展示视频、账号、文案、封面和完整时间，可分页调整 | 看清完整安排与冲突，汇总任务数、实际账号、预计结束时间 |

Footer 为上一步、保存草稿、确认排期；确认即生效并进入计划详情，无需再次启动。

按规则编排同样可设置“发布前人工检查”，其默认值、适用任务及实际平台能力与普通发布一致；最终预览说明哪些任务可自动完成、哪些任务需在执行时人工处理。需要人工检查的项确认排期后可自动准备，但必须等待检查后才最终提交。

重新生成安排前显示变化范围，保留仍有效的人工调整。改期、移出、追加或暂停都明确影响哪些未开始任务；已开始执行的项（含提交后核验与等待人工核对）和已发布项不通过重新编排改写，历史结果不重建。

长期计划是否进入首版重点另按实际需求决定；本轮不据此删除原型已有入口。定时产出由[内容生产](content-production.md)负责，未来可按明确授权衔接当前发布能力，不提前新增工作流编辑器。

## 5. 计划进度展现什么，如何处理人工事项

### 单任务入口、执行控制与失败恢复（本轮推荐待确认）

**一条任务只有一个执行现场。** 单任务 ID、批次、计划只是查看范围不同；从任何入口打开同一 ID，都引用原安排、阶段、回执和尝试历史，不启动第二次执行。任务页看当前阶段、控制方、等待／失败原因与动作；批次按账号展开队列、间隔、受阻数量；计划按平台和安排展开，均可定位具体任务。对象是否归并不影响这条一致性规则。

| 打开时的情况 | 可以做什么 | 对原范围的影响 |
| --- | --- | --- |
| 尚未开始 | 编辑允许修改的安排／字段，或取消；账号与顺序变化重新检查队列 | 保留任务 ID 和归属，原批次／计划同步变化，不独立另起执行 |
| 自动执行中 | 默认查看；需要操作时申请人工接管 | 系统在安全节点停止继续操作并交出任务与窗口，再允许人工操作；只阻断相关账号，其他账号可继续 |
| 等待人工 | 有权限且未被他人处理时进入原窗口修复／微调 | 当前账号后续依赖任务等待；完成后明确交回自动执行，重新检查后沿原阶段继续 |
| 已提交、结果未明 | 等待自动核验，必要时人工核对 | 不允许重发或覆盖现场；同账号下一条仍等待 |
| 明确失败且确认未发布 | 修正后重试原任务，或取消 | 重试回到原账号队列，记录新尝试，不复制任务、批次或重跑成功项 |
| 另一位运营正在处理 | 显示处理人与当前情况，允许查看，禁用冲突的修改／提交 | 明确交接且确认原控制已停止后才能更换处理人；刷新、断线或第二个标签页不能擅自夺取控制 |

排他控制覆盖任务、真实账号及浏览器窗口，并跨所有批次、计划和共享该账号的互动任务生效；只在某个页面禁用按钮不足以避免冲突。接管、重试、取消都在提交动作前重新核对真实状态；已开始提交无法安全交接时先核对结果。接管是控制过程说明，不增加顶层状态，也不允许人为跳过硬检查。

| 异常 | 系统与人的分工 | 呈现与恢复 |
| --- | --- | --- |
| 提交前临时网络／上传问题，已确认不会重复发布 | 系统有限次数退避重试，只恢复必要步骤 | 执行中；展示失败步骤、尝试次数与下一次重试时间，不无限重试 |
| 登录、验证码、文件缺失、字段修正 | 需要人提供信息，转待人工处理 | 明确修复动作与影响范围，修复后重新检查；不用通用“重试”替代所有修复 |
| 提交后超时、断连、结果未知 | 先自动核验，无法确认再请人核对 | 自动核验属执行中，人工核对属待人工处理；不能因超时标失败并直接重发 |
| 平台明确拒绝，或安全重试用尽且确认未发布 | 标记失败，保留原任务与尝试 | 修正后重试、改期或取消；批次／计划保留失败数量和原因 |

内容自身问题只影响该条，在确认未发布并安全释放后其他任务可继续；账号问题阻断该账号，平台共同限制阻断该平台，共享设备问题影响依赖该设备的任务。结束可表达“8 条已发布／1 条失败／1 条取消”；还有重试、未决回执或人工事项时不能提前结束。结束后的“重试明确失败项”重新校验范围，只处理符合条件的原任务，更新当前进度并保留以前的失败尝试；已发布与未决项不混入重试。

**互动单独衔接：** 创建时选配动作、执行账号、评论内容／模板及触发条件；未启用就不产生互动任务。取得可靠作品身份和发布结果后，再按平台可执行条件触发；条件未满足则等待，不凭点击发布就开始。发布页显示关联互动 ID、进度与处理入口，互动详情和恢复由互动管理承接。发布与互动分开统计，例如发布完成 8／10、已触发互动完成 5／8；互动失败不改写发布结果，也不重跑发布，重复回执不重复创建互动。共享账号／窗口时共用资源队列，默认优先发布，已开始的动作先安全结束再释放。

**推荐：顶部看本次结果，中间按平台展开，下面定位任务与人工待办。** 单平台普通发布复用结果、任务与人工处理能力，直接看当前平台，不展示多平台选择或空分组；计划再按实际平台分组。查看范围来自真实任务关联，不要求为普通发布新建计划对象。

```text
[打开对应窗口] → 完成验证 → [重新检查并继续]
```

这是信息结构示例，不承诺实际页面布局或真实平台能力。已发布、执行中、待人工处理等主状态只计一次；自动核验计入执行中，必须人工核对计入待人工处理。人工问题项数另标单位，不与任务数相加。下一次排期、暂停范围、自动／人工辅助方式在组内显示，技术通道按需展开。

单平台普通发布可按账号展开队列，例如“账号 A：已发布 1／5，当前第 2 条，待执行 3 条”，并定位当前视频。账号需要登录或验证时，仅阻断该账号及其依赖任务，其他独立账号可继续；已提交结果不明时先核对，保留现场，不推进同账号下一条。明确结束且未发布的单条失败不自动扩大为全批失败。

发布进度按实际任务计数，不把“检查、上传、填写”等节点各算固定百分比，不平均平台百分比。取消和范围调整保留数量与原因，不通过缩小分母伪装全部成功。“今日”仅为查询范围，跨日未完成任务仍能找到。

### 前置、后置检查怎么展现

| 层级 | 前置负责什么 | 后置负责什么 | 默认呈现 |
| --- | --- | --- | --- |
| 本次执行／关联计划 | 配置与授权范围、跨平台冲突、共享资源 | 汇总各平台结果，核对总量、范围变化与未决项 | 顶部一行检查摘要，可展开 |
| 平台组 | 平台规则、字段、通道能力与组级依赖 | 对齐本平台任务、作品结果及缺失回执 | 组内简短状态；有问题才突出 |
| 单条任务 | 临近执行时核验文件、账号、窗口、占用与最新字段 | 提交后取得本条结果，必要时转核对 | 显示当前步骤、原因和下一步 |

每组保留前后检查职责，有独立过程时再展开，不固定堆三组大型步骤条。上层引用下层已有可信结果，不重复检测或确认；创建时通过不保证未来执行时仍有效。

正常检查通过后自动继续、自动收尾。等待未来时间或正常回执显示等待原因；只有明确需要人工判断、技术不足或异常时进入处理。修复后重新检查，权限、文件等硬条件不能靠无依据的“人工通过”绕过，超时也不能自动通过。

单任务／单账号问题只影响依赖范围，平台共同条件问题影响该组，真正共享问题才扩大阻断。其他独立任务可继续；同账号未决提交结果先核对，不能让下一条覆盖现场。浏览器并行数量按实际资源判断，不把原型“5 个窗口”当正式容量。

### 人工处理与结果收尾

<a id="7-发布结果与异常下一步必须清楚"></a>

**5 个窗口统一微调的工作方式，推荐待确认：**

1. 从发布批次打开处理区，按账号队列取最多 5 条可执行任务，每个窗口对应一个不同账号的当前任务；账号不足 5 个时只开实际需要的窗口，不为同账号的多条视频并开多个提交窗口。
2. 系统准备页面、文件和文案；处理区列出账号、视频、当前阶段及对应窗口入口。运营逐窗微调并核对，同一组不因某条先完成而自动替换为新视频。
3. 若已验证浏览器能力支持系统最终提交，提供“提交已核对的 N 条”，范围只限运营明确确认的当前项；否则由运营在各平台窗口最终点击发布，系统逐条核验结果。只打开窗口、返回工作区或确认准备完成均不代表发布成功。人工微调方式中的最终确认不等于要求全自动任务再次开始。
4. 当前任务取得明确结果后，运营点“准备下一组”，复用已释放窗口或准备其他账号的后续任务。结果不明或待人工修复的窗口保留，不覆盖现场；无需等所有任务成功，其他可释放窗口仍可继续。批次持续展示总进度、当前窗口和待处理项。

页面采用“批次进度＋当前窗口列表＋当前任务说明”的组织方式，复用既有执行工作区。窗口数量是本次处理容量，5 为当前场景示例，不作为固定业务上限。离开后可从原批次找回任务、步骤与未决事项；重新进入先核验实际窗口，不仅凭页面记忆认定现场仍可用。

| 需要人做什么 | 入口与恢复 |
| --- | --- |
| 登录／验证 | 打开正确账号窗口 → 完成后重新检查 → 回原阶段 |
| 微调并最终提交 | 展示视频、账号、待核对字段和窗口 → 在平台完成提交 → 系统核验；返回本系统不等于已提交 |
| 核对是否发出 | 查看正确账号与作品；已发则补可信结果，确认未发且旧执行结束后才重新准备 |
| 补作品链接／时间 | 保留原平台、账号、视频；使用填写的实际时间，重复链接定位原记录，明显跨平台错误阻止保存 |

同一账号登录问题合并一个入口，明确受影响任务数。人工处理区显示平台、账号、视频、原因、等待时长、影响范围和继续条件；使用原任务，不另建一套待办业务对象。浏览器内调整后的实际字段按取得的证据记录，未知值不伪装成已核实。

浏览器已打开、内容已填好、已点击提交、平台已受理、已发布是不同证据。已提交或结果不明时不直接重发；重复／延迟回执、补链接不能重复产生作品或后续动作。系统外历史补录只记录事实，不触发发布。

各任务持续核验，组结束时自动对账，全部执行结束后汇总。失败、取消与未核实项必须可解释，不显示全绿。引导评论／初始互动独立展示，互动失败不改写视频发布结果；作品观察与互动分别由[作品管理](works.md)、[互动管理](interaction.md)承接。

**这一项真正需要确认的业务取舍：**

| 问题 | 当前推荐 |
| --- | --- |
| “已发布”是否必须等平台审核通过、作品可见？ | 以可追溯的发布结果及记录完整性作为发布完成，审核／可见性在作品中继续跟踪；平台仅受理但未证明发布时不能直接算成功 |
| 生效前检查发现部分平台／任务不可用，是否先执行其他项？ | 给出受影响清单，由运营明确选择仅提交可用项，其他保留草稿；不静默改变本次确认范围。执行中新增局部问题则按依赖范围处理 |

## 6. 原型核验与修改清单

核验日期：2026-11-05。范围为当前 `index.html` 加载后实际生效的发布模块，以及成片入口、文件与账号选择、作品和互动回链。采用独立浏览器与隔离的演示数据，走查任务列表、两步新建、计划列表与详情、三步计划预览、人工执行及边界恢复；同时核对源码。组合异常通过独立演示场景复现，不代表真实平台执行或原型已获人工验收。本轮只修改设计稿与索引。

### 设计稿还需要补齐的共用边界

- **文件与执行条件：** 当前可选判断主要覆盖发布占用和平台使用归属，尚不能代表文件可访问、账号已登录、设备在线。创建检查与临近执行检查分别呈现；本地视频明确当前设备、待校验与重新选择路径，避免“记录文件名”被理解为准备完成。
- **权限与归属：** 成片选择已有使用者限制，但发布任务／计划的负责人、谁能处理他人任务、谁可暂停或取消整计划尚未形成一致方案。需要沿用已有角色和数据范围，补清创建、查看、修改、处理、取消权限；不因演示可点击就认定业务已授权。
- **时间与恢复：** 正常账号串行等待不算错过排期。因暂停、离线等错过明确时间时，恢复前确认补发或改期；等待未来时间、跨日与正常核验不因零点改变结果。需明确可接受延迟和补发规则，不承诺长期无人值守能力。
- **规模验证：** 当前支持 B站、百度、小红书三个发布平台，但规模样本仍按四组取账号。已复现载入时报错，只生成 3 条发布样本，弹窗未关闭，未完成宣称的 200 条场景。先按当前平台集合修正样本与失败恢复，再验证 200 条安排的分页、选择、错误定位和连续处理；不能将此次加载当作容量验收通过。

### 修改顺序与仍需判断的事项

先修 N2（时间与默认值）、G2（提交后恢复）、P2（计划任务记录连续性）；随后统一状态动作，完善新建与草稿，再补进度、核验、结果纠错和规模走查。复用既有公共控件、选择器和步骤结构，避免同时重做作品或互动页面。

仍需业务判断的事项集中为：发布完成是否包含审核通过／可见；提交前部分不可用项能否明确排除后先发可用项；发布负责人和角色可操作范围；错过时间后的补发规则。推荐方案分别见 §5 及本节边界说明。上述未决项不影响先修已经复现的正确性问题。
