# ADR-0014：M3 内容池按业务团队隔离

- Status: Accepted（隔离主张不变；**第 5 条「不建设游戏关联」已于 2026-09-23 被用户决策取代**）
- Date: 2026-09-16（增补 2026-09-23）
- Scope: M3 内容池、挖掘策略、挖掘任务及 source_content/material
- 2026-09-23 增补：游戏维度改口为「做」，见下方第 5 条与「增补记录」。**权限模型不变**：内容仍是按业务团队隔离，游戏关联不构成新的隔离维度或授权边界。

## Decision

- 内容业务数据只按业务团队隔离，不按游戏隔离。
- 同一业务团队内运营成员可以查看该团队全部内容池、素材、策略和任务；管理员可以查看全部业务团队。
- `source_content.team_id` 必填；来源唯一键为 `team_id + platform + platform_content_id`。同一作品被不同团队发现时，各团队可以有独立来源与素材记录。
- 普通运营和高级运营在 M3 内容模块使用同团队范围；管理员跨团队创建、处理和审计必须记录目标团队。
- ~~M3 不建设游戏关联、跨团队共享关联表或团队内领取锁。~~ 未来若需要跨团队共享，另行提出 Product/Decision，不通过放宽查询实现。（2026-09-23 增补：**「不建设游戏关联」已被取代**——游戏关联纳入本期，见下条；「不建设跨团队共享关联表」与「不建设团队内领取锁」仍然有效。）
- **（2026-09-23 新增）游戏关联纳入本期**：`discovery_strategies` 与 `source_contents` 均带 `game_id`，
  迁移 `20260922_035/036` 已落地并把既有行回填为默认游戏 `other`；策略与内容池界面均有「游戏」列。
  游戏关联用于内容归属与筛选，**不改变**上面的团队隔离与授权判断。

## Consequences

- 列表、详情、入池、忽略、恢复、转素材全部复用团队授权判断。
- `material` 至少保存 `team_id` 与唯一 `source_content_id`；跨团队同作品不得互相泄露。
- 当前只有一个团队时界面看起来是全量，测试仍需覆盖第二团队和管理员，证明隔离真实存在。
- 不采用旧 M3 草案中的**游戏范围条件**（即“按游戏限制可见范围”）；V2-Q02 已关闭，其他 V2-Q03～Q06 仍按阶段处理。
  （2026-09-23 澄清：不采用的是“把游戏当作授权维度”，不是“记录游戏归属”——后者已纳入本期。）

## 增补记录

2026-09-23：原第 5 条主张「M3 不建设游戏关联」。实施结果与该主张相反——Cloud 已为
`discovery_strategies` 与 `source_contents` 落地 `game_id`（迁移 `20260922_035/036`），
界面亦以「游戏」列呈现且必填。用户同日裁定「修改为做游戏纬度」，故本条按实施与决策事实改写。
原「不建设跨团队共享关联表」「不建设团队内领取锁」不受影响，继续有效。
