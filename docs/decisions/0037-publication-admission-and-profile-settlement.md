# Decision 0037: 发布并发准入与实际 Profile 安全结算

## Status

Accepted — 2026-11-25。由已授权的 CHG108 实施；本决策不表示运行验收已完成。

## Context

批次按固定组并发后，原串行执行器无法同时承载自动操作、保留的人工现场和原稿核验。M6 的三槽同时限制自动操作与保留窗口；等待人工没有可信停手事实，核验领取也没有 Cloud 侧实际 Profile 占位。仅增加线程数会造成跨批、跨平台或发布与核验之间的资源争用。

新核验占位不因超时释放，必须能够处理领取响应丢失、会话更换和本机重启。旧版已领取但尚未开窗的核验也属于升级风险，代次与时间不能证明其已结束。

## Decision

- Cloud 维护批次位置、固定组、授权与资源准入，继续复用发布 task、attempt、observation、作品和现有 Scheduler。保存与首次启动的业务边界保持不变。
- 自动执行名额与保留窗口分开且均有界。原执行线程在提交前已知等待点登记原活现场并停止继续发起业务动作后，才可报告可靠挂起；Cloud 明确确认后仅释放自动名额。UID、Profile、窗口继续保留，原 attempt 恢复须重新准入。失联不推断停手或释放。
- 发布域持久记录以 BitBrowser 主账号与实际 Profile 标识环境，持有人仅为原发布 attempt 或原核验代次。发布与核验领取同事务争用，无 TTL、无通用任务或租约引擎。按父批次、实际 Profile、task、attempt 的共同顺序锁定并重验预读身份；纯数据库竞争的重试不得重放外部动作。
- Agent 先持久化核验原键，再持久化领取的原代与冻结输入，可能开窗前写屏障，可信关闭后保存结算包直到确认。活动重放只能在本机证明未跨可能开窗屏障时继续原读取；其余只核实原现场。已结算键只取原确认，不开启新代。
- 领取应答在本机保存前丢失时，允许原键的仅结算请求。尚无已提交领取时保存取消围栏，晚到原请求只能取终结确认；已有占位时只结算原持有人。不会返回新快照、派发工作或许可。原持有人的有效 ReportSafe 凭据，或当前同 owner 的 Strict 凭据，可处理这一安全恢复；其他 owner 不得跨范围结算。
- 正常观察和作品更新仍要求 Strict；ReportSafe 仅处理原结果与原占位安全收尾。现场证据矛盾时拒绝并保留占位。具体 DTO、枚举与反馈由 Cloud 提供方正式契约维护。
- 新并发领取和恢复要求 Cloud-Agent `2026.11.25.2`，不允许旧协议领取新工作；原尝试安全收尾保持兼容。这是有门槛的协调升级，不作为可混合部署的新工作兼容变更。
- 切换时先封新领取、停止旧执行器并核实在途核验退出和实际 Profile 安全关闭，保守承接旧活动 attempt。无法证明安全的环境继续阻断。回退前也须结算新协议占位，不直接恢复不认识该占位的旧执行器。

## Consequences

- 自动5、保留窗口10仅为可配置的受控验证初值，两端取有效较小值；少于配置N的可用独立Profile直接成较小组，不增加运营表单参数。
- 同一个旧现场可能持续占用环境，需按实际证据核实，不以可用性为由释放未知现场。
- 必须覆盖实际 MySQL 竞争、旧已领未开窗切换、满人工挂起后独立环境继续、应答丢失后换会话仅凭原键结算，以及后继持有人保护。
- 原型输入仍来自 Cloud `web/example/`；原型与受控测试不替代真实平台及安装版验收。
