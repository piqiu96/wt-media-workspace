### 0.1 文档层级

本项目需求文档分为两层：

1. **整体产品需求说明书**

跨文档出现差异时，按以下顺序处理：

1. 负责该业务对象的章节详细文档；
2. 第一章、第二章、第三章确定的全局定位、架构与角色体系；
3. 整体产品需求说明书；
4. 历史讨论稿和旧版本文档。

例如：

- 内容来源对象以第四章为准；
- 成片与生产对象以第五章为准；
- `publication` 的创建和成功口径以第六章为准；
- 互动任务模型以第七章为准；
- 统计口径以第八章为准，但不得改变业务章节定义的成功状态。

### 0.3 后续维护原则

后续需求调整应先修改对应章节详细文档，再同步更新本整体文档。不得只修改总文档而不更新详细章节，也不得让旧对象继续出现在新模块中。

# 第一章：项目概述

## 1.1 项目背景

随着游戏自媒体账号、运营平台和内容生产规模增加，依赖人工操作、零散工具和本地脚本的方式已经难以支撑长期运营。

当前主要问题包括：

- 账号、内容、素材、成片、发布、互动和统计数据分散；
- 系统用户、比特浏览器账号、Browser Profile、代理和社媒账号容易错配；
- 内容整理、素材下载、合成和发布存在大量重复操作；
- 本地生产与云端自动生产缺少统一管理；
- 发布和互动异常后难以判断实际结果；
- 批量任务缺少统一进度、失败原因和精确重试能力；
- 运营数据无法形成统一漏斗、积压和效果分析；
- 零散脚本缺少日志、可观测、升级、备份和持续维护能力。

因此，需要建设一套统一的模块化自媒体运营平台，将账号、内容、素材生产、成片、发布、互动和数据统计连接成可持续运营的闭环。

## 1.2 项目定位

本系统是一套面向游戏自媒体运营团队的内部运营管理与辅助执行平台。

系统由以下部分组成：

```text
云端管理系统
+
兼容Windows与macOS的本地运营端
+
本地 Agent
+
云端 Agent
+
比特浏览器及外部平台能力
```

项目采用“自动生产 + 辅助执行”的定位：

- 云端可持续执行内容监控、自动生产、效果采集、统计和清理；
- 本地 Agent 负责依赖比特浏览器、本地文件和本地登录环境的操作；
- 发布最终提交、验证码和外部结果无法确认等场景仍由运营参与。

本系统不是：

- 面向所有行业的通用社交媒体 SaaS；
- 自研指纹浏览器；
- 完全无人值守的自动发稿机器人；
- 通用低代码工作流平台；
- 任意脚本执行平台；
- 多个临时脚本的简单集合。

## 1.3 建设目标

系统建设目标包括：

1. 建立账号、内容、素材、成片、发布、互动和统计的完整业务闭环；
2. 支持本地人工生产与云端自动生产协同；
3. 保证用户、比特浏览器账号、Profile、代理和社媒账号关系正确；
4. 为内容发现、生产、发布和互动提供批量和定时能力；
5. 统一管理任务进度、结果、失败原因、重试和人工处理；
6. 建立正式业务数据、运行状态、日志和统计的追踪体系；
7. 保持产品简单易用，减少普通运营接触技术参数；
8. 支持客户端、Agent、平台适配和配置持续升级。

## 1.4 核心业务闭环

```text
用户与执行环境准备
→ 抖音内容发现
→ source_content
→ material
→ 本地或云端生产
→ composite_output
→ publication
→ tracked_object
→ 互动与平台效果采集
→ 数据统计
```

各模块职责：

- 用户与账号：提供正确的账号、Profile、代理和登录环境；
- 内容挖掘：人工与自动发现统一入池，经人工处理转为正式素材；
- 素材生产：将素材加工为可发布成片；
- 发布管理：完成 B站、百家号发布配置、辅助填写和结果回填；
- 互动管理：围绕 B站、百家号明确作品执行点赞、收藏和评论；
- 数据统计：汇总业务完成情况、流程转化、异常积压和作品效果。

## 1.5 用户角色

系统固定采用三个角色：

| 角色 | 定位 |
|---|---|
| 普通运营 | 完成日常内容、素材、生产、发布、互动和个人数据查看 |
| 高级运营 | 管理业务规则、公共资源、生产计划、异常处理和负责游戏范围数据 |
| 技术 | 同时承担高级运营和技术职责，拥有全局业务管理、系统配置、平台适配、Agent、运行状态、技术日志和故障处理权限 |

不建设自定义角色、组织架构、部门、团队层级和复杂 RBAC。

高级运营的管理范围通过负责游戏和授权业务范围控制，不通过“团队组织”对象实现。

技术因当前岗位职责同时覆盖高级运营和技术，可查看和处理全局业务数据、业务规则、素材状态、发布记录和互动任务。所有关键业务修改必须记录操作日志。技术权限不能绕过运营电脑、本地 Agent、比特浏览器 Profile、Cookie 和本地文件访问边界。

## 1.6 V2 建设范围

V2 覆盖：

- 用户、角色和游戏范围；
- 社媒账号、Browser Profile 和代理管理；
- 抖音链接查询、关键词搜索、关键词监控和作者监控，其中链接查询和关键词搜索已确认可由业务方提供接口；
- 本地生产、云端自动生产和云端成片池；
- B站、百家号本地辅助发布和手工补录；
- 点赞、收藏和评论；
- 运营工作、流程转化、账号环境和平台效果统计；
- 本地 Agent、云端 Agent、日志、状态和异常管理；
- Windows、macOS Intel和macOS Apple Silicon桌面端。

V2 明确不建设：

- B站、小红书、百度内容发现；
- Excel 作品链接导入；
- 关注、转发、私信和主动搜索作品互动；
- 完全无人值守自动发布；
- 云端可视化浏览器发布；
- 用户上传未知脚本；
- 通用工作流编排和插件市场；
- 微服务、Kitex、消息队列集群和复杂分布式调度；
- Linux桌面客户端；
- 桌面关闭后的无人值守本地 Agent；
- 本地完整业务数据库；
- 综合绩效评分、风险评分、爆款评分和自由拖拽 BI。

## 1.7 项目成功标准

V2 成功标准包括：

- 主要业务链路可以完整运行；
- 用户、账号、Profile 和代理关系不发生明显串乱；
- 本地 Agent 和云端 Agent 能完成各自任务；
- 批量任务支持部分成功和失败项处理；
- 高风险任务不会盲目重复执行；
- 关键任务具备状态、进度、日志和明确异常处理；
- 普通运营能够独立完成主要日常操作；
- 系统具备持续升级、备份、排障和长期运行能力。

在缺少真实运行基线前，不在整体需求中承诺固定人力降幅、日产量、并发账号数和发布成功率。

# 第二章：系统架构

## 2.1 架构原则

系统采用：

```text
Go + Hertz 模块化单体云端
+
Python 统一 Agent 执行框架
+
Tauri 2 + Vue 3/Vite 兼容Windows与macOS的本地运营端
```

核心原则：

- 简单优先，不提前微服务化；
- 业务控制与实际执行分离；
- 云端保存正式业务数据；
- 本地与云端任务按任务类型固定执行位置；
- 不建设 `execution_scope` 表和动态路由平台；
- 外部平台差异集中在适配层；
- 长任务由 Agent 执行，不长期占用普通 HTTP 请求；
- 失败可见、结果可追踪、异常可恢复。

## 2.2 技术选型

| 层级 | 技术选型 |
|---|---|
| 云端业务服务 | Go + CloudWeGo Hertz |
| 云端架构 | 模块化单体 |
| 前端 | Vue 3 + Vite |
| 桌面外壳 | Tauri 2 |
| 桌面支持范围 | Windows、macOS Intel（x86_64）、macOS Apple Silicon（arm64） |
| 本地 Agent | Python |
| 云端 Agent | Python |
| Agent 打包 | 按操作系统和CPU架构分别构建的PyInstaller Sidecar |
| 云端数据库 | MySQL |
| 本地运行数据库 | SQLite |
| 云端文件 | 对象存储 |
| 本地文件 | 本地文件系统 |
| Agent 通信 | HTTPS JSON API |
| 本地通信 | `127.0.0.1` 本地 API |

首版不使用 Kitex、Kafka、RabbitMQ 和独立分布式调度平台。

## 2.3 总体组成

```text
云端 Linux
├── Vue 运营后台
├── Go + Hertz 业务服务
├── 定时调度
├── Python 云端 Agent
├── MySQL
└── 对象存储

运营电脑（Windows / macOS Intel / macOS Apple Silicon）
├── Tauri 桌面客户端
├── 内置 Vue 页面
├── Python 本地 Agent
├── SQLite
├── 比特浏览器
├── Python / FFmpeg
└── 本地素材与成片目录
```

云端 Linux 首版不建设桌面环境，不执行依赖比特浏览器和可视化浏览器的发布、互动及账号操作。

桌面客户端、本地Agent、FFmpeg及原生依赖需要按Windows、macOS Intel和macOS Apple Silicon分别构建和发布。客户端应识别操作系统及CPU架构，并获取对应升级包。不同系统上的比特浏览器和平台自动化能力必须分别进行兼容验证。

## 2.4 职责边界

### 云端 Go 服务

负责：

- 用户、角色、权限和正式业务数据；
- 业务状态和规则校验；
- 任务创建、领取控制和结果回写；
- 定时规则扫描；
- 配置、统计、日志和可观测；
- Agent 注册、心跳和版本管理。

### Python Agent

负责：

- 任务领取和执行；
- 比特浏览器、本地文件、FFmpeg 和 Python 工具调用；
- 云端自动生产、抓取、文件处理和数据采集；
- 进度、心跳、日志和结果回传。

Agent 不得直接修改云端 MySQL。

### Tauri 桌面客户端

负责：

- 承载运营页面；
- 启动、停止和升级本地 Agent；
- 检测本地依赖；
- 文件和目录选择；
- 桌面通知和本地诊断。

Tauri 不承担核心业务逻辑，不直接读写 SQLite。

## 2.5 任务协同

任务协同流程：

```text
用户操作或定时规则
→ Go 校验并创建正式任务
→ 本地 Agent 或云端 Agent 领取
→ 执行前二次校验
→ 分阶段执行并上报
→ Go 校验结果
→ 更新正式业务对象
```

执行位置由任务类型固定：

### 本地 Agent

- Profile 同步、创建和修改；
- 代理和 Cookie 操作；
- 账号检查；
- 本地合成；
- 发布；
- 点赞、收藏和评论。

### 云端 Agent

- 云端自动生产；
- 云端合成和文件处理；
- 抖音定时监控；
- 平台效果数据采集；
- 日级统计；
- 过期文件及数据清理。

本地 Agent 离线时，本地任务等待，不自动转移到云端。

## 2.6 本地运行与存储

本地 Agent 作为 Tauri Sidecar 运行，仅监听 `127.0.0.1`。

SQLite 只保存：

- 本地任务执行快照；
- 待回传结果；
- 本地文件索引；
- 下载缓存；
- 同步游标；
- 最近环境检测结果。

正式业务数据仍以云端 MySQL 为准，SQLite 不作为离线业务数据库。

本地成片默认只保存在本地；云端自动生产文件保存在对象存储。文件上传下载必须校验大小和 Hash。

## 2.7 可观测与安全

系统应提供：

- 云端服务和云端 Agent 状态；
- 本地 Agent、比特浏览器、Python、FFmpeg、SQLite 和磁盘状态；
- 定时任务最近结果；
- 任务积压、失败和中断情况；
- 外部依赖最近状态；
- 关键操作、任务和配置日志；
- Agent 和配置版本兼容检查。

日志不得记录完整 Cookie、密码、代理密码、Token 和 API Key。

# 第三章：用户与账号管理

## 3.1 模块定位

用户与账号管理负责：

- 系统用户、角色和游戏范围；
- 社媒账号；
- 比特浏览器账号绑定；
- Browser Profile；
- 代理资源；
- Cookie 和登录状态；
- 批量上号、账号检查和本地环境校验。

系统是比特浏览器的运营编排和数据管理层，不替代比特浏览器内核及实际浏览器环境。

## 3.2 用户与登录

系统固定三个角色：

- 普通运营；
- 高级运营；
- 技术。

普通运营和高级运营按负责游戏控制业务数据范围，技术查看全部云端数据。

首版使用用户名和密码登录。同一系统用户只允许一个有效会话，新登录立即使旧会话失效。

系统不建设：

- 部门、团队和组织架构；
- 自定义角色；
- 账号负责人及交接流程；
- 手机号登录、第三方登录和 MFA。

## 3.3 系统用户与比特浏览器账号

关系固定为：

```text
一个系统用户
→ 最多绑定一棵比特浏览器主账号树（main_user_id）
→ 管理 Cloud 分配给该用户的多个 browser_profile
```

同一个 `main_user_id` 可以绑定多个系统用户，以支持一个主账号下多个子账号分别对应多个运营。每个系统用户只看见 Cloud 分配给自己的 `browser_profile`；主账号树相同不自动产生跨用户访问权限。

同一自然人有多个不同的比特浏览器主账号树时，应创建多个系统用户分别使用。

比特浏览器 API 返回的 `mainUserId` 归一化为 `main_user_id`，用于校验比特侧主账号身份；`userId` 归一化为 `profile_user_id`，用于记录 Profile/子账号归属。二者都不表示业务负责人。

所有比特浏览器相关操作前必须校验当前 `main_user_id`。不一致或无法确认时：

- 阻止同步、创建和修改 Profile；
- 阻止代理和 Cookie 操作；
- 阻止账号检查、发布和互动；
- 不写入任何正式变更；
- 不自动改绑到新比特账号。

## 3.4 社媒账号 `media_account`

`media_account` 直接归属于当前系统用户：

```text
media_account.user_id
```

不设置负责人、交接人和临时账号类型。

一个社媒账号可关联零个或多个游戏，并可以绑定一个 `browser_profile`，也可以暂时不绑定。账号进入可执行状态、上号完成、发布或互动预检前必须至少关联一个游戏；已启用游戏在媒体账号域对已登录用户默认可选择、关联和筛选：

- 已绑定 Profile：可执行检查、发布和互动；
- 未绑定 Profile：可用于发布补录和数据记录。

一个 Profile 可绑定不同平台的多个账号，同一平台最多绑定一个账号。

账号仅在当前用户范围内去重：

```text
user_id + platform + platform_account_id
```

账号标签使用 `media_account_tag`。发布和互动页面中的“账号组”不是独立核心对象，而是按用户权限、游戏、平台、账号状态和标签条件保存的一次筛选快照；任务创建后必须保存实际账号 ID 列表，后续标签变化不改写历史任务范围。

## 3.5 Cookie 与账号识别

账号初始接入支持：

- 批量 Cookie 导入；
- 接码链接；
- 人工验证码上号。

账号名称、平台账号 ID 和头像在登录检查后回填。

Cookie 采用简单双字段：

```text
original_cookie
active_cookie
```

Cookie 是否存在不能代表账号登录正常，登录状态必须以实际账号检查结果为准。

## 3.6 Browser Profile 管理

统一对象名称：

```text
browser_profile
```

同步采用：

```text
扫描
→ 生成 Diff
→ 人工集中确认
→ 正式应用
```

扫描阶段不直接修改正式数据。

Diff 主要处理：

- 新增 Profile；
- 名称和分组变化；
- 代理变化；
- 疑似本地删除；
- 已绑定账号环境变化。

处理方式只保留：

- 接受本地变化；
- 恢复系统配置。

云端不提供远程删除本地比特 Profile 的能力。

## 3.7 代理管理

代理对象统一为：

```text
proxy_resource
```

支持 Excel、CSV、TXT 和多行文本导入代理资源。这里的 Excel 仅用于代理文档导入，不代表内容发现支持 Excel 链接导入。

代理支持：

- 格式解析和预览；
- 连通性检测；
- 到期时间和供应商；
- 按平台配置 Profile 配额；
- 批量创建 Profile 时自动分配；
- 写入比特浏览器后读回验证。

一个代理可以绑定多个 Profile，配额按目标平台已分配 Profile 数量计算。

## 3.8 批量上号和检查

三种上号方式独立处理：

1. 批量 Cookie；
2. 接码链接；
3. 人工验证码。

批量创建 Profile、代理分配、Cookie 写入和账号检查按单条独立执行：

- 已成功项不回滚；
- 失败项保留原因；
- 支持单独重试；
- 代理容量不足时执行前提示。

账号检查至少识别：

- 正常；
- 未登录；
- 账号不匹配；
- 待验证；
- Profile 失效；
- 代理异常；
- 账号受限；
- 检查失败。

## 4.1 模块定位

建设外部内容进入系统的统一自动化入口，包含内容池、挖掘策略、挖掘任务三个页面。

流程：分享链接 / 关键词搜索 / 博主搜索 / 自动挖掘 → source_content 内容池 → 人工筛选与转素材 → material → 后续内容生产。

## 4.2 内容池

- 单/批量分享链接提交“解析并入池”，成功即创建或更新 source_content。
- 关键词和博主主动搜索展示临时结果，选择后才加入内容池。
- 主动入口不创建自动挖掘业务 crawl_task，也不自动创建 material。
- 内容池支持列表、详情、检索、批量处理、转素材、忽略与恢复。
- 状态为 pending / material_created / ignored，外部可访问性独立。

## 4.3 挖掘策略

统一 discovery_strategy，strategy_type 当前 keyword / author；引用 content_channel 的 channel_type。当前仅实现抖音，未来渠道预留能力抽象而不预建插件市场或工作流引擎。

策略只定义业务规则及关联的周期配置，不自行执行。页面支持名称、渠道、关键词列表/博主身份、执行周期、启停与执行记录；不提供自动转素材选项或可视化调度器。

## 4.4 挖掘任务

脚本/后台调度触发，Cloud 校验并创建 crawl_task，Cloud Agent 执行，Cloud 持有业务事实。

业务四态 pending / running / success / failed；记录快照、渠道、类型、开始/结束、扫描/发现/新增/重复/失败数量、错误和日志。部分失败映射、计数单位及首次触发等细节按 V2 待决明确，不增加第五状态或假成功。

同策略同周期防重、同策略不重复并行排队、重启恢复不能重复入池。工作流只是基于真实记录的只读业务流转视图（2026-09-23 注：独立的只读业务流转视图本期不交付，Cloud 全仓无相关实现，本条交付要求按本章分歧清单第 5 条处理，移出本期、后续版本再评估；ADR-0013 第 8 条「不允许编排/拖拽/条件分支/任意脚本」的禁止性约束保持不变）。

## 4.5 来源与素材

source_content 按 platform + platform_content_id 唯一；material.source_content_id 唯一，source_content 不反向保存 material_id。

人工转换逐条事务提交，并发只建一个素材；失败保留正确状态，批量部分失败不回滚其他成功项。素材保存不可变来源快照，来源重复更新不得覆盖人工处理和素材业务字段。忽略内容不被自动发现恢复。

内容共享、游戏关系及跨范围忽略语义仍需明确，不能以本次范围调整覆盖既有权限架构。

## 4.6 范围与验收

M3 不含视频下载、文件存储/校验、剪辑、AI 评分、自动生产、发布、互动和数据分析。元数据已创建不等于文件可生产。

三个人工入口和两种自动策略都须用真实接口验证入池；入池后无素材、人工转素材后可追踪。仅配置保存、任务列表或模拟数据不能通过完整 M3 验收。

# 第五章：素材生产

## 5.1 模块定位

素材生产负责将正式 `material` 转化为可发布的 `composite_output`，承接内容发现并向发布管理提供成片。

系统支持：

- 本地人工生产；
- 云端自动生产。

两种生产方式最终统一进入同一成片资产体系。

## 5.2 核心流程

### 本地人工生产

```text
material
→ material_usage
→ compose_pool_item
→ task
→ composite_output
```

### 云端自动生产

```text
material
→ production_rule
→ compose_pool_item
→ task
→ composite_output
→ composite_output_pool
→ composite_output_claim
→ 下载到本地
```

云端自动生产不创建 `material_usage`。

## 5.3 素材库 `material`

`material` 是正式生产输入，来源包括：

- 第四章 `source_content` 转换；
- 运营创建的私有素材；
- 私有素材经高级运营确认后转为公共素材。

素材生命周期：

```text
active
paused
retired
```

- `active`：允许领取和生产；
- `paused`：停止新领取和自动生产，默认不影响已存在生产链路；
- `retired`：停止新增使用，保留历史任务、成片和发布记录。

如需停止已领取素材继续生产，应单独对 `material_usage`、`compose_pool_item` 或执行任务中断，而不是依赖素材状态静默中断。

## 5.4 我的素材 `material_usage`

`material_usage` 表示某个运营领取并使用某个素材的关系，仅用于本地人工生产。

同一用户对同一 `material` 默认只有一个有效关系。

支持：

- 领取；
- 下载；
- 合成前自动补下载；
- 放弃和恢复；
- 文件缺失重新下载或定位；
- 高级运营对异常使用关系强制中断。

## 5.5 合成策略

合成策略体系：

```text
composite_strategy_template
→ composite_strategy
→ composite_strategy_snapshot
```

- 技术维护模板及底层能力；
- 高级运营维护业务策略和默认策略；
- 普通运营选择可用策略并调整当前任务参数；
- 每次生产保存实际策略快照、模板版本、参数和随机信息。

支持同一素材使用多个策略生成多个版本。

`production_rule` 通过 JSON 策略选择配置使用策略，不单独建设 `strategy_group`。

## 5.6 合成任务台与执行任务

`compose_pool_item` 表示一次生产意图：

```text
使用哪个素材
+
采用什么策略
+
希望生成什么成片
```

`task` 表示一次实际执行尝试。

关系：

```text
compose_pool_item
→ 一个或多个 task
→ 成功后创建 composite_output
```

失败处理：

- 临时技术失败：复用原生产意图和策略快照，新建执行任务；
- 策略或参数变化：新建 `compose_pool_item`；
- 多版本和复刻：新建 `compose_pool_item` 和新的成片。

失败、取消、文件损坏和结果校验失败不创建成片。

## 5.7 自动生产规则 `production_rule`

`production_rule` 由高级运营创建，负责：

- 生产范围；
- 执行周期；
- 素材筛选；
- 单次和每日生产数量；
- 策略选择 JSON；
- 目标成片池；
- 重复生产风险控制。

自动生产由云端定时调度触发，由云端 Agent 执行。

高风险素材只阻止该素材继续自动生产，不阻塞整条规则。

## 5.8 成片与云端成片池

`composite_output` 是唯一成片资产。

核心原则：

> 一个成片，一个资产，可以同时存在云端文件和本地文件。

本地生产的完整文件默认保存在本地；云端自动生产文件保存在对象存储。

`composite_output_pool` 用于分发云端成片和控制可见范围，不是文件存储对象。

`composite_output_claim` 表示运营领取某个成片的使用关系：

- 同一成片同一时间只能存在一个有效领取；
- 领取后允许下载并进入发布流程；
- 领取不等于发布；
- 未领取云端成片默认按 7 天规则清理；
- 本地文件删除不删除 `composite_output` 正式记录。

池的可见和领取范围使用 `policy` JSON 控制，不建设复杂策略表。

## 5.9 重复风险

发布前至少检查：

1. 同一 `composite_output` 是否已发布；
2. 相同文件 Hash 是否已发布；
3. 同一 `material` 在目标平台、目标账号和时间窗口内是否重复使用。

重复风险以提示和必要控制为主，不直接删除历史对象。

# 第六章：发布管理

## 6.1 模块定位与核心对象

发布管理负责将 `composite_output` 组织成面向平台和账号的一次发布单，并辅助运营完成发布及结果回填。

核心关系：

```text
composite_output
→ publication
→ tracked_object
```

其中：

- `composite_output`：成片资产；
- `publication`：发布单和发布过程记录；
- `tracked_object`：已发布作品的数据跟踪和互动目标对象。

不再建设“发布包”独立对象。待发布内容统一通过 `publication` 的过程状态承载。

## 6.2 发布方式

P0 只保留：

| 方式 | 说明 |
|---|---|
| 本地辅助发布 | Agent 打开 Profile、上传视频并填写发布元素，运营人工检查和最终提交 |
| 手工补录 | 运营在手机、平台后台或其他工具完成发布后回系统补录 |

不细分手机发布、外部发布和其他工具发布，统一归为手工补录。

## 6.3 `publication` 创建和状态

`publication` 在运营完成发布配置并点击保存或保存并去发布时创建，不在成片生成或下载时创建。

手工补录在校验通过后直接创建已发布记录。

主要状态：

```text
draft
ready
publishing
pending_manual_submit
pending_backfill
published
failed
cancelled
```

运营侧展示：

- 待发布；
- 发布中；
- 等你确认；
- 待补链接；
- 已发布；
- 发布未完成；
- 已取消。

只有同时具备明确平台、账号、发布时间、发布链接和关联成片，并进入 `published`，才算真实发布成功。

`pending_backfill` 不计为已发布成功，应单独展示和处理。

## 6.4 发布账号规则

本地辅助发布要求：

```text
media_account 已绑定 browser_profile
```

手工补录只要求系统中存在 `media_account`，可以使用未绑定 Profile 的账号。

补录时账号不存在，可以新增待验证的未绑定账号。

## 6.5 本地辅助发布

流程：

```text
保存发布配置
→ publication = ready
→ 运营开始发布
→ 创建执行 task
→ Agent 打开 Browser Profile
→ 上传视频并填写发布元素
→ publication = pending_manual_submit
→ 运营检查和人工提交
→ 系统获取或运营补充发布链接
→ publication = published
```

P0 中 Agent 不自动点击最终发布按钮。

Agent 或桌面异常退出时，系统不得直接猜测成功或失败；应结合当前阶段进入失败、待确认或待补链接状态。

## 6.6 批量配置与连续发布

支持批量选择成片并批量配置：

- 平台；
- 账号或账号筛选条件；
- 标题；
- 简介；
- 标签；
- 封面；
- 分区或分类。

批量配置后生成多条独立 `publication`，允许运营逐条微调。

连续发布采用串行方式：

- 一次只处理一条 publication；
- 当前条进入人工确认；
- 运营完成、稍后再发或取消后，才进入下一条；
- 不同时打开大量窗口；
- 不等同于无人值守批量发布。

## 6.7 平台发布元素和配置

B站和百家号分别维护独立平台适配流程。

发布流程由代码固定，易变化内容通过一份 JSON 配置维护：

```text
platform_publish_config
```

原 `platform_element_config` 与 `platform_publish_config` 合并，不再拆分。

配置可包含：

- 页面地址；
- selector 和备用定位；
- 等待条件；
- 超时；
- 平台字段限制；
- Agent 和适配器版本要求；
- 启用状态。

## 6.8 手工补录

手工补录必须关联：

- `composite_output`；
- 平台；
- `media_account`；
- 发布时间；
- 发布链接。

补录成功后：

```text
publication = published
→ 创建或关联 tracked_object
→ 更新成片、领取和素材相关发布状态
```

P0 不建设批量手工补录。

## 6.9 发布异常和结果

发布前校验：

- 当前比特账号身份；
- Profile 是否存在；
- 账号登录状态；
- 代理状态；
- 本地成片文件；
- 发布元素完整性；
- 平台配置版本。

失败和取消必须区分：

- `failed`：系统辅助执行未完成；
- `cancelled`：运营主动取消本次发布单。

错误已发布记录不物理删除，可由有权限人员作废或标记异常，并保留操作记录。

发布成功且链接有效后才创建或关联 `tracked_object`。

系统不建设 `publication_attempt`，重试通过 `publication` 的重试信息和实际执行 `task` 追踪。

# 第七章：互动管理

## 7.1 模块定位与范围

互动管理围绕明确的作品目标，组织系统内社媒账号执行：

- 点赞；
- 收藏；
- 评论。

明确不建设：

- 关注；
- 转发；
- 私信；
- 主动搜索作品互动；
- 评论回复和评论点赞；
- 自动养号；
- 无人监管循环互动。

互动目标只来自：

- 我方已发布作品；
- 运营手工录入的明确外部作品链接。

## 7.2 核心对象

核心关系：

```text
tracked_object
→ interaction_task
→ task
```

- `tracked_object`：一个明确的作品目标；
- `interaction_task`：针对一个作品、使用一批账号执行一组动作的业务任务；
- `task`：某个媒体账号对该作品的一次实际执行。

一个 `interaction_task` 只关联一个 `tracked_object`。批量选择多个作品时，分别创建多条 `interaction_task`。

整体文档不设置 `interaction_item`，也不将批量选择强制抽象为独立核心业务对象。

## 7.3 互动目标

外部作品录入流程：

```text
粘贴明确作品链接
→ 识别平台
→ 解析作品 ID
→ 标准化链接
→ 按平台 + 作品 ID 去重
→ 创建或复用 tracked_object
```

目标状态：

- 可用；
- 不可用；
- 已停用。

已产生互动任务或数据记录的目标不能物理删除，只能停用。

## 7.4 评论模板与内容

评论模板分为：

- 个人模板：创建人使用；
- 公共模板：在授权业务范围内共享。

一个模板可维护多条完整评论，支持：

- 逐条录入；
- 按换行批量粘贴；
- 随机、顺序或手工分配；
- 重复评论风险提示。

DeepSeek 仅用于生成候选评论：

```text
作品信息和运营要求
→ 生成候选评论
→ 运营删除、修改和确认
→ 保存为模板或用于当前任务
```

Agent 执行阶段不调用 DeepSeek，只使用已确认的评论快照。模型和 API 配置由服务端维护，不建设运营配置页面。

## 7.5 互动任务与执行

创建流程：

```text
选择目标
→ 选择点赞、收藏、评论
→ 按平台和账号分类筛选有权限账号
→ 配置评论内容
→ 系统预检查
→ 保存待执行或立即执行
```

开始执行时，为每个账号创建一个实际 `task`。一个账号级 task 可以完成该账号对同一作品的一组动作。

执行要求：

- 同一 Browser Profile 同时只能执行一个敏感任务；
- 执行前校验实际登录账号；
- 点赞和收藏先判断当前状态，禁止盲目点击；
- 已经完成的动作不重复点击；
- 评论提交后区分成功、失败和待确认；
- 单个账号失败不影响其他账号；
- 作品失效时停止该互动任务剩余执行。

## 7.6 基础风控

系统只建设一份简单的全局基础风控配置，包括：

- 单账号互动最小间隔；
- 每日点赞、收藏和评论上限；
- 评论最小间隔；
- 连续失败暂停阈值；
- 重复评论提醒比例；
- 临时技术异常自动重试次数。

普通运营不能关闭或绕过风控。

不建设平台级、账号级、账号分类级复杂规则覆盖和智能风控模型。

## 7.7 状态、结果和重试

`interaction_task` 应能够展示：

- 待执行；
- 执行中；
- 已完成；
- 部分完成；
- 执行失败；
- 已暂停或待处理；
- 已取消。

动作结果区分：

- 本次成功；
- 执行前已完成；
- 失败；
- 待确认；
- 跳过；
- 未执行。

重试只执行失败动作。评论待确认时不得自动重复提交。

运营不能直接把失败或未知结果修改为成功，只能重新检查、处理异常或补充备注。

# 第八章：数据统计

## 8.1 模块定位

数据统计用于汇总内容发现、素材生产、发布、互动、账号和运行环境数据。

首版以内部运营管理为主、平台作品效果为辅，重点回答：

- 当前哪里存在积压和异常；
- 各游戏、平台、账号和用户完成了多少业务结果；
- 内容到发布的流程转化是否正常；
- 发布和互动执行是否稳定；
- 账号、Profile 和代理是否可用；
- 云端自动生产是否真正形成可领取、可发布的成片；
- 作品播放量和点赞量是否增长。

统计模块只查询、汇总、展示和导出，不允许用户直接修改汇总数字。

## 8.2 数据来源和基础口径

统计以正式业务记录为事实来源：

```text
crawl_task、source_content
material、material_usage、compose_pool_item、task
production_rule、composite_output
composite_output_pool、composite_output_claim
publication
tracked_object、interaction_task、实际执行 task
user、media_account、browser_profile、proxy_resource
platform_metric_snapshot
```

不使用已删除对象：

- `crawl_result`；
- `interaction_item`；
- `publication_attempt`；
- `production_signal`。

任务数量和执行尝试次数分开统计。重试只增加执行次数，不增加业务任务数量。

历史统计按业务发生时保存的用户、游戏、平台和账号快照计算，不随后续主数据变化改写。

## 8.3 时间和效果指标

快捷时间范围：

- 今日；
- 昨日；
- 近 3 日；
- 近 7 日；
- 自定义时间。

平台效果首版核心指标：

- 累计播放量；
- 累计点赞量；
- 时间段播放增量；
- 时间段点赞增量；
- 点赞率。

评论量和收藏量在平台能够稳定获取时作为辅助指标。

不统计：

- 转发量；
- 粉丝变化；
- 粉丝增长归因；
- 收益预测。

平台效果采用日级快照：

- 发布后前 7 日每日自动采集一次；
- 超过 7 日后停止自动采集，按需手动更新；
- 同一作品同一天保留最后一次有效结果；
- 累计值异常下降时标记异常，不直接覆盖。

## 8.4 运营工作和流程统计

统计范围包括：

- 内容发现和待选处理；
- 素材创建、领取和使用；
- 合成任务、失败和重试；
- 本地及云端成片产出；
- 云端成片领取和发布使用；
- 发布创建、成功、失败、取消和补录；
- 点赞、收藏和评论动作；
- Cookie、接码、账号检查、Profile 和代理维护。

云端自动生产计入系统产出和对应游戏产量，不计入任何用户的人工工作量。

批量操作按实际处理对象数统计，不以点击次数或批次数作为核心工作量。

## 8.5 内容生产漏斗与积压

生产发布漏斗：

```text
source_content
→ material
→ material_usage
→ composite_output
→ publication
→ published
```

每层展示数量、上一层转化率和积压量。

重点积压包括：

- 待处理 `source_content`；
- 长时间未使用素材；
- 待执行及失败合成任务；
- 未发布成片；
- 云端已领取未发布成片；
- 待补链接 publication；
- 发布和互动失败；
- 待确认 Diff；
- 账号、Profile 和代理异常。

## 8.6 发布统计

发布统计统一以 `publication` 为业务对象。

统计：

- 创建发布单数；
- 发布成功数；
- 发布失败数；
- 已取消数；
- 待补链接数；
- 人工补录数；
- 重试次数；
- 发布成功率；
- 从成片到发布的转化率。

`pending_backfill` 单独统计，不计入 `published` 成功数量。

一次批量发布按实际生成的 `publication` 条数统计。

## 8.7 互动统计

互动统计以：

```text
tracked_object
interaction_task
实际执行 task 和动作结果
```

为基础。

统计：

- 互动任务数；
- 完成、部分完成、失败和取消任务数；
- 点赞、收藏和评论计划、成功、失败次数；
- 执行前已完成状态命中次数；
- 涉及的去重作品和账号数；
- 评论来源；
- 重试和失败原因。

批量选择是操作方式，不作为核心工作量对象。

## 8.8 账号与环境统计

统计：

- 社媒账号规模和平台分布；
- 待识别、已识别、绑定和未绑定 Profile 账号；
- 最近实际检查的登录状态；
- Cookie 和接码维护情况；
- Browser Profile 数量、失效、代理和待确认 Diff；
- 比特浏览器账号最近身份校验结果；
- 代理可用、到期、停用和平台配额；
- 账号及运行环境异常总览。

Profile 和代理超过 24 小时未同步或检查时，只标记“数据可能已过期”，不自动判定异常。

## 8.9 看板、下钻和导出

系统采用统一统计首页，根据角色和游戏范围控制数据，不为三种角色建设三套独立看板。

首页重点展示结果、积压和异常；模块页展示转化和原因；明细页用于审计和核对。

所有核心卡片支持：

```text
统计汇总
→ 业务明细
→ 原业务记录
```

最多保持两层下钻。

Excel 只导出当前筛选结果，导出权限与查看权限一致，不得导出 Cookie、代理密码和敏感比特身份信息。

## 8.10 明确不建设

首版不建设：

- 自由拖拽 BI；
- 自定义统计公式；
- 综合绩效评分；
- 账号综合风险评分；
- 内容爆款评分；
- AI 经营分析；
- 跨模块自由拼接报表；
- 独立数据仓库；
- 直接修改统计汇总数字。

首版采用业务表直接查询和简单日级汇总表，正式业务表始终是事实来源。
