# 第三章：用户与账号管理

## 3.1 模块概述与范围

用户与账号管理模块用于管理系统登录用户、社媒账号、比特浏览器环境及代理资源，为后续内容发布、互动执行和账号检查提供基础运行环境。

本章负责：

- 系统用户、角色及游戏范围管理；
- 社媒账号的创建、识别、状态维护和查询；
- 比特浏览器账号与系统用户的一对一绑定；
- Browser Profile 的同步、批量创建、绑定及状态检查；
- 代理资源的批量导入、检测、配额管理和 Profile 分配；
- CK 导入、真实 CK 回写及登录状态检查；
- 本地比特浏览器数据与系统数据之间的 Diff 确认；
- 用户、账号、Profile 和代理相关的异常提示与验收要求。

本章不建设：

- 部门、团队、组织架构；
- 账号负责人及账号交接流程；
- Browser Profile 负责人；
- 自研浏览器内核、指纹浏览器或完整浏览器管理系统；
- CK 历史版本、快照表或复杂凭证资产管理；
- 代理采购、续费和供应商结算系统；
- 比特浏览器本地 Profile 的云端远程删除。

系统定位为比特浏览器的运营编排和数据管理层。实际浏览器环境、Cookie、代理和 Profile 仍由比特浏览器本地客户端承载，本系统通过本地接口完成必要的读取、创建、修改和检查。

## 3.2 用户管理

### 3.2.1 用户角色

系统固定设置三个角色：

| 角色 | 说明 |
|---|---|
| 普通运营 | 负责日常账号、素材、发布和互动操作 |
| 高级运营 | 负责更大范围的运营管理和业务配置 |
| 技术 | 同时承担高级运营和技术职责，拥有系统全部权限、全局业务权限和全局数据权限 |

不建设自定义角色和复杂权限编排。

### 3.2.2 游戏范围

普通运营和高级运营按负责游戏控制业务数据范围。

- 一个用户可以负责多个游戏；
- 一个游戏可以分配给多个用户；
- 高级运营仍受负责游戏范围限制；
- 技术不受游戏范围限制。

游戏范围用于账号、素材、发布、互动和数据统计等业务数据筛选，不单独建设平台范围权限。

技术可基于当前职责处理全局业务规则、业务数据、素材状态、发布记录和互动任务。所有关键业务修改必须记录操作日志，且不能绕过运营电脑、本地 Agent、比特浏览器 Profile、Cookie 和本地文件访问边界。

### 3.2.3 用户登录

首版采用用户名和密码登录。

- 用户由技术创建；
- 技术可重置用户密码；
- 用户可修改自己的密码；
- 不建设手机号登录、第三方登录、单点登录和多因素认证。

### 3.2.4 单会话限制

一个系统用户同时只允许一个有效登录会话。

当同一用户在新的设备或浏览器重新登录后：

1. 新登录会话立即生效；
2. 原登录会话立即失效；
3. 原设备后续请求被拒绝并跳转到登录页；
4. 原设备不得继续同步 Profile、写入 CK、执行账号检查、发布或互动任务。

同一浏览器的多个标签页可以共享同一登录会话，不互相踢出。

该机制同时用于避免同一系统用户在多台电脑上同时操作不同的比特浏览器本地环境。

### 3.2.5 用户状态

用户状态保持简单：

- `enabled`：正常使用；
- `disabled`：禁止登录。

用户停用后：

- 不删除用户；
- 不删除其社媒账号；
- 不删除 Browser Profile 镜像；
- 不删除代理关系；
- 不删除历史发布、互动和统计数据。

不建设账号交接流程。后续需要调整数据时，由技术直接处理相关记录并记录操作日志。

### 3.2.6 用户操作记录

系统记录以下关键操作：

- 创建和修改用户；
- 修改角色；
- 修改游戏范围；
- 启用、停用用户；
- 重置密码；
- 重新绑定比特浏览器账号。

日志只记录操作结果和必要摘要，不记录密码、CK、代理密码等敏感原文。

## 3.3 社媒账号管理

### 3.3.1 核心对象

社媒账号统一使用 `media_account` 管理。

社媒账号直接归属于当前系统用户：

```text
media_account.user_id
```

系统不设置媒体账号业务负责人字段：

- 账号负责人；
- 账号交接人；
- 修改负责人流程。

当前登录用户创建、导入、上号和操作自己的社媒账号。技术因拥有全局业务与技术权限，可查看和管理全部用户数据。

### 3.3.2 账号与游戏

一个社媒账号首版只归属一个游戏。

该规则用于统一内容、素材、发布、互动和统计数据范围，避免一个账号同时归属多个游戏造成数据混乱。

### 3.3.3 账号与 Browser Profile

`media_account` 可以绑定一个 `browser_profile`，也可以暂时不绑定。

```text
media_account.browser_profile_id
```

规则如下：

- 绑定 Profile：可执行账号检查、发布和互动；
- 未绑定 Profile：可用于发布补录和数据记录；
- 后续完成 Profile 绑定后，自然具备执行条件；
- 不单独设置“执行账号”和“记录账号”类型字段。

一个 Browser Profile 可以同时绑定不同平台的多个社媒账号，例如同时绑定一个 B 站账号和一个百家号账号。

同一个 Browser Profile 在同一平台下最多绑定一个账号。

### 3.3.4 账号创建与识别

批量导入账号时，初始通常只有以下一种内容：

- 原始 CK；
- 接码链接。

账号名称、平台账号 ID、头像等信息在登录成功后再由系统检查并回填。

导入后立即创建一条待识别 `media_account`：

```text
status = pending_identification
```

登录并检查成功后回填：

- 平台账号 ID；
- 账号名称；
- 头像；
- 登录状态；
- 最近检查时间。

### 3.3.5 账号去重

社媒账号只在当前系统用户范围内去重，不做全系统唯一。

唯一校验维度：

```text
user_id + platform + platform_account_id
```

同一个真实平台账号可以分别存在于不同系统用户的数据中。

待识别账号在平台账号 ID 回填后，再按当前用户范围执行重复校验。发现重复时：

- 不创建第二条正式账号；
- 不覆盖原账号 CK；
- 不覆盖原账号 Profile；
- 将本次记录标记为重复；
- 提示用户查看当前用户下已存在的账号。

### 3.3.6 账号标签

账号标签由普通运营在自己的运营端创建和使用。

使用一张简单关系表：

```text
media_account_tag
```

建议结构：

```text
id
user_id
media_account_id
tag_name
created_at
```

唯一约束：

```text
user_id + media_account_id + tag_name
```

规则如下：

- 标签属于创建它的当前用户；
- 不建设全局标签定义表；
- 不建设标签审批、层级、颜色和复杂标签中心；
- 支持批量添加、批量移除；
- 支持按任一标签、全部标签和排除标签筛选；
- 发布和互动通过标签筛选目标账号；
- 不增加固定的“允许发布”“允许互动”字段。

标签只代表业务选择意图，最终是否可执行仍需校验账号、Profile、代理和登录状态。

### 3.3.7 CK字段

`media_account` 直接保存两个大字段：

```text
original_cookie LONGTEXT
active_cookie   LONGTEXT
```

含义：

- `original_cookie`：最初批量导入的原始 CK，长期保留，不覆盖；
- `active_cookie`：浏览器当前真实使用并回写的 CK。

建议附带：

```text
cookie_status
active_cookie_updated_at
```

流程如下：

```text
导入原始 CK
→ 写入 original_cookie
→ 写入 Browser Profile
→ 完成登录和账号检查
→ 从浏览器读取当前平台真实 CK
→ 写入 active_cookie
```

如果登录或读取失败：

- 保留 `original_cookie`；
- 不更新 `active_cookie`；
- 标记 CK 或登录检查失败。

不建设：

- CK快照表；
- CK历史版本表；
- Profile级CK资产表；
- 复杂凭证接入表。

CK操作始终以具体 `media_account` 和平台为上下文。同一个 Profile 即使同时登录不同平台，系统也只处理当前账号所属平台的 CK，不在产品层暴露 Cookie 拆分逻辑。

### 3.3.8 CK导入与导出

支持：

- 单条导入；
- 批量导入；
- 单条导出；
- 批量导出；
- 写入绑定 Profile；
- 从 Profile 读取真实 CK；
- 登录状态检查。

导出时提供两个明确选项：

- 导出原始 CK；
- 导出当前真实 CK。

没有 `active_cookie` 时，不使用原始 CK 冒充真实 CK。

### 3.3.9 账号状态

账号状态拆成业务状态和登录状态。

业务状态：

| 状态 | 说明 |
|---|---|
| `enabled` | 正常使用 |
| `disabled` | 暂停使用 |
| `retired` | 已退役 |

登录状态：

| 状态 | 说明 |
|---|---|
| `unknown` | 未检查 |
| `normal` | 登录正常 |
| `not_logged_in` | 未登录 |
| `verification_needed` | 需要验证 |
| `expired` | 登录失效 |
| `restricted` | 账号受限 |
| `account_mismatch` | 实际登录账号与系统记录不一致 |
| `environment_error` | Profile或代理环境异常 |

账号是否可执行，最终以实际账号检查结果为准，不能通过是否存在 CK 判断。

### 3.3.10 账号检查

账号列表提供：

- 单个账号检查；
- 批量账号检查。

检查内容包括：

1. 当前比特浏览器账号是否匹配；
2. 绑定 Profile 是否存在；
3. Profile 当前代理是否正常；
4. 代理是否到期或停用；
5. 当前平台是否登录；
6. 实际登录账号是否与系统账号匹配；
7. 是否需要验证码或安全验证；
8. 是否存在账号限制。

检查结果保持简单：

- 正常；
- 未登录；
- 账号不匹配；
- 待验证；
- Profile失效；
- 代理异常；
- 账号受限；
- 检查失败。

批量检查采用队列执行，不一次性打开大量 Profile。

## 3.4 Browser Profile 管理

### 3.4.1 命名与定位

数据库和代码统一使用：

```text
browser_profile
```

页面中文可显示为“浏览器环境”或“比特窗口”。

不使用 `browser_window`，避免与临时运行窗口混淆；不使用 `browser`，避免概念过于宽泛。

`browser_profile` 表示一个长期保存 Cookie、代理、指纹和登录状态的持久化浏览器环境。

### 3.4.2 与系统用户的关系

一个系统用户只允许绑定一个比特浏览器账号。

```text
user 1 —— 1 比特浏览器账号
user 1 —— N browser_profile
```

如果同一个自然人确实拥有多个比特浏览器账号，则在本系统创建多个系统用户分别使用。

`browser_profile` 通过：

```text
browser_profile.user_id
```

与当前系统用户绑定，表示该 Profile 属于该系统用户所绑定的比特浏览器本地环境。

该字段不是“负责人”。

### 3.4.3 比特浏览器账号身份

比特浏览器 API 返回的 `mainUserId` 用于识别当前主账号/root 归属，系统归一化为 `main_user_id`。

比特浏览器 API 返回的 `userId` 用于记录 Profile/子账号归属，系统归一化为 `profile_user_id`。该字段用于审计和诊断，不替代 Cloud 侧的用户/Profile 分配权限。

首次绑定时：

1. 当前系统用户启动并登录比特浏览器；
2. 系统读取全部 Profile；
3. 校验所有 Profile 返回的 `main_user_id` 是否一致，并校验每个 Profile 均有 `profile_user_id`；
4. 用户确认绑定；
5. 系统在用户记录中保存绑定的比特侧 `main_user_id`；
6. 完成首次 Profile 同步。

建议保存：

```text
user.bit_main_user_id
user.bit_account_status
user.bit_account_bound_at
user.bit_account_last_verified_at
```

`browser_profile` 同时保存比特接口原始字段：

```text
browser_profile.bit_profile_id
browser_profile.main_user_id
browser_profile.profile_user_id
```

比特接口原始字段保持原意，不改造成账号负责人或业务字段。

### 3.4.4 同步前强校验

所有涉及比特浏览器的操作必须先校验当前比特账号：

- Profile同步；
- 批量创建 Profile；
- 批量绑定代理；
- CK写入和读取；
- 账号检查；
- 打开 Profile；
- 发布任务；
- 互动任务。

校验规则：

```text
当前 Profile.main_user_id
==
当前系统用户绑定的 bit_main_user_id
```

如果不一致、无法识别、比特浏览器未启动或未登录：

- 立即停止操作；
- 禁止同步；
- 禁止写入任何正式数据；
- 不新增 Profile；
- 不更新 Profile；
- 不把原 Profile 标记失效；
- 不更新代理关系；
- 不更新 CK。

页面强提醒：

> 当前比特浏览器登录账号与本系统用户绑定账号不一致。为避免 Browser Profile、社媒账号和代理数据错乱，当前环境不可用，请切换回正确的比特浏览器账号后重试。

系统不得自动将当前用户改绑到新检测到的比特账号。

### 3.4.5 Profile同步

同步采用：

```text
扫描
→ 生成 Diff
→ 人工集中确认
→ 正式应用
```

扫描阶段不直接修改正式数据。

同步数据主要包括：

- Profile ID；
- Profile名称；
- 分组 ID、分组名称；
- Profile状态；
- 当前代理配置；
- `main_user_id`；
- `profile_user_id`；
- 比特侧更新时间；
- 最近同步时间。

系统运营字段不得被同步覆盖，包括：

- `media_account` 关系；
- 游戏归属；
- 标签；
- 原始 CK；
- 真实 CK；
- 代理配额；
- 代理到期时间；
- 系统业务备注。

### 3.4.6 全量身份验证

同步时需要验证本次返回的全部 Profile。

流程：

1. 先抽取少量 Profile 做快速预校验；
2. 预校验通过后拉取完整 Profile 列表；
3. 对每个 Profile 的 `main_user_id` 做全量校验，并确认每个 Profile 都有 `profile_user_id`；
4. 所有 `main_user_id` 一致且与当前系统用户绑定值相同时，才允许生成可应用 Diff。

任意 Profile 身份不匹配时，整批同步禁止应用。

单个 Profile 被删除不会导致账号身份校验失败。Profile删除属于数据 Diff，不属于比特账号身份变化。

如果当前比特账号下没有任何 Profile，且接口无法独立返回当前账号身份，则本次无法完成安全校验，禁止同步。

### 3.4.7 Diff处理

Diff集中展示：

- 新增 Profile；
- Profile名称变化；
- 分组变化；
- 代理变化；
- 疑似删除 Profile；
- 新发现代理；
- 已绑定账号的 Profile 环境变化。

处理方式只提供：

- 接受本地变化；
- 恢复系统配置。

不支持永久忽略。未处理的差异在下次同步时继续提示。

对于 Profile名称和分组，以比特浏览器实际值为准。本系统可以发起修改，但修改成功后必须重新读取比特浏览器结果进行验证。

### 3.4.8 Profile新增、修改和删除

支持：

- 批量创建 Profile；
- 绑定已有 Profile；
- 批量修改 Profile名称或分组；
- 批量绑定代理；
- 打开 Profile；
- 检查 Profile；
- 停用或归档系统镜像记录。

不在云端提供“删除本地比特 Profile”功能。

原因是 Profile 属于用户电脑上的本地资源，云端没有常驻在运营电脑上的本地 Agent，技术也无法绕过用户本地环境远程删除。

用户在比特浏览器本地删除 Profile 后：

1. 下次同步发现 Profile 缺失；
2. 进入 Diff；
3. 用户确认；
4. 系统将 Profile 标记为本地失效；
5. 不自动删除 `media_account`；
6. 已绑定账号不能继续执行本地任务。

## 3.5 代理管理

### 3.5.1 模块命名

原“静态 IP 管理”统一改为：

```text
代理管理
```

数据库对象建议使用：

```text
proxy_resource
```

代理资源可能包含静态 IP，也可能包含域名代理、认证账号等，不应仅以出口 IP 表达。

### 3.5.2 代理导入

运营购买的代理通常以文档、Excel、CSV或文本形式提供，因此系统支持：

- Excel批量导入；
- CSV批量导入；
- TXT批量导入；
- 直接粘贴多行代理；
- 标准模板导入；
- 常见格式智能解析。

常见格式包括：

```text
host:port:username:password
```

```text
protocol://username:password@host:port
```

导入时先解析并预览，无法识别的行要求人工修正，不直接入库。

### 3.5.3 代理字段

代理资源至少维护：

- 代理协议；
- Host；
- Port；
- 用户名；
- 密码；
- 地区；
- 到期时间；
- 供应商；
- 运营状态；
- 最近检测时间；
- 最近检测结果；
- 备注。

可以额外记录检测到的真实出口 IP：

```text
observed_exit_ip
```

### 3.5.4 Profile与代理关系

一个代理可以绑定多个 Browser Profile。

```text
proxy_resource 1 —— N browser_profile
```

Profile实际使用哪个代理，以比特浏览器当前配置为准。

在系统中更换代理时必须执行：

```text
选择新代理
→ 校验配额
→ 调用比特浏览器API修改
→ 重新读取Profile验证
→ 更新系统关系
```

如果本地修改失败，系统不得提前更新正式绑定关系。

### 3.5.5 平台配额

代理支持按平台设置 Profile 配额。

默认规则示例：

- 百家号：一个代理最多一个 Profile；
- B站：一个代理允许多个 Profile。

系统支持：

- 全局平台默认配额；
- 单个代理覆盖默认配额。

配额按已经分配给目标平台的 Profile 数量计算，Profile一旦分配代理即占用配额，不等待账号登录成功。

代理配额达到上限时，默认禁止继续分配。用户需调整配额或选择其他代理。

### 3.5.6 自动分配

批量创建 Profile 时，系统可以自动分配代理。

只有满足以下条件的代理才能参与自动分配：

- 检测正常；
- 未过期；
- 未停用；
- 对应平台剩余配额充足。

执行前必须展示分配预览，允许用户人工调整。

### 3.5.7 比特浏览器外部修改

用户直接在比特浏览器中修改 Profile代理后：

1. 系统同步发现代理变化；
2. 生成 Diff；
3. 用户集中确认；
4. 系统更新 Profile与代理关系。

如果发现系统中不存在的新代理，确认后创建一条基础代理记录，并提示补充：

- 到期时间；
- 平台配额；
- 供应商；
- 备注。

代理已有使用记录时不物理删除，只能停用。

代理不设置负责人和个人归属字段，其使用范围由实际 Profile和账号关系体现。

## 3.6 批量上号与运行流程

### 3.6.1 上号方式

系统支持三种独立方式：

1. 人工验证码上号；
2. 批量 CK 导入；
3. 接码链接获取验证码上号。

三种方式不混入同一操作队列。

页面入口建议：

```text
账号管理
├── 批量导入/导出CK
├── 接码上号
├── 人工验证码上号
└── 账号检查
```

同一个账号后续可以更换维护方式，不设置固定登录方式字段。

### 3.6.2 批量CK模式

流程：

```text
选择平台、游戏和导入模式
→ 批量导入原始CK
→ 创建待识别media_account
→ 批量创建browser_profile
→ 自动分配代理
→ 展示预览
→ 本地调用比特浏览器API创建Profile
→ 写入CK
→ 执行账号检查
→ 获取账号ID和名称
→ 回填media_account
→ 回写active_cookie
```

默认一条 CK 创建一个新 Profile。

已有 Profile 的账号，使用单独的“绑定已有 Profile”操作，不与新建批次混合。

### 3.6.3 接码链接模式

流程：

```text
选择平台、游戏和接码模式
→ 批量导入接码链接
→ 创建待识别media_account
→ 批量创建browser_profile
→ 自动分配代理
→ 逐个打开Profile
→ 获取验证码并登录
→ 检查账号身份
→ 回填账号ID和名称
→ 回写active_cookie
```

接码手机号到期后不做续租管理，只做提醒和更新当前绑定信息。

建议提醒节点：

- 到期前7天；
- 到期前3天；
- 到期前1天；
- 到期后标记已到期。

### 3.6.4 人工验证码模式

百家号等场景可采用人工验证码上号。

系统提供：

- 打开指定 Profile；
- 展示待处理账号；
- 标记等待验证码；
- 标记登录成功；
- 标记失败或跳过；
- 登录成功后执行账号检查和信息回填。

不建设复杂流程编排。

### 3.6.5 批量创建和失败处理

批量创建 Profile 和绑定代理按单条独立执行。

某一条失败时：

- 已成功项不回滚；
- 失败项保留明确原因；
- 支持单独重试；
- Profile创建成功但CK写入失败时，保留 Profile并标记待处理；
- 代理容量不足时，执行前提示缺口，不直接开始整批任务。

## 3.7 权限、异常与验收要求

### 3.7.1 权限原则

- 普通运营和高级运营操作当前用户及其业务范围内的数据；
- 高级运营仍受游戏范围限制；
- 技术拥有系统全部权限、全局业务权限和全局数据权限；
- 本地 Profile、代理和 CK 操作还必须满足当前系统用户与比特浏览器账号身份一致；
- 技术的云端权限不能绕过本地资源和本地比特账号限制。

### 3.7.2 关键异常

系统至少处理以下异常：

- 比特浏览器未启动；
- 比特浏览器未登录；
- 当前比特账号与系统绑定账号不一致；
- 无法获取 `main_user_id` 或任一 Profile 的 `profile_user_id`；
- Profile列表为空且无法验证账号身份；
- Profile在本地被删除；
- Profile实际登录账号与系统记录不一致；
- 代理失效、过期或配额不足；
- CK写入失败；
- CK读取失败；
- 接码链接失效；
- 批量任务部分失败；
- 同一用户在新设备登录导致旧会话失效。

### 3.7.3 操作日志

记录以下关键操作：

- 比特账号首次绑定和重新绑定；
- Profile同步、创建、修改和失效确认；
- Diff确认结果；
- 代理导入、分配、修改和停用；
- CK导入、导出和回写；
- 账号识别和重复校验；
- 账号状态修改；
- 批量检查结果；
- 用户登录和被踢下线记录。

日志不得记录完整 CK、密码和代理密码。

### 3.7.4 核心验收要求

1. 一个系统用户只能绑定一个比特浏览器账号。
2. 同一自然人有多个比特账号时，通过多个系统用户分别使用。
3. 一个系统用户同时只能有一个有效登录会话。
4. 比特账号身份不一致时，所有本地相关操作必须被阻断，且零正式数据写入。
5. 同步必须先生成 Diff，经人工确认后才能应用外部修改。
6. Profile删除只产生失效 Diff，不影响比特账号身份校验。
7. `browser_profile` 使用 `main_user_id` 校验比特侧主账号归属，使用 `profile_user_id` 记录 Profile/子账号归属，二者都不解释为业务负责人。
8. `media_account` 不设置负责人和交接流程，直接归属于当前系统用户。
9. 一个 Profile 可以绑定不同平台的多个账号，同平台最多一个账号。
10. 社媒账号只在当前用户范围内去重。
11. `original_cookie` 与 `active_cookie` 分开保存。
12. CK存在不代表账号登录正常，必须以实际账号检查结果为准。
13. 代理支持文档批量导入、智能解析、检测、平台配额和批量分配。
14. 系统对 Profile和代理的修改必须真正写入比特浏览器并读回验证。
15. 云端不提供本地 Profile远程删除能力。
16. 批量创建和批量检查必须支持部分成功、失败重试和明确错误反馈。
