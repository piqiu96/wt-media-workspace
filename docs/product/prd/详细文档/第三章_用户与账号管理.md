# 第三章：用户与账号管理

## 3.1 模块概述与范围

用户与账号管理模块用于管理系统登录用户、社媒账号、比特浏览器环境及代理资源，为后续内容发布、互动执行和账号检查提供基础运行环境。

本章负责：

- 系统用户、角色及类目范围管理；
- 社媒账号的创建、识别、状态维护和查询；
- 系统用户与比特浏览器主账号树的绑定，以及同一主账号树下多个 Cloud 用户的 Profile 权限隔离；
- Browser Profile 的同步、批量创建、绑定及状态检查；
- 代理资源的批量导入、检测、配额管理和 Profile 分配；
- CK 导入、真实 CK 回写及登录状态检查；
- 本地比特浏览器数据与系统数据之间的 Diff 确认；
- 用户、账号、Profile 和代理相关的异常提示与验收要求。

本章不建设：

- 部门、团队、组织架构；
- 账号负责人及账号交接流程；
- Browser Profile 负责人；
- 自研浏览器内核、指纹浏览器或完整浏览器管理系统；
- CK 历史版本、快照表或复杂凭证资产管理；
- 代理采购、续费和供应商结算系统；
- 比特浏览器本地 Profile 的云端远程删除。

系统定位为比特浏览器的运营编排和数据管理层。实际浏览器环境、Cookie、代理和 Profile 仍由比特浏览器本地客户端承载，本系统通过本地接口完成必要的读取、创建、修改和检查。

## 3.2 用户管理

### 3.2.1 用户角色

系统固定设置三个角色：

| 角色 | 说明 |
|---|---|
| 普通运营 | 负责日常账号、素材、发布和互动操作 |
| 高级运营 | 一般业务管理所属团队及负责类目；M3–M5 管理本团队所有类目的 Cloud 业务数据，不获得其他用户本地敏感资源权限 |
| 管理员 | 拥有全部 Cloud 用户、配置、业务和数据权限，但不能绕过 Desktop、Local Agent、BitBrowser 身份与本地资源边界 |

不建设自定义角色和复杂权限编排。

用户 UID 直接使用 `users.id`，采用自增主键并由系统生成，用户不能修改。

### 3.2.2 运营团队与类目范围

系统增加扁平运营团队，用于隔离不同团队的数据：

- 一个普通运营或高级运营必须属于一个运营团队；
- 一个用户不能同时属于多个运营团队；
- 一个团队可以包含多个高级运营和普通运营；
- 管理员不属于运营团队且不受团队限制；
- 不建设部门树、子团队、负责人关系和多级审批；
- 团队不提供停用功能；
- 无用户且无历史业务数据的空团队可以删除，有关联数据的团队只能保留；
- 用户转移团队后，新业务数据使用新团队，历史数据保留原团队归属。

普通运营和高级运营按负责类目控制业务数据范围。

- 一个用户可以负责多个类目；
- 一个类目可以分配给多个用户；
- 高级运营的数据范围为所属运营团队与负责类目范围的交集；
- 普通运营的数据范围为本人资源与负责类目范围的交集；
- 管理员不受运营团队和类目范围限制。

类目范围用于账号、素材、发布、互动和数据统计等业务数据筛选，不单独建设平台范围权限。

**M3–M5 业务特例（2026-10-26）：** 内容池 `source_content` 与素材库 `material` 是团队公共资源；普通运营可查看、处理本团队所有类目的数据，类目多选初次默认本人负责项，不作为这两个公共库的强授权边界。高级运营在 M3–M5 管理本团队所有类目，管理员可跨团队。合成策略另须指定一个类目和一个同团队有效运营负责人，任务创建按策略团队／类目／负责人硬匹配。该特例不扩展到 M2 本地资源、M6 发布、互动或统计；详细规则见第四、第五章和 ADR-0023。所有页面的类目筛选、表单与人工导入选项只列启用类目；停用类目仅用于历史行名称解析，类目管理页仍展示全部状态。新建合成策略、创建合成任务素材筛选、内容池筛选与人工导入、挖掘策略表单、用户列表筛选都必须遵守该口径。

高级运营和管理员可使用 Desktop 的 M3–M5 共用 Cloud 业务页面，登录时不再因角色整体拦截；M2 的本机浏览器操作入口仍按原有角色准入和当前登录用户身份校验，不能通过管理角色查看或执行其他运营电脑上的资源。Desktop 会话单活与替换规则对所有允许登录的角色一致。

管理员可处理全局业务规则、业务数据、素材状态、发布记录和互动任务。所有关键业务修改必须记录操作日志，且不能绕过运营电脑、本地 Agent、比特浏览器 Profile、Cookie 和本地文件访问边界。

### 3.2.3 用户登录

首版采用用户名和密码登录。

- 用户由管理员创建；
- 管理员可重置用户密码，并在创建或重置成功后查看、复制本次新密码；关闭结果后不能再次查询原文；
- 用户可修改自己的密码；
- 不建设手机号登录、第三方登录、单点登录和多因素认证。

### 3.2.4 登录会话限制

认证状态只由 `user_sessions` 表达，`users` 只保存业务身份，不保存当前登录状态。

- Web：同一用户可以在多个浏览器或标签页同时登录，互不踢出，也不要求确认；每次登录各自建立一条有效会话。
- Desktop：同一用户同时只允许一条有效 Desktop 会话。该限制用于避免同一系统用户在两台电脑上同时操作不同的比特浏览器本地环境。

第二台 Desktop 登录且凭据校验成功后：

1. 若已存在有效 Desktop 会话，系统返回桌面登录冲突，并给出当前有效会话的标识；
2. 用户取消：不创建新会话，服务端不写任何登录状态，原 Desktop 继续有效；
3. 用户确认继续：重新提交登录并携带冲突中给出的会话标识；一致时系统使旧会话失效（原因记为 Desktop 已被替换）并创建新会话；
4. 确认时若当前会话已变化，系统再次返回冲突，页面不得静默重试；
5. 旧 Desktop 的下一次 Cloud 请求被拒绝，并收到明确的“账号已在另一台电脑登录”错误；页面清除本地登录凭证并跳转登录页；
6. 旧 Desktop 上本地 Agent 不被停止，已领取的任务继续执行并上报到终态或超时收敛；只有新操作被拒绝。

登录会话与比特浏览器主账号绑定是两项独立事实。替换登录会话不改变已确认的 `bit_main_user_id`；同一台电脑重新登录后，Desktop 用新的 Desktop 会话换取新的本地 Agent 凭证，不要求重新绑定比特浏览器主账号。执行中的任务不因会话替换迁移到其他电脑。

密码修改、管理员重置密码、停用用户和管理员强制下线会在同一事务内使该用户的全部会话失效，Web 与 Desktop 都需重新登录。登出只失效当前会话，不影响其他 Web 会话或另一条 Desktop 会话。

### 3.2.5 用户状态

用户状态保持简单：

- `enabled`：正常使用；
- `disabled`：禁止登录。

用户停用后：

- 该用户全部登录会话立即失效，重新启用不恢复旧会话；
- 不删除用户；
- 不删除其社媒账号；
- 不删除 Browser Profile 镜像；
- 不删除代理关系；
- 不删除历史发布、互动和统计数据。

不建设复杂账号交接流程。后续需要调整数据时，由管理员按明确的数据迁移操作处理并记录操作日志。

### 3.2.6 用户操作记录

系统记录以下关键操作：

- 创建和修改用户；
- 修改角色；
- 修改运营团队；
- 修改类目范围；
- 启用、停用用户；
- 重置密码；
- 解除错误的比特浏览器账号绑定。

日志只记录操作结果和必要摘要，不记录密码、CK、代理密码等敏感原文。

### 3.2.7 个人信息

登录后的右上角展示用户头像和昵称，菜单提供“个人信息”“退出”。个人信息是独立页面；退出结束当前会话并跳转登录页。昵称默认等于用户名，可由本人修改；头像默认使用系统头像，可由本人从系统预设头像中选择。用户名、用户 UID、角色及授权范围仍按现有规则管理，不因修改昵称或头像而变化。个人信息在 Cloud Web 和 Desktop 均可访问。

个人信息页展示个人资料、比特浏览器主账号绑定状态，以及当前电脑 Local Agent 与比特浏览器的检查结果。系统不绑定设备，也不提供设备换绑或解绑入口：换电脑只需在新电脑登录 Desktop，Desktop 同一用户只保留一条有效会话；确认替换后旧电脑失去本地执行资格，但旧电脑上已领取的任务仍会执行完成并上报结果。

比特浏览器主账号的首次绑定、重新绑定与解除规则见 §3.4.3。页面只展示脱敏后的主账号摘要与验证时间，不提供手工输入 `main_user_id` 的入口。Local Agent 与比特浏览器的检查结果只说明当前电脑此刻能否执行，不作为持久绑定状态。

### 3.2.8 系统管理与桌面环境可见性（2026-10-27）

系统管理三页按角色开放，Cloud Web 与 Desktop 使用同一套判据：

- **用户管理**：仅管理员可见，创建、修改、重置密码、停用与删除只对管理员开放。
- **运营团队**：高级运营与管理员可见；高级运营只读，新增、重命名、删除只对管理员开放。团队人数由服务端随团队列表返回（`OperationTeam.user_count`），页面不读用户列表——那条接口只对管理员开放，按用户列表现算会让高级运营看到整列为 0。
- **类目管理**：高级运营与管理员可见；高级运营看到全部启停状态的类目，但不显示关联情况与写入口，关联详情仍只对管理员开放。普通运营访问管理视图的类目列表返回 403。
- **普通运营**：看不到系统管理分组。

桌面端提供同样三个页面，复用 Cloud Web 的页面组件文件，不各写一套。菜单隐藏只减少误入；每一处写入口仍由服务端角色校验把关，不能靠隐藏控件实现权限。

桌面环境（本地日志、本机设置）只对普通运营与高级运营开放，管理员不进入。浏览器窗口是本机执行面：Cloud Web 对所有角色只读；Desktop 上普通运营与高级运营可以同步、打开/关闭、编辑和设置本人窗口的代理，高级运营切换到查看成员时只读，管理员不进入。代理管理在 Cloud Web 与 Desktop 对三种角色开放，普通运营维护名称、地区、供应商、标签和备注，高级运营与管理员额外管理连接信息、到期、配额、启停和删除；窗口级代理写入只在浏览器窗口页执行。Cookie 接入在普通运营及高级运营本人 Desktop 执行。社媒账号页三种角色都可进入，本地操作按账号归属判定（见 §3.3）。

## 3.3 社媒账号管理

### 3.3.1 目标与范围

社媒账号围绕矩阵账号日常维护、人工登录后识别、Cookie 接入组织。本模块未投入使用，按已确认原型整体重构；不继承旧页面、旧开户流程或数据模型，不建设新旧兼容层。唯一交互入口见[社媒账号原型](../../../../example/proto/social-accounts/index.html)，视觉与交互遵循现行前端规范。

首期平台为 B站（`bilibili`）、百度（`baidu`）。不提供接码轮询、接码链接换绑、验证码代填、首次进入自动全量检查、周期检查、凭证历史中心或审批流程。人工在浏览器中完成登录/验证码，再回系统检查是核心路径，与接码自动化无关。

### 3.3.2 账号归属与角色

账号直接归属于创建它的系统用户；不增加负责人、交接人和账号转移流程。昵称、UID、头像来自平台识别，不在资料编辑中手填登录状态或平台身份。

| 角色 | 默认查看与筛选 | 展示差异 | 本机操作与凭证 |
| --- | --- | --- | --- |
| 普通运营 | 本人，无团队/使用人筛选 | 不重复显示本人归属 | Desktop 维护本人账号 |
| 高级运营 | 默认本人，可选同团队成员或全部成员 | 增加使用人 | 本人可执行；成员仅维护 Cloud 业务资料 |
| 管理员 | 默认全部，团队与使用人联动 | 增加运营团队与使用人 | 不代执行本机操作，不提供凭证入口 |

账号维护、检查和窗口操作不因未分类阻断。选择类目时使用当前归属用户可用的已启用类目，发布/互动仍按各自任务预检校验类目、窗口、代理和登录条件。Cloud 归属与团队边界继续有效，不增加额外审批。

### 3.3.3 日常维护与台账

账号列表的两个独立新增入口为“新增账号”“批量CK接入”。主要信息依次为账号与 UID、平台、类目/标签、窗口、登录状态与可执行性、运营备注；角色附加归属信息按上表展示。窗口名称打开只读窗口详情，不跳转离开列表。

新增台账选择平台，可填写类目、标签、备注；允许未绑定窗口、未分类、未导入 Cookie 保存。保存后可继续绑定窗口，也可稍后处理。不设置独立“记录账号/执行账号”类型。

账号详情为 800px 只读 Drawer，无业务 Footer。编辑资料仅修改类目、标签和运营备注；启停单独确认，停用表示不再参与新任务选用，不退出平台登录、不删除账号或窗口。列表筛选、分页、选择与滚动位置在浮层关闭后保留。行操作不超过五项时平铺，超过时收进“更多”；分页不提供跳页器。

### 3.3.4 类目与标签

一级类型固定 `game/ai/anime`，二级选项来自已有类目配置。同一账号允许零个或多个类目，多选必须属于同一一级；先选一级再选二级，切换一级清空二级。不增加层级表、占位类目或“暂不分类”选项；未选时显示“请选择一级分类”，允许保存为空。

筛选只选一级时覆盖该类型全部类目；二级可多选。分类与归属为普通文字，关联窗口等可追溯对象使用链接。标签输入后回车生成，可逐项移除；支持按任一、全部、排除标签筛选，不建设标签中心、层级、颜色或审批。

### 3.3.5 窗口绑定与人工登录后识别

账号可绑定一个窗口，一个窗口可关联不同平台账号，同平台最多一个账号。绑定/换绑只改变关联，不清除原窗口 Cookie，也不向新窗口自动写 Cookie。候选窗口保留不可用原因；同平台已被其他账号关联时不可选择。

人工登录路径：新增台账并绑定已有窗口（已有账号可直接打开绑定窗口）→ 运营自行完成目标平台登录/验证 → 返回点击“检查并同步” → 系统识别昵称、UID、头像与登录状态并回填。无需先导入 Cookie、无需先分类；检查不重新登录或覆盖浏览器 Cookie。

首次识别取得 UID 后确认账号身份；相同 UID 的后续检查同步更新平台昵称与头像。实际 UID 与台账不同，展示原账号和窗口当前账号的昵称、UID 供核对，不自动替换原身份；用户可打开窗口登录正确账号或重新选择正确窗口。

### 3.3.6 检查、登录结论和去重

启停是业务配置；登录结论包括未检查、正常、未登录、待验证、失效、受限、身份不一致、环境异常。本次检查执行结果与上次登录结论分别保存。检查失败不覆盖上次有效平台资料和登录结论，不提示同步成功；界面明确标示上次结论和本次失败。

检查通过本人 Desktop 同步调用本机 Agent，按需验证窗口、代理、目标平台登录及身份。只读到 Cookie 不代表登录有效；保存 Cookie 的回退值不冒充实时已验证会话。账号列表不自动全量检查；支持单项检查和选中后逐项批量检查。

重复身份按 `user_id + platform + platform_account_id` 判断，不做跨用户合并。识别到当前用户已有同平台同 UID 时，使用/定位已有账号，不覆盖其 Cookie 或窗口，不创建第二条正式已识别账号。

### 3.3.7 Cookie 查看、更新与内部保护

本人可从独立凭证入口查看、复制最初导入值和最近确认的当前值；没有当前值时如实显示为空，不以原始输入冒充。已绑定但没有 Cookie 的账号仍可维护登录凭证。单条更新输入新的 Cookie，确认目标账号、平台和窗口后“更新并检查”，与资料编辑分开。

任何写 Cookie 操作先核实目标平台占用与实际登录情况，保存并验证写前值后才可执行。只修改目标平台信息，不清空其他平台会话，不覆盖其他账号；保护动作失败则不写，操作结果未知先核实不重放。内部保留必要版本供防误覆盖，不增加运营备份步骤、历史中心和通用审计。

### 3.3.8 批量 Cookie 接入

输入平台、类目和逐行 Cookie → 校验并预览 → 修正错误或明确继续有效行 → 确认接入 → 逐项准备窗口、写入、识别及保存账号。预览不创建窗口、不写 Cookie、不创建正式账号。

优先新建窗口。确认不能新建时才允许选择空闲窗口；Cloud 未关联不代表本机没有登录。复用前确认目标平台没有其他账号关联、没有残留登录且没有冲突操作；情况不明或已占用不能写。创建结果未知时先核实，不能直接改为复用或再次创建。

接入成功必须同时有目标窗口、真实 UID、明确登录结论与正式账号关系；未完成登录/资料同步不算成功。需要人工登录时打开对应窗口，人工完成后检查并继续；无须重新导入整批。

### 3.3.9 批次结果与恢复

批次有七个互斥计数：总数、成功、失败、跳过、执行中、待处理、待确认；总数等于其余六项之和。检查成功表示取得检查结论（可为未登录/失效），Cookie 接入成功表示该项真正完成，不能混用。

单项保留原行号、关联账号、窗口、阶段与可操作原因。跳过可恢复原项，已成功项不重放；失败按原因提供人工登录、检查、重新选择窗口或继续。总继续按钮只在存在可自动继续项时出现并展示真实条数。未知结果先核实，再决定是否重试。关闭浮层不丢失批次，不建设独立恢复控制台。

### 3.3.10 页面反馈与验收

首次读取失败在内容区提供重试；已有列表刷新失败保留列表，仅显示一次错误 Toast。错误红色、成功绿色、信息蓝色，使用共享反馈组件。空数据、筛选无结果和无权限使用现有公共规范，不自建全局规则。

验收覆盖三角色、同一级多类目与回车标签、只读详情、保留列表上下文、人工登录后真实识别、相同 UID 更新资料、不同 UID 对照、重复身份、当前检查失败保留旧结论、Cookie 写前保护与平台隔离、窗口新建优先和占用阻断、批次互斥计数与跳过恢复。交互以原型为准；模拟演示不等于真实平台验收。

## 3.4 Browser Profile 管理

### 3.4.1 命名与定位

数据库和代码统一使用：

```text
browser_profile
```

页面中文可显示为“浏览器环境”或“比特窗口”。

不使用 `browser_window`，避免与临时运行窗口混淆；不使用 `browser`，避免概念过于宽泛。

`browser_profile` 表示一个长期保存 Cookie、代理、指纹和登录状态的持久化浏览器环境。

### 3.4.2 与系统用户的关系

一个系统用户最多绑定一棵比特浏览器主账号树。

```text
user N —— 1 BitBrowser main_user_id
user 1 —— N Cloud 分配的 browser_profile
```

同一个 `main_user_id` 可以绑定多个系统用户，用于一个主账号及其子账号分别对应多个运营的场景。共享主账号树只表示比特侧根身份一致，不表示这些系统用户可以互相访问 Profile。

如果同一个自然人确实拥有多个不同的比特浏览器主账号树，则在本系统创建多个系统用户分别使用。

`browser_profile` 与当前系统用户和当前比特主账号同时绑定，表示 Cloud 将该 Profile 授权分配给当前系统用户：

```text
browser_profile.user_id = 当前系统用户.id
AND browser_profile.main_user_id = 当前系统用户.bit_main_user_id
```

正常查询、读取、更新、删除、分配和执行预检都必须同时满足这两个条件。同一 `bit_profile_id` 在旧主账号下已有记录时，新主账号插入新记录；旧记录不删除、不迁移。切回旧主账号时旧 Profile 自然恢复可见。唯一约束为 `(user_id, main_user_id, bit_profile_id)`。

`user_id` 不是“负责人”，也不能由相同 `main_user_id` 自动推导。

### 3.4.3 比特浏览器账号身份

比特浏览器 API 返回的 `mainUserId` 用于识别当前主账号/root 归属，系统归一化为 `main_user_id`。

比特浏览器 API 返回的 `userId` 用于记录 Profile/子账号归属，系统归一化为 `profile_user_id`。该字段用于审计和诊断，不替代 Cloud 侧的用户/Profile 分配权限。

首次绑定时：

1. 当前系统用户启动并登录比特浏览器；
2. Local Agent 通过比特浏览器 API 真实读取当前主账号身份；
3. 系统只接受 Agent 实读的 `main_user_id`，页面不提供手工输入入口；
4. 用户确认绑定；
5. 系统在用户记录中保存绑定的比特侧 `main_user_id`；
6. 只保存用户与主账号树的绑定和验证时间，不在 M2-A 创建或更新正式 `browser_profile`，也不要求读取完整 Profile 列表；正式 Profile 扫描、Diff 和授权同步归 M2-B。

建议保存：

```text
user.bit_main_user_id
user.bit_account_status
user.bit_account_bound_at
user.bit_account_last_verified_at
```

`browser_profile` 同时保存比特接口原始字段：

```text
browser_profile.bit_profile_id
browser_profile.main_user_id
browser_profile.profile_user_id
```

比特接口原始字段保持原意，不改造成账号负责人或业务字段。

已绑定用户再次刷新本机状态时：

- 系统只允许当前比特浏览器 `main_user_id` 与用户已绑定 `bit_main_user_id` 一致；
- 一致时刷新本机环境状态和验证时间；
- 不一致时阻断新的比特浏览器相关操作，不得静默改绑；
- 用户可在明确确认后重新绑定：重绑只更新用户的 `bit_main_user_id`、绑定时间和验证时间，不删除、不迁移、不失效旧主账号下的 Profile；切回旧主账号时旧 Profile 自然恢复；
- 登录会话与主账号绑定相互独立：重新登录或更换电脑不改变已确认的 `bit_main_user_id`，也不解除绑定。

如果系统故障或历史错误导致用户绑定了错误的比特浏览器主账号，管理员可在 Cloud 用户管理中解除该用户的比特浏览器账号绑定。解除绑定只清空用户主账号绑定，不删除已有 Browser Profile 镜像、媒体账号、代理关系或历史记录，也不改变 Desktop 登录会话；后续比特浏览器相关操作会因未绑定主账号被拒绝。解除后，目标用户必须在自己的 Desktop 上重新绑定正确的比特浏览器账号。

### 3.4.4 同步前强校验

所有涉及比特浏览器的操作必须先校验当前比特账号：

- Profile同步；
- 批量创建 Profile；
- 批量绑定代理；
- CK写入和读取；
- 账号检查；
- 打开 Profile；
- 发布任务；
- 互动任务。

校验规则：

```text
Profile.user_id == 当前系统用户.id
AND Profile.main_user_id == 当前系统用户绑定的 bit_main_user_id
```

执行前统一经过执行预检，至少确认：用户已启用、当前 Desktop 会话有效（已领取任务按 claim 后的执行身份判定）、主账号已绑定、比特浏览器正在运行、实际主账号与绑定一致、Profile 双作用域、本地 Profile 存在、动作要求的平台登录态满足、本地文件可用。预检结果按 `{code, message, retryable, recovery_action}` 返回，页面按 `code` 处理，不解析文案。

Profile 不在当前双作用域内时，列表与详情不返回该数据。媒体账号引用的 Profile 越界时，页面显示“未找到对应的浏览器环境”，执行返回 `PROFILE_NOT_FOUND`；Profile 明确属于其他系统用户时返回 `PROFILE_ASSIGNED_TO_OTHER_USER`。

如果主账号不一致、无法识别、比特浏览器未启动或未登录、实时事实过期：

- 立即停止操作；
- 禁止同步；
- 禁止写入任何正式数据；
- 不新增 Profile；
- 不更新 Profile；
- 不把原 Profile 标记失效；
- 不更新代理关系；
- 不更新 CK。

页面强提醒：

> 当前比特浏览器登录账号与本系统用户绑定账号不一致。为避免 Browser Profile、社媒账号和代理数据错乱，当前环境不可用，请切换回正确的比特浏览器账号后重试。

系统不得自动将当前用户改绑到新检测到的比特账号。

### 3.4.5 Profile同步

同步采用：

```text
扫描
→ 生成 Diff
→ 人工集中确认
→ 正式应用
```

扫描阶段不直接修改正式数据。

同步只作用于当前登录运营本人的窗口（`browser_profiles.user_id = 当前用户`）。高级运营切换到查看其他成员时只读，不产生 Diff，也不能替成员确认。

- 已登记窗口的名称、分组、比特备注变化，在运营确认后按比特实际值更新。
- 新发现的未登记窗口默认不认领；运营在预览中勾选后才建立 Cloud 归属，未勾选的窗口下次同步继续提示。
- 同一 `bit_profile_id` 已登记在其他运营名下时标为归属冲突：不可勾选、不可改派，也不因本方扫描而改变原归属。
- 比特中已不存在的窗口，确认后标记为本地缺失，保留 Cloud 记录、关联账号和历史；不自动删除账号。
- Agent 不可达或结果无法核实时不写正式数据，也不下发重复创建；页面提示先核实本机状态。

同步数据主要包括：

- Profile ID；
- Profile名称；
- 分组 ID、分组名称；
- Profile状态；
- 当前代理配置；
- `main_user_id`；
- `profile_user_id`；
- 比特侧更新时间；
- 最近同步时间。

系统运营字段不得被同步覆盖，包括：

- `media_account` 关系；
- 类目归属；
- 标签；
- 原始 CK；
- 真实 CK；
- 代理配额；
- 代理到期时间；
- 系统业务备注。

### 3.4.6 全量身份验证

同步时需要验证本次返回的全部 Profile。

流程：

1. 先抽取少量 Profile 做快速预校验；
2. 预校验通过后拉取完整 Profile 列表；
3. 对每个 Profile 的 `main_user_id` 做全量校验，并确认每个 Profile 都有 `profile_user_id`；
4. 所有 `main_user_id` 一致且与当前系统用户绑定值相同时，才允许生成可应用 Diff。

任意 Profile 身份不匹配时，整批同步禁止应用。

单个 Profile 被删除不会导致账号身份校验失败。Profile删除属于数据 Diff，不属于比特账号身份变化。

如果当前比特账号下没有任何 Profile，且接口无法独立返回当前账号身份，则本次无法完成安全校验，禁止同步。

### 3.4.7 Diff处理

Diff集中展示：

- 新增 Profile；
- Profile名称变化；
- 分组变化；
- 代理变化；
- 疑似删除 Profile；
- 新发现代理；
- 已绑定账号的 Profile 环境变化。

处理方式：

- 新增窗口：由运营逐项勾选后认领；未勾选视为暂不登记。
- 名称、分组、比特备注变化：接受本地变化后更新 Cloud 镜像。
- 代理变化：可恢复系统托管配置（比特明确返回成功后确认关系；结果不确定时先读取核对），或保留比特实际代理并改为比特自管；未知代理勾选后才创建资源。
- 疑似删除：接受后标记本地缺失，保留 Cloud 记录与账号关系。
- 归属冲突：只展示，不提供认领或改派。

不支持永久忽略。未处理的差异在下次同步时继续提示。

对于 Profile名称和分组，以比特浏览器实际值为准。本系统发起修改后必须重新读取比特浏览器结果；读回不能证实的结果标为待确认，不冒充成功。

### 3.4.8 Profile新增、修改和删除

支持：

- 创建 Profile（经本机 Agent 在比特中创建并读回核实）；
- 修改 Profile名称、分组和比特备注；
- 批量打开、关闭窗口；
- 批量设置托管代理；
- 业务启停（停用前须确认窗口已关闭）；
- 本地缺失后的业务停用与恢复同步。
- 对确认已在比特删除且同步标记缺失的窗口，单项或批量清理 Cloud 记录。

不在云端提供“删除本地比特 Profile”功能。

原因是 Profile 属于用户电脑上的本地资源，云端没有常驻在运营电脑上的本地 Agent，技术也无法绕过用户本地环境远程删除。

用户在比特浏览器本地删除 Profile 后：

1. 下次同步发现 Profile 缺失；
2. 进入 Diff；
3. 用户确认；
4. 系统将 Profile 标记为本地失效；
5. 不自动删除 `media_account`；
6. 已绑定账号不能继续执行本地任务。

日常窗口列表默认展示全部记录，增加独立“窗口状态”列与筛选，并放在运行状态之前；筛选只提供“已找到 / 未找到”，不选择即全部，不增加双标签。“清理已删除窗口”入口承担缺失记录批量清理，缺失行可单项“删除”，清理清单及同步结果使用同一名称，最终确认按钮也是“删除”。运营须先确认窗口确已在比特删除；若是切换主账号或权限变化，应先恢复访问再同步。清理时每个窗口独立执行：解除关联账号，登录与检查结论回到待核验，释放托管代理名额，物理删除 Cloud 窗口记录并留下不含凭据的技术审计。账号、平台身份和历史保留，需由运营手动重新绑定新窗口；不自动猜测替代窗口。普通窗口不提供删除，待核实代理操作先处理，批量清理只重试失败项。Cloud 清理不向比特发起删除请求。

同步窗口区分“本次待处理”和“历史待处理”：历史缺失只在完整读取成功后保留处理入口，不重复算作本次新增异常；运营可核实或确认后删除。读取失败、超时、比特主账号不符以及无法核实身份的零窗口响应均不得改变已有窗口状态，也不得提供基于本次读取的删除判断。

窗口列表的代理信息提供只读查看：系统托管资源以侧栏展示资源状态、检测、到期、额度和与当前窗口的配置关系；比特自管且有代理地址时以居中弹窗展示最近同步的协议、地址和时间；直连不提供代理详情。查看不会检测或修改代理，不显示认证秘密；缺失窗口的代理内容须标注为上次同步信息。

## 3.5 代理管理

### 3.5.1 模块命名

原“静态 IP 管理”统一改为：

```text
代理管理
```

数据库对象使用：

```text
proxies
```

代理资源可能包含静态 IP，也可能包含域名代理、认证账号等，不应仅以出口 IP 表达。每条代理属于一个运营团队，并维护名称与标签；存量代理不按个人回填团队，迁移时整体清理。

### 3.5.2 代理导入

运营购买的代理通常以文档、Excel、CSV或文本形式提供，因此系统支持：

- Excel批量导入；
- CSV批量导入；
- TXT批量导入；
- 直接粘贴多行代理；
- 标准模板导入；
- 常见格式智能解析。

常见格式包括：

```text
host:port:username:password
```

```text
protocol://username:password@host:port
```

导入时先解析并预览，按原行号列出有效、重复、无效三类结果并允许勾选；提交只导入勾选的有效行，服务端再次查重。无法识别的行要求人工修正，不直接入库。结果计数满足「提交总数 = 成功 + 失败 + 跳过 + 处理中 + 未处理 + 待确认」。

### 3.5.3 代理字段

代理资源至少维护：

- 所属团队；
- 名称；
- 代理协议；
- Host；
- Port；
- 用户名；
- 密码；
- 地区；
- 供应商；
- 标签；
- 到期时间；
- 启停（`enabled`）；
- 最近检测时间、结果和原因；
- 最大窗口数（配额）；
- 备注。

列表与窗口页不返回代理密码；用户名和密码只在有权限的代理详情中查看和复制。动态代理的来源提取 URL 为只写秘密，更新时可沿用已保存值，接口不回显原文。

### 3.5.4 Profile与代理关系

一个代理可以绑定多个 Browser Profile。

```text
proxies 1 —— N browser_profile
```

窗口有两种代理方式：

- **系统托管**：`browser_profiles.proxy_id` 指向一条代理资源，占用该代理的窗口配额，名单与凭据由 Cloud 管理。
- **比特自管**：没有 `proxy_id`，代理地址由比特中的实际配置决定；不计入任何代理资源的配额。

Profile实际使用哪个代理，以比特浏览器当前配置为准。窗口级代理写入只在「浏览器窗口」页面执行，代理管理页不直接改写窗口。

在系统中更换托管代理时必须执行：

```text
选择新代理
→ 服务端校验团队归属、启停、到期、检测结果与配额
→ 调用比特浏览器API修改
→ 比特明确返回成功后更新系统关系
```

只有比特明确成功才建立新的正式关系。请求超时、断开、桌面/Agent 中断或异常响应一律按本次失败处理：清除临时额度预留、保留旧正式关系，允许用户直接重试，不进入人工待确认状态。代理连接检测和比特写入结果分别表达。改为比特自管只解除正式关系，保留比特中的实际地址；解绑并改为直连才清除比特中的实际代理，且必须先通过 Agent 读回证实。

### 3.5.5 窗口配额

一个 Browser Profile 同时最多使用一个有效代理。一个代理可以绑定多个 Profile，但不得超过：

```text
max_profiles
```

配额按当前正式绑定该代理的有效 Profile 数量计算，与 Profile 中登录的平台账号数量无关。比特自管窗口不占配额。

代理配额达到上限时，默认禁止继续分配。用户需调整配额或选择其他代理。配额不得低于当前正式占用；检查配额与写入代理关系在同一把代理级锁内完成，防止并发操作同时抢到最后一个名额。

### 3.5.6 分配预览

本期批量设置代理由运营手动选择目标代理，系统不自动挑代理。

只有满足以下条件的代理才能参与分配：

- 同团队；
- 检测正常；
- 未过期；
- 未停用；
- 剩余窗口配额充足。

执行前必须展示逐窗口的分配预览与总配额需求；开始后逐项写入并读回，失败的窗口单独列出，允许重试而不重复分配已成功的窗口。

### 3.5.7 比特浏览器外部修改

用户直接在比特浏览器中修改 Profile代理后：

1. 系统同步发现代理变化；
2. 生成 Diff；
3. 用户集中确认；
4. 系统更新 Profile与代理关系。

如果发现系统中不存在的新代理，勾选确认后创建一条基础代理记录，并提示补充：

- 到期时间；
- 窗口配额；
- 供应商；
- 备注。

同一扫描中多个代理匹配同一实际地址时列为冲突，系统不猜测、不写入。

代理已有正式窗口引用时不允许物理删除，只能停用；删除前服务端重新检查占用。到期由到期时间现算，不自动解除窗口关系，也不改写检测结果。

代理不设置负责人和个人归属字段，其使用范围由所属团队和实际窗口关系体现。

### 3.5.8 团队范围与角色

- 每条代理必须属于一个运营团队。普通运营和高级运营只能读取本人团队；管理员可跨团队查看。
- 普通运营创建代理时团队固定为本人团队；高级运营与管理员可管理连接信息、到期、配额、启停和删除。普通运营可维护名称、地区、供应商、标签和备注。
- 服务端按角色与团队校验读写；页面隐藏控件不构成权限边界。
- 列表不单列团队，详情显示团队；管理员列表支持按团队筛选。

### 3.5.9 检测归属

代理连通性由 Cloud 服务端直接对已保存的协议、主机和端口发起探测，不依赖本机 Agent、比特窗口或某台工作站在线。结果分为：

- 正常；
- 连接失败；
- 认证失败；
- 超时；
- 参数无效。

只有检测正常且未停用、未到期、仍有配额的代理可分配。检测结果按被探测的连接版本保存：慢检测返回时若地址已变更，旧结果丢弃，不能覆盖新连接状态。检测成功不顺延到期时间。

动态代理的地址提取仍使用运营自己的工作站在本机执行；地址取回后由 Cloud 保存并检测。

## 3.6 账号接入与登录维护入口

账号维护、人工登录后识别、Cookie 接入与批次处理统一见 §3.3，不另设“开户”模块。Browser Profile、代理是复用的资源能力，规则分别见 §3.4、§3.5。接码自动化及链接换绑不属于当前范围，不保留独立入口、队列或流程占位。

## 3.7 权限、异常与验收要求

### 3.7.1 权限原则

- 普通运营操作本人且在授权类目范围内的数据；
- 高级运营一般业务操作所属团队与负责类目交集内的 Cloud 数据；M3–M5 按下条特例覆盖本团队所有类目；
- 管理员拥有系统全部 Cloud 权限、全局业务权限和全局数据权限；
- 本地 Profile、代理和 CK 操作还必须满足当前系统用户与比特浏览器账号身份一致；
- 高级运营和管理员的云端权限不能绕过本地资源和本地比特账号限制。
- M3–M5 的 Cloud 业务页面在 Cloud Web 和 Desktop 共用页面上执行相同服务端授权；高级运营仅本团队所有类目、管理员跨团队，本机资源仍按当前登录用户绑定。内容池和素材库的类目选择是筛选，合成策略的类目及指定负责人是创建任务的硬匹配条件（ADR-0023）。

### 3.7.2 关键异常

系统至少处理以下异常：

- 比特浏览器未启动；
- 比特浏览器未登录；
- 当前比特账号与系统绑定账号不一致；
- 无法获取 `main_user_id` 或任一 Profile 的 `profile_user_id`；
- Profile列表为空且无法验证账号身份；
- Profile在本地被删除；
- Profile实际登录账号与系统记录不一致；
- 代理失效、过期或配额不足；
- CK写入失败；
- CK读取失败；
- 批量任务部分失败；
- 同一用户登录第二台 Desktop 导致旧 Desktop 会话被替换；
- 本地 Agent 凭证与当前 Desktop 会话不匹配或已过期；
- 运行中任务长时间没有活动上报，按执行超时收敛。

### 3.7.3 操作日志

记录以下关键操作：

- 比特账号首次绑定、管理员解除错误绑定和用户重新绑定；
- Profile同步、创建、修改和失效确认；
- Diff确认结果；
- 代理导入、分配、修改和停用；
- CK导入、导出和回写；
- 账号识别和重复校验；
- 账号状态修改；
- 批量检查结果；
- 用户登录、Desktop 登录冲突确认、强制下线和密码重置导致的会话失效记录。

日志不得记录完整 CK、密码和代理密码。

### 3.7.4 核心验收要求

1. 一个系统用户最多绑定一棵比特浏览器主账号树。
2. 同一个 `main_user_id` 可以绑定多个系统用户，但各用户只能访问 Cloud 分配给自己的 Profile；同一自然人有多个不同主账号树时，通过多个系统用户分别使用。
3. Web 允许同一用户多条有效登录会话；Desktop 同一用户同时只允许一条有效会话，第二台 Desktop 登录须经冲突确认，旧 Desktop 收到明确的会话被替换错误。
4. 比特账号身份不一致时，所有本地相关操作必须被阻断，且零正式数据写入。
5. 同步必须先生成 Diff，经人工确认后才能应用外部修改。
6. Profile删除只产生失效 Diff，不影响比特账号身份校验。
7. `browser_profile` 以 `user_id + main_user_id` 双作用域限定访问，使用 `profile_user_id` 记录 Profile/子账号归属，二者都不解释为业务负责人。
8. `media_account` 不设置负责人和交接流程，直接归属于当前系统用户。
9. 一个 Profile 可以绑定不同平台的多个账号，同平台最多一个账号。
10. 社媒账号只在当前用户范围内去重。
11. Cookie 输入、写前保留值与确认读回值按 §3.3 区分，当前值不得由未验证输入冒充。
12. CK存在不代表账号登录正常，必须以实际账号检查结果为准。
13. 代理支持文档批量导入、智能解析、检测、统一窗口配额和批量分配。
14. 系统对 Profile 字段的修改必须写入比特浏览器并读回验证；托管代理绑定以比特明确成功响应为准，不确定时读取核对，代理直连解绑仍须读回验证。
15. 云端不提供本地 Profile远程删除能力。
16. 批量创建和批量检查必须支持部分成功、失败重试和明确错误反馈。
17. 本地 Agent 使用当前 Desktop 会话换取的限权凭证访问 Agent API；凭证与会话同寿命，不落库、不写日志、不进入页面；用户会话凭证不能调用 Agent API。
18. 任务按用户范围领取并携带本次执行的 attempt 标识；旧 attempt 的结果不能覆盖新 attempt。
19. 运行中任务超过执行超时且没有活动上报时：无外部副作用的任务标记为可重试的中断，有外部副作用的任务标记为结果未知且不自动重试。
20. Agent 的最终结果先写入本地待上报存储再上报；重启或网络恢复后先补报，不重跑已完成任务。
21. 本地操作统一经过执行预检，失败按错误码返回，页面不解析错误文案。
