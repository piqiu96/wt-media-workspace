# 第一章：项目概述

## 1.1 项目背景

随着游戏自媒体账号数量、运营平台和内容生产规模持续增加，依赖人工操作、零散工具和本地脚本的运营方式，已经难以支撑稳定、持续和规模化的日常运营。

当前业务主要存在以下问题：

1. **运营流程分散**  
   账号、内容、素材、成片、发布、互动和数据统计由不同工具或人工记录管理，业务数据缺少统一衔接，容易出现重复录入、任务状态不清和结果无法追溯。

2. **账号与本地环境容易对应错误**  
   社媒账号实际执行依赖比特浏览器、Browser Profile、代理、Cookie和本地登录环境。用户、比特浏览器账号、Profile和社媒账号之间缺少明确校验时，容易发生串号、代理绑定错误和本地数据污染。

3. **素材生产依赖大量重复操作**  
   内容整理、素材下载、模板选择、视频处理和成片记录需要人工反复执行，人工触发与自动触发也缺少统一的 Cloud 生产管理。

4. **发布和互动执行效率较低**  
   发布、点赞、评论和收藏依赖平台页面和本地浏览器环境，逐条操作效率低，批量任务缺少统一进度、失败原因和重试机制。

5. **任务异常难以处理**  
   现有脚本通常只关注是否完成，缺少任务状态、执行阶段、异常恢复和结果确认。程序退出或网络异常后，可能无法判断是否已经产生真实外部结果。

6. **运营数据缺少统一沉淀**  
   内容、素材、成片、发布、互动和平台效果数据分散，难以按游戏、平台、账号、运营人员和时间范围统一统计。

7. **现有工具难以长期维护**  
   平台页面、接口和本地依赖持续变化，零散脚本缺少版本、日志、可观测、升级和备份能力，无法形成稳定的运营基础设施。

因此，需要建设一套统一的模块化自媒体运营平台，将账号、内容、素材、生产、发布、互动和统计纳入同一业务闭环，并通过云端管理系统、本地运营端和Agent协同，降低重复劳动，提高数据正确性和持续运营能力。

## 1.2 项目定位与建设目标

### 1.2.1 项目定位

模块化自媒体运营平台是一套面向游戏自媒体运营团队的内部运营管理与辅助执行平台。

系统由云端管理系统、Cloud Scheduler / Worker / Crawler、跨平台本地运营端、Local Agent 及外部平台能力共同组成，统一管理账号、内容、素材、成片、发布、互动和数据统计。本地运营端支持 Windows 与 macOS，其中 macOS 需兼容 Intel 和 Apple Silicon 两种芯片架构。

项目不以完全替代运营人员为目标，而是在保留人工控制和风险确认的前提下，将重复、标准化和适合程序执行的工作交由系统及Agent处理。

本项目不是：

- 面向所有行业的通用社交媒体SaaS；
- 自研指纹浏览器；
- 完全无人值守的自动发稿机器人；
- 通用低代码或工作流平台；
- 任意脚本执行平台；
- 多个临时脚本的简单集合。

### 1.2.2 核心价值

1. **统一管理**  
   统一管理用户、账号、Browser Profile、代理、内容、素材、成片、发布、互动和统计数据。

2. **提升效率**  
   通过批量操作、定时监控、Cloud 自动生产和 Local Agent 本机执行减少运营重复劳动。

3. **降低风险**  
   通过身份校验、绑定关系、任务状态和结果验证，降低账号、Profile、代理和本地环境串乱风险。

4. **过程可控**  
   任务具备进度、状态、失败原因、重试和人工处理入口，高风险任务不会盲目重复执行。

5. **持续运营**  
   系统具备日志、可观测、升级、备份和异常恢复能力，不以一次性工具方式建设。

### 1.2.3 建设目标

- 建立账号、内容、素材、成片、发布、互动和统计的完整运营闭环；
- 支持人工发起与策略自动发起共用 Cloud 内容生产底座；
- 统一管理系统用户、比特浏览器账号、Browser Profile、代理和社媒账号；
- 标准化B站、百家号辅助发布及点赞、评论、收藏互动；
- 为高频操作提供批量、自动填写、定时调度和失败项重试能力；
- 保证核心业务结果可追溯到任务、用户、Agent和执行日志；
- 建立统一的数据统计和明细下钻能力；
- 保持产品简单易用，减少普通运营接触复杂技术配置。

### 1.2.4 自动化定位

项目采用“自动生产＋辅助执行”的自动化定位。

可以自动持续运行的能力包括：

- 抖音关键词和作者监控；
- `compose_strategy.schedule` 自动创建生产任务；
- Cloud Worker 视频合成、成片校验和对象存储提交；
- 平台效果数据采集；
- 日级统计汇总；
- 过期文件和数据清理。

需要本地环境或人工参与的能力包括：

- 比特浏览器账号确认；
- Browser Profile同步和差异确认；
- 代理、Cookie和登录异常处理；
- B站、百家号辅助发布；
- 点赞、评论和收藏；
- 外部执行结果无法确认时的人工处理。

系统不承诺在没有运营人员和本地环境参与的情况下完成全部发布和互动操作。

## 1.3 业务范围与核心流程

系统围绕游戏自媒体运营的主要流程，提供以下核心能力：

```text
用户与账号管理
→ 内容发现
→ 素材生产与成片管理
→ 发布管理
→ 互动管理
→ 数据统计
```

### 1. 用户与账号管理

统一管理系统用户、社媒账号、Browser Profile、代理资源和账号登录状态，为后续生产、发布和互动提供正确的账号及执行环境。

### 2. 内容发现

首版通过抖音链接导入、关键词搜索和作者监控获取内容，并将符合条件的内容转入素材生产流程。

### 3. 素材生产与成片管理

人工与自动生产都创建 `compose_task`，由 Cloud Compose Worker 使用模板和合成策略生成正式 `composite_output`。运营按权限直接预览、下载或进入发布，不建设成片池和领取关系。

### 4. 发布管理

支持B站和百家号单条、批量辅助发布，提供执行进度、失败重试、发布链接回填和人工发布补录。

### 5. 互动管理

围绕指定作品或落地链接执行点赞、评论和收藏，支持批量任务、评论模板、AI辅助评论、执行进度和基础风控。

### 6. 数据统计

统一统计内容发现、素材生产、成片、发布、互动和平台效果数据，并支持按权限、游戏、平台、账号、运营人员和时间范围查看。

### 7. 核心闭环

```text
发现内容
→ 转为素材
→ 生成成片
→ 完成发布
→ 执行互动
→ 采集效果数据
→ 形成运营统计
```

各模块的具体对象、状态和业务规则，以第三至第八章的详细说明为准。

## 1.4 用户角色与使用场景

系统采用三类角色：

- 普通运营；
- 高级运营；
- 技术。

具体权限以第三章为准。

### 1. 普通运营

主要负责日常内容运营和任务执行，包括：

- 管理本人账号和本地环境；
- 使用内容和素材；
- 发起 Cloud 合成并查看任务进度；
- 管理、预览和下载本人权限范围内的成片；
- 完成辅助发布；
- 执行点赞、评论和收藏；
- 查看权限范围内的任务和数据。

### 2. 高级运营

主要负责业务管理、资源分配和运营质量控制，包括：

- 管理公共素材、合成策略、模板和自动执行规则；
- 查看负责范围内的合成任务、成片和生产异常；
- 控制自动生产的素材范围与数量上限；
- 查看负责游戏范围内运营数据；
- 处理业务异常和审核事项；
- 协调运营任务和资源。

### 3. 技术

主要负责系统运行、配置和故障处理，包括：

- 管理用户、角色和权限；
- 维护平台适配配置；
- 查看云端和本地Agent状态；
- 处理系统、任务和外部依赖异常；
- 查看技术日志；
- 执行升级、数据修复和环境维护；
- 基于当前职责处理全局业务规则、业务数据和异常。

技术当前同时承担高级运营和技术职责，拥有完整云端业务管理与技术管理权限。所有关键业务修改必须记录操作日志；该权限不能绕过对应运营电脑和本地 Agent 直接访问本地 Browser Profile、Cookie 和文件资源。

## 1.5 V2建设范围与项目边界

### 1.5.1 V2建设范围

V2覆盖：

- 用户、角色和权限管理；
- 社媒账号、Browser Profile和代理管理；
- 抖音内容发现；
- Cloud 人工/自动素材生产；
- 成片管理与全局下载中心；
- B站、百家号辅助发布；
- 点赞、评论和收藏互动；
- 平台效果和运营数据统计；
- Local Agent、Cloud Scheduler / Worker / Crawler、日志和运行状态管理；
- Windows、macOS Intel和macOS Apple Silicon桌面端。

V2重点建立完整运营闭环和稳定执行能力，不追求覆盖所有平台及所有自动化场景。

### 1.5.2 内容发现边界

支持：

- 抖音链接导入；
- 抖音关键词搜索；
- 抖音关键词定时监控；
- 抖音作者定时监控。

不建设：

- B站、小红书和百度内容搜索；
- Excel链接导入；
- 通用竞品账号监控。

### 1.5.3 素材生产边界

支持：

- 人工创建 Cloud 合成任务；
- `compose_strategy.schedule` 自动生产；
- 合成模板和策略；
- 我的成片；
- 原素材/成片下载和发布衔接；
- 失败重试和重复风险提示。

不建设通用视频编辑器、任意拖拽式合成流程和用户自定义脚本执行能力。

### 1.5.4 发布与互动边界

发布支持：

- B站和百家号辅助发布；
- 单条和批量发布；
- 发布状态、失败重试和链接回填；
- 人工发布记录补录。

互动支持：

- 点赞；
- 评论；
- 收藏；
- 评论模板；
- AI辅助评论；
- 批量执行和基础风控。

明确不建设：

- 完全无人值守自动发布；
- 云端可视化浏览器发布；
- 关注、转发、私信；
- 主动搜索作品进行互动；
- 通用多平台发布编排器。

### 1.5.5 本地执行与技术边界

首版本地执行支持Windows与macOS运营电脑，并依赖本地Agent、比特浏览器及相应本地运行环境。macOS需同时兼容Intel（x86_64）和Apple Silicon（arm64）。

桌面客户端、Local Agent 及其他本地依赖应按操作系统和 CPU 架构提供匹配版本。不同系统上的平台自动化和本地文件落地能力必须经过独立兼容验证；M4-M5 的 FFmpeg / FFprobe 由 Cloud Compose Worker 按部署架构单独验证。

首版不建设：

- Linux桌面客户端；
- 桌面关闭后Agent长期常驻；
- 云端远程唤醒运营电脑；
- 无人值守远程控制本地浏览器；
- 本地完整业务数据库；
- 微服务和Kitex内部RPC；
- Kafka、RabbitMQ和分布式调度平台；
- 动态Agent路由和 `execution_scope` 配置表；
- 通用插件市场；
- 可视化工作流编排；
- 大型APM和复杂告警平台。

后续新增平台、自动化或复杂架构，应基于真实业务规模和运行数据重新评估，不在V2阶段提前建设。

## 1.6 项目成功标准

项目成功以业务闭环、运营可用、数据正确和持续运行能力为核心，不以功能数量为唯一标准。

### 1. 业务流程闭环

系统能够完整支撑：

```text
账号与环境准备
→ 内容发现
→ 素材生产
→ 成片生成
→ 发布
→ 互动
→ 数据统计
```

各模块数据可以正常衔接，不需要运营人员反复录入，也不依赖技术人员日常修改数据库。

### 2. 账号与数据正确

系统应保证：

- 用户、比特浏览器账号、Browser Profile、代理和社媒账号关系清晰；
- 比特浏览器身份不一致时能够及时阻断；
- 本地与云端状态差异能够被发现和处理；
- 外部平台执行失败时不写入错误正式结果；
- 批量任务中的单条失败不影响其他成功项。

### 3. 运营效率提升

高频操作具备批量或自动化能力，减少重复录入、重复下载、重复配置和多页面切换。

### 4. 任务过程可控

运营人员能够查看：

- 任务状态和执行进度；
- 成功、失败和中断结果；
- 失败原因；
- 是否可以重试；
- 是否需要人工确认；
- 批量任务的成功和失败数量。

### 5. 简单易用

普通运营无需理解复杂技术架构即可完成主要日常工作。页面结构、操作入口、状态提示和异常处理应清晰一致。

### 6. 系统可持续运营

系统具备：

- 云端和本地运行状态查看；
- Agent和依赖检测；
- 关键操作和任务日志；
- 失败任务集中处理；
- 客户端、Agent和平台配置升级；
- 数据及云端文件基础备份；
- 异常定位和故障恢复。

### 7. V2验收原则

V2达到以下条件即可视为完成核心建设：

1. 第三至第八章确认的核心业务流程可以正常运行；
2. Local Agent 与 Cloud Scheduler / Worker / Crawler 能够完成各自范围内的任务；
3. 用户、账号、Profile和代理关系不存在明显串乱；
4. 内容、素材、成片、发布、互动和统计形成业务闭环；
5. 批量任务支持部分成功和失败项处理；
6. 关键任务具备进度、状态、日志和异常处理能力；
7. 普通运营能够独立完成主要日常操作；
8. 系统具备持续升级和故障排查能力。

在缺少真实运行基线前，第一阶段暂不承诺具体的人力降幅、每日产量、并发账号数和发布成功率。系统正式运行并积累数据后，再制定量化运营和稳定性指标。
