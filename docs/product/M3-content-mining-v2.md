## 1. 目标与产品结构

建设外部内容进入 WT Media 的统一自动化入口，持续获得可供后续生产使用的内容来源。

内容挖掘包含且仅包含三个核心子模块：

- 内容池：人工主动发现入口及所有正式来源内容的统一处理页面。
- 挖掘策略：定义自动发现的业务规则。
- 挖掘任务：查看一次自动执行的记录、统计、状态和错误。

流程：外部来源 → 人工导入/搜索或自动挖掘 → source_content → 人工筛选或按策略规则自动转素材 → material → 后续内容生产。

当前仅实现抖音；未来渠道预留抽象，不承诺本期支持。素材创建仅代表元数据已提交，不能显示视频已下载或可用于合成。

## 2. 内容池的两个主动入口

界面「发现内容」下拉提供两个入口（`ContentPoolPage.vue:444-445`）：

| 入口 | 用户操作与正式写入时点 | 不允许的副作用 |
| --- | --- | --- |
| ID/链接发现 | 输入视频 ID 或分享链接（纯 ID、`douyin.com/video/<id>`、`v.douyin.com` 短链）→ 搜索 → 选择加入内容池 | 未选择结果不写正式来源或素材；失败目标不建残缺来源 |
| 关键词发现 | 输入关键词 → 搜索/加载结果 → 选择加入内容池 | 未选择结果不写正式来源或素材 |

两个入口都走 `POST /content-pool/search`（`ID/链接发现` 用 `query` 模式，`关键词发现` 用 `keyword` 模式），
再由 `POST /content-pool/import-results` 提交入池。原“分享链接”入口名称与实现不符，已按事实改写：
所谓“解析即入池”的意图在 `import-results` 提交时给出，不存在独立的“分享链接”入口。
遗留接口 `POST /content-pool/import-url` 在界面侧**零调用**，仅作兼容保留。

博主搜索（**2026-09-23 暂停**）：原设计为「输入名称/账号/主页 → 定位博主 → 获取作品 → 选择加入内容池」，
不按模糊昵称静默认定唯一作者，未选择作品不入池。该入口本期不交付、不计入 M3 验收，
接口、字段与枚举保留，后续版本再评估。
暂停期间的事实是**服务端硬禁用**——`author-search` 恒返回 `400 / 14006「博主搜索接口维护中」`
（`service/manual_search.go:172-174`），界面亦无入口。暂停期间不得以作者 ID 输入或占位数据宣称该入口可用。

主动入口可用短期技术查询任务，但不创建代表自动挖掘的 crawl_task。界面保留失败条目与已加载结果，
批量独立处理，已成功条目不因其他失败而回滚。链接入池意图在提交时已经给出，不强加第二次“选择导入素材”确认。

数量口径：ID/链接发现单批不超过 100 个目标、按 10 个分批；关键词搜索默认返回 20 条、上限 30 条，有分页。

## 3. 内容池管理与素材转换

列表至少展示封面、标题、平台、游戏、作者、互动（浏览/赞/藏）、来源方式、发布时间、处理状态与操作。

**来源方式**四枚举与界面标签（`ContentPoolPage.vue:414`）：

| 枚举 | 界面标签 |
| --- | --- |
| `link` | ID/链接发现 |
| `search` | 关键词发现 |
| `author` | 博主发现（暂停期间不产出） |
| `strategy` | 挖掘策略 |

**内容池处理状态**三值（`ContentPoolPage.vue:467`）：

| 状态 | 说明 |
| --- | --- |
| pending | 待处理 |
| material_created | 已转素材 |
| ignored | 已忽略 |

**挖掘任务项**的处理状态另有六值，属于任务范畴而非内容池状态（见第 5 节）。

支持列表/详情、条件检索、单条/批量转素材、忽略与恢复。恢复不删除历史处理事实；不能借恢复生成重复素材。外部可访问性独立于处理状态，外部作品下架不自动改变人工处理状态。

**审核模式**：内容池提供逐条审核队列（`ContentPoolPage.vue:32-38, 598`），按待处理队列依次处理，
每条可「转素材并下一条」「忽略并下一条」或「跳过」，用于替代批量勾选的高效流转场景。

**素材库**不是独立页面，而是同一页面在 `/material-library` 路由下的**只读模式**
（`ContentPoolPage.vue:21, 114`）：强制按 `status=material_created` 过滤，隐藏发现入口、统计卡与状态筛选，
只保留查看。素材库最小只读能力即由此满足。

转素材：

1. 校验当前用户对来源的处理权限。
2. 在单条事务中锁定来源、检查已有 material、创建或关联 material、更新来源状态并记录处理人/时间。
3. 创建失败不把来源标为 material_created；允许重试。
4. 批量逐条独立提交，返回每条真实结果；批量上限 500 条。
5. 素材库最小只读列表/详情能读回来源关联及精简不可变快照。

数据库规则：`source_content.team_id` 必填；同一团队内 unique(team_id, platform, platform_content_id)；unique(material.source_content_id)。source_content 不反向保存 material_id。跨团队同作品允许独立业务记录。

重复发现只更新允许变化的最新来源信息，不覆盖素材业务字段、不可变来源快照、人工忽略状态和首次来源。自动发现不会恢复 ignored；人工恢复/转素材必须显式操作。跨运营范围的忽略语义仍需确认。

> 2026-09-23 实测：8 线程并发导入同一条目库中只落 1 行、8 路并发转素材只生成 1 个 material
> 且全库无重复 `source_content_id`，唯一约束兜底有效。

## 4. 挖掘策略

统一对象 discovery_strategy：

- strategy_type：本期 keyword；`author` 已暂停（取值保留，后续版本再评估）；
- channel_type：引用 content_channel，当前仅抖音；
- 配置字段：`keywords`（列表）/`keyword`（单关键词，二者取其一）、`author` 与 `author_id`（随 `author` 暂停延后）、
  `game_id`（必填，默认 `other`）、`platform`（本期仅 `douyin`）；
- 名称、启停状态（稳定作者身份随 `author` 暂停延后）；
- 页面可配置关联的执行周期，并展示最近执行时间、执行记录；
- 关键词与博主策略共用生命周期，不分别建 keyword_strategy / author_strategy。该约束保留；暂停期间只有 keyword 在使用。

策略配置与执行分离：

- 策略定义“找什么”；执行周期描述“何时触发”。
- Cloud Scheduler 负责时间计算与触发，任务承担一次执行记录，Cloud Crawler 执行外部请求；M3 不创建 Agent 任务，也不由 Desktop 参与。
- 页面显示“每天 09:00”或“每若干小时”等业务配置，不提供 Cron 编辑器、节点编排或可视化调度器。
- **周期语法已确定为三种**：`manual`（手动执行）、`interval:<N>`（每 N 分钟）、`daily HH:MM`（每天固定时刻）；
  界面分别显示为「手动执行」「每 N 分钟」「每天 HH:MM」。时区默认 `Asia/Shanghai`。
- **启用策略不触发立即执行**：`setStrategyStatus` 不创建任务，首次触发等下一个计划窗口。
- 编辑只影响后续创建任务；历史任务保留当次配置快照。
- 停用后不创建新周期任务，在途任务按已记录快照完成；历史策略/任务/来源保留。

> 2026-09-23 实测偏离（缺陷 D2）：`schedule` 缺少服务端格式校验，`schedule="garbage"` 会被接受并入库，
> 界面原样显示为执行周期「garbage」，且该策略永远不会被触发。支持的语法以上表为准，
> “非法取值应被拒绝”是应有行为，当前未达标。

策略可配置自动转素材。规则字段：

| 字段 | 含义 |
| --- | --- |
| `auto_material` | 是否自动转素材；关闭时策略结果全部进入内容池 |
| `material_rule` | `AND` 或 `OR`；其他取值必须拒绝，不得猜测或降级 |
| 阈值 | `like_threshold`、`favorite_threshold`；大于 0 参与规则，小于等于 0 忽略 |

`auto_material` 为真时至少需要一个正阈值；`AND` 要求全部正阈值通过，`OR` 要求任一通过。命中的发现结果入池后按规则自动转为 material，未命中的留在内容池等待人工处理。任务统计须分别显示发现、新增、自动转素材与待审核数量；自动入池不等于已完成生产。

自动转素材失败不得记为成功：来源留在待处理并记录失败原因，可重试（见第 3 节）。条件集合本期就是上表四项——开关、连接方式与点赞/收藏两个阈值。发布时间、时长、作者、是否带货等其他条件不属本期范围；新增条件须先有明确产品决策，不得按渠道或策略类型私自扩展，也不得把「未配置阈值」解释为「全部命中」。

> 2026-09-23 更新：本版原写“不提供自动转素材开关”，与实施结果冲突。用户已确认自动转素材为 M3 范围内的正式能力，本节按确认结果改写；ADR-0013 第 3 条随之增补。PRD 融合按 `delivery/milestones/README.md` 的 Milestone-first 规则留待 M3 完整验收后处理。

旧版高级筛选、两种作者首次模式、立即执行/人工任务重试按钮不因旧文档存在而自动加入新页面，是否保留须明确决策。

## 5. 挖掘任务

crawl_task 记录一次脚本或后台调度触发的自动挖掘执行，不承担业务配置或工作流定义。必须能追溯策略、当次配置、渠道、触发来源及计划时间。

业务状态五种：

| 状态 | 含义 | 界面标签 |
| --- | --- | --- |
| pending | 已创建，待执行 | 待执行 |
| running | 执行中 | 执行中 |
| success | 成功 | 成功 |
| failed | 失败 | 失败 |
| partial_success | 部分成功：至少一项失败且至少一项成功入池 | 部分成功 |

`partial_success` 的精确判定：记 `processed = added + duplicate + pending + auto_materialized`；
若 `failed > 0`，则 `processed > 0` 时为 `partial_success`、`processed == 0` 时为 `failed`；
否则为 `success`。注意人工关键词任务走 `import-results`，各条目要么成功要么整体失败，
**无法达到 `partial_success`**；该状态主要来自按 ID/链接逐目标抓取的路径。

多关键词或批量作品部分失败时，不丢弃已成功入池结果；应显示成功事实、失败数量及原因。这类部分失败由 `partial_success` 表达，界面显示为“部分成功”，可仅对失败项重新执行；不让技术 task 成功直接决定业务 success。

> 2026-09-23 更新：本版原写“不新增 partial 第五态”。该状态已端到端落地并有真实证据（任务状态、失败项重试），本节按实施事实改写。

**失败项重试**：仅 `failed` 与 `partial_success` 终态的任务可重试（`retryFailed`）；重试创建**新任务**，
新任务的 `parent_task_id` 指向原任务，`snapshot.retry_items` 只包含失败项；**原任务不可变**，
其终态与统计不被重试改写。非失败任务、或没有失败项时重试返回 `400 / 14008`。

**任务项处理状态**六值（`CrawlTasksPage.vue:198`）：

| 状态 | 界面标签 |
| --- | --- |
| `unprocessed` | 未入池 |
| `pending` | 待审核 |
| `auto_materialized` | 自动转素材 |
| `material_failed` | 转素材失败 |
| `duplicate` | 重复 |
| `failed` | 失败 |

任务列表/详情包含：

- 任务 ID、策略名称、渠道、任务类型、开始/结束时间、状态；
- 统计数字、错误原因、执行日志和必要的阶段摘要。

**统计口径分两层**。落库 `stats_json` 七项：
`scanned`（扫描）、`found`（发现）、`added`（新增）、`duplicate`（重复）、`failed`（失败）、
`auto_materialized`（自动转素材）、`pending`（待审核）。
界面列表只展示其中五项：`发现 N · 新增 N · 自动素材 N · 待审核 N · 失败 N`
（`CrawlTasksPage.vue:176`）；`scanned` 与 `duplicate` 保留在数据层与详情中。

统计须区分单位：接口失败不等同于“1 条作品失败”；关键词级、作品级数量不可混加。明确计数口径、未扫描范围、重试去重和并发新增归属后再定正式合同，不能仅让界面数字相加好看。

**调度与防重**：同策略已有 pending/running 任务时不重复排队；同策略同计划周期幂等防重；
跨策略发现同作品由全局唯一约束兜底。防重有两层——服务端比较计划窗口键，
加数据库唯一键 `uq_crawl_tasks_strategy_schedule (strategy_id, schedule_key)`。

> 2026-09-23 实测偏离（缺陷 D3）：手工 `POST /discovery-strategies/:id/run` 连调两次会产生 2 条 pending 任务，
> 因为该路径传入空计划键，唯一索引不拦空值。“不重复排队”仍是要求，当前在手工路径上未达标；
> 周期触发路径的防重经实测有效。

> 2026-09-23 实测偏离（缺陷 D-scheduler）：独立 `cmd/discovery-scheduler` 进程首次 tick 即 panic 退出
> （`schedulerResourcePlan()` 缺 `clientsResource()`），因此**本期内没有任何进程在执行真实周期调度**。
> 第 8 节“必须能通过真实周期触发”的要求未达标，不能因为调度语义（窗口键、双层防重）正确就视为已交付。

重启恢复不重复入池、不篡改终态统计，不批量补跑全部历史周期。有限网络重试属于运行保障，不等于建设用户自定义流程。

不建设 crawl_result、全量任务作品历史、多版本 raw_json、执行中人工取消或新工作流状态机。

## 6. 渠道扩展与运行链路

content_channel 是受控渠道能力抽象；不要求本期增加渠道后台或独立数据库表。channel_type 与 strategy_type 分别表达来源渠道和发现方式；不得把二者混成 douyin_keyword 一类组合业务类型。

至少能描述：链接解析、内容详情、关键词搜索、作者查找/作品列表是否受支持。作者查找/作品列表本期为暂停能力：能力描述保留，但不作为 M3 验收项。未来接入新渠道允许新增适配实现和合同，但不重复建设内容池、策略和任务业务模型；不承诺未来零代码修改。

**本期交付的是功能链路，不是独立视图**：策略执行 → 生成 crawl_task → Worker 领取执行 →
结果写入内容池（含按规则自动转素材）。该链路以真实业务记录为准，各段都有真实数据库读回。
素材未生成时展示未转素材，不将自动入池画成已完成生产。

> 2026-09-23 更新：本版原要求「业务流转视图只读展示策略 → 定时触发 → 任务 → 内容池 → 素材」。
> 用户 2026-09-23 裁定该项「就当没有」——**本期不交付独立的只读业务流转视图**，后续版本再评估。
> 上述功能链路是数据流事实，不是视图交付。ADR-0013 第 8 条中「不允许编排、拖拽、条件分支或任意脚本」
> 的**禁止性**约束保持不变：被移除的只是“必须提供一个只读视图”这条交付要求，不是对新增工作流能力的解禁。

参考图用于页面结构、层级和 WT 视觉规范；B站、快手等预留内容不可点击执行，图片中的数据不作为真实证据。

## 7. 边界与权限

不做视频下载、文件存储/校验、剪辑、AI 评分、自动生产、发布、互动和数据分析；不建设通用工作流引擎、任意脚本执行、渠道插件市场或其他平台的真实采集。

权限沿用三角色框架。按 ADR-0014，M3 内容按业务团队隔离：同团队运营全量可见，管理员跨团队可见。
**游戏维度已纳入本期**（ADR-0014 已于 2026-09-23 增补）：`discovery_strategies` 与
`source_contents` 均带 `game_id`，迁移 `20260922_035/036` 已把既有行回填为 `other`；
策略与内容池界面均有「游戏」列。服务端必须执行授权，不能由客户端过滤替代。

> 2026-09-23 实测：operator 跨团队读/改/跑策略均返回 `403 / 11003`；
> operator 的任务与策略列表只含本团队；admin 可见多团队。

凭据留在服务端；内容详情和日志不得泄露供应方凭据；原始数据与技术错误按权限脱敏。
