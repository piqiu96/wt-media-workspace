# PRD 写作规范与 AI 编写指引

**先确定读者要理解的结论与关系，再选择表达形式，最后写文字。** 可读性优化必须减少读者自行归类、推导和来回查找的工作；拆段、加标题、换成表格本身不算完成。

适用于内容运营平台 PRD 的新建、补充、修改与整理。本规范通过[实践规范索引](README.md)按任务加载。原型、正式需求与本次已确认变更提供业务事实；写作整理不授权改变功能、交互或规则。

## 1. 写作前，先组织信息

复杂章节先完成以下判断，再动笔。判断过程用于组织草稿，不作为固定标题或分析过程写进正式 PRD。

1. **确定核心结论。** 本节回答读者的哪个问题？用一句话给出最重要的答案。
2. **划分主题。** 将事实归入职责明确的主题。同级内容按同一维度分类；不把页面、状态、权限、指标和异常任意并列。例如成片占用、账号执行顺序、平台额度、资源恢复各有归属。
3. **建立关系。** 判断是先后流程、状态与动作、条件分支、数量关系，还是简单事实；保留“同时满足／任一满足”、判断优先级及适用范围。
4. **安放例外。** 决定哪些条件影响当前选择，哪些属于后续恢复，哪些是共用规则。错误位置的信息移回所属主题，不能因为“必须保留”就留在原处。
5. **选择主表达。** 从第 3 节选能直接展示关系的形式，再写图表未覆盖的必要文字。

如果只能列出原文顺序和若干小标题，却说不清分类或流程关系，继续整理信息，不开始改写。

## 2. 用金字塔组织阅读顺序

**结论先行，同级分类，下层解释。** 模块先让读者理解业务，页面先让读者找到用途、操作和直接反馈，再进入必要规则与特殊情况。

- **先给答案。** 首句说明核心规则，图表给出判断依据或操作路径；不先堆定义、限制和背景。
- **同级有共同维度。** 状态按状态列，阶段按先后列，条件按判断顺序列；主题不同则分开归属，不强行装入同一表。
- **流程体现递进。** 明确触发、分支和去向；条件有先后时，展示检查顺序，避免让读者自己猜哪个限制优先。
- **例外有位置。** 影响当前决策的限制就近出现，恢复与特殊处理放在正常路径之后；不让读者先读完全部边界才能理解功能。
- **抽象规则落到实例。** 用具体对象或数字说明容易混淆的边界；实例仅代入已有规则，不能暗含新前提或成为新规则。

这是一套组织原则，不是每页必须具备的章节模板。简单规则一句话说清即可。

## 3. 按关系选表达形式

复杂逻辑优先用能独立解释主要关系的图表。**只选择有助于回答读者问题的形式，不按“每节一图一表”凑数量。**

| 读者要理解的关系 | 主表达 | 文字只补什么 |
| --- | --- | --- |
| 先做什么、何时分支、资源如何取得与释放 | 流程图；确有状态迁移问题时用状态图 | 图中放不下的适用范围、证据或例外 |
| 某个状态能做哪些操作 | 状态动作矩阵 | 矩阵未展开的共用条件或单独处理流程 |
| 多个条件决定下一步 | 决策表或条件分支图，通常选其一 | 分母、阈值等必要定义 |
| 多个指标、数量或资源上限容易混淆 | 简短定义／公式＋具体数字案例 | 案例没有覆盖的边界，如未知值或零分母 |
| 多个字段需要并列查阅 | 字段表 | 不能在单元格中清楚表达的条件 |
| 单个动作、字段或简单规则 | 一句话或短步骤 | 无需为了规范再配图表 |

图表本身须能读懂：节点和行列使用业务用语；条件写清与／或、等号边界和先后顺序；矩阵说明条件项和空白的含义。图过大、表过宽或单元格塞满段落时，先检查是否混入不同主题。

## 4. 修改原文与消除重复

每次修改现有 PRD，执行以下动作：

1. **定位并归类。** 读取受影响章节及直接关联规则，按第 1 节重新组织，不从“逐句换一种说法”开始。
2. **融入原章节。** 重写受影响段落，移走错位内容，合并同类信息，同时删除被替代的旧文；不在末尾持续追加“补充说明”。
3. **一项信息有一个主要载体。** 图已讲清的流程不再逐步复述；矩阵已列明的动作不再逐状态解释；实例已说明的边界不再追加同义长文。文字只填补尚未表达的信息。
4. **复用既有规范。** 正式 PRD 不重复通用弹窗关闭、输入反馈和按钮视觉；只写业务差异。其他页面可引用规则，保留当前决策必需的简短结论。
5. **对照业务含义。** 检查迁移前后的条件、动作、反馈、限制、指标与例外，保留原型阶段、按钮与状态名称；不靠删规则压字数，不自行补需求。

主题不同时可以移位，业务含义必须有去处；不为每次修改建立迁移台账。明显矛盾只简要列为待确认，不自行折中或扩大为业务审计。

**交付前清理正文。** PRD 只保留当前有效的产品事实，不保留中间分析、修改过程、讨论历史、被替代的方案或“改进说明”等写作自评。多轮修改后重新整合正文，不持续追加补丁；交付前删除已解决问题的记录、重复解释和无独立信息价值的内容。影响业务含义的未解决问题可以单列待确认，相关规则不得擅自删除或改写。

## 5. 必须纠正的写法

| 错误做法 | 必须改成 |
| --- | --- |
| 长段落拆成五个带标题的短段落就交付 | 先明确主结论、主题与关系，再选择主表达；无法减少读者推导工作则继续整理 |
| 原文讲到什么就依次保留什么 | 按主题重新归属，按分类或流程组织，移除已被图表承载的复述 |
| 流程图后再写一遍完整操作步骤 | 图作为主路径，正文只写图外条件；需要逐步指引时直接选择步骤，不重复两套 |
| 状态矩阵后逐状态展开同样动作 | 矩阵用于查动作；另文仅说明矩阵未覆盖的处理流程 |
| 用多个表格堆放同一主题的散乱信息 | 先建立条件关系，合成可判断的决策表；主题不同则拆开归属 |
| “未达成、已结束、可用资源”等抽象解释不断追加 | 给出明确口径，再代入一组具体业务数字 |
| 为精简删掉必要限制，或把未知当零 | 保留条件及未知、零分母等边界，删除重复解释 |
| 为了完整增加章节、图表或常识提示 | 简单事实直接写，已有规范直接引用，无独立信息价值就删除 |

## 6. AI 执行与验收

**编写前：** 理解现有原型与已提供事实，确定修改范围和章节位置；复杂章节先完成第 1 节的信息组织，不默认重新核查全部业务。

**编写时：** 按“结论 → 主图表／简洁说明 → 必要补充”呈现；用具体主语和动作，保持术语一致。一个段落只解释一件未被其他载体讲清的事，不强制固定标题数量。

**交付前：**

- [ ] 只看首句，能否在几秒内说出核心结论？
- [ ] 复杂主题能否通过一张主图或表理解主要逻辑？简单主题是否已用一句话说清？
- [ ] 同级内容是否按一致维度分类，流程或判断是否按顺序递进？
- [ ] 图表后是否仍有完整复述，矩阵后是否仍逐状态重复，实例后是否仍有同义长解释？
- [ ] 是否混入其他主题，存在长段文字或需要读者自行拼接的条件？
- [ ] **逐段删除没有独立信息价值的解释；必要条件、定义和例外保留或改用更有效的表达。**
- [ ] 业务含义是否完整，旧文与补丁是否已合并，引用与修改范围是否正确？

未通过的项直接修正文档，不在末尾追加解释。交付时只说明改动和必要待确认项，写作分析留在评审材料，不进入正式 PRD。
