# PRD 写作规范与 AI 编写指引

适用于内容运营平台的新建、补充、修改和可读性优化任务。目标是让读者快速理解功能、完成操作、找到必要规则，并避免 PRD 在多次修改后不断堆叠。

本文件为本轮评审稿，尚未接入项目入口。业务事实以现有原型、正式需求和本次已确认变更为依据；写作优化本身不授权增删功能、改变交互或调整规则。

## 1. 按读者理解顺序组织

默认顺序是：**理解业务 → 理解页面 → 理解操作 → 理解必要规则与特殊情况。**

- 模块开头说明服务谁、解决什么问题，以及与相邻模块的关系。
- 页面围绕用途、展示信息、用户操作和直接反馈展开；先写正常流程。
- 限制按理解需要就近说明。影响当前选择的条件放在操作旁，恢复与异常处理放在正常流程之后。
- 跨页面共用的规则集中维护；当前操作离不开的结论仍就近简述，避免读者反复跳转。
- 一个章节回答一个明确问题。标题使用读者能理解的功能、页面或动作，避免将多个主题拼成抽象标题。

层次通常为“模块 → 功能／页面 → 交互行为 → 必要规则”，只使用当前内容需要的层级。简单页面可以一段说明加一张表；复杂流程再分步骤。不得为凑齐模板增加空泛标题。

## 2. 修改已有 PRD 的强制动作

每次修改都执行下表。范围以本次受影响内容为限，不借机开展全章业务审计。

| 动作 | 必须怎么做 | 完成时怎么检查 |
| --- | --- | --- |
| 定位原文 | 读取目标章节及直接关联规则，先找到现有归属 | 新内容有明确位置，没有另建同义章节 |
| 融入变更 | 新需求优先写入原章节；修改功能时重组受影响段落 | 删除新增段落后，不会留下与新内容冲突的旧说法 |
| 合并同类信息 | 把同一条件、动作或结果合并到合适位置，移除被替代的重复内容 | 同一事实不需要在多处分别修改 |
| 保留业务含义 | 对照修改前内容，检查触发条件、动作、结果、限制、指标和例外 | 没有为了缩短文本而漏掉条件，也没有增加推断出的规则 |
| 按阅读需要排列 | 先呈现操作及直接反馈，再安放相关限制和异常 | 能连续读懂正常操作，异常也有明确去处 |
| 复用全局规范 | 常规交互、反馈和视觉引用已有规范；仅写业务特例 | 没有逐页重复关闭弹窗、输入反馈或通用按钮样式 |
| 重读完整局部 | 连同变更前后的段落、表格和引用一起阅读 | 术语、条件、标题和链接一致，没有“原文＋补丁” |

“补充说明”“另需注意”等段落不能作为持续维护方式。只有内容确实没有合适归属时，才新增有明确职责的章节。

发现直接影响表述的明显矛盾时，简要标记位置与待确认事项；继续处理无关内容，不自行折中出新规则，不扩展为历史评审或规则审计。

## 3. 按信息类型选择表达形式

页面应让读者找到：做什么、看什么、如何操作、操作后怎样、必须知道哪些条件。这五项是检查问题，不是五个必备标题。

| 内容 | 优先写法 | 使用边界 |
| --- | --- | --- |
| 简单列表／详情 | 用途短段落，随后说明展示、筛选与支持动作 | 已有共用行为不重述；只读详情不凭空补操作 |
| 多阶段新建／配置 | 按原型阶段分步，每步说明操作与反馈，交代保存或创建结果 | 不因整理文档新增阶段或更改按钮 |
| 多个字段 | 字段表，列出含义、输入及必要条件 | 单个简单字段直接说明，不建空泛大表 |
| 状态与动作 | 状态动作表，区分入口、可用动作和关键条件 | 以真实状态、按钮为准；进展提示与业务结果不要混成一套状态 |
| 多条件判断 | 独立条件列表或分支表 | 保留“同时满足”与“满足任一”的关系 |
| 简单交互／少量规则 | 简洁段落或短列表 | 不把一句话拆成大型表格 |

流程按用户做事的顺序描述。仅在影响用户选择、等待或下一步时说明系统处理；底层技术保障机制不冒充用户操作。

## 4. 语言与取舍

- **一个段落一件事。** 页面信息、操作、结果和例外混在一起时，按含义拆开。
- **用具体主语和动词。** 优先写“运营点击……，系统展示……”，少用“进行相关处理”“满足相应条件”等模糊表达。
- **先写正向行为。** 先说明可以做什么、会发生什么，再说明必要限制；权限、安全与不可逆条件必须保留。
- **拆开多重条件。** 一个句子含多个独立动作、条件分支或例外时改用短句、步骤或条件列表；不设机械字数上限。
- **术语与界面一致。** 同一对象、状态、字段和按钮使用同一名称，不为文风变化创造同义称呼。
- **正文只写当前结论。** 需要时用一句话说明取舍；不写讨论过程、废弃方案或反复自证的解释。
- **复杂度与业务匹配。** 标题、表格和说明必须帮助读者定位信息；删除没有独立信息价值的内容，不删除必要业务条件。

## 5. 写作反模式与正确写法

以下句式仅用于说明写法，不定义任何业务能力。

| 不推荐的模式 | 正确写法 |
| --- | --- |
| 原文后不断追加：“补充：另需……；再次补充……” | 回到对应操作，合并为一份当前规则，移除被替代的说法 |
| 超长段落同时讲字段、提交、并发和失败恢复 | 分别写“填写内容”“提交结果”“失败后如何继续”，只保留有实际内容的分组 |
| 一句话容纳多个条件：“当 A 且 B，除非 C，否则……” | 用“同时满足 A、B 时可操作；出现 C 时……”明确条件关系 |
| 操作与异常交叉：“点击提交；若失败……；成功后进入……” | 先写“提交成功后进入……”，再写失败的保留与恢复方式 |
| 连续否定：“不能修改、不得重试、不允许……” | 先说明当前可用动作，再集中保留影响操作的禁止条件 |
| 同一规则在列表、详情、弹窗全文重复 | 完整规则维护一次，各处保留当前动作所需结论与必要引用 |
| 只有边界集合，没有正常路径 | 先按“选择 → 配置 → 确认”写清实际路径，再说明适用的边界 |
| 把技术机制写成用户步骤：“先完成幂等与事务校验” | 写用户结果：“重复提交不会重复创建；创建失败不遗留部分记录” |
| 每页机械生成五个标题，或把所有文字变成表格 | 简单页面直接说明；步骤、字段、状态分别选合适形式 |
| 为显得完整补常识、提示或推测能力 | 引用全局规范；无业务差异的信息省略，未确认能力不写成需求 |

## 6. AI 编写与自检

**编写前**

1. 理解任务涉及的现有原型和已提供事实，确定本次功能、页面与修改范围；按需阅读，不默认重新核查全部业务。
2. 找到现有章节和规则归属，决定复用、重组或必要新增的位置。
3. 保留已确认的阶段、按钮、状态和条件。信息缺失不能自行补成新需求。

**编写时**

1. 先写正常操作和直接反馈，再补充理解所需的规则与异常。
2. 修改已有功能时直接整理受影响内容，同时合并重复项；不以文末补丁代替修改。
3. 采用本文件第 3 节中的适当形式，保持术语和同类信息写法一致；不强制统一标题数量。

**提交前**

- [ ] 能快速知道功能用途，并顺着文档完成正常操作。
- [ ] 页面信息、入口、动作与结果容易找到；状态与动作一致。
- [ ] 受影响旧段落已重组，没有矛盾旧文、重复补充或散落规则。
- [ ] 多条件关系、必要限制和例外完整，未增删业务含义。
- [ ] 没有无必要长句、常识说明、重复全局规范或机械标题。
- [ ] 正文只表达当前结论，引用准确，修改范围与授权一致。

不通过的项直接修正文档，不在末尾追加解释来弥补。交付时简述修改位置与需评审事项，不复制一遍正文。
