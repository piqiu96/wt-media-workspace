# 文档与知识事实治理规范

## 1. 目的与适用范围

本规范定义 WT Media 文档的分类、事实归属、冲突裁定、生命周期、历史处置、默认加载边界、关闭检查和自动校验。它适用于 Workspace 中的产品、工程、规范、契约、决策、交付记录和 AI 产出；运行仓按各自 `AGENT-INDEX.md` 执行，跨仓系统事实仍由 Workspace 维护。

八条不可协商的规则：

1. Git 保存事实；聊天、AI 记忆和临时总结不是事实源。
2. 当前事实写入正式文档，一件事实只有一个归属位置。
3. 历史默认退场；只有证明有持续追溯价值才保留。
4. 不设“产品 > 工程 > 实现”的全局顺序；按事实归属裁定。
5. 用户本轮明确裁定优先，但必须回写对应正式事实源后才长期生效。
6. 代码只证明“现在怎么实现”，不能自行改变正式需求。
7. 关闭意味着把当前事实回写正式文档，并让过程记录退出默认上下文。
8. 不建立第二套 Delivery、状态或上下文事实。

## 2. 四类内容与目录职责

| 类型 | 位置 | 回答的问题 | 最小内容 | 不写什么 |
| --- | --- | --- | --- | --- |
| 产品需求 | `docs/product/` | 用户要什么、什么算完成 | 背景、用户问题、用户路径、业务规则、边界、验收 | 技术方案、执行进度、实现细节 |
| 工程设计 | `docs/engineering/` | 系统现在如何分工和实现 | 当前有效设计、设计理由、边界 | 实施计划、CHG 编号、过程史、已废弃方案 |
| 规范与契约 | `docs/standards/`、`docs/contracts/`、`docs/decisions/`、`docs/devops/`、`docs/reference/` | 必须遵守什么、由谁执行 | 可执行规则、owner、执行或校验方式 | 阶段报告、过程叙述、未确认草案 |
| 执行记录 | `delivery/active/`、`delivery/planned/`、`delivery/milestones/`、`delivery/completed/`、`delivery/reports/` | 这次交付做了什么、验收到什么程度 | CHG 的 `Change` / `Done When`、验证、阻塞和结论 | 长期产品事实、第二份状态源 |

产品需求一篇只回答一个需求，工程设计一篇只回答一个设计问题。规范与契约写成可执行规则，声明 owner 和执行方式；只有兼容性需要时才升版本，不因普通文字修订制造新版本。

目录职责固定如下：

- `docs/` 只保存当前有效事实，不长期保留旧版本和过程历史；`docs/superpowers/` 是待逐项处置的旧集合，不作为新增事实的落点。
- `delivery/active/` 只保存当前正在执行的 CHG。
- `delivery/planned/` 保存已确认但尚未启动的交付项，不属于历史。
- `delivery/milestones/` 保存当前 Milestone 的业务闭环定义，不存开发流水账。
- `delivery/completed/` 保存确有追溯价值的已完成交付记录，默认不进入 AI 上下文。
- `delivery/reports/` 保存阶段审计和专项检查报告；结论必须回写正式事实源。
- `docs/superpowers/` 是旧计划、旧设计的混合集合，不因目录名自动视为历史；按内容判断，默认不加载。

不新增统一 `archive/`，也不新增 Draft / Current / Superseded / Historical 等长期文档状态字段。能由目录位置表达的生命周期，不再增加状态。

## 3. 当前事实、临时标记与历史

- `docs/` 中的内容必须回答当前问题。已被新事实完全吸收的旧版本不留在 `docs/`。
- 新事实替换旧事实时，直接修改当前正式文档；旧版本由 Git 保存，不额外保留副本。
- 旧文档暂时不能删除、且可能仍被外部引用时，才在文首使用临时标记 `SUPERSEDED`，并写明可解析的替代文档。
- `SUPERSEDED` 不是长期状态，也不是“永久保留旧版本”的理由；引用迁移完成后应删除或移出当前文档树。
- 历史文档、`delivery/completed/` 和旧 AI 分析只用于追溯，不默认加载，也不参与当前冲突裁定。
- 已归档记录保持原样，不重写正文、不重排、不做“内容整合”。

## 4. 冲突裁定

1. 先确定争议事实属于哪个领域，再由该领域的正式事实源裁定：
   - 产品能力、业务对象、状态、权限、验收 → 业务 PRD / 页面正式规格；
   - 系统职责、模块边界、数据归属 → Engineering；
   - API、Schema、状态枚举、错误码 → Contract；
   - 页面信息架构 → AdminUI 规范；
   - 交互与反馈 → 交互规范；
   - 视觉与组件实现 → 前端视觉规范；
   - 当前实际行为 → 代码只证明“现在怎么实现”，不能自行改变正式需求。
2. 同一领域内部：当前正式事实 > 上层摘要 > CHG 临时描述 > 历史 / `SUPERSEDED` / AI 临时内容。
3. 用户本轮明确裁定优先于已有描述，但必须回写对应正式事实源；回写前只视为本次已确认变更，聊天不成为长期事实源。
4. 不同领域真正冲突时，不允许 AI 自行综合第三种解释。必须列出冲突事实、各自来源、事实归属领域，以及建议修改的正式来源。
5. 代码与正式文档不一致时，先判定“代码尚未实现需求”还是“文档已经过期”，不能默认以现状代码为准。
6. 历史文档、已完成 CHG、旧 AI 分析只用于追溯，不参与当前冲突裁定。

## 5. 默认加载边界与预算

默认不加载：

- `delivery/completed/`、`delivery/reports/`；
- 历史分析、旧 Evidence、旧计划；
- `docs/superpowers/` 中的过程和分析内容；
- 全量 Skills 源码；
- 全量代码、构建产物、缓存、临时和生成目录。

读取顺序由 `AGENT-INDEX.md` §4 负责。任务确实需要扩大范围时，说明要解决的问题并只读取相关部分。

`docs/superpowers/` 中的单篇内容只有在当前任务明确引用、且被判断为仍然有效的方法时才读取。仍然有效的方法应提升到 `docs/`，旧副本按历史处置规则退场。

`.ai/CURRENT_CONTEXT.md` 是可再生的导航快照，硬上限为 8000 字符，由 `scripts/verify/verify_ai_workspace.py` 校验。单任务 20 篇 / 20k 字是阅读目标，不是新的硬门禁。

## 6. CHG 与 Milestone 关闭检查

CHG 完成前确认：

- `Done When` 全部满足，必要验证通过并留下读数；
- 当前产品、工程、Contract、Decision 事实已回写各自正式文档；
- 没有残留的过期“当前”描述，`SUPERSEDED` 指针已处理；
- 相关索引已更新，链接可解析；
- 过程记录（`plan.md`、`checkpoint.md`、`evidence/`）已退出默认上下文；只有确有追溯价值时才移入 `delivery/completed/`；
- 状态只写在 `change.md`，`delivery/LEDGER.md` 同步，不产生第二份状态。

Milestone 关闭前确认：

- 目标、业务闭环和验收已闭环；
- 没有遗留的 Active CHG 或未收口阻塞；
- 下一 Milestone 的范围和依赖清楚；
- 闭环卡只保留当前业务事实，不写开发流水账。

CHG 状态词以 `delivery/MASTER_IMPLEMENTATION_PLAN.md` §3 和 `scripts/verify/verify_product_master_alignment.py` 为准；ADR 的 Accepted / Superseded 约定以 `docs/decisions/README.md` 为准。本规范不复制这两套词表。

## 7. 历史内容处置与删除

按以下顺序处置历史内容：

1. 已被新事实完全吸收、没有独立追溯价值 → 删除；Git 已能承担追溯。
2. 执行历史有明确审计或证据价值 → `delivery/completed/`。
3. 阶段性审计报告仍有独立价值 → `delivery/reports/`。
4. 暂时因外部引用无法删除 → 临时标记 `SUPERSEDED` 并指向替代文档，引用迁移后删除。
5. Git / PR 已能充分承担追溯 → 不额外保存历史副本。

删除前先检查引用。仍有外部引用且无法立即迁移时，使用临时标记；没有引用且无审计价值时直接删除。删除整个归档记录必须遵守 `delivery/completed/README.md` 的边界，并由有权限的 owner 确认。

## 8. 定期治理

- **每周**：检查本周新增或修改的文档是否有明确 owner、正确目录、可解析索引；确认没有把计划、进度或临时分析写进 `docs/`。
- **每月**：审计 `docs/superpowers/`、`delivery/reports/` 和新增的 `delivery/completed/` 记录；删除已无价值的内容，提升仍然有效的方法，修正过期路径和重复定义。
- **每次发布**：确认产品、工程、Contract、Decision 的当前事实已反映到正式文档；确认索引、契约和状态词一致；确认没有未收口的 Active CHG 被误当作已发布事实。

定期治理的结论回写正式事实源，不新增报告作为第二事实。

## 9. 责任

- **产品 owner**：确认产品需求、业务规则和验收事实。
- **技术 owner**：确认 Engineering、Contract、Decision 和实现边界。
- **AI**：先读事实源再回答；不发明第三种解释；发现冲突时列出冲突和归属；用户裁定后回写正式文档。
- **Reviewer**：检查事实、范围和验证，不只检查文字是否通顺。
- **Delivery owner**：维护 CHG 状态、验证记录和关闭归档，不建立第二套状态。

## 10. AI 对话产物与 Review 结论落点

- 分析结论 → 如果长期有效，写入 Product、Engineering、Contract 或 Decision；否则不保存。
- 实施计划 → 当前 CHG 的 `plan.md`。
- 工作进度和交接 → 当前 CHG 的 `checkpoint.md`。
- 验证证据 → 当前 CHG 的 `evidence/`。
- 架构或技术决策 → `docs/decisions/` 的 ADR。
- 阶段总结 → 产品或工程正式文档；聊天记录不作为存档。
- 一次性代码发现 → PR / Review 评论；需要跟踪时再建 CHG 或登记到当前 CHG。
- Review 结论只有在回写正式事实源后才成为项目事实；一次性评论留在 PR，不复制成长期文档。
- AI 记忆和对话摘要不能作为唯一事实源。

## 11. 代码注释边界

代码注释只保留“为什么这样做”以及代码本身看不出的约束、取舍和风险。不写变更史、辩护稿、复述代码或与实现无关的背景。具体规则由 [代码演进评估规范](代码演进评估规范.md) 负责，本规范不重复。

## 12. 自动检查映射

| 检查 | 负责内容 |
| --- | --- |
| `scripts/docs/check.py` | 必需索引、治理标记、顶层目录注册、`AGENT-INDEX.md` 事实路径、当前文档相对链接、`SUPERSEDED` 替代指针、spec 索引完整性 |
| `scripts/verify/verify_delivery_governance.py` | Active CHG、归档边界和只读约束 |
| `scripts/verify/verify_product_master_alignment.py` | CHG 状态词、LEDGER 行和主计划对齐 |
| `scripts/verify/verify_ai_workspace.py` | `.ai/CURRENT_CONTEXT.md` 快照预算和入口 |
| `scripts/verify/verify_skills.py` | Skill 源与分发一致性 |
| `scripts/verify/verify_m0_config.py` | 仓库映射、Contract 映射和配置一致性 |

检查失败时修事实或索引，不用措辞绕过。

## 13. 质量判据

一份合格文档：

- 回答一个具体问题，而不是承载多个主题；
- 只写当前有效事实，不把历史过程混入正文；
- 有明确 owner、适用边界和执行方式；
- 可被 Review、可被验证，链接和路径可解析；
- 不写成巨型文档，不把报告当规范，不把计划当产品事实；
- 不以聊天记录、AI 记忆或单次分析作为唯一来源；
- 关闭时能让读者只读当前文档就得到完整事实。
