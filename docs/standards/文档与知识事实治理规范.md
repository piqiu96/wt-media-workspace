# 文档与知识事实治理规范

## 1. 核心原则

1. 当前产品、工程、Contract、规范和决策事实由对应正式 SSOT 保存。Git / PR 保存历史与变更证据，不是当前事实的 Owner。
2. 一个事实只有一个正式 Owner；Delivery 记录引用事实，不复制事实正文。
3. 代码只证明当前实际实现，不能自行改变正式需求。
4. AI 对话、AI Memory、临时 Summary 默认不是事实源。
5. 用户本轮明确裁定可以覆盖已有描述，但必须回写正式 SSOT 后才长期生效。
6. 历史默认退场；只有证明有持续追溯价值才保留。
7. 不设置“产品 > 工程 > 实现”的全局优先级；按事实所属领域裁定。
8. 不同正式事实源真正冲突时，AI 不允许自行综合第三种解释。
9. CHG / Milestone 关闭时必须完成事实收口。
10. 不建立第二套 Delivery、状态或 Context 事实源。
11. 默认渐进式加载，禁止无目的的全项目扫描。

## 2. 文档与事实归属

| 类型 | 位置 | 负责内容 | 不写什么 |
| --- | --- | --- | --- |
| 产品需求 | `docs/product/` | 背景、用户问题、用户路径、业务规则、边界、验收 | 技术方案、执行进度、实现细节 |
| 工程设计 | `docs/engineering/` | 当前有效设计、设计理由、边界 | 实施计划、CHG 编号、过程史、已废弃方案 |
| 规范与契约 | `docs/standards/`、`docs/contracts/`、`docs/decisions/`、`docs/devops/`、`docs/reference/` | 可执行规则、owner、执行或校验方式 | 阶段报告、过程叙述、未确认草案 |
| 执行记录 | `delivery/active/`、`delivery/planned/`、`delivery/milestones/`、`delivery/completed/`、`delivery/reports/` | 本次交付范围、验收、验证和结论 | 长期产品事实、第二份状态源 |

一份文档负责一个边界清晰、Owner 单一的主题。是否拆文件由可维护性决定，不机械按需求数量或问题数量拆分。规范与契约写成可执行规则，只有兼容性需要时才升版本。

目录职责：

- `docs/` 只保存当前有效事实，不长期保留旧版本和过程历史。
- `delivery/active/` 只保存当前正在执行的 CHG。
- `delivery/planned/` 保存已确认但尚未启动的交付项，不属于历史。
- `delivery/milestones/` 保存当前 Milestone 的业务闭环定义，不存开发流水账。
- `delivery/completed/` 保存确有追溯价值的已完成交付记录，默认不进入 AI 上下文。
- `delivery/reports/` 保存阶段审计和专项检查报告；结论必须回写正式事实源，无长期价值时删除。

CHG 默认只要求：

```text
delivery/active/<CHG>/change.md
delivery/active/<CHG>/evidence/     # 仅必要时
```

`plan.md`、`checkpoint.md` 是可选文件，只在确实帮助实施或跨执行器接力时创建，不强制每个 CHG 都有。临时执行状态优先写入 `.ai/WORK_STATE.md`：可选、gitignored、不作为正式事实源，仅用于 Codex / Claude Code 临时接力；现有机制已能承担相同职责时不新增重复文件。

Evidence 按风险分级，不为所有 CHG 制造完整模板：

| 风险 | 最低证据 |
| --- | --- |
| L | PR、CI 或定向测试足够 |
| M | 保存必要测试摘要或关键验证读数 |
| H | Contract、跨端、状态机、权限、异步、外部副作用等保存正式 evidence |

### 2.1 最终制品保留原则

`example/` 和各CHG的 `evidence/` 只保留当前最终交付稿及其必要组成，不承担过程文件仓库职责。

| 位置 | 保留 | 不保留 |
| --- | --- | --- |
| `example/common/`、`example/proto/` | 当前可打开的HTML、显示与交互必需的CSS/JS/图片、必要使用说明；需要出图时只留最终效果图 | 多版原型、修前/修后对照包、过时截图、生成过程说明、测试脚本/fixtures、日志与缓存 |
| `delivery/active/<CHG>/evidence/` | 最终交付入口、必要最终效果稿、用户审批原件、与明确代码基线对应的最终验收结论 | 中间分析与多轮结论、失败/成功测试流水、一次性测试脚本/fixtures、原始运行日志、调试JSON、重复截图与页面缓存 |

- 同一效果只保留一个当前入口。evidence可引用example中的最终原型，不复制一套HTML或整包截图；必要入口别名也必须指向当前稿。
- 历史由Git / PR追溯，不另建archive、backup、before/after或V1/V2目录保存过程副本。原型必需引擎属于最终稿依赖，按当前资源职责命名，不作为历史版本陈列。
- 中间验证可在临时目录或既有忽略缓存中执行，完成后不提交；长期有效的自动化测试留在所属工程，执行历史交给CI / PR。不能为清理目录而修改、伪造或丢失仍影响验收的失败事实，最终结论必须说明PASS/FAIL/未验收和对应基线。
- H风险的必要审计要求仍适用，但保存最终审批和验收结论即可；不能把过程日志堆积等同于验收充分，也不能把旧版本通过结果当最新稿已验收。

## 3. 当前事实与历史退场

- `docs/` 中的内容必须回答当前问题。新事实替换旧事实时直接修改当前正式文档，旧版本由 Git 保存，不额外保留副本。
- 旧文档暂时不能删除、且可能仍被外部引用时，才在文首使用临时标记 `SUPERSEDED`，并写明可解析的替代文档。
- `SUPERSEDED` 只能是过渡状态，不能成为旧文档长期保留机制；引用迁移完成后应删除或移出当前文档树。
- 历史文档、`delivery/completed/`、`delivery/reports/` 和旧 AI 分析只用于追溯，不默认加载，也不参与当前冲突裁定。
- 已归档记录保持原样，不重写正文、不重排、不做“内容整合”。

历史内容处置顺序：

1. 已被新事实完全吸收、没有独立追溯价值 → 删除；Git 已能承担追溯。
2. 执行历史有明确审计或证据价值 → `delivery/completed/`。
3. 阶段性审计报告仍有独立价值 → `delivery/reports/`。
4. 暂时因外部引用无法删除 → 临时标记 `SUPERSEDED` 并指向替代文档，引用迁移后删除。
5. Git / PR 已能充分承担追溯 → 不额外保存历史副本。

旧 AI 分析与旧计划不是新的正式事实落点，也不是自动历史归档。当前仍有效的方法提炼到 `docs/standards/`、`docs/engineering/` 或 `skills/`；已被正式规则吸收的删除；AI 历史分析和旧方案删除；极少数确有长期参考价值的放入合适的 `docs/reference/` 并默认不加载。禁止把整个目录简单迁移到 `archive/` 后长期保留。

处置时只做以下判断之一：

| 判断 | 适用情况 |
| --- | --- |
| KEEP | 当前有效事实、仍然有效的方法、必须保留的审计证据 |
| MERGE | 同一事实在多处重复或分散，合并到单一 Owner，其余位置改为指针或删除 |
| MOVE | 有审计价值 → `delivery/completed/`；专项报告 → `delivery/reports/`；有效方法 → `docs/`；少量参考 → `docs/reference/` |
| DELETE | 已被新事实吸收且无独立价值、旧 AI 分析、旧计划、临时文件 |
| SUPERSEDE | 仍有外部引用、暂时不能删除；必须写替代链接，迁移后删除 |
| REVIEW | Owner 或事实归属不清、仍在被使用、无法判断是否有审计价值 |

## 4. 冲突裁定

1. 先确定争议事实属于哪个领域，再由该领域的正式 SSOT 裁定：
   - 产品能力、业务对象、状态、权限、验收 → 业务 PRD / 页面正式规格；
   - 系统职责、模块边界、数据归属 → Engineering；
   - API、Schema、状态枚举、错误码 → Contract；
   - 页面信息架构 → AdminUI 规范；
   - 交互与反馈 → 交互规范；
   - 视觉与组件实现 → 前端视觉规范；
   - 当前实际行为 → 代码只证明“现在怎么实现”，不能自行改变正式需求。
2. 同一领域内部：当前正式事实 > 上层摘要 > CHG 临时描述 > 历史 / `SUPERSEDED` / AI 临时内容。
3. 用户本轮明确裁定优先于已有描述，但必须回写对应正式事实源；回写前只视为本次已确认变更，聊天不成为长期事实源。
4. 不同领域真正冲突时，不允许 AI 自行综合第三种解释。必须列出冲突事实、各自来源、事实归属领域，以及建议修改的正式来源。
5. 代码与正式文档不一致时，先判定“代码尚未实现需求”还是“文档已经过期”，不能默认以现状代码为准。
6. 历史文档、已完成 CHG、旧 AI 分析只用于追溯，不参与当前冲突裁定。

## 5. AI 默认加载与 Plan 规则

AI 规划任务时，默认只有以下来源可以作为当前决策依据：

```text
1. 用户本轮明确输入
2. 当前 CHG / Feature
3. 当前 CHG 明确引用的正式 SSOT
4. 当前真实代码
```

默认不得把以下内容作为当前需求依据：

```text
delivery/completed/
delivery/reports/
历史 Milestone 过程记录
SUPERSEDED 文档
旧 AI Summary
旧 Analysis
临时 Plan
WORK_STATE 中未经确认的推测
历史聊天
```

如果因追溯问题必须读取历史内容，必须明确说明：

> 仅用于历史追溯，不作为当前实现依据。

默认采用渐进式加载。AI 从用户当前任务、当前 CHG、明确 References 和相关正式 SSOT 开始，只有出现事实缺口时才扩大上下文，禁止无目的的全项目扫描。不设固定篇数或字数门槛。

普通 Plan 默认只输出：

```text
1. 任务理解
2. 当前事实与约束
3. 计划修改
4. 明确不修改
5. 冲突 / 未确认项（存在时才写）
```

Plan 要求：

- 先用简短语言确认当前任务；
- 不输出长篇搜索过程；
- 不展示中间推理流水账；
- 不因为阅读到历史文档扩大范围；
- 引用只列真正影响决策的来源，通常只保留少量决定性引用；
- 找不到正式依据时明确写“未找到正式文档定义，本判断仅基于当前代码 / 本次推断”。

关键判断必须区分：

```text
正式需求事实
正式工程 / Contract / 规范事实
当前代码事实
AI 推断
```

禁止把 AI 推断伪装成需求。

## 6. CHG / Milestone 收口

CHG 完成前确认：

- `Done When` 全部满足，必要验证通过并留下读数；
- 当前产品、工程、Contract、Decision 事实已回写各自正式文档；
- 没有残留的过期“当前”描述，`SUPERSEDED` 指针已处理；
- 相关索引已更新，链接可解析；
- `change.md` 是唯一状态源；`evidence/` 按风险保留；可选的 `plan.md`、`checkpoint.md`、`.ai/WORK_STATE.md` 不进入正式事实；
- 只有确有追溯价值的记录才移入 `delivery/completed/`，无独立价值的过程记录直接退场。

Milestone 关闭前确认：

- 目标、业务闭环和验收已闭环；
- 没有遗留的 Active CHG 或未收口阻塞；
- 下一 Milestone 的范围和依赖清楚；
- 闭环卡只保留当前业务事实，不写开发流水账。

CHG 状态词以 `delivery/MASTER_IMPLEMENTATION_PLAN.md` §3 和 `scripts/verify/verify_product_master_alignment.py` 为准；ADR 的 Accepted / Superseded 约定以 `docs/decisions/README.md` 为准。本规范不复制这两套词表。

## 7. AI 对话

AI 对话产物落点：

- 分析结论 → 长期有效时写入 Product、Engineering、Contract 或 Decision；否则不保存。
- 实施计划 → 当前 CHG 的 `change.md`，复杂时可选 `plan.md`。
- 工作进度和交接 → 可选 `.ai/WORK_STATE.md`；需要正式接力时用可选 `checkpoint.md`。
- 验证证据 → 当前 CHG 的 `evidence/`，按风险决定深度。
- 架构或技术决策 → `docs/decisions/` 的 ADR。
- 阶段总结 → 产品或工程正式文档；聊天记录不作为存档。
- 一次性代码发现 → PR / Review 评论；需要跟踪时再建 CHG 或登记到当前 CHG。
- Review 结论只有在回写正式事实源后才成为项目事实；一次性评论留在 PR，不复制成长期文档。
- AI 记忆和对话摘要不能作为唯一事实源。

代码注释属于代码演进规则，见[代码演进评估规范](代码演进评估规范.md) §4。

## 8. 自动检查

| 检查 | 负责内容 |
| --- | --- |
| `scripts/docs/check.py` | 必需索引、治理标记、顶层目录注册、`AGENT-INDEX.md` 事实路径、当前文档相对链接、`SUPERSEDED` 替代指针、spec 索引完整性 |
| `scripts/verify/verify_delivery_governance.py` | Active CHG、LEDGER 一致性、归档边界和只读约束 |
| `scripts/verify/verify_product_master_alignment.py` | CHG 状态词、LEDGER 行和主计划对齐 |
| `scripts/verify/verify_ai_workspace.py` | `.ai/CURRENT_CONTEXT.md` 快照入口与工具预算 |
| `scripts/verify/verify_skills.py` | Skill 源与分发一致性 |
| `scripts/verify/verify_m0_config.py` | 仓库映射、Contract 映射和配置一致性 |

`.ai/CURRENT_CONTEXT.md` 的 8000 字符上限是工具配置，不是知识治理体系的核心规则。

治理节奏采用事件驱动：

- 强制：CHG Close、Milestone Done；
- 自动：`docs/check.py`、CI 和现有验证脚本；
- 人工专项：发现明显 Fact Drift、大 Milestone 完成、大版本、文档规模显著增长；
- 月度检查仅作推荐，不作为强制行政流程。

检查失败时修事实或索引，不用措辞绕过。不新增治理平台或第二套检查脚本。

## 9. 质量判据

一份合格文档：

- 回答一个边界清晰的问题，而不是承载多个主题；
- 只写当前有效事实，不把历史过程混入正文；
- 有明确 Owner、适用边界和执行方式；
- 可被 Review、可被验证，链接和路径可解析；
- 不写成巨型文档，不把报告当规范，不把计划当产品事实；
- 不以聊天记录、AI 记忆或单次分析作为唯一来源；
- 关闭时能让读者只读当前文档就得到完整事实；
- 能明确判断内容应 KEEP、MOVE、DELETE、SUPERSEDE 还是 REVIEW。
