# 代码演进评估规范

## 1. 目的

指导 Cloud、Agent、Desktop 等仓库在持续迭代过程中的代码演进。随需求变化、多人协作以及 AI 辅助开发增加，代码容易逐渐积累：

- 已失效的历史信息；
- 重复维护的事实；
- 无实际使用场景的抽象；
- 不可解释的兼容逻辑；
- 隐式依赖和隐藏规则。

这些问题会增加后续开发、维护以及 AI 理解代码的成本。

本规范的目标：

> 在满足当前业务需求的同时，保持代码结构清晰、事实来源明确、修改成本可控。

本规范鼓励合理演进，不限制正常重构、优化和工程改进。

本规范不是为了：

- 限制 AI 编码能力；
- 禁止抽象设计；
- 要求一次性治理全部历史代码；
- 替代架构、产品和技术决策文档。

### 使用原则

本规范作为代码演进过程中的判断依据，不作为每次修改的强制流程。

根据任务范围和风险选择性参考：

- 小范围修改：遵循基本原则即可；
- 模块调整：关注事实来源和复杂度变化；
- 架构、Contract 或边界变化：结合对应正式文档确认。

避免为了满足规范本身增加不必要的研发成本。

## 2. 适用范围

本规范适用于：

- `wt-media-cloud`
- `wt-media-agent`
- `wt-media-desktop`
- `wt-media-workspace`

以及 Claude Code、Codex 等 AI 辅助开发场景。

系统架构、模块职责和跨仓边界以对应架构文档为准，本规范关注代码长期演进过程中的健康维护。

## 3. 非目标

本规范不是：

- 代码格式规范；
- 编程语言规范；
- 架构设计规范；
- 强制代码审查流程；
- 大规模重构计划。

发现历史问题时，应结合当前业务修改逐步治理，而不是为了规范本身扩大改造范围。


# 4. 当前事实优先

代码应该表达当前系统真实存在的规则，而不是保存完整的历史过程。

## 4.1 注释表达当前原因

注释可以解释：

-   当前设计原因；
-   业务约束；
-   安全要求；
-   代码无法直接表达的重要信息。

例如：

``` go
// Agent执行结果需要经过Cloud校验后，才能更新正式业务状态。
```

不推荐：

``` go
// M2阶段讨论过Agent是否直接修改数据库。
// 后续可能支持其他方案。
```

历史讨论、方案取舍和未来规划应该进入：

-   Decision；
-   History；
-   Delivery 文档。

代码注释只保留当前有效的事实和结论。

------------------------------------------------------------------------

## 4.2 不重复解释代码

避免：

``` go
// 查询用户
func GetUser()
```

代码已经表达的信息不需要重复说明。

注释应该回答：

> 为什么这样设计？

而不是：

> 代码正在做什么？

------------------------------------------------------------------------

## 4.3 注释保持简洁

注释应优先描述：

-   当前事实；
-   当前约束；
-   最终设计结论；
-   必要业务规则。

避免记录：

-   修改过程；
-   讨论过程；
-   多轮方案比较；
-   已废弃方案；
-   推导过程。

例如：

不推荐：

``` go
// 最开始考虑方案A，
// 后来因为一致性问题改成方案B，
// 中间经过多次讨论，
// 最终决定使用当前方式。
// 未来可能重新评估。
```

推荐：

``` go
// 发布结果需要等待平台确认后才能更新最终状态。
```

如果需要记录决策背景，应放入对应文档，而不是代码注释。


# 5. 保持事实来源唯一

系统中的重要事实应该有明确来源。

包括：

- 配置；
- 状态定义；
- 业务规则；
- 枚举；
- 跨模块约定。

推荐：

```text
配置文件
    ↓
Config结构
    ↓
业务代码使用
```

避免：

```text
配置文件
+
代码常量
+
脚本参数
+
业务逻辑
```

同时维护同一个事实。

## 5.1 合理副本可以存在

不是所有重复都是问题。

以下情况允许存在：

- 不可变历史快照；
- 审计记录；
- 任务创建时保存的上下文；
- 生成代码；
- 测试数据。

要求：

> 副本需要能够解释来源、用途和生命周期。

# 6. 控制增量复杂度

代码演进过程中，新增复杂度应该服务于当前真实需求。

不要因为：

- 未来可能支持；
- 感觉以后会变化；
- 希望提前通用化；

提前建设：

- 通用框架；
- 空抽象层；
- 未使用扩展点；
- 复杂流程编排。

## 6.1 抽象来自真实需求

推荐：

存在多个真实场景：

```text
实现A
实现B
实现C
```

再考虑：

```text
公共抽象
```

不推荐：

只有一个实现：

```text
未来可能出现B/C/D
```

提前增加复杂抽象。

## 6.2 新增复杂度需要有收益

新增：

- interface；
- manager；
- adapter；
- wrapper；
- factory；

应能够说明：

1. 当前解决什么问题；
2. 当前有哪些使用场景；
3. 是否降低已有复杂度。

如果只是为了未来可能变化，应优先保持简单实现。

# 7. 防御和兼容逻辑要有边界

防御代码不是问题，没有边界的防御代码才会造成复杂度。

---

## 7.1 应保留的防御

包括：

- 参数校验；
- 空值处理；
- 外部服务失败处理；
- 网络异常处理；
- 数据一致性保护。

这些用于保证当前系统可靠性。

## 7.2 谨慎增加行为改变逻辑

包括：

- 自动 fallback；
- 静默修正；
- 隐式兼容；
- 自动猜测恢复。

增加前需要明确：

1. 保护哪个当前场景；
2. 失败结果是什么；
3. 如何验证行为正确。

不能为了未知未来无限增加分支。

# 8. 保持模块和仓库边界

修改代码时，不应该为了方便绕过已有架构边界。

例如：

- Desktop 不逐渐承担 Cloud 业务规则；
- Agent 不成为业务数据中心；
- 业务模块不随意依赖其他模块内部实现。

新增依赖前考虑：

1. 是否属于当前模块职责；
2. 是否应该通过已有接口或 Contract；
3. 是否只是为了绕过已有设计。

# 9. 修改即治理

不要求单独开展大规模代码清理。

采用：

```text
正常业务修改
        ↓
发现附近明显问题
        ↓
确认不会扩大范围
        ↓
顺手修复
        ↓
继续完成当前需求
```

适合顺手处理：

- 失效注释；
- 明显重复事实；
- 已确认无用分支；
- 临时遗留代码。

不建议：

- 为代码美化进行大范围重构；
- 修改无关模块；
- 改变已有业务行为。

# 10. AI 辅助开发原则

Claude Code、Codex 等 AI 修改代码时，应优先理解已有设计，而不是简单扩大实现。

修改前关注：

1. 当前事实来源在哪里？
2. 是否已经存在类似能力？
3. 是否新增重复规则？
4. 是否引入新的隐藏依赖？
5. 新增复杂度是否解决当前问题？

AI 可以：

- 优化实现；
- 提取合理公共代码；
- 修复明显问题；
- 改善可读性。

避免：

- 根据历史注释推断未来需求；
- 为未知情况增加大量保护；
- 为单次需求建立通用框架；
- 复制已有逻辑形成新的事实来源。

# 11. 修改前快速检查

提交修改前，可以简单思考：
1. 我新增的信息是当前事实，还是历史/未来信息？
2. 这个配置、状态、规则是否已有来源？
3. 是否为了未来可能需求增加复杂度？
4. 新增防御逻辑是否保护当前真实场景？
5. 是否引入新的隐藏依赖？

不需要填写表格，不需要额外流程，不必过度去回溯校准，发挥AI的智能快速抉择能力。
