# 业务状态模型

本目录整理业务对象的状态及流转语义，供 Product、Engineering、Delivery 和具体任务**引用为状态说明**，减少重复描述。它不是独立的产品或合同事实源；状态的新增、变更与冲突裁定仍归 `docs/product/`、已接受 Decision 和提供方维护的 Contract / Schema。引用本目录不代替更新正式基线，也不使 Workspace 成为运行时依赖。

## 文档分工

## 全局规则

1. **一个状态字段只表达一个维度。** 业务生命周期、一次执行、环境或文件事实、派生判断分开。`material.video_status` 可以表示云端源视频准备情况，但不能被叫作 `material` 的业务生命周期。
2. **状态须有可检验的语义。** 新增取值前，确认它是独立阶段，改变核心能力，有明确进入与退出条件，并且确实需要持久化。标签、失败原因、步骤进度、UI 提示、风险和“是否可执行”通常分别用字段、执行记录或派生判断表达。
3. **失败归属于发生失败的过程。** 一次操作失败通常不改主体对象的业务状态；在执行对象、错误字段或关联记录中留存。已终结的一次执行不能通过改回排队状态来抹掉失败事实。确需在同一业务任务内做技术重试时，必须保留每次尝试的错误与结果；“重做一次业务生产”创建新任务。
4. **执行对象与资产对象分开。** `crawl_task`、`compose_task`、`file_transfer_task` 记录过程；`material`、`composite_output` 记录资产。资产不以“排队中 / 合成失败”表达执行结果。
5. **状态与影响分开。** 例如“停用”是状态；“不再创建新任务”是该状态导致的能力变化。已有历史关系与执行记录默认保留，除非已有明确规则另作规定。
6. **跨端差异不写进业务状态机。** 只记录业务结果；本地与 Cloud 事实存在差异时，依既有同步和读回规则判断，不把 Diff、窗口运行或页面提示并入业务状态。
7. **没有稳定状态机就明说。** 不为文档齐全而补造 enum。计划中尚未落地的模型应标明阶段，不与当前代码事实混为一谈。

## 对象模板

每个**已确认有稳定状态字段**的对象按下列七节写。对象有多个独立维度时，明确本节描述的字段；无状态机对象只说明其业务定位、事实与排除原因。

```markdown
## object_name（字段；状态类别）

### 1. 定位
### 2. 状态
| 状态 | 展示名称 | 含义 | 是否终态 |
| --- | --- | --- | --- |
### 3. 状态流转
### 4. 流转条件
### 5. 状态能力
| 状态 | 核心能力 A | 核心能力 B |
| --- | ---: | ---: |
### 6. 状态影响
### 7. 非状态说明
```

能力矩阵里的“可”仍受权限和其他真实事实约束，不代表单凭此状态即可执行。终态针对**该字段和这条对象记录**，不表示关联对象不可再变化。

## 维护与冲突处理

- 先读当前 Product、已接受 Decision、当前 Milestone 和 Architecture / Contracts；代码只用于一致性核对，不据此创造产品状态。被后续明确 Decision 取代的旧文档，保留历史来源并注明取代关系。
- 发现冲突时写出两边的准确位置和采用的明确依据。仍无法判断的列为待确认项，不改数据库 enum、Migration 或 API 契约。本目录变更不能绕过相关产品与 Contract 审核。
- PRD 暂不批量重写；后续具体修改可引用本目录的相应状态说明，同时保留页面专有规则。引用不能代替正式产品或合同变更。
