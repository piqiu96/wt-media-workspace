# M2-B 媒体账号多游戏关系设计

日期：2026-09-03

状态：用户已确认设计，待规格评审
范围：CHG-20260805-032 的媒体账号—游戏关系；不包含 M2-C 代理闭环和检查项 7/8 真实样本验收。

## 1. 目标和边界

一个媒体账号可关联零个或多个游戏。账号、标签、Cookie、检查记录和 Browser Profile 绑定继续属于原账号，不因迁移而删除或重建。

账号可暂不关联游戏；进入可执行状态、上号完成、发布或互动预检时，必须至少关联一个游戏。多游戏的关联事实由 Cloud 保存，Agent 和 Desktop 不保存第二份业务关系。

本次同时修改 Cloud Web 的新增、编辑、列表、详情与游戏筛选页面。M2-C 的代理资源、代理检查项 3/4，以及检查项 7/8 的真实样本校验不在本设计中。

## 2. 授权规则

在媒体账号域，所有已启用游戏默认可被已登录的 `admin`、`senior_operator` 和 `operator` 选择、关联和筛选；账号的用户归属、运营分组、Profile 授权和本地敏感操作边界保持不变。

现存 `users.game_ids` 不删除，也不作为媒体账号创建、更新、筛选或可执行校验的限制。它保留给尚未审计的后续模块；如果其他模块也要改为游戏公开，需要独立决策和影响审计。

该规则取代 ADR-0009 在**媒体账号域**中“资源与游戏范围取交集”的限制，不改变其余角色、团队和本地资源边界。

## 3. 数据模型与一次性迁移

新增 Cloud 关系表 `media_account_games`：

- `media_account_id`：引用 `media_accounts.id`；
- `game_id`：游戏稳定标识；
- `(media_account_id, game_id)` 唯一，防止重复关联；
- `game_id, media_account_id` 索引，支持按游戏筛选；
- 外键删除策略不得级联删除媒体账号历史。

迁移步骤：

1. 创建关系表和索引。
2. 清空关系表中的历史/测试关联数据。
3. 将 `media_accounts.game_id` 的每条非空值一次性迁移为关系行。
4. 通过查询核对：旧列非空账号数、关系表去重后的账号数和迁移后零关系账号数符合预期。
5. 删除 `media_accounts.game_id` 及其索引。

不删除 `media_accounts`、`media_account_tags`、Cookie 字段、检查记录或 `browser_profile_id`。本地没有线上流量，故不保留双写或渐进兼容列。

回滚仅在恢复备份或重新添加旧列并从关系表为每个账号选择一个确定游戏后执行；多游戏关系无法无损压回单值列，因此正常运行后的回滚不是无损操作。

## 4. Cloud API 与服务语义

`game_ids: string[]` 是创建、更新和响应的正式字段：

- 创建：存入去重后的完整集合；空数组允许。
- 更新：`game_ids` 出现时完整替换该账号所有关系；空数组清空全部关系。
- 列表：`game_ids` 返回完整排序集合；多游戏账号只返回一次。
- 筛选：`game_ids` 使用“命中任一所选游戏”语义；旧 `game_id` 查询等价于只传一个游戏。
- 执行资格：从“`game_id` 非空”改为“`len(game_ids) > 0`”。

为未同步的外部消费者保留请求与响应 `game_id`：

- 只传 `game_id` 的创建/更新请求按单元素 `game_ids` 处理；
- 同时传 `game_id` 和 `game_ids` 且内容不一致时拒绝；
- 响应 `game_id` 是排序后第一个 `game_ids` 元素，空集合返回空值；
- Cloud Web 完成改造后只传/读 `game_ids`，不再依赖兼容字段。

服务、Store、路由和账号组筛选均以关系表为事实源；游戏筛选使用 `EXISTS` 或去重 join，禁止因一账号多游戏重复返回。

## 5. Cloud Web 交互

- 新增账号：游戏控件为可清空多选，提交 `game_ids`。
- 编辑账号：加载完整 `game_ids`，保存时完整替换；清空表示解除全部游戏关联。
- 列表：游戏列显示全部关联游戏名称；详情和账号信息弹窗同样显示完整集合。
- 筛选：游戏控件多选，选择多个游戏时按“任一命中”过滤。
- 没有游戏关系的账号明确显示“未绑定游戏”；检查和后续执行仍给出不可执行原因。

页面不会把多游戏关系折叠回单值，也不会在只修改名称、备注、标签或 Profile 时隐式修改游戏关系。

## 6. 失败行为与一致性

- 关系写入失败时，账号基础字段和关系集合不显示为已更新；服务操作在同一 Cloud 数据库事务内完成。
- 不存在或停用的游戏不可关联；迁移历史中指向不存在/停用游戏的记录必须在迁移前报告并由操作者处理，不能静默丢弃。
- 清空游戏关系不会解除 Profile、删除 Cookie 或改变检查结果，但可执行预检必须失败并明确说明未绑定游戏。
- Cloud Web 只修改 Cloud 关系；不调用 Agent、Desktop 或 BitBrowser，因此没有本地副作用。

## 7. 验证与交付

测试先行覆盖：

1. 服务：创建、完整替换、清空、去重、公开游戏权限、至少一个游戏的执行资格。
2. 路由：`game_ids` 请求/响应、旧字段兼容、冲突字段拒绝、多游戏筛选。
3. MySQL Store：关系表写入、事务、按任一游戏筛选且无重复、读取稳定排序。
4. Web：API 序列化、创建/编辑多选、完整展示和多选筛选参数。
5. 迁移：真实 MySQL 中迁移计数、唯一键、旧列删除以及保留账号其他关联的查询验证。

交付证据记录迁移前后计数、验证 SQL、自动化测试、Cloud/Web 构建和当前环境人工点验。Cloud、Desktop 生成资产和 Workspace 治理记录各自独立提交。
