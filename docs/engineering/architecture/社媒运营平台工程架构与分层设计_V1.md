## 第一章 架构目标与设计原则

### 1.1 架构背景

系统同时包含云端业务管理、本地浏览器自动化、本地文件处理、视频合成、辅助发布、互动执行和数据采集，单一 Web 后台或纯云端架构无法覆盖全部运行场景。

系统采用：

```text
Cloud 云端业务中心
+
Agent 统一执行端
+
Desktop 本地控制台
```

Agent 分为：

```text
Local Agent：运行在运营电脑
Cloud Agent：运行在云端 Linux
```

Local Agent 与 Cloud Agent 共用同一 Python 核心框架，根据运行模式加载不同能力。

### 1.2 架构目标

1. **Cloud 统一管理正式业务事实**  
   用户、权限、素材、成片、发布、互动、正式任务和统计口径均以 Cloud MySQL 为准。

2. **Agent 统一承担实际执行**  
   FFmpeg、浏览器、比特浏览器、文件、抓取、发布、互动和效果采集统一通过 Agent 执行。

3. **Desktop 保持轻量**  
   Desktop 负责进程控制、本机能力桥接、状态展示和人工确认，不复制 Cloud 业务规则。

4. **降低一人维护成本**  
   采用少目录、强边界、低抽象、按需演进的方式，避免为未来需求提前建设微服务、插件市场和工作流引擎。

5. **支持多端独立构建与版本管理**  
   Cloud、Agent、Desktop 独立构建、独立发版，通过 Contract 和版本矩阵协作。

6. **保证构建可复现**  
   Python、FFmpeg、浏览器运行时、第三方补丁和跨端协议均需锁定版本、Hash 和兼容关系。

### 1.3 核心设计原则

#### 原则一：Cloud 是业务事实中心

Cloud 最终确认：

- 用户和权限；
- 业务对象状态；
- 正式任务；
- 发布和互动结果；
- 业务配置；
- 审计和统计口径。

Agent 只能上报结构化执行事实，不能直接修改 Cloud 数据库或自行决定正式业务状态。

#### 原则二：Agent 是唯一执行入口

所有依赖以下能力的实际操作统一由 Agent 完成：

- Python 执行任务；
- FFmpeg；
- 文件下载、校验和合成；
- 比特浏览器；
- 浏览器自动化；
- 平台抓取；
- 发布和互动；
- 平台效果采集。

#### 原则三：Desktop 是本地控制壳

Desktop 负责：

- Local Agent 启停和健康检查；
- 文件选择；
- 安全存储；
- 系统信息；
- 环境检测展示；
- 人工确认；
- 安装和更新。

Desktop 不直接操作 SQLite、FFmpeg、浏览器和正式业务状态。

#### 原则四：平台差异集中在 Agent

平台页面、元素、状态识别和接口差异集中在：

```text
platforms/douyin
platforms/bilibili
platforms/baijiahao
```

Cloud 只保存统一业务对象、平台枚举和必要配置。

#### 原则五：固定流程加必要配置

平台执行采用：

```text
代码固定流程
+
必要 JSON 元素配置
```

不建设运营可视化工作流编排器，不允许 Cloud 动态下发 Python 代码。

#### 原则六：保守处理高风险动作

发布提交、评论提交、点赞、收藏、Cookie 写入和 Profile 修改等动作，在结果无法确认时进入 `result_uncertain`，不得盲目自动重试。

#### 原则七：真实问题驱动演进

首版不建设：

- 微服务；
- 消息队列；
- Kubernetes；
- 动态插件市场；
- 独立配置中心；
- 通用离线业务模式；
- 用户自定义脚本；
- 完全无人值守发布；
- 独立 Contracts 仓库。

### 1.4 支持范围

#### 桌面系统

```text
Windows x64
macOS Intel x86_64
macOS Apple Silicon arm64
```

Linux 桌面端不在首版范围内。

#### 平台能力

| 平台 | 内容发现 | 发布 | 互动 | 效果采集 |
|---|---:|---:|---:|---:|
| 抖音 | 支持 | 不支持 | 不支持 | 不作为我方发布效果 |
| B站 | 不支持 | 支持 | 支持 | 支持 |
| 百家号 | 不支持 | 支持 | 支持 | 支持 |

互动动作只包含点赞、收藏和评论。

## 第二章 总体运行架构与核心流转

### 2.1 总体架构

```text
                         ┌────────────────────────────┐
                         │          Cloud             │
Web / Desktop ──────────→│ Go + Hertz Cloud API      │
                         │ MySQL / Object Storage     │
                         │ Scheduler                  │
                         └──────────────┬─────────────┘
                                        │ HTTPS
                                        │ 领取、心跳、进度、结果
                    ┌───────────────────┴───────────────────┐
                    │                                       │
           ┌────────▼────────┐                    ┌─────────▼────────┐
           │   Cloud Agent   │                    │   Local Agent    │
           │ Linux 独立进程   │                    │ 运营电脑本地进程  │
           └─────────────────┘                    └─────────┬────────┘
                                                           │
                                                 127.0.0.1 HTTP + SSE
                                                           │
                                                  ┌────────▼────────┐
                                                  │ Tauri Desktop   │
                                                  └─────────────────┘
```

三项固定边界：

```text
Desktop 不执行重型任务
Agent 不连接 Cloud MySQL
Cloud 不直接操作运营电脑资源
```

### 2.2 三端职责

#### Cloud

负责：

- 用户、权限、账号和业务对象；
- 正式任务创建、租约和结果校验；
- 定时规则扫描；
- 对象存储资产；
- 平台配置、审计和统计；
- Cloud API 和 Cloud-Agent API；
- 统一业务 Web。

#### Local Agent

负责：

- 比特浏览器和 Browser Profile；
- Cookie、代理和账号检查；
- 本地文件；
- 本地 FFmpeg；
- 云端成片下载；
- B站、百家号辅助发布；
- B站、百家号互动；
- 本地任务快照和待回传结果。

#### Cloud Agent

负责：

- 抖音关键词和作者监控；
- 云端下载和生产；
- 云端 FFmpeg；
- 对象存储上传；
- B站、百家号效果采集；
- 文件和数据清理。

#### Desktop

负责：

- 登录和本机初始化；
- Local Agent 生命周期；
- 本地环境展示；
- 文件选择；
- 任务实时进度；
- 人工确认；
- 组件更新。

### 2.3 通信关系

#### Web / Desktop 与 Cloud

采用 HTTPS JSON API。

#### Desktop 与 Local Agent

采用：

```text
127.0.0.1 HTTP
+
SSE 实时事件
```

Local Agent 只监听本机回环地址，并使用每次启动生成的本地 Token。Token 仅由 Tauri Rust 层持有。

#### Agent 与 Cloud

采用：

```text
HTTPS API
+
轮询或长轮询
```

首版不使用 MQ、gRPC 或 WebSocket 任务推送。

### 2.4 正式任务流转

```text
用户或定时规则发起
→ Cloud 校验权限和业务状态
→ Cloud 创建业务对象和正式 task
→ Agent 领取 task
→ Agent 执行前再次校验
→ Agent 分阶段执行并上报
→ Cloud 校验执行事实
→ Cloud 更新正式业务状态
```

手动抖音关键词搜索和链接查询仍通过 Cloud Agent 执行。Cloud 创建短生命周期查询任务，前端轮询结果；未被运营确认的数据不写入 `source_content` 和 `material`。

### 2.5 数据事实来源

| 数据类型 | 事实来源 |
|---|---|
| 用户、权限和业务对象 | Cloud MySQL |
| 正式任务和最终状态 | Cloud MySQL |
| 本地执行检查点 | Local SQLite |
| 待回传结果 | Local SQLite |
| 本地文件是否存在 | 本地文件系统 |
| 云端文件是否存在 | 对象存储 |
| Profile 实际状态 | 比特浏览器 |
| 社媒登录状态 | 平台页面和浏览器环境 |
| 平台作品效果 | 最近一次有效采集结果 |

### 2.6 文件流转

#### 本地生产

```text
Cloud 保存素材元数据
→ Local Agent 下载或读取素材
→ 文件校验
→ 本地 FFmpeg 合成
→ 创建本地成片
→ Cloud 创建 composite_output 记录
```

完整本地成片默认不自动上传云端。

#### 云端生产

```text
Cloud 创建生产任务
→ Cloud Agent 下载素材
→ 云端合成
→ 上传对象存储
→ 创建 composite_output
→ 进入 composite_output_pool
```

运营领取后由 Local Agent 下载并建立本地文件索引。

### 2.7 断网、退出与恢复

- Local Agent 离线时，本地任务等待，不迁移至 Cloud Agent。
- Desktop 退出时，Local Agent 进入 `draining`，停止领取新任务并保存检查点。
- 网络中断时允许保存检查点和待回传结果，不允许启动新的发布和互动任务。
- 会话失效时，Local Agent 停止新的敏感操作。
- 外部结果不明确时进入待核实状态，不自动重复执行。

### 2.8 并发原则

1. 同一 Browser Profile 同时只能执行一个敏感浏览器任务；
2. 同一账号不得并发发布和互动；
3. Local Agent 与 Cloud Agent 不能同时领取同一任务；
4. Cloud 使用任务租约保证领取唯一性；
5. Agent 使用本地资源锁保证本机互斥；
6. 高风险动作不因超时直接重试。

## 第三章 工程工作区、仓库与协议治理

### 3.1 工程目录与仓库结构

工程采用一个本地跨仓库执行根目录、一个治理仓库和三个运行代码仓库：

```text
wt-media/                              # AI 跨仓库执行根目录，非 Git 仓库
├── .codex/skills/                     # 跨仓库聚合 Skills，自动生成
├── .claude/skills/                    # 跨仓库聚合 Skills，自动生成
├── AGENTS.md                          # Codex 跨仓库总规则，自动生成
├── CLAUDE.md                          # Claude 跨仓库总规则，自动生成
├── .skill-sync.lock.json              # 根工作区 Skill 同步记录
├── wt-media.code-workspace            # 本地 IDE 工作区文件，自动生成
│
├── wt-media-workspace/                # Git：文档、Skills、决策记录、交付治理
├── wt-media-cloud/                    # Git：Cloud 运行代码
├── wt-media-agent/                    # Git：Agent 运行代码
└── wt-media-desktop/                  # Git：Desktop 运行代码
```

| 目录或仓库 | 是否为 Git 仓库 | 职责 |
|---|---:|---|
| 最外层 `wt-media/` | 否 | Codex / Claude 跨仓库执行根目录和本地聚合配置 |
| `wt-media-workspace` | 是 | 产品文档、架构、协议治理、Skills 源码、决策记录、交付记录和版本矩阵 |
| `wt-media-cloud` | 是 | Go Cloud、统一业务 Web、MySQL、任务控制和 Cloud Contracts |
| `wt-media-agent` | 是 | Local/Cloud Agent、执行器、平台适配器和 Local Agent Contracts |
| `wt-media-desktop` | 是 | Tauri 本地壳、Agent 管理、系统桥接和安装包 |

最外层 `wt-media/` 不初始化为第五个 Git 仓库，也不使用 Git Submodule。四个 Git 仓库保持同级独立。

### 3.2 执行根目录与 Workspace 边界

#### 最外层执行根目录 `wt-media/`

最外层目录用于：

- 同时打开 Cloud、Agent、Desktop 和 Workspace；
- 从一个 AI 会话修改多个仓库；
- 承载跨仓库聚合后的 `.codex/skills` 和 `.claude/skills`；
- 承载自动生成的根 `AGENTS.md`、`CLAUDE.md` 和 IDE Workspace 文件；
- 执行跨仓库 Contract、Skill、版本矩阵和发布检查。

它不是正式事实源，不保存需要人工维护的源码，也不作为运行端的编译或运行依赖。

#### 治理仓库 `wt-media-workspace`

Workspace 保存：

- 产品需求；
- 工程架构；
- 决策记录；
- 项目级和各端专项 Skills 源码；
- 当前交付记录；
- Contract 归属地图；
- 版本兼容矩阵；
- 发布清单；
- 执行根目录和 Skill 分发模板；
- 跨仓库同步与校验脚本。

Workspace 不保存：

- Cloud、Agent、Desktop 运行代码；
- 数据库 Migration；
- 正式 Contract 源文件；
- 生产配置和密钥；
- Agent、FFmpeg 或安装包等二进制制品。

三个运行仓库不得在编译或运行时依赖 Workspace；最外层执行根目录也不得成为产品运行依赖。

### 3.3 Contracts 归属

原则：

> 谁提供接口，谁维护正式 Contract。

#### Cloud 仓库

```text
contracts/
├── cloud-api/
├── cloud-agent-api/
├── business-schemas/
├── task-schemas/
├── business-enums/
└── cloud-error-codes/
```

#### Agent 仓库

```text
contracts/
├── local-agent-api/
├── local-event-schemas/
├── local-status-enums/
└── local-error-codes/
```

#### Workspace

只维护：

```text
docs/contracts/
├── ownership.md
├── contract-map.md
├── compatibility-policy.md
└── breaking-change-policy.md
```

Desktop 不定义正式 Contract，只消费 Cloud 和 Agent Contract。

### 3.4 Contract 版本

每类 Contract 包含：

```text
API 主版本
+
Contract 修订版本
```

例如：

```text
cloud_api_version = v1
cloud_agent_api_version = v1
local_agent_api_version = v1
contract_revision = 2026.07.14.1
```

运行时只检查版本兼容，不动态下载协议文件。

### 3.5 生成代码

生成代码可提交 Git，但必须：

- 明确标记自动生成；
- 禁止人工修改；
- CI 校验生成结果；
- 生成器版本锁定。

### 3.6 Skills 唯一源码与分类

所有正式 Skill 的唯一事实源统一放在：

```text
wt-media-workspace/skills/
├── common/
├── workspace/
├── cloud/
├── agent/
├── desktop/
└── tool-overrides/
    ├── codex/
    └── claude/
```

分类含义：

| 分类 | 分发范围 |
|---|---|
| `common` | Cloud、Agent、Desktop、Workspace 和跨仓库执行根目录 |
| `workspace` | Workspace 仓库和跨仓库执行根目录 |
| `cloud` | Cloud 仓库和跨仓库执行根目录 |
| `agent` | Agent 仓库和跨仓库执行根目录 |
| `desktop` | Desktop 仓库和跨仓库执行根目录 |
| `tool-overrides` | Codex 或 Claude 确有差异时追加的少量工具专属内容 |

默认只维护一份通用 `SKILL.md`。工具差异通过小型 Override 合并生成，禁止长期维护 `skills-codex`、`skills-claude` 两套完整事实源。

### 3.7 Skills 分发目标

Skills 同时分发到单仓库目录和跨仓库执行根目录。

#### 单仓库分发

```text
wt-media-cloud/
├── .codex/skills/
└── .claude/skills/

wt-media-agent/
├── .codex/skills/
└── .claude/skills/

wt-media-desktop/
├── .codex/skills/
└── .claude/skills/
```

各代码仓库只接收：

```text
common
+
当前仓库专项 Skills
```

这些生成副本提交 Git，以保证：

- 单独克隆和打开仓库即可使用；
- Codex / Claude 启动时不依赖 Workspace 在本机存在；
- CI、沙箱和代码审查可以看到实际使用的 Skill 版本；
- 每个代码版本能够追踪对应 Skill 版本。

#### 跨仓库聚合分发

当一次 AI 任务需要同时修改 Cloud、Agent、Desktop 时，从最外层 `wt-media/` 启动会话，并生成：

```text
wt-media/.codex/skills/
wt-media/.claude/skills/
```

聚合内容为：

```text
common
+
workspace
+
cloud
+
agent
+
desktop
```

根目录聚合副本只用于本地跨仓库会话，不提交 Git，其唯一来源仍是 `wt-media-workspace/skills`。

### 3.8 Skills 同步方式

同步采用确定性的单向复制：

```text
wt-media-workspace/skills
→ 各仓库 .codex/skills 和 .claude/skills
→ 最外层执行根目录 .codex/skills 和 .claude/skills
```

禁止：

- 从生成目录反向同步回 Workspace；
- 直接修改生成后的 `SKILL.md`；
- 使用符号链接跨仓库引用 Skills；
- 让代码仓库在运行时读取 Workspace Skills；
- 靠人工复制维持 Codex 和 Claude 两个目录。

不采用符号链接的原因包括 Windows 权限和检出差异、AI 沙箱可能不跟随仓库外链接、单仓库克隆后链接失效以及不同工具扫描行为不一致。

### 3.9 Skills 分发配置与命名

Workspace 使用明确的分发配置，例如：

```text
wt-media-workspace/config/skills-distribution.yaml
```

配置中定义：

- 目标目录；
- 应包含的 Skill 分类；
- 目标工具；
- 生成副本是否提交 Git；
- 工具 Override；
- 同步版本和校验策略。

跨仓库聚合后所有 Skill 位于同一搜索范围，因此 Skill 名称必须使用明确前缀，例如：

```text
common-architecture-review
cross-repo-change
cross-repo-contract-change
cloud-database-migration
agent-platform-adapter-change
desktop-sidecar-update
release-cross-platform-verification
```

禁止使用容易冲突的泛化名称，如 `testing`、`release`、`architecture`。

### 3.10 同步脚本与一致性校验

Workspace 提供：

```text
wt-media-workspace/scripts/
├── sync_skills.py
├── verify_skills.py
└── prepare_ai_workspace.py
```

推荐能力：

```text
sync_skills.py sync              # 同步全部目标
sync_skills.py sync --repo agent # 只同步 Agent
sync_skills.py sync --tool codex # 只同步 Codex
sync_skills.py check             # 只检查，不修改
sync_skills.py diff              # 展示差异
```

跨仓库会话启动前统一执行：

```text
prepare_ai_workspace.py
→ 检查四个仓库目录
→ 聚合根 Skills
→ 生成根 AGENTS.md 和 CLAUDE.md
→ 生成 wt-media.code-workspace
→ 写入同步 Lock
→ 校验 Hash
```

同步过程必须删除映射中已经移除的旧 Skill，但遇到未登记的未知文件时应停止并提示，不得静默覆盖。

### 3.11 生成标记与同步 Lock

生成的 `SKILL.md` 顶部应包含：

```text
GENERATED FILE — DO NOT EDIT DIRECTLY
Source: wt-media-workspace/skills/...
Source-Hash: sha256:...
```

各代码仓库和执行根目录保存：

```text
.skill-sync.lock.json
```

至少记录：

- Skill 同步 Schema 版本；
- Skills 修订版本；
- 源文件树 Hash；
- `.codex/skills` 文件数和目录 Hash；
- `.claude/skills` 文件数和目录 Hash；
- 目标仓库或执行根目录标识。

代码仓库 CI 校验本仓库生成副本，Workspace 全局校验在四个仓库同级存在时检查所有分发目标。最外层执行根目录属于本地缓存，不作为代码仓库 CI 的提交内容。

### 3.12 根规则与仓库规则

跨仓库执行根目录自动生成：

```text
wt-media/AGENTS.md
wt-media/CLAUDE.md
```

根规则负责：

- 标明当前目录不是 Git 仓库；
- 列出四个子仓库及其职责；
- 要求修改前检查 Contract 和架构边界；
- 要求分别执行各仓库测试；
- 禁止跨仓库混合提交；
- 要求完成后更新版本兼容矩阵和变更摘要。

各仓库自行维护：

```text
AGENTS.md
CLAUDE.md
```

仓库规则包含本仓库目录、命令、禁止事项和测试要求。它们不建议由 Workspace 整体覆盖，只可由模板和校验脚本辅助检查，避免规则与实际代码脱节。

### 3.13 跨仓库 AI 会话流程

需要同时修改多个运行端时，标准流程为：

```text
在最外层 wt-media/ 准备 AI 工作区
→ 从 wt-media/ 启动 Codex 或 Claude
→ 读取根规则和 cross-repo Skills
→ 判断受影响的 Contract 及提供方
→ 分别修改 Cloud、Agent、Desktop
→ 分别执行各仓库测试
→ 执行跨端 Contract 和集成验证
→ 更新 Workspace 交付记录、兼容矩阵或决策记录
→ 各仓库分别提交
```

跨仓库核心 Skill 至少包含：

```text
cross-repo-change/
└── SKILL.md
```

它应规定先修改接口提供方 Contract，再生成消费端代码，禁止复制三端业务规则，并要求分别输出各仓库变更摘要。

### 3.14 分支和版本

采用：

```text
main
+
短生命周期 feature 分支
+
版本 tag
```

Cloud、Agent、Desktop 独立版本，不要求版本号相同。经过联调的组合记录在 Workspace `release-matrix.yaml`。Skill 变更涉及多个仓库时，Workspace 源码与受影响仓库中的生成副本应在同一个跨仓库变更计划中提交，但仍保持各仓库独立 Commit 和版本历史。

### 4.6 跨模块规则

普通业务模块不得直接修改或查询其他模块内部表，应通过公开 Service 能力协作。

Analytics 作为只读统计模块，允许通过专用 Read Model、数据库视图或明确的只读查询层跨模块读取，但不得直接修改业务表。

业务链路图只表示领域流转，不等于 Go 包必须形成相同 import 链。编译依赖必须避免循环。

### 4.7 Task 模块

- 正式任务；
- 任务类型；
- 执行位置；
- 领取和租约；
- 进度和阶段；
- 结果和错误；
- 取消和重试关系。

Task 不决定发布、互动和生产业务是否成功。

### 4.8 定时调度

Cloud 内部使用轻量扫描器：

- 抖音监控策略；
- 自动生产规则；
- 效果采集；
- 日级统计；
- 过期文件清理；
- 任务租约回收。

调度器只负责触发和防重复，业务规则仍由对应模块实现。

### 4.9 Web 单一事实源

`wt-media-cloud/web` 是业务页面唯一源码，包括内容发现、素材、生产、发布、互动和统计。

Desktop 不复制一套完整业务前端，而是通过 Tauri WebView 承载统一 Cloud Web。Desktop 仅额外维护本地环境、组件、文件和 Agent 控制页面。

远程业务页面不得默认获得本地高权限能力；允许调用的 Tauri Command 必须使用明确白名单和权限范围。

不构建包含所有端依赖的万能 Agent。

- 开发和测试使用独立 `.venv`；

- Cloud Agent 使用 Docker 镜像；
- 用户机器不安装 Python，不执行 pip。

### 5.11 FFmpeg

FFmpeg 作为独立锁定二进制组件管理：

- 不依赖系统 PATH；
- Agent 使用绝对路径；
- 按平台和架构分别准备；
- 校验 SHA256、CPU 架构、编码器和 Filter；
- 记录许可证、源码版本和编译信息。

### 5.12 受控第三方补丁

浏览器控制依赖需要调整上传文件限制时，采用：

```text

→ 校验源码 Hash
→ 应用版本化 Patch
→ 构建定制 Wheel
→ 专项测试
→ 安装定制 Wheel
→ PyInstaller 打包
```

禁止手工修改 `.venv/site-packages`。

定制版本应明确标识，例如：

```text
1.2.3+wt.1
```

### 5.13 测试隔离

每次测试生成唯一 `test_run_id`，并隔离：

- 本地根目录；
- SQLite；
- 日志；
- 输入输出文件；
- Cloud 测试数据库；
- 对象存储前缀；
- 比特浏览器测试分组；
- 社媒测试账号。

真实外部动作只有显式设置 `WT_MEDIA_EXTERNAL_E2E=1` 才允许执行。

不允许运行时：

- `pip install`；
- 在线修改 Python 依赖；
- 从未知地址下载 FFmpeg；
- 用户自行选择组件版本。

Cloud 回滚需保留旧镜像和数据库备份。Desktop 程序目录与用户数据目录分离，程序回滚不得删除用户数据。

### 7.11 日志和诊断

日志分为：

1. 进程运行日志；
2. 任务执行记录；
3. Cloud 正式审计日志。

诊断包可包含版本、组件状态、脱敏日志和失败任务摘要，不得包含 Cookie、密码、完整 Token 和用户媒体原文件。

## 第八章 架构边界、验收与演进原则

### 8.1 全局责任

```text
Cloud
= 业务事实、规则、权限和正式任务

Agent
= 自动化、文件和外部平台执行

Desktop
= 本地控制、系统桥接和人工交互

Workspace
= 文档、Skills 源码、决策记录和跨仓库治理

最外层 wt-media/
= Codex / Claude 跨仓库执行根目录和聚合配置
```

### 8.2 全局禁止事项

1. Agent 直接连接 Cloud MySQL；
2. Desktop 直接读取 Agent SQLite；
3. Vue 直接访问 Local Agent；
4. Cloud 直接控制运营电脑浏览器；
5. Agent 自行创建正式业务任务；
6. Agent 自行决定正式业务状态；
7. 普通业务模块直接修改其他模块数据；
8. Handler 直接执行 SQL；
9. Runtime 承载平台业务规则；
10. Platform Adapter 修改 Cloud 状态；
11. 将 SQLite 建设成完整离线业务库；
12. 高风险外部动作盲目自动重试；
13. Cloud 动态下发 Python 代码；
14. 用户上传执行脚本；
15. 正式运行依赖系统 Python；
16. 依赖系统 PATH 中的 FFmpeg；
17. 手工修改 `site-packages` 作为发布方案；
18. 构建时使用未锁定最新版依赖；
19. 测试环境操作正式 Profile 和账号；
20. 敏感信息进入普通日志；
21. 运行端依赖 Workspace 才能启动；
22. 直接修改生成后的 `.codex/skills` 或 `.claude/skills`；
23. 使用跨仓库符号链接代替 Skill 分发；
24. 跨仓库 AI 会话在未校验根 Skills 和 Contract 的情况下开始修改；
25. 未经决策记录改变仓库、协议或事实来源。

### 8.3 架构验收

#### 仓库

- 四个仓库职责清晰；
- 最外层 `wt-media/` 明确为非 Git 的跨仓库执行根目录；
- 三个运行仓库可独立构建；
- Workspace 不包含运行代码；
- 不使用 Git Submodule 和跨仓库 Skill 符号链接；
- 各仓库存在 `AGENTS.md` 和 `CLAUDE.md`；
- 各仓库 `.codex/skills`、`.claude/skills` 与同步 Lock 一致；
- 根执行工作区能够由 `prepare_ai_workspace.py` 确定性重建；
- 版本组合可追踪。

#### Cloud

- 模块化单体；
- Handler、Service、Repository 边界清晰；
- 普通模块不跨表修改；
- Analytics 只读；
- 长任务交给 Agent；
- Migration 独立管理。

#### Agent

- Local/Cloud 共用 Core；
- 模式依赖分离；
- `src/wt_media_agent` 为正式包；
- Local Agent 不依赖系统 Python；
- FFmpeg 锁定；
- 第三方修改通过 Patch 和定制 Wheel；
- SQLite 只承担本地执行状态；
- 高风险动作有待核实机制。

#### Desktop

- 统一业务 Web 不重复开发；
- 本地页面和高权限能力由 Desktop 管理；
- Rust 统一代理 Agent；
- Token 不暴露给 Vue；
- 三个平台分别构建；
- 安装目录与用户数据分离。

#### Contract

- Contract 归提供方；
- 消费端生成代码不可人工修改；
- 版本可追踪；
- 主版本不兼容时禁止敏感操作。

#### 测试和发布

- 四环境隔离；
- 构建可复现；
- 依赖和组件锁定；
- 各目标平台完成冒烟测试；
- 发布组合进入 Workspace；
- 失败测试保留脱敏诊断产物。

### 8.4 架构演进条件

#### 拆分微服务

只有出现独立扩容、独立团队、故障隔离或数据库负载等真实问题时评估。

#### 引入消息队列

只有轮询形成明确瓶颈，并具备幂等、重放和监控能力时评估。

#### 拆分 Contracts 仓库

只有多团队高频协作和独立 SDK 发布需求出现时评估。

#### Agent 独立更新

只有 Agent 更新频率显著高于 Desktop，且具备签名、回滚和兼容验证能力时评估。

#### 提取 UI 共享包

只有 Cloud Web 与 Desktop 本地页面出现大量稳定复用组件时评估。

#### 引入平台插件体系

只有平台数量明显增长且固定注册成为真实维护瓶颈时评估。

### 8.5 决策记录机制

以下变更必须新增决策记录：

- 新增仓库；
- 拆分微服务；
- 引入消息队列；
- 改变 Contract 归属；
- 改变正式任务创建方；
- 新增支持平台；
- 改变数据事实来源；
- Desktop 获得新的高权限能力；
- 引入动态代码或插件；
- Agent、FFmpeg 改为独立在线更新；
- 修改桌面支持系统。

决策记录至少记录背景、候选方案、最终决策、影响、迁移和回滚。

| 决策 | 结论 |
|---|---|
| 总体架构 | Cloud + Agent + Desktop |

| Contracts | 接口提供方维护 |

| 微服务 / MQ | 首版不建设 |
