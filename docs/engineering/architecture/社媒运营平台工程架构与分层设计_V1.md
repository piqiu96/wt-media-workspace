## 第一章 架构目标与设计原则

### 1.1 架构背景

系统同时包含云端业务管理、Cloud 视频合成、本地浏览器自动化、本地文件落地、辅助发布、互动执行和数据采集。云端生产与必须依赖运营电脑环境的操作使用不同执行边界。

系统采用：

```text
Cloud 云端业务中心与内部 Worker
+
Agent 本地/外部执行端
+
Desktop 本地控制台
```

Agent 分为：

```text
Local Agent：运行在运营电脑
Cloud Agent：运行在云端 Linux
```

Local Agent 与 Cloud Agent 共用同一 Python 核心框架，根据运行模式加载不同能力。M4-M5 视频生产是 ADR-0017 确认的 Cloud-owned 能力，不进入两类 Agent。

### 1.2 架构目标

1. **Cloud 统一管理正式业务事实**  
   用户、权限、素材、成片、发布、互动、正式任务和统计口径均以 Cloud MySQL 为准。

2. **按运行环境划分实际执行**
   Cloud 内部 Worker 承担服务端公开数据任务、文件准备和视频合成；Agent 承担依赖运营电脑、BitBrowser、浏览器登录态、本地文件落地以及平台发布、互动和效果采集的执行。

3. **Desktop 保持轻量**  
   Desktop 负责进程控制、本机能力桥接、状态展示和人工确认，不复制 Cloud 业务规则。

4. **降低一人维护成本**  
   采用少目录、强边界、低抽象、按需演进的方式，避免为未来需求提前建设微服务、插件市场和工作流引擎。

5. **支持多端独立构建与版本管理**  
   Cloud、Agent、Desktop 独立构建、独立发版，通过 Contract 和版本矩阵协作。

6. **保证构建可复现**  
   Python、FFmpeg、浏览器运行时、第三方补丁和跨端协议均需锁定版本、Hash 和兼容关系。

### 1.3 核心设计原则

#### 原则一：Cloud 是业务事实中心

Cloud 最终确认：

- 用户和权限；
- 业务对象状态；
- 正式任务；
- 发布和互动结果；
- 业务配置；
- 审计和统计口径。

Agent 只能上报结构化执行事实，不能直接修改 Cloud 数据库或自行决定正式业务状态。

#### 原则二：本机和外部平台执行通过 Agent，Cloud 自有任务通过内部 Worker

所有依赖以下能力的实际操作统一由 Agent 完成：

- Python 自动化任务；
- 运营电脑本地文件落地与校验；
- 比特浏览器；
- 浏览器自动化；
- 平台抓取；
- 发布和互动；
- 平台效果采集。

不依赖运营电脑环境的 Cloud 自有执行包括：

- M3 公开数据内容发现（ADR-0015）；
- M4-M5 原素材准备、FFmpeg 视频合成、对象存储写入与恢复（ADR-0017）。

Cloud 自有 Worker 不得获得 BitBrowser、Cookie、本机文件路径或浏览器登录态。

#### 原则三：Desktop 是本地控制壳

Desktop 负责：

- Local Agent 启停和健康检查；
- 文件选择；
- 安全存储；
- 系统信息；
- 环境检测展示；
- 人工确认；
- 安装和更新。

Desktop 不直接操作 SQLite、FFmpeg、浏览器和正式业务状态。

#### 原则四：平台差异集中在 Agent

平台页面、元素、状态识别和接口差异集中在：

```text
clients/bilibili
clients/baijiahao
```

Cloud 只保存统一业务对象、平台枚举和必要配置。`douyin` 内容发现按 ADR-0015 归 Cloud 内部 Crawler，不在 Agent 侧保留平台目录。

#### 原则五：固定流程加必要配置

平台执行采用：

```text
代码固定流程
+
必要 JSON 元素配置
```

不建设运营可视化工作流编排器，不允许 Cloud 动态下发 Python 代码。

#### 原则六：保守处理高风险动作

发布提交、评论提交、点赞、收藏、Cookie 写入和 Profile 修改等动作，在结果无法确认时进入 `result_uncertain`，不得盲目自动重试。

#### 原则七：真实问题驱动演进

首版不建设：

- 微服务；
- 消息队列；
- Kubernetes；
- 动态插件市场；
- 独立配置中心；
- 通用离线业务模式；
- 用户自定义脚本；
- 完全无人值守发布；
- 独立 Contracts 仓库。

#### 原则八：同步本地原子操作与长流程编排分离

BitBrowser Local API 的单次调用是同步操作。环境检测、Profile 扫描、单 Profile 创建/修改/开关、单代理写入/解绑、单账号 Cookie 读写和单账号检查，不统一包装为 Cloud 异步任务。

短操作采用：

```text
Desktop 页面
→ Cloud 权限与环境预检
→ Tauri 安全桥
→ Local Agent 同步调用 BitBrowser
→ Agent 立即读回
→ Cloud 校验并保存正式结果
→ 页面展示最终结果
```

批量 Profile、批量代理、批量检查、批量上号、接码轮询和等待人工验证码使用专用 batch/item 业务过程模型。Agent 在每个 item 内仍同步调用 BitBrowser。发布、互动等本地长耗时、可恢复流程继续使用正式异步 Agent 任务；视频合成使用 Cloud 内部 `compose_task`，不创建 Agent task。

同步 HTTP 返回不等于业务成功。凡涉及外部修改，必须完成必要读回；超时且无法证明结果时进入 `result_uncertain` 或人工确认，不能盲目重试。

### 1.4 支持范围

#### 桌面系统

```text
Windows x64
macOS Intel x86_64
macOS Apple Silicon arm64
```

Linux 桌面端不在首版范围内。

#### 平台能力

| 平台 | 内容发现 | 发布 | 互动 | 效果采集 |
|---|---:|---:|---:|---:|
| 抖音 | 支持 | 不支持 | 不支持 | 不作为我方发布效果 |
| B站 | 不支持 | 支持 | 支持 | 支持 |
| 百家号 | 不支持 | 支持 | 支持 | 支持 |

互动动作只包含点赞、收藏和评论。

## 第二章 总体运行架构与核心流转

### 2.1 总体架构

```text
                         ┌────────────────────────────┐
                         │          Cloud             │
Web / Desktop ──────────→│ Go + Hertz Cloud API      │
                         │ MySQL / Object Storage     │
                         │ Scheduler / Worker / FFmpeg│
                         └──────────────┬─────────────┘
                                        │ HTTPS
                                        │ 领取、心跳、进度、结果
                    ┌───────────────────┴───────────────────┐
                    │                                       │
           ┌────────▼────────┐                    ┌─────────▼────────┐
           │   Cloud Agent   │                    │   Local Agent    │
           │ Linux 独立进程   │                    │ 运营电脑本地进程  │
           └─────────────────┘                    └─────────┬────────┘
                                                           │
                                                 127.0.0.1 HTTP + SSE
                                                           │
                                                  ┌────────▼────────┐
                                                  │ Tauri Desktop   │
                                                  └─────────────────┘
```

三项固定边界：

```text
Desktop 不执行重型任务
Agent 不连接 Cloud MySQL
Cloud Worker 不直接操作运营电脑资源
```

### 2.2 三端职责

#### Cloud

负责：

- 用户、权限、账号和业务对象；
- 正式任务创建、租约和结果校验；
- 定时规则扫描；
- 原素材准备、视频合成和成片完整性校验；
- Compose Worker 领取、租约、heartbeat、超时和恢复；
- 对象存储资产；
- 平台配置、审计和统计；
- Cloud API 和 Cloud-Agent API；
- 统一业务 Web。

#### Local Agent

负责：

- 比特浏览器和 Browser Profile；
- Cookie、代理和账号检查；
- 本地文件；
- 原素材和成片下载到运营电脑；
- B站、百家号辅助发布；
- B站、百家号互动；
- 本地任务快照和待回传结果。

#### Cloud Agent

负责：

- B站、百家号效果采集；
- 文件和数据清理。

抖音关键词内容挖掘不在此列：按 ADR-0015 由 Cloud 内部 Crawler 执行，不创建 Cloud Agent 任务，Desktop 不参与。

M4-M5 视频合成同样不在 Cloud Agent 职责内：按 ADR-0017 由 Cloud 内部 Compose Worker 执行，Cloud Agent 不下载合成输入、不调用 FFmpeg、不上传成片。

#### Desktop

负责：

- 登录和本机初始化；
- Local Agent 生命周期；
- 本地环境展示；
- 文件选择；
- 任务实时进度；
- 人工确认；
- 组件更新。

### 2.3 通信关系

#### Web / Desktop 与 Cloud

采用 HTTPS JSON API。

#### Desktop 与 Local Agent

采用：

```text
127.0.0.1 HTTP
+
SSE 实时事件
```

Local Agent 只监听本机回环地址，并使用每次启动生成的本地 Token。Token 仅由 Tauri Rust 层持有。

#### Agent 与 Cloud

采用：

```text
HTTPS API
+
轮询或长轮询
```

首版不使用 MQ、gRPC 或 WebSocket 任务推送。

Cloud 内部 Scheduler 与 Worker 通过 MySQL 业务任务表协作，不通过 Agent API，也不使用 MQ。

### 2.4 正式任务流转

```text
用户或定时规则发起
→ Cloud 校验权限和业务状态
→ Cloud 创建业务对象和正式 task
→ Agent 领取 task
→ Agent 执行前再次校验
→ Agent 分阶段执行并上报
→ Cloud 校验执行事实
→ Cloud 更新正式业务状态
```

依据 ADR-0013 与 ADR-0015，M3 主动链接与关键词查询由 Cloud 内部的受控 Crawler 执行（Cloud Discovery Worker 领取 `crawl_task` 后调用），不创建、分配或执行 Cloud Agent / Local Agent task。链接点击“解析并入池”即给出入池意图，解析成功由 Cloud 创建或更新 `source_content`；关键词搜索未选择结果前不写正式数据。入池结果在关闭自动转素材时不创建 `material`；开启时按产品基线 §4 的 `auto_material` / `material_rule` / 阈值规则自动生成，其余由人工转素材另行提交。博主搜索与作者策略已于 2026-09-23 暂停，不在本期范围。

（2026-09-23 更正：原表述为“由 Cloud Agent 执行”与“均不自动创建 `material`”。前者已被 ADR-0015 取代——该 ADR 的 Supersedes 正指向本句；后者随自动转素材成为 M3 正式能力而调整。见 ADR-0013 增补记录。）

M3 使用统一 `discovery_strategy`（`strategy_type` 本期为 keyword；`author` 已暂停、取值保留），引用受控 `content_channel` 的 `channel_type`。渠道定义能力边界，平台适配由 Cloud 内部的渠道适配器承担（ADR-0015）；Cloud 拥有正式任务、业务合同与来源身份。仅实现抖音；不得按渠道/策略组合复制业务模型或建立通用工作流引擎。具体模型与接口仍由 Cloud 提供方正式合同确定。

依据 ADR-0017，M4-M5 使用 `compose_strategy` 与 `compose_task`：人工或 Scheduler 只创建 `pending compose_task`，Cloud Compose Worker 从 MySQL 原子领取并执行 FFmpeg，成功校验并写入对象存储后才创建 `composite_output`。该链路不创建 `production_rule`、`compose_pool_item` 或 Agent task。

### 2.5 数据事实来源

| 数据类型 | 事实来源 |
|---|---|
| 用户、权限和业务对象 | Cloud MySQL |
| 正式任务和最终状态 | Cloud MySQL |
| 本地执行检查点 | Local SQLite |
| 待回传结果 | Local SQLite |
| 本地文件是否存在 | 本地文件系统 |
| 云端文件是否存在 | 对象存储 |
| Profile 实际状态 | 比特浏览器 |
| 社媒登录状态 | 平台页面和浏览器环境 |
| 平台作品效果 | 最近一次有效采集结果 |

### 2.6 文件流转

#### Cloud 视频生产

```text
Cloud 创建 compose_task
→ Cloud File Transfer Worker 按需准备原素材
→ Compose Worker 校验输入
→ Cloud FFmpeg 合成
→ 校验并上传对象存储
→ 创建 composite_output
```

#### 下载到运营电脑

```text
用户下载原素材或成片
→ Cloud 创建 file_transfer_task(execution_scope=local_agent)
→ Local Agent 使用短时受控下载信息写入本地文件
→ 校验 Hash 并回报进度/结果
```

本地文件只是 `material` 或 `composite_output` 的一处文件位置，不创建第二条素材或成片记录。

### 2.7 断网、退出与恢复

- Local Agent 离线时，本地任务等待，不迁移至 Cloud Agent。
- Desktop 退出时，Local Agent 进入 `draining`，停止领取新任务并保存检查点。**这一动作的落地形态是「请停」而不是「硬杀」**
  （CHG-20260923-059 T-03）：Desktop 在 `RunEvent::Exit` 里发 **SIGTERM** → 等一段宽限（`[sidecar] stop_timeout_ms`，出货 `5000`）
  → 到点仍未退出才强杀；**退出报告必须区分「请停后自己退出」与「被强杀」**——两者都结束，但只有前者证明了在飞请求真的收尾了。
  Agent 侧在 `serve()` 里安置 SIGTERM 处理器，把 `shutdown()` 派到自己的线程，并令 `httpd.daemon_threads = False`：
  `ThreadingHTTPServer` 默认为 `True` 时 `_Threads` **不登记守护线程**，`server_close()` 的 join 会变成空转
  ——「等」的这一半就没了。
- 网络中断时允许保存检查点和待回传结果，不允许启动新的发布和互动任务。
- 会话失效时，Local Agent 停止新的敏感操作。
- 外部结果不明确时进入待核实状态，不自动重复执行。

### 2.8 并发原则

1. 同一 Browser Profile 同时只能执行一个敏感浏览器任务；
2. 同一账号不得并发发布和互动；
3. Agent task 只能被一个 Agent 领取；`compose_task` 只能被一个 Cloud Compose Worker 领取；
4. Cloud 使用任务租约保证领取唯一性；
5. Agent 使用本地资源锁保证本机互斥；
6. 高风险动作不因超时直接重试。

### 2.9 M0/M1 工程就绪门禁

目录、接口占位、Mock 页面、内存 Store 和健康检查不能单独证明工程底座完成。M0/M1 完成后必须形成一个可由运营人工验收的真实端到端环境。

M0 负责真实组件就绪：

- Cloud、Web、Agent、Desktop 均使用正式依赖完成 bootstrap、test、build 和 start/stop；
- Cloud Migration 可在真实 MySQL 上从空库执行；
- Desktop 必须完成真实 Vue/Tauri Rust 构建，echo 脚本和 Mock-only 入口不通过；
- Local Agent 使用可安装包入口启动，健康检查、配置和用户数据目录真实可用；
- CI 执行与本地同语义的 Contract、构建和测试门禁。

M1 负责真实跨端闭环：

- Cloud 的正式 task、租约、幂等和 Agent Registry 持久化到 MySQL，进程重启后仍可恢复；
- `task_schemas` 由 Cloud 作为提供方发布正式版本，非 noop 业务 Executor 不得依赖占位 Schema；
- Local Agent 使用 SQLite 保存检查点、离线待回传结果和恢复游标；
- Desktop 使用真实 Tauri Command 管理 Local Agent 进程、Token、HTTP/SSE 和 Cloud WebView，不使用 Mock 服务冒充验收；
- 人工验收必须完成登录、创建任务、Agent 领取、进度展示、成功回写以及 Cloud/Agent/Desktop 重启恢复。

M0/M1 的历史脚手架和 noop 证据可以复用，但只有满足上述门禁后才能重新标记为 `DONE`。

## 第三章 工程工作区、仓库与协议治理

### 3.1 工程目录与仓库结构

工程采用一个本地跨仓库执行根目录、一个治理仓库和三个运行代码仓库：

```text
wt-media/                              # AI 跨仓库执行根目录，非 Git 仓库
├── .agents/skills/                    # 执行 Skill 副本，prepare_ai_workspace.py 生成
├── .codex/skills/                     # 跨仓库聚合 Skills，sync_skills.py 自动生成
├── .claude/skills/                    # 跨仓库聚合 Skills，sync_skills.py 自动生成
├── wt-media.code-workspace            # 本地 IDE 工作区文件
│
├── wt-media-workspace/                # Git：文档、Skills、决策记录、交付治理
├── wt-media-cloud/                    # Git：Cloud 运行代码
├── wt-media-agent/                    # Git：Agent 运行代码
└── wt-media-desktop/                  # Git：Desktop 运行代码
```

| 目录或仓库 | 是否为 Git 仓库 | 职责 |
|---|---:|---|
| 最外层 `wt-media/` | 否 | Codex / Claude 跨仓库执行根目录和本地聚合配置 |
| `wt-media-workspace` | 是 | 产品文档、架构、协议治理、Skills 源码、决策记录、交付记录和版本矩阵 |
| `wt-media-cloud` | 是 | Go Cloud、统一业务 Web、MySQL、任务控制和 Cloud Contracts |
| `wt-media-agent` | 是 | Local/Cloud Agent、执行器、平台适配器和 Local Agent Contracts |
| `wt-media-desktop` | 是 | Tauri 本地壳、Agent 管理、系统桥接和安装包 |

最外层 `wt-media/` 不初始化为第五个 Git 仓库，也不使用 Git Submodule。四个 Git 仓库保持同级独立。

### 3.2 执行根目录与 Workspace 边界

#### 最外层执行根目录 `wt-media/`

最外层目录用于：

- 同时打开 Cloud、Agent、Desktop 和 Workspace；
- 从一个 AI 会话修改多个仓库；
- 承载跨仓库聚合后的 `.codex/skills` 和 `.claude/skills`，以及 `prepare_ai_workspace.py` 生成的 `.agents/skills/`；
- 承载 `wt-media.code-workspace`（多根工作区定义；它不是本仓脚本的产物）；
- 执行跨仓库 Contract、Skill、版本矩阵和发布检查。

它不是正式事实源，不保存需要人工维护的源码，也不作为运行端的编译或运行依赖。它**不承载**入口文件、执行快照或任何治理事实源：Agent 的入口与权威一律在 `wt-media-workspace` 仓内（`AGENT-INDEX.md` 与两个薄入口）。

#### 治理仓库 `wt-media-workspace`

Workspace 保存：

- 产品需求；
- 工程架构；
- 决策记录；
- 项目级和各端专项 Skills 源码；
- 当前交付记录；
- Contract 归属地图；
- 版本兼容矩阵；
- 发布清单；
- 执行根目录和 Skill 分发模板；
- 跨仓库同步与校验脚本。

Workspace 不保存：

- Cloud、Agent、Desktop 运行代码；
- 数据库 Migration；
- 正式 Contract 源文件；
- 生产配置和密钥；
- Agent、FFmpeg 或安装包等二进制制品。

三个运行仓库不得在编译或运行时依赖 Workspace；最外层执行根目录也不得成为产品运行依赖。

### 3.3 Contracts 归属

原则：

> 谁提供接口，谁维护正式 Contract。

#### Cloud 仓库

```text
contracts/
├── cloud-api/
├── cloud-agent-api/
├── business-schemas/
├── task-schemas/
├── business-enums/
└── cloud-error-codes/
```

#### Agent 仓库

```text
contracts/
├── local-agent-api/
├── local-event-schemas/
├── local-status-enums/
└── local-error-codes/
```

#### Workspace

只维护：

```text
docs/contracts/
├── ownership.md
├── contract-map.md
├── compatibility-policy.md
└── breaking-change-policy.md
```

Desktop 不定义正式 Contract，只消费 Cloud 和 Agent Contract。

### 3.4 Contract 版本

每类 Contract 包含：

```text
API 主版本
+
Contract 修订版本
```

例如：

```text
cloud_api_version = v1
cloud_agent_api_version = v1
local_agent_api_version = v1
contract_revision = 2026.07.14.1
```

运行时只检查版本兼容，不动态下载协议文件。

### 3.5 生成代码

生成代码可提交 Git，但必须：

- 明确标记自动生成；
- 禁止人工修改；
- CI 校验生成结果；
- 生成器版本锁定。

### 3.6 Skills 唯一源码与分类

所有正式 Skill 的唯一事实源统一放在：

```text
wt-media-workspace/skills/
├── common/
├── workspace/
├── cloud/
├── agent/
├── desktop/
└── tool-overrides/
    ├── codex/
    └── claude/
```

分类含义：

| 分类 | 分发范围 |
|---|---|
| `common` | Cloud、Agent、Desktop、Workspace 和跨仓库执行根目录 |
| `workspace` | Workspace 仓库和跨仓库执行根目录 |
| `cloud` | Cloud 仓库和跨仓库执行根目录 |
| `agent` | Agent 仓库和跨仓库执行根目录 |
| `desktop` | Desktop 仓库和跨仓库执行根目录 |
| `tool-overrides` | Codex 或 Claude 确有差异时追加的少量工具专属内容 |

默认只维护一份通用 `SKILL.md`。工具差异通过小型 Override 合并生成，禁止长期维护 `skills-codex`、`skills-claude` 两套完整事实源。

### 3.7 Skills 分发目标

Skills 同时分发到单仓库目录和跨仓库执行根目录。

#### 单仓库分发

```text
wt-media-cloud/
├── .codex/skills/
└── .claude/skills/

wt-media-agent/
├── .codex/skills/
└── .claude/skills/

wt-media-desktop/
├── .codex/skills/
└── .claude/skills/
```

各代码仓库只接收：

```text
common
+
当前仓库专项 Skills
```

这些生成副本提交 Git，以保证：

- 单独克隆和打开仓库即可使用；
- Codex / Claude 启动时不依赖 Workspace 在本机存在；
- CI、沙箱和代码审查可以看到实际使用的 Skill 版本；
- 每个代码版本能够追踪对应 Skill 版本。

#### 跨仓库聚合分发

当一次 AI 任务需要同时修改 Cloud、Agent、Desktop 时，从最外层 `wt-media/` 启动会话，并生成：

```text
wt-media/.codex/skills/
wt-media/.claude/skills/
```

聚合内容为：

```text
common
+
workspace
+
cloud
+
agent
+
desktop
```

根目录聚合副本只用于本地跨仓库会话，不提交 Git，其唯一来源仍是 `wt-media-workspace/skills`。

### 3.8 Skills 同步方式

同步采用确定性的单向复制：

```text
wt-media-workspace/skills
→ 各仓库 .codex/skills 和 .claude/skills
→ 最外层执行根目录 .codex/skills 和 .claude/skills
```

禁止：

- 从生成目录反向同步回 Workspace；
- 直接修改生成后的 `SKILL.md`；
- 使用符号链接跨仓库引用 Skills；
- 让代码仓库在运行时读取 Workspace Skills；
- 靠人工复制维持 Codex 和 Claude 两个目录。

不采用符号链接的原因包括 Windows 权限和检出差异、AI 沙箱可能不跟随仓库外链接、单仓库克隆后链接失效以及不同工具扫描行为不一致。

### 3.9 Skills 分发配置与命名

Workspace 使用明确的分发配置，例如：

```text
wt-media-workspace/config/skills-distribution.yaml
```

配置中定义：

- 目标目录（`path`，相对 workspace 仓库的父目录）；
- 应包含的 Skill 分类（`groups`）；
- 目标工具（`tools`）；
- 目标类型（`kind`：`repository` 需与 `repository-map.yaml` 一致，`distribution` 为非仓库落点）；
- 生成副本是否提交 Git（`commit_generated`）；
- 同步版本标记（`skills_revision`）。

该文件是分发目标的唯一声明，`sync_skills.py` 不得在代码中保留目标清单副本。

跨仓库聚合后所有 Skill 位于同一搜索范围，因此 Skill 名称必须使用明确前缀，例如：

```text
common-architecture-review
cross-repo-change
cross-repo-contract-change
cloud-database-migration
agent-platform-adapter-change
desktop-sidecar-update
release-cross-platform-verification
```

禁止使用容易冲突的泛化名称，如 `testing`、`release`、`architecture`。

### 3.10 同步脚本与一致性校验

Workspace 提供：

```text
wt-media-workspace/scripts/
├── sync_skills.py
├── verify_skills.py
├── verify_ai_workspace.py
├── workspace_config.py
└── prepare_ai_workspace.py
```

推荐能力：

```text
sync_skills.py sync              # 同步全部目标
sync_skills.py sync --repo agent # 只同步 Agent
sync_skills.py sync --tool codex # 只同步 Codex
sync_skills.py check             # 只检查，不修改
sync_skills.py diff              # 展示差异
```

跨仓库会话启动前统一执行：

```text
prepare_ai_workspace.py
→ 检查四个仓库目录
→ 生成执行根 Skill 副本（.agents/skills/executing-wt-media-change）
→ 生成执行状态快照 wt-media-workspace/.ai/CURRENT_CONTEXT.md

sync_skills.py sync
→ 按 config/skills-distribution.yaml 把 skills/ 分发到 5 处落点
```

同步过程必须删除映射中已经移除的旧 Skill，但遇到未登记的未知文件时应停止并提示，不得静默覆盖。

### 3.11 生成标记与同步 Lock

生成的 `SKILL.md` 顶部应包含：

```text
GENERATED FILE — DO NOT EDIT DIRECTLY
Source: wt-media-workspace/skills/...
Source-Hash: sha256:...
```

各代码仓库各自保存：

```text
.skill-sync.lock.json
```

至少记录：

- Skill 同步 Schema 版本；
- Skills 修订版本；
- 源文件树 Hash；
- `.codex/skills` 文件数和目录 Hash；
- `.claude/skills` 文件数和目录 Hash；
- 目标仓库标识。

代码仓库 CI 校验本仓库生成副本，Workspace 全局校验在四个仓库同级存在时检查所有分发目标。最外层执行根目录属于本地缓存，不作为代码仓库 CI 的提交内容。

### 3.12 入口规则与仓库规则

跨仓库执行根目录**不生成、也不承载**任何入口文件。Agent 的入口与权威一律在 `wt-media-workspace` 仓内：`AGENT-INDEX.md` 是治理规范正文与路由的唯一权威源；`AGENTS.md` 与 `CLAUDE.md` 只声明权威源与最小硬约束，不复制正文。

各仓库自行维护：

```text
AGENTS.md
CLAUDE.md
```

仓库规则包含本仓库目录、命令、禁止事项和测试要求，由各仓按实际实现维护。Workspace 说明跨仓关系和共同交付目标，不覆盖目标仓的规则正文；Agent 进入目标仓后按该仓的入口、`AGENT-INDEX.md` 与 `DIRECTORY_MAP.md` 理解本地边界。

### 3.13 跨仓库 AI 会话流程

需要同时修改多个运行端时，标准流程为：

```text
在最外层 wt-media/ 准备 AI 工作区
→ 从 wt-media/ 启动 Codex 或 Claude
→ 读取 wt-media-workspace 的 `AGENT-INDEX.md` 与 cross-repo Skills
→ 判断受影响的 Contract 及提供方
→ 分别修改 Cloud、Agent、Desktop
→ 分别执行各仓库测试
→ 执行跨端 Contract 和集成验证
→ 更新 Workspace 交付记录、兼容矩阵或决策记录
→ 各仓库分别提交
```

跨仓库核心 Skill 至少包含：

```text
cross-repo-change/
└── SKILL.md
```

它应规定先修改接口提供方 Contract，再生成消费端代码，禁止复制三端业务规则，并要求分别输出各仓库变更摘要。

### 3.14 分支和版本

采用：

```text
main
+
短生命周期 feature 分支
+
版本 tag
```

Cloud、Agent、Desktop 独立版本，不要求版本号相同。经过联调的组合记录在 Workspace `release-matrix.yaml`。Skill 变更涉及多个仓库时，Workspace 源码与受影响仓库中的生成副本应在同一个跨仓库变更计划中提交，但仍保持各仓库独立 Commit 和版本历史。

### 4.2 推荐目录

wt-media-cloud/
├── .codex/skills/              # 自动生成并提交 Git
├── .claude/skills/             # 自动生成并提交 Git
├── .skill-sync.lock.json

│   └── server/

│   ├── app/

### 4.3 目录职责

```text
cmd
= 启动入口

internal/app
= 依赖装配、路由和生命周期

internal/modules
= 业务规则和业务接口

internal/infra
= 数据库、日志、对象存储、调度等技术实现

contracts
= Cloud 提供的跨端协议

web
= 统一业务 Web
```

### 4.4 单模块结构

首版保持轻量：

```text
internal/modules/publication/
├── model.go
├── dto.go
├── service.go
├── repository.go
├── handler.go
├── routes.go
├── errors.go
└── service_test.go
```

不强制每个模块建立完整 Clean Architecture 目录，也不强制所有 Repository 定义接口。

### 4.5 调用方向

```text
routes
→ handler
→ service
→ repository
→ infra/database
```

- Handler 负责 HTTP；
- Service 负责业务规则、状态流转和事务；
- Repository 负责 SQL 和持久化；
- Infra 负责通用技术实现。

### 4.6 跨模块规则

普通业务模块不得直接修改或查询其他模块内部表，应通过公开 Service 能力协作。

Analytics 作为只读统计模块，允许通过专用 Read Model、数据库视图或明确的只读查询层跨模块读取，但不得直接修改业务表。

业务链路图只表示领域流转，不等于 Go 包必须形成相同 import 链。编译依赖必须避免循环。

### 4.7 Task 模块

Task 负责：

- 正式任务；
- 任务类型；
- 执行位置；
- 领取和租约；
- 进度和阶段；
- 结果和错误；
- 取消和重试关系。

Task 不决定发布、互动和生产业务是否成功。

M4-M5 `compose_task` 是生产模块内部的业务执行事实，由 Cloud Compose Worker 直接领取；它不复制到通用 Agent Task 模块。通用 Task 仍服务于确需 Agent 执行的发布、互动等跨端流程。

正式 task、租约、幂等键和 Agent Registry 必须持久化到 Cloud MySQL。内存实现只能用于单元测试或显式开发实验，不能作为端到端或生产完成证据。

任务类型的输入、阶段、结果和错误必须由 Cloud 提供方维护的正式 `task_schemas` 定义。`task_schemas` 处于 `placeholder_only` 时，只允许已明确锁定的基础/noop 验证，不允许后续业务 Executor 将占位内容视为正式契约。

### 4.8 定时调度

Cloud 内部使用轻量扫描器：

- 抖音监控策略；
- `compose_strategy` 自动执行配置；
- 效果采集；
- 日级统计；
- 过期文件清理；
- 任务租约回收。

调度器只负责触发和防重复，业务规则仍由对应模块实现。

M3 V2 的周期配置可在策略页面填写，但策略本身不执行、不持有定时器。默认沿用 Cloud 轻量调度边界；若部署受控触发脚本，应经过同一鉴权、启用校验、计划时间幂等和任务创建入口，不能脚本直接写业务表或重复实现规则。每日时刻/间隔、时区及首次触发语义需在合同前明确；本次未决策引入外部调度平台。

`crawl_task` 的 pending/running/success/partial_success/failed 是内容挖掘业务五态（2026-09-23 更正：原表述为四态，缺 `partial_success`），不修改通用技术 `task` 状态机。`partial_success` 的判定为 `processed = added + duplicate + pending + auto_materialized`：`failed > 0` 时 `processed > 0` 为 `partial_success`、`processed == 0` 为 `failed`，否则为 `success`（Web 页面标签依次为 待执行/执行中/成功/部分成功/失败）。自动执行按策略的 `auto_material` 开关、`material_rule`（`AND`/`OR`，其他取值必须拒绝）、`like_threshold` 与 `favorite_threshold` 条件化自动转素材：命中项入池后自动生成 `material`，未命中项留在内容池待人工处理；阈值 >0 才参与判定、≤0 跳过，`auto_material` 为真时至少需要一个正阈值（2026-09-23 更正：原表述为「自动执行仅入池，素材转换由人工操作」）。工作流仅从真实记录派生只读状态，不持久化新的工作流实例（2026-09-23 注：独立的只读业务流转视图本期未交付，Cloud 全仓无相关实现；ADR-0013 第 8 条「不允许编排/拖拽/条件分支/任意脚本」的禁止性约束保持不变，只读流转视图的交付要求移出本期、后续版本再评估）。

真实调度持久化、抢占/防重和重启恢复必须在 M3 第一个定时抓取消费者之前交付。对象存储的上传、校验、生命周期和恢复能力必须在 M5 第一个云端成片消费者之前交付。

M5 自动生产沿用“Scheduler 只创建任务、Worker 统一领取执行”的职责分离。Scheduler 扫描 `compose_strategy.schedule`，以策略、时间槽和素材形成幂等键创建 `pending compose_task`；不得在调度调用栈中下载文件或执行 FFmpeg。

### 4.9 Web 单一事实源

`wt-media-cloud/web` 是业务页面唯一源码，包括内容发现、素材、生产、发布、互动和统计。

Desktop 不复制一套完整业务前端，而是通过 Tauri WebView 承载统一 Cloud Web。Desktop 仅额外维护本地环境、组件、文件和 Agent 控制页面。

远程业务页面不得默认获得本地高权限能力；允许调用的 Tauri Command 必须使用明确白名单和权限范围。

### 4.10 M4-M5 Cloud 视频生产

M4-M5 的正式工程设计见 `docs/engineering/specs/2026-09-24-m4-m5-cloud-content-production.md`。核心边界为：

```text
material / material_usage / compose_strategy
→ compose_task
→ Cloud Compose Worker Pool
→ FFmpeg / FFprobe
→ Object Storage
→ composite_output
```

- HTTP Server 创建和查询业务对象，不同步等待视频生成；
- Worker 通过 MySQL 原子领取、租约和 heartbeat 恢复，不引入 MQ；
- `file_transfer_task` 统一表达 Cloud 输入准备和 Local Agent 本地下载；
- `composite_output` 只在真实文件校验与对象存储落盘后创建；
- Desktop / Local Agent 不执行 FFmpeg。

### 5.1 定位

- Task Runner；
- 取消和重试；
- 进度；

### 5.2 推荐目录

wt-media-agent/

│       ├── runner/             # 任务领取与执行调度
│       ├── executors/          # 任务类型的执行编排
│       ├── clients/            # 外部系统协议
│       ├── services/           # 本机公共能力

├── config/                     # 运行时唯一读取的配置目录
├── config_online/              # 发布替换源，运行时不读取

├── tests/
├── pyproject.toml

├── CLAUDE.md

不保留 `modes/`、`core/`、`communication/`、`runtimes/`、`platforms/`、`generated/`，也不保留根级 `patches/`、`packaging/`。目录职责、依赖方向与配置目录约定的完整定义见 ADR-0016。

### 5.3 `src/wt_media_agent` 的作用

```text
src/
= Python 源码根目录

wt_media_agent/
= 可安装、可导入、可打包的正式 Python 包
```

保留该结构可以避免测试误用仓库根目录源码，并能验证实际安装和 PyInstaller 打包行为。

### 5.4 分层关系

```text
bootstrap
→ runner
→ executors
→ clients / services / storage

runtime    ← 被以上各层引用，自身不依赖任何业务层
local_api  ← 与 runner 平行的本机控制面
```

#### bootstrap

进程装配与生命周期。解析配置、初始化日志与运行目录、按显式有序序列启动组件、处理信号与优雅关闭。是唯一的生产初始化入口，Local / Cloud / sidecar 三种模式各有一个。

#### runner

任务生命周期：领取、租约、资源锁、取消、进度、错误捕获、结果回传、checkpoint 与离线补报。

#### executors

任务类型的执行步骤编排。新增业务能力主要在这一层增加实现。

#### clients

外部系统协议：Cloud API、比特浏览器、平台身份识别与代理。对外部系统暴露类型化方法，统一处理连接、超时、重试与错误映射。

#### services

本机公共能力：浏览器与 CDP、Cookie 读取、网络探测、系统探针。被多个 executor 复用的能力放这里。

#### storage

SQLite 连接、checkpoint 与迁移。

#### runtime

Agent 自身的运行时能力：配置、日志、生命周期、健康检查、上下文、版本、常量与环境上报。改的是 Agent 自己而不是业务时，才动这一层。

#### 依赖方向

依赖只能自上而下。禁止 `clients → executors`、`services → executors`、`utils → 业务层`。`executors/` 不得直接使用 `sqlite3`、`subprocess`、`socket`、`http.client`、`urllib` 或 `requests`；执行器访问外部与存储必须经 clients / services / storage。`utils/` 只放纯函数，禁止业务 Helper。该规则以零依赖的 AST 测试固化。

### 5.6 Local API

Local 模式启动：

```text

+
SSE
```

只提供健康、环境、状态、取消、拉取和关闭等控制能力，不通过本地 API 直接创建正式业务任务。

健康检查分两个端点：

- `GET /healthz`：既有契约路径，字段冻结，不得扩展。
- `GET /api/v1/health`：聚合健康检查，返回 Agent 版本、Agent 状态、Cloud 状态、BitBrowser 状态与 Storage 状态。

聚合健康检查不得触发任何对外写请求（含 heartbeat），也不得因依赖不可用而抛异常，只能把对应状态降级为 `abnormal` 或 `unknown`。

### 5.8 本地目录和日志

仓库中不维护正式 `logs/` 目录。

Local Agent 使用系统用户数据目录：

#### Windows

```text
%LOCALAPPDATA%\WTMedia\Agent\
```

#### macOS

```text
~/Library/Application Support/WTMedia/Agent/
~/Library/Logs/WTMedia/Agent/
```

开发环境使用：

```text
wt-media-agent/.local/
```

Cloud Agent 默认输出结构化日志到 stdout/stderr。

用户数据目录内部再分三类，均懒创建：

```text
data/          # SQLite 数据库
logs/          # agent.log、task.log、error.log
versions/      # 版本与升级产物
```

三个日志文件**同时**存在于开发态：`<repo>/.local/logs/`（CHG-057 T-03，此前开发态只走 stderr、一个文件也不写）。
它们是**纯文本**，各自**按小时轮转**：正在写的恒为稳定默认文件 `agent.log`，每小时结束的归档名为
`agent.log.<YYYY-MM-DD-HH>`（本机时区；`task`/`error` 同理）。**只按天保留**（默认 14 天，超期自动删除），
**没有单文件上限也没有总量预算**；单条超长截断并标
`truncate=true original_size=<n>`（默认阈值 1 MiB，与 Desktop 同值同形）。`agent.log` 全量且是唯一含
traceback 的文件，`task.log` 只收 `wt_media_agent.runner.*`，`error.log` 只收 ERROR 且每行带 `error_code`。
数值与口径的权威落点是
[程序总纲 §3 CHG-B](../specs/2026-09-23-launch-engineering-optimization-program.md)。

Desktop 拥有自己的一份，与 Agent 互不转存：`~/Library/Logs/WTMedia/Desktop/`（开发态
`<repo>/.local/logs/`），稳定文件 `desktop.log`、归档 `desktop.log.<YYYY-MM-DD-HH>`，保留与截断阈值同上；
只记 Desktop 自身的启动退出、配置加载、Agent 启停与健康检查、sidecar 异常退出。
两份日志都不靠命名冲突防护多实例，而靠**单实例守卫**（Desktop `tauri-plugin-single-instance`、
Agent 单绑定 8765）。

Desktop 的运行目录是**四个根**，由 `src-tauri/src/app_paths.rs` 解析（CHG-20260923-058 T-03）：数据根、
`versions`、日志根、缓存根。它与上面 Agent 的布局有一处**有意的不对称**——装机态的数据根**就是**组件目录，
开发态整体下沉一层：

```text
~/Library/Application Support/WTMedia/Desktop/            # 数据根（settings.toml 在这里）
~/Library/Application Support/WTMedia/Desktop/versions/   # 版本与升级产物
~/Library/Logs/WTMedia/Desktop/                           # 日志（上文那棵）
~/Library/Caches/WTMedia/Desktop/                         # 缓存
```

开发态：`<repo>/.local/{data,data/versions,logs,cache}`。

**缓存不在数据根之内**：macOS 的 `~/Library/Caches` 本就是系统可以自行清理的位置，缓存放进去是照约定，
不是疏忽。后果要记住：清理命令要保护的「数据根」与它要清的「缓存根」是**两个不同的根**，不是父子关系
（`commands::storage::Resolved` 因此同时解析两者，清理命令只碰后者）。`cache` 是 CHG-C 才入基线的目录
（此前只有 `data`/`logs`/`versions`），**只有 Desktop 有它，Agent 侧没有**。

**配置不在数据目录内。** 配置随产物分发，不随用户数据走，因此始终读仓库根或安装目录下的 `config/`，见 ADR-0016 第 6 条。

**出货配置怎么进产物**（CHG-20260923-059 T-05）：发布替换的**动作发生在产物上**——打包完成后由
`scripts/stage-release-config.sh` 把 `config_online/` 整目录覆盖进 `.app` 的 `Contents/Resources/config`，
**不写进 `tauri.conf.json` 的 `bundle.resources`**：Tauri 会拒绝匹配不到任何文件的 glob
（`glob pattern config/* path not found or didn't match any files.`），于是**任何还没跑过发布步骤的检出都编译不过**。
冻结后的 Agent 由**可执行文件的位置**推导配置目录（`.app` 里是 `Contents/Resources/config`，
否则可执行文件旁边的 `config/`），两处都命中不了时先 `WARNING` 再回落内置默认值——
「发布包没带配置」正是安静回落会藏住的那件事。凭证**不从这两个目录来**（ADR-0016 第 7 条）。

### 5.11 视频合成边界

Local Agent 只负责把原素材或成片下载到运营电脑并执行文件大小与 Hash 校验。若未来 Agent 因其他独立能力需要 FFmpeg，必须另建 Decision，不能恢复本地视频合成作为隐式依赖。

### 6.5 Agent 生命周期

```text
Desktop 启动
→ 校验 Agent 和组件
→ 启动 Local Agent
→ 等待运行文件
→ 健康检查
→ 建立事件连接
```

**「校验」的具体形态在 CHG-20260923-059 T-04 落定**：先读包内 `Contents/Resources/sidecar-manifest.json`，
按 SHA-256 比对**要启动的那个文件**，不通过就拒绝启动并说清原因，且**不回退**到 Python 调试路径
（安静回退会把「包坏了」变成「开发环境里好好的」）。没有记录时**工程树容忍、包里拒绝**
（`cargo test` 的树里没有记录，不这样区分就起不了 Agent）。这份记录写在 sidecar 的 ad-hoc 签名**之后**、
外层签名**之前**——签名会改写文件，签名之后写进去的字节不会再被封面盖住。它是**包一致性检查**，
不是用来对抗能改包者的安全边界（ad-hoc 签名没有信任锚）。

**「健康检查」是两段式闸门（T-02）**：第一信号是 Agent 在 `bind` + `listen` **之后**打印的 readiness 行，
第二信号是 `/healthz` 真的应答；`[sidecar] start_timeout_ms`（出货 `15000`）是这道闸门的真超时。
**认证失败是致命的第三态**：令牌漂移时 `/healthz` 在 `_check_auth` 之后答 **401** ⇒ 立即失败，不等超时。
「实例已在运行」也在这条链上：`already_running` 只在受管槽位**非空**时才真的问一次 `/healthz`
——槽位为空时**一个请求都不发**（那个端口上可能是开发机上别人的 Agent）；句柄在而 Agent 不应答 ⇒
如实报「未在运行」、丢弃句柄并允许重启。

以上流程必须由真实 Tauri/Rust 和 Local Agent 进程完成。仅存在 Rust 模块文件、前端 Mock Service、静态状态页或健康检查脚本，不构成 Desktop 已完成的证据。

退出：

```text
Agent 进入 draining
→ 停止领取新任务
→ 保存检查点
→ 正常关闭
→ 超时后才允许强制终止
```

**落地形态（T-03）**：`RunEvent::Exit` → SIGTERM → 宽限 `[sidecar] stop_timeout_ms`（出货 `5000`）
→ 到点才强杀；报告区分「请停后自己退出」与「被强杀」。Agent 侧 SIGTERM 处理器把 `shutdown()`
派到自己的线程，且 `daemon_threads = False`——否则 `server_close()` 的 join 是空转，「等」的这一半等于没有。

历史 `m0_scaffold_health`、noop 和局部 M2 release 只证明其记录范围内的事实，不自动满足重新修订后的 M0/M1/M2 里程碑退出门禁。里程碑状态以 `delivery/MASTER_IMPLEMENTATION_PLAN.md` 的当前退出条件和最新综合 Evidence 为准。

**桌面产物侧的五类版本各有来源（CHG-20260923-059 T-06 落定）**：Desktop（`tauri.conf.json` 的版本）、
Agent（包版本）、**前端构建**（workspace 复制构建产物时 stamp，此前无任何表示）、
**Contract**（`config/contract-map.yaml`，跨仓修订号的权威落点）、
**组件与资源**（`Contents/Resources` 逐文件 sha256 的合并摘要）。第五类是**内容摘要**而不是被人递增的号——
没有「谁来 bump」这个问题，改了内容摘要就变。出包时写一份 `versions.json` 进产物、另复制一份到发布目录并进
`SHA256SUMS`；挂载 DMG 后 `--verify` 复算出同一摘要，两处不一致即说明产物在签名后被动过。

**Desktop ↔ sidecar 的版本关系是 pin 而不是等值**：`src-tauri/agent-compat.json` 记录受支持的 Agent 范围，
不匹配**必拒**；**改 pin 即评审**——兼容是评审闸门，不是「版本号相等」这个算术事实。

> 以下为 M0 时点（`0.1.0-m0-health`）的历史发布快照，`contract_state: placeholder_only` 只代表该时点状态；当前正式契约状态以 `docs/contracts/contract-map.md` 为准。

### 7.10 更新和回滚

首版 Desktop、Local Agent 和 Python 补丁作为一组发布。Cloud FFmpeg / FFprobe 随 Compose Worker 镜像独立锁定和发布。

不允许运行时：

- `pip install`；
- 在线修改 Python 依赖；
- 从未知地址下载 FFmpeg；
- 用户自行选择组件版本。

Cloud 回滚需保留 API、Scheduler、Worker 旧镜像和数据库备份。Desktop 程序目录与用户数据目录分离，程序回滚不得删除用户数据。

**「升级不覆盖用户数据」的判据是路径，不是名字清单（CHG-20260923-059 T-07 落定）**：受保护的是一组**路径**
——数据根下除 `settings.toml` 与 `versions/` 之外的一切，含 SQLite、检查点与待回传结果。写成路径而不是
「哪些文件名要保护」的清单，是因为清单会随功能增长而漏项，而「数据根里除这两样以外的东西都不是安装器的」
不需要跟着功能更新。**本程序不实现升级器**：交付的是这条判据，没有升级动作可供验证——
成功事实 #8 因此是**路径判据**而非实测读数。

## 第八章 架构边界、验收与演进原则

### 8.1 全局责任

```text
Cloud
= 业务事实、规则、权限、正式任务和 Cloud 自有 Worker

Agent
= 运营电脑本地能力、浏览器自动化和外部平台执行

Desktop
= 本地控制、系统桥接和人工交互

Workspace
= 文档、Skills 源码、决策记录和跨仓库治理

最外层 wt-media/
= Codex / Claude 跨仓库执行根目录和聚合配置
```

### 8.2 全局禁止事项

1. Agent 直接连接 Cloud MySQL；
2. Desktop 直接读取 Agent SQLite；
3. Vue 直接访问 Local Agent；
4. Cloud 直接控制运营电脑浏览器；
5. Agent 自行创建正式业务任务；
6. Agent 自行决定正式业务状态；
7. 普通业务模块直接修改其他模块数据；
8. Handler 直接执行 SQL；
9. Runtime 承载平台业务规则；
10. Platform Adapter 修改 Cloud 状态；
11. 将 SQLite 建设成完整离线业务库；
12. 高风险外部动作盲目自动重试；
13. Cloud 动态下发 Python 代码；
14. 用户上传执行脚本；
15. 正式运行依赖系统 Python；
16. Cloud Compose Worker 依赖系统 PATH 中的 FFmpeg，或 Desktop / Agent 执行视频合成；
17. 手工修改 `site-packages` 作为发布方案；
18. 构建时使用未锁定最新版依赖；
19. 测试环境操作正式 Profile 和账号；
20. 敏感信息进入普通日志；
21. 运行端依赖 Workspace 才能启动；
22. 直接修改生成后的 `.codex/skills` 或 `.claude/skills`；
23. 使用跨仓库符号链接代替 Skill 分发；
24. 跨仓库 AI 会话在未校验根 Skills 和 Contract 的情况下开始修改；
25. 未经决策记录改变仓库、协议或事实来源；
26. 复述代码、记录变更史或为决策辩护的注释。

### 8.3 架构验收

#### 仓库

- 四个仓库职责清晰；
- 最外层 `wt-media/` 明确为非 Git 的跨仓库执行根目录；
- 三个运行仓库可独立构建；
- Workspace 不包含运行代码；
- 不使用 Git Submodule 和跨仓库 Skill 符号链接；
- 各仓库保留 `AGENT-INDEX.md`、`AGENTS.md`、`CLAUDE.md`；三个运行仓库另有 `DIRECTORY_MAP.md`。Workspace 入口提供项目概览，运行仓入口说明如何进入本仓规则；各仓正式规则归各自的 `AGENT-INDEX.md`，运行仓目录事实与禁止扫描区归 `DIRECTORY_MAP.md`；
- 各仓库 `.codex/skills`、`.claude/skills` 与同步 Lock 一致；
- 根执行工作区能够由 `prepare_ai_workspace.py` 确定性重建；
- 版本组合可追踪。

#### Cloud

- 模块化单体；
- Handler、Service、Repository 边界清晰；
- 普通模块不跨表修改；
- Analytics 只读；
- 长任务按执行环境交给 Cloud Worker 或 Agent；
- Migration 独立管理。
- 正式任务、租约、幂等和 Agent Registry 使用 MySQL 持久化；
- Scheduler 在首个定时业务消费者前完成重启恢复和防重验收；
- Object Storage 在首个云端成片消费者前完成完整性和恢复验收。
- Compose Worker 的有界并发、租约、heartbeat、超时、重试和真实 FFmpeg 媒体验收通过。

#### Agent

- Local/Cloud 共用 Core；
- 模式依赖分离；
- `src/wt_media_agent` 为正式包；
- Local Agent 不依赖系统 Python；
- Local / Cloud Agent 不执行 M4-M5 视频合成；
- 第三方修改通过 Patch 和定制 Wheel；
- SQLite 只承担本地执行状态；
- 高风险动作有待核实机制。

#### Desktop

- 统一业务 Web 不重复开发；
- 本地页面和高权限能力由 Desktop 管理；
- Rust 统一代理 Agent；
- Token 不暴露给 Vue；
- 三个平台分别构建；
- 安装目录与用户数据分离。
- Vue/Tauri Rust 能真实构建和启动，不接受 echo 或 Mock-only 验收；
- 能真实管理 Local Agent 生命周期并代理 HTTP/SSE；
- 能在同一人工链路中承载 Cloud Web、展示任务进度并验证重启恢复。

#### Contract

- Contract 归提供方；
- 消费端生成代码不可人工修改；
- 版本可追踪；
- 主版本不兼容时禁止敏感操作。
- 非 noop 业务 Executor 开始前，提供方必须发布对应正式 `task_schemas`。

#### 测试和发布

- 四环境隔离；
- 构建可复现；
- 依赖和组件锁定；
- 各目标平台完成冒烟测试；
- 发布组合进入 Workspace；
- 失败测试保留脱敏诊断产物。

### 8.4 架构演进条件

#### 拆分微服务

只有出现独立扩容、独立团队、故障隔离或数据库负载等真实问题时评估。

#### 引入消息队列

只有轮询形成明确瓶颈，并具备幂等、重放和监控能力时评估。

#### 拆分 Contracts 仓库

只有多团队高频协作和独立 SDK 发布需求出现时评估。

#### Agent 独立更新

只有 Agent 更新频率显著高于 Desktop，且具备签名、回滚和兼容验证能力时评估。

#### 提取 UI 共享包

只有 Cloud Web 与 Desktop 本地页面出现大量稳定复用组件时评估。

#### 引入平台插件体系

只有平台数量明显增长且固定注册成为真实维护瓶颈时评估。

### 8.5 决策记录机制

以下变更必须新增决策记录：

- 新增仓库；
- 拆分微服务；
- 引入消息队列；
- 改变 Contract 归属；
- 改变正式任务创建方；
- 新增支持平台；
- 改变数据事实来源；
- Desktop 获得新的高权限能力；
- 引入动态代码或插件；
- Agent、FFmpeg 改为独立在线更新；
- 修改桌面支持系统。

决策记录至少记录背景、候选方案、最终决策、影响、迁移和回滚。
