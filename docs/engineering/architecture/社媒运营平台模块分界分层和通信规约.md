# 模块化自媒体运营平台：前端、Desktop 与 Agent 架构边界及通信规约

## 1. 文档目的

本文用于统一以下架构决策和执行边界：

1. `wt-media-cloud`、`wt-media-desktop`、`wt-media-agent`、`wt-media-workspace` 各自负责什么；
2. Cloud 与 Desktop 前端页面如何组织、复用和独立构建；
3. 共享模块、Cloud 独有模块、Desktop 独有模块如何划分；
4. Desktop 前端应如何调用 Cloud API、Tauri Runtime 和本地 Agent；
5. 纯 Cloud、纯本地和混合业务分别采用什么通信链路；
6. 哪些依赖方向允许，哪些实现方式禁止；
7. 后续 Codex、开发人员和代码评审应遵守哪些规则。

---

# 2. 核心架构结论

## 2.1 Cloud 与 Desktop 是两个独立前端应用

Cloud 和 Desktop 分别拥有：

- 独立入口；
- 独立路由；
- 独立菜单；
- 独立布局装配；
- 独立构建产物；
- 各自独有页面和能力。

但二者不维护两套重复的 Vue 源码。

```text
Cloud App
= 共享基础能力
+ 共享业务模块
+ Cloud 独有页面
+ Cloud 路由和菜单
```

```text
Desktop App
= 共享基础能力
+ 共享业务模块
+ Desktop 独有页面
+ Desktop 路由和菜单
+ Tauri Runtime
```

## 2.2 所有 Vue 源码统一放在 `wt-media-cloud/web`

当前阶段不增加新的前端仓库。

```text
wt-media-cloud/web/
└── 唯一 Vue 前端源码工程
    ├── Cloud App
    ├── Desktop App
    ├── 共享业务模块
    └── 共享基础能力
```

需要区分物理位置与逻辑归属：

- 物理上，Vue 源码位于 `wt-media-cloud/web`；
- 逻辑上，`apps/desktop` 属于 Desktop 前端应用；
- `apps/desktop` 不属于 Go Cloud 后端业务；
- `wt-media-cloud/web` 实际承担的是统一前端工程职责。

后续规模足够大时，可以再考虑拆分为 `wt-media-frontend`，当前阶段不拆。

## 2.3 `wt-media-desktop` 不再保存 Vue 页面

`wt-media-desktop` 删除或迁出：

- `index.html`；
- Vite 配置；
- Vue 入口；
- Vue 页面；
- Vue Store；
- Vue Service；
- TDesign、Pinia 等前端依赖。

但 `wt-media-desktop` 不是简单的通信转发仓库。它负责：

- Tauri 窗口与生命周期；
- 系统托盘；
- 本地文件系统；
- 本地 Agent 进程管理；
- 环境检测；
- 安全存储；
- 软件更新；
- 安装包、签名、图标和发布；
- Vue 与本机系统之间的原生桥接。

# 3. 四个仓库的最终职责

| 仓库 | 核心职责 |
|---|---|
| `wt-media-cloud` | Go 云端后端、OpenAPI、数据库迁移、全部 Vue 前端源码 |
| `wt-media-desktop` | Tauri 原生壳、本机系统能力、安装包和客户端更新 |
| `wt-media-agent` | Python 自动化执行、浏览器控制、合成、发布和互动执行 |
| `wt-media-workspace` | 多仓库开发、版本锁定、联合构建、发布脚本和架构文档 |

# 5. 前端三层边界

## 5.1 `apps`：应用装配层

`apps` 负责定义当前构建的是哪个应用，主要职责包括：

- 应用入口；
- 路由组合；
- 菜单组合；
- 平台布局；
- Runtime 注入；
- 平台独有页面。

`apps` 层不承载大量共享业务逻辑。

### Cloud 独有页面

- 用户管理；
- 角色权限；
- 云端系统设置；
- 全局生产规则；
- 云端 Agent 管理；
- 技术管理页面。

```text
apps/cloud/pages/
├── users/
├── roles/
├── cloud-settings/
└── cloud-agent/
```

### Desktop 独有页面

- 本地 Agent 状态；
- 本地日志；
- 本地环境检测；
- 本地设置；
- 软件更新；
- 客户端关于页面；
- 本地缓存和路径管理。

```text
apps/desktop/features/
├── local-agent/
├── local-logs/
├── environment/
├── local-settings/
└── updater/
```

## 5.2 `modules`：共享业务模块层

Cloud 和 Desktop 都需要使用的业务功能放入 `modules`。

| 模块 | Cloud | Desktop |
|---|---:|---:|
| 工作台 | 使用 | 使用 |
| 内容发现 | 使用 | 使用 |
| 素材管理 | 使用 | 使用 |
| 合成任务 | 使用 | 使用 |
| 成片管理 | 使用 | 使用 |
| 发布管理 | 使用 | 使用 |
| 互动管理 | 使用 | 使用 |
| 媒体账号 | 使用 | 使用 |
| 任务中心 | 使用 | 使用 |
| 数据统计 | 使用 | 使用或精简使用 |

每个业务模块建议包含：

```text
modules/tasks/
├── pages/
├── components/
├── api.ts
├── store.ts
├── routes.ts
├── types.ts
├── utils.ts
└── index.ts
```

前端模块按照用户任务和操作场景划分，不要求与 Go 后端模块一一对应。

## 5.3 `shared`：通用基础层

`shared` 只能包含不依赖具体业务、不依赖特定平台的代码。

可以包含：

- Design Token；
- 通用页面容器；
- 通用表格；
- 基础状态组件；
- HTTP 客户端；
- 通用错误处理；
- 分页 Composable；
- Runtime 接口；
- 日期、字符串和校验工具。

不能包含：

- 素材领取；
- 发布执行；
- 账号绑定业务；
- Agent 进程控制；
- 本地日志读取；
- 软件更新实现；
- Tauri `invoke` 调用。

只要代码直接依赖以下内容，就不能放入 `shared`：

```text
@tauri-apps/*
invoke(...)
本地文件路径
本地进程
系统托盘
软件更新
本地 Agent
安全存储
操作系统信息
```

---

# 6. 模块依赖方向

允许：

```text
apps → modules
apps → shared
modules → shared
```

禁止：

```text
shared → modules
shared → apps
modules → apps
```

业务模块之间不得随意深入引用彼此内部文件。每个模块通过 `index.ts` 暴露稳定公共接口。

---

# 7. Cloud 与 Desktop 的路由边界

不再使用一套路由表加大量 `desktopOnly` 守卫。

```text
apps/cloud/router.ts
apps/desktop/router.ts
```

Cloud 路由：

```text
共享业务路由
+ Cloud 独有路由
```

Desktop 路由：

```text
共享业务路由
+ Desktop 独有路由
```

这样可保证：

- Cloud 不包含 Desktop 独有页面；
- Desktop 不包含 Cloud 管理页面；
- 菜单和权限逻辑清晰；
- 构建边界明确；
- 避免页面中到处判断 `isDesktop`。

---

# 8. Cloud 与 Desktop 的页面复用原则

共享业务不代表两个平台的全部操作完全一致。

例如发布管理：

| Cloud | Desktop |
|---|---|
| 创建发布任务 | 创建发布任务 |
| 查看任务状态 | 查看任务状态 |
| 查看失败原因 | 查看失败原因 |
| 不直接操作本机 | 立即执行 |
| 不打开本地浏览器 | 打开浏览器 |
| 不读取本地日志 | 查看本地日志 |

差异较小时，共用页面，通过 Capability 控制操作。

差异较大时，采用：

```text
共享 Workspace 组件
+ Cloud 薄包装页
+ Desktop 薄包装页
```

禁止复制整套页面。

# 9. Runtime 与 Capability 边界

平台无关接口放在：

```text
shared/runtime/
```

```ts
export interface AppRuntime {
  capabilities: RuntimeCapabilities

  openLocalFolder(path: string): Promise<void>
  openLocalLog(taskId: string): Promise<void>
  executeLocalTask(taskId: string): Promise<void>
}
```

Desktop Runtime 调用 Tauri：

```text
apps/desktop/runtime/
├── tauri-runtime.ts
├── filesystem-runtime.ts
├── local-agent-runtime.ts
├── updater-runtime.ts
└── secure-store-runtime.ts
```

业务模块不允许直接检测 `__TAURI_INTERNALS__`，页面中也不允许直接大量调用 `invoke()`。

# 10. 三类通信模型

系统通信统一分成：

1. 前端直接调用 Cloud；
2. Desktop 前端通过 Tauri 调用 OS 或本地 Agent；
3. Cloud、Desktop、Tauri、Agent 共同参与的混合业务流程。

---

# 11. 通信模型一：前端直接调用 Cloud

## 11.1 适用范围

适用于纯云端业务数据的读取和修改：

- 登录与用户信息；
- 内容发现；
- 素材库；
- 媒体账号；
- 用户权限；
- 发布记录；
- 互动任务；
- 数据统计；
- 云端配置；
- 任务定义和最终状态。

## 11.2 示例：查询素材库

```text
MaterialListPage.vue
        ↓
modules/materials/api.ts
        ↓
shared/api/http.ts
        ↓ HTTPS
wt-media-cloud/cmd/server
        ↓
HTTP Router / Middleware
        ↓
internal/modules/material
        ↓
Repository / MySQL
        ↓
返回素材列表
```

Cloud 与 Desktop 复用同一套页面主体、API、类型、Store、筛选和分页逻辑。

## 11.3 边界要求

该流程不经过：

- Tauri Runtime；
- Rust Command；
- 本地 Agent。

普通业务请求不得设计为：

```text
Desktop Vue
→ Tauri
→ Rust HTTP Client
→ Cloud API
```

## 11.4 原则

> 只涉及云端业务数据和云端状态时，Vue 前端直接调用 Cloud API。

---

# 12. 通信模型二：Desktop 调用 OS 或本地 Agent

## 12.1 适用范围

适用于必须访问本机的能力：

- 打开本地目录；
- 读取本地日志；
- 选择文件；
- 检测依赖环境；
- 启停本地 Agent；
- 获取 CPU、内存和磁盘信息；
- 控制窗口和托盘；
- 软件更新；
- 安全存储。
- BitBrowser 环境检测、Profile 扫描及单项短操作；
- 单 Profile 创建、修改、打开、关闭及读回；
- 单代理写入、解绑及读回；
- 单账号 Cookie 读写和账号检查。

这些本地短操作必须先完成 Cloud 权限、当前会话、Desktop 节点、`main_user_id`、Profile授权和敏感操作互斥校验，再由 Tauri 调用 Local Agent。页面不得直接访问 Local Agent 端口，也不得持有 Local Agent 动态凭据。

## 12.2 示例：打开本地日志目录

```text
LocalLogsPage.vue
        ↓
apps/desktop/features/local-logs/service.ts
        ↓
apps/desktop/runtime/filesystem-runtime.ts
        ↓ Tauri invoke
command: open_log_directory
        ↓
wt-media-desktop/src-tauri/src/commands/filesystem.rs
        ↓
wt-media-desktop/src-tauri/src/services/filesystem/
        ↓
操作系统文件管理器
```

## 12.3 职责拆分

### Vue 页面

负责展示、按钮、加载、进度、错误和用户确认。

### Desktop Runtime

负责封装 Tauri Command 名称、转换参数、统一错误和隐藏底层实现。

### Rust Command

负责接收参数、参数与权限校验、调用 Service 和返回标准结果。

### Rust Service

负责真正访问操作系统、限制路径、管理进程和处理系统错误。

## 12.4 示例：启动本地 Agent

```text
AgentStatusPage.vue
        ↓
local-agent/service.ts
        ↓
local-agent-runtime.ts
        ↓ Tauri invoke
command: start_local_agent
        ↓
commands/agent.rs
        ↓
services/local_agent/process.rs
        ↓
启动 wt-media-agent
```

启动后，Tauri 继续负责：

```text
端口检测
→ 健康检查
→ 版本校验
→ 状态事件通知前端
```

## 12.5 边界要求

页面不得直接写：

```ts
invoke('start_local_agent')
```

必须通过：

```text
页面
→ Desktop Feature Service
→ Desktop Runtime
→ Tauri Command
→ Rust Service
```

Cloud Web 不得导入 `@tauri-apps/*` 或 `apps/desktop/runtime`。

# 13. 通信模型三：混合业务调用

混合业务同时涉及：

- Cloud 业务数据；
- Desktop 本地执行；
- Tauri 进程和系统能力；
- Python Agent 自动化；
- 执行进度与最终结果回写。

典型场景包括发布、互动、本地合成、批量浏览器操作、批量上号、接码轮询和等待人工验证码。

混合流程不等于所有步骤都异步。批量流程由 Cloud 保存 batch/item 过程状态，Local Agent 在单个 item 内同步调用 BitBrowser，并把读回后的结果投影回 Cloud。只有发布、互动、合成等长耗时流程或确需租约恢复的通用执行才创建正式异步 task。

## 13.1 示例：执行一条发布任务

### 第一阶段：Cloud 创建任务

```text
DesktopPublicationPage.vue
        ↓
modules/publication/api.ts
        ↓
shared/api/http.ts
        ↓ HTTPS
wt-media-cloud API
        ↓
internal/modules/publication
        ↓
创建 publication
创建 execution task
        ↓
MySQL
```

Cloud 返回：

```text
publication_id
task_id
task_status = pending
```

Cloud 是该任务的唯一事实来源。

### 第二阶段：Desktop 请求本地执行

```text
DesktopPublicationPage.vue
        ↓
publication-local-execution.service.ts
        ↓
local-agent-runtime.ts
        ↓ Tauri invoke
command: execute_publication_task
        ↓
commands/agent.rs
        ↓
services/local_agent/
```

传给 Tauri 的内容应尽量精简：

```text
task_id
execution_token
必要的本地执行参数
```

不建议由 Vue 将完整业务对象直接传给 Agent。

### 第三阶段：Tauri 启动或通知 Agent

```text
确认 Agent 是否运行
        ↓
未运行则启动 Agent
        ↓
执行健康检查
        ↓
向 Agent 下发 task_id
```

```text
Tauri local_agent service
        ↓
本地 HTTP / IPC / stdin 协议
        ↓
wt-media-agent
```

推荐 Agent 使用短期执行凭证读取 Cloud 任务快照：

```text
Agent
  ↓ task_id + execution_token
Cloud API
  ↓
获取经过授权的任务快照
```

只有 Agent 不允许联网或必须由 Desktop 统一控制凭证时，才由 Tauri 获取任务后转发给 Agent。

### 第四阶段：Agent 执行自动化

```text
打开指定浏览器 Profile
        ↓
进入发布页面
        ↓
上传本地成片
        ↓
填写标题和其他元素
        ↓
提交或辅助完成发布
        ↓
获取发布结果和链接
```

Tauri 负责 Agent 生命周期，但不实现平台发布流程。

### 第五阶段：上报进度

本地即时状态：

```text
Agent
→ Tauri Event
→ Desktop Vue
```

用于实时进度、当前步骤和本地日志。

Cloud 持久状态：

```text
Agent 或 Tauri
→ Cloud API
→ 更新 task 状态
```

用于持久化、跨设备查看、审计、重试和最终状态。

本地事件不能成为最终业务状态来源。

### 第六阶段：回写结果

成功时：

```text
task_id
publication_id
status = success
published_url
published_at
account_id
execution_summary
```

失败时：

```text
task_id
status = failed
error_code
error_message
failed_step
retryable
```

```text
Agent / Tauri
        ↓ HTTPS
Cloud Task API
        ↓
internal/modules/publication
internal/modules/task
        ↓
更新 publication
更新 task
记录执行日志摘要
```

### 完整时序

```text
用户
 │
 │ 点击“执行发布”
 ▼
Desktop Vue
 │
 │ 1. 创建发布任务
 ▼
Cloud API
 │
 │ 保存 publication / task
 │ 返回 task_id
 ▼
Desktop Vue
 │
 │ 2. 请求本地执行
 ▼
Tauri Runtime
 │
 │ 3. 启动或通知 Agent
 ▼
Python Agent
 │
 │ 4. 获取任务快照
 ├──────────────────────► Cloud API
 │                         │
 │ ◄──────────────────────┤
 │
 │ 5. 执行浏览器发布
 ▼
目标平台
 │
 │ 返回发布结果
 ▼
Python Agent
 │
 ├── 本地进度事件 ───────► Tauri ─────► Desktop Vue
 │
 └── 最终结果回写 ───────► Cloud API
                              │
                              ▼
                       publication / task
                              │
                              ▼
                         Desktop Vue 查询
```

# 14. 三类通信的判断规则

| 判断问题 | 是 | 通信方式 |
|---|---:|---|
| 是否只操作云端业务数据？ | 是 | Vue → Cloud |
| 是否需要访问本机文件、进程或系统？ | 是 | Vue → Tauri |
| 是否是短时、单项、可立即读回的 BitBrowser 操作？ | 是 | Vue → Cloud预检 → Tauri → Agent同步执行与读回 → Cloud投影 |
| 是否是批量、等待人工或需要逐项恢复的浏览器流程？ | 是 | Cloud batch/item → Tauri → Agent逐项同步执行 |
| 是否是发布、互动、合成等长耗时流程？ | 是 | Vue → Cloud创建异步任务 → Tauri → Agent |
| 是否需要保存最终业务状态？ | 是 | 写入 Cloud |
| 是否只是展示本地即时进度？ | 是 | Agent → Tauri Event → Vue |
| 是否需要跨设备查看状态？ | 是 | 必须回写 Cloud |

# 15. Cloud、Tauri 与 Agent 的职责边界

## 15.1 Cloud 负责

- 业务数据；
- 用户与权限；
- 任务定义；
- 任务分配；
- 任务最终状态；
- 业务配置；
- 统计和审计；
- 跨设备同步；
- 最终结果记录。
- 本地短操作的授权预检、操作许可、正式结果校验和业务投影；
- 批量Profile、代理、检查和上号的batch/item过程事实。

## 15.2 Tauri 负责

- Agent 启停和健康检查；
- 本地进程生命周期；
- 本地路径和文件权限；
- 本地日志读取；
- 安全凭证管理；
- 软件更新；
- 系统托盘；
- 桌面通知；
- 窗口管理；
- 操作系统信息；
- 将受控本机能力暴露给 Vue。
- 代理 Desktop Vue 与 Local Agent 的受控同步调用，不在 Vue 中暴露 Agent 凭据和底层端口。

## 15.3 Agent 负责

- 浏览器自动化；
- 合成执行；
- 发布执行；
- 互动执行；
- 依赖具体业务流程的本地任务；
- 执行日志；
- 执行结果采集。
- 同步调用 BitBrowser Local API，并对外部修改执行必要读回；
- 在专用batch/item中逐项执行Profile、代理、Cookie、账号检查和上号步骤。

## 15.4 事实来源原则

> Cloud 是业务数据、任务定义和最终任务状态的唯一事实来源。

Tauri 不重新实现素材、发布和互动等 Cloud 业务领域；Agent 不管理用户、权限和业务真相。

# 16. Desktop 独有功能实现规范

每个 Desktop 独有功能拆成两部分：

```text
Vue 展示和交互
→ wt-media-cloud/web/src/apps/desktop

原生能力实现
→ wt-media-desktop/src-tauri
```

## 软件更新

前端负责版本、更新日志、进度、确认和错误展示；Tauri 负责检查、签名验证、下载、安装和重启。

## 本地 Agent

前端负责状态、按钮、依赖、当前任务和日志展示；Tauri 负责进程、端口、健康检查、sidecar、崩溃检测和依赖安装。

## 本地设置

前端负责表单；Tauri 负责配置读写、安全存储、目录校验和系统设置应用。

# 18. 前端构建与产物交付规范

采用单一前端工程、双入口、双构建：

```text
apps/cloud/main.ts
→ dist-cloud
→ Cloud 部署
```

```text
apps/desktop/main.ts
→ dist-desktop
→ wt-media-desktop
→ Tauri 打包
```

推荐由 `wt-media-workspace` 联合构建：

```text
wt-media-cloud/web
    ↓ build:desktop
dist-desktop
    ↓ 复制构建产物
wt-media-desktop/.generated/frontend
    ↓
tauri build
```

Tauri 配置指向稳定目录：

```json
{
  "build": {
    "frontendDist": "../.generated/frontend"
  }
}
```

# 19. API 契约与认证规范

以 `wt-media-cloud/contracts/OpenAPI` 作为 Cloud API 契约来源，生成到：

```text
web/src/generated/api/
```

规则：

1. 自动生成目录禁止手工修改；
2. API 变化后重新生成；
3. 业务模块在生成客户端之上封装业务语义；
4. 不重复手写请求和响应类型；
5. Cloud 与 Desktop 共用同一套客户端。

Desktop 认证建议：

- Access Token 保存在前端内存；
- Refresh Token 或长期凭证存入 Tauri 安全存储；
- Desktop Vue 直接使用 Access Token 调用 Cloud API；
- 不在 localStorage、日志、URL 参数或明文配置中保存敏感凭证。

# 20. 明确禁止事项

1. 禁止在 Cloud 和 Desktop 仓库分别维护重复业务页面；
2. 禁止把 Tauri、本地 Agent、文件系统、更新和安全存储实现放进 `shared`；
3. 禁止所有 Cloud 请求默认经过 Tauri；
4. 禁止页面直接大量调用 `invoke()`；
5. 禁止使用大型 `utils.js`；
6. 禁止单一路由表依赖大量平台守卫；
7. 禁止引入第二套完整 UI 组件库；
8. 禁止将本地即时事件当作最终业务状态；
9. 禁止 Tauri 重复实现 Cloud 业务领域；
10. 禁止 Agent 管理用户、权限和业务真相。

---

# 21. 渐进迁移原则

推荐顺序：

1. 建立 `apps/modules/shared/generated`；
2. 迁移 Desktop Vue 入口和独有页面；
3. 拆分 Cloud/Desktop 路由和菜单；
4. 将 Accounts、Tasks、Dashboard 迁入共享模块；
5. 将 Users 迁入 Cloud 独有页面；
6. 建立 Desktop Runtime；
7. 将 Tauri 调用从页面移入 Runtime；
8. 调整 API 客户端结构；
9. 引入 OpenAPI 代码生成；
10. 配置双 Vite 构建；
11. 由 Workspace 复制 `dist-desktop`；
12. 删除 Desktop 仓库中的旧 Vue 工程。

每一步必须独立验证：

```text
npm run build:cloud
npm run build:desktop
cargo tauri build
```

# 22. 最终架构原则

1. Cloud 与 Desktop 是两个前端应用，但共享一套 Vue 源码工程；
2. 共享业务放 `modules`，平台独有功能放 `apps`；
3. 通用基础能力放 `shared`，但 `shared` 不依赖具体平台和业务；
4. Desktop Vue 页面位于统一前端工程，Desktop 原生能力位于 Tauri 仓库；
5. Desktop Vue 直接调用 Cloud API，不通过 Tauri 转发普通业务请求；
6. Cloud 是业务数据、任务定义和最终任务状态的唯一事实来源；
7. Tauri 负责本机系统能力和 Agent 生命周期，不实现 Cloud 业务领域；
8. Agent 负责具体自动化执行，不管理用户、权限和业务真相；
9. 所有 Tauri 能力通过 Runtime/Service 封装；
10. 本地即时状态可以通过 Tauri Event 展示，但最终状态必须回写 Cloud；
11. 禁止复制页面、禁止双 UI 体系、禁止模块依赖越界；
12. 纯 Cloud、纯本地和混合业务必须使用对应通信模型。

---

# 23. 一句话架构定义

> `wt-media-cloud/web` 维护 Cloud 与 Desktop 的全部 Vue 前端源码；Cloud 与 Desktop 通过独立入口装配共享业务模块和各自独有页面。Desktop Vue 直接调用 Cloud API，通过 Tauri Runtime 调用本机能力；Cloud 保存业务真相，Tauri 管理本机环境和 Agent 生命周期，Agent 负责自动化执行。
