# 产品事实、评审意见与演进中原型的对照

当成熟项目同时存在正式 PRD、评审文档、设计稿或持续演进的原型时，使用本参考。

## 不采用简单的“谁优先”规则

不同资料回答不同问题：

- **正式 PRD / 契约 / ADR：** 当前批准的业务含义、对象与数据契约、权限和验收要求。
- **用户确认的决策：** 产品负责人明确作出的选择，包括当前设计过程中已确认但尚未回写 PRD 的决策。
- **评审文档：** 产品探索、问题描述、备选方案、建议、人工反馈和决策成熟度。评审文件可能同时包含已确认决策和未批准建议。
- **原型：** 当前已经实现的表达，以及可实际体验的证据。原型不能证明其业务语义正确或已经获批。
- **前端规范 / common 参考：** 公共视觉与交互约定，不负责定义模块专属业务事实。

没有任何一个来源在所有问题上都天然优先。必须判断具体事实由谁维护、当前成熟度是什么。

## 对照流程

1. 阅读最新正式 PRD 和相关评审资料，不沿用过期摘录。
2. 提取用户明确确认的决策及其准确范围。不能因为一项建议出现在 review 文件或已经写进原型，就将其升级为已确认。
3. 检查相关原型的实际行为，识别它与 PRD、review 的差异。
4. 按主题对照：对象职责、用户流程、字段/指标定义、生命周期/状态、权限、跨模块交接、异常恢复和界面表达。
5. 将每项差异分类：
   - **一致：** review 只是补充展示方式，没有改变 PRD 事实。
   - **PRD 细节缺口：** review 补充了 PRD 尚未说明的体验细节。
   - **评审建议：** 有价值，但尚未确认。
   - **已确认但未回写的产品变化：** 用户已经确认，PRD 需要有控制地更新。
   - **真实冲突：** 不同来源对业务行为或数据语义给出了不同规定。
   - **仅原型偏离：** 代码与现有决策不一致，且没有支持该变化的确认记录。
6. 从运营理由、简洁性、数据真实性、权限、实现证据和跨模块影响评估，推荐最小且自洽的解决方案。
7. 有依据的 D2/D3 展示决策可自主收敛。D1 业务/数据/权限/核心流程冲突必须整理为简洁问题并附推荐方案，不能静默改写正式事实源。
8. 获得批准后，在原有归属的 PRD/规范中直接更新。不要另建一份“最终设计 PRD”。验收前，当前模块工作稿仍是设计讨论的工作入口。

## 差异报告格式

| 主题 | 正式事实 | Review / 用户决策 | 原型证据 | 判断 | 推荐方案 | 是否需批准 |
|---|---|---|---|---|---|---|

使用准确的章节引用。区分“PRD 未提及”和“PRD 明确冲突”。review 中有 PRD 未写明的细节，不自动代表冲突。

## 特别注意

- 原型可能模拟并不存在的数据、状态、API、批次 ID 或外部平台行为。不得将其描述为已交付能力。
- 正式 PRD 可能过时或内部矛盾。它是当前批准基线，但不是不可质疑的真理；有充分产品证据时应提出修订建议。
- review 文件可能保留早期方案和已否决建议。只有当前有效决策可以指导实施。
- UI 上的状态标签不等于底层状态机定义。
- 新增聚合视图不自动意味着需要新增业务实体或数据库表。
- 便捷入口可以跳转到其他模块，但不应因此转移该模块的业务流程归属。
- 数据能力尚不可用时，应明确提示限制或暂缓展示字段；不得用语义相近但不同的指标替代。
