# PRD、评审意见与演进中原型的对照

当多个资料来源对同一产品有不同描述时，用本参考帮助判断。局部小改动无需机械完成整份差异审计。

## 不简单规定谁永远优先

不同资料通常承担不同职责：

- **正式 PRD / 契约 / ADR：** 当前批准的业务含义、对象/数据契约、权限和验收要求。
- **用户明确确认的决定：** 产品负责人在讨论中明确作出的选择；较新的明确决定可以改变旧方案，但应识别是否需要同步正式文档。
- **评审文档：** 问题、探索、备选方案、建议、人工反馈和决策成熟度；其中可能混有历史方案和已确认结论。
- **原型：** 当前实现和可体验证据；不能仅凭“代码存在”推断业务规则已经批准。
- **前端规范 / common：** 公共视觉和交互约定，不负责定义模块业务事实。

判断时考虑内容归属、更新时间、作者权限、明确确认程度和影响范围。最新内容不一定自动正确，正式 PRD 也不一定永远最新。

## 实用对照方法

1. 阅读与当前任务有关的最新资料，不要重复审计无关部分。
2. 找出用户明确确认的结论，避免重复提问。
3. 检查原型实际做法，区分真实能力、演示数据和视觉表达。
4. 只有发现实质差异时才分类：展示细节补充、PRD 细节缺口、已确认但未回写的变化、待确认建议、真实业务/数据/权限冲突，或原型偏离。
5. 结合用户任务、数据真实性、运营效率、实现成本和跨模块影响，推荐最简单合理的解决方案。
6. 高影响决定需要人工确认时，集中给出推荐和影响；其他事项自主推进。
7. 决策稳定后更新原有 PRD/规范，不另建一份平行“最终 PRD”。

## 特别注意

- “PRD 未提及”不等于“PRD 明确禁止”。
- Review 中出现不等于已经确认；原型实现也不等于业务已经存在。
- 旧 PRD 可能需要更新；不要以文档权威为理由保留明显不合理体验。
- 不能把本地模拟 ID、批次、统计或日志描述为真实后端能力。
- 不要为了展示简洁而合并语义不同的数据状态。
- 只在当前任务确实需要时才输出逐项差异表；简单问题用结论和理由即可。
