# 工作方式参考

本文件是思考路线，不是每次任务都要逐项打勾的流程。根据任务大小、风险和已有信息选择必要步骤。

## 1. 理解当前问题

弄清用户要完成的事情、目标用户、当前痛点和本次修改范围。按需查看相关 PRD、评审记录、设计规范、组件和原型。

如果 PRD、review 和原型并存，使用 source-reconciliation.md 理解它们各自代表什么；不必为了局部修改而审计无关模块。

## 2. 形成产品判断

当业务逻辑尚不清楚时，关注真正影响方案的对象、角色、流程、数据来源、状态、权限和异常情况。

不要为了形式完整，把所有分析维度都写一遍。优先发现：
- 用户实际要完成什么任务；
- 当前方案哪里妨碍完成任务；
- 哪些数据和状态是真实可信的；
- 页面与上下游如何衔接；
- 哪些决定会影响业务语义或风险。

## 3. 设计交互与视觉

明确用户完成任务所需的关键操作、反馈和恢复路径。使用项目现有设计系统和公共模式，按真实内容密度组织页面。

不要把所有页面强制做成同一布局；统一的是组件语言、交互习惯和视觉秩序，而不是业务表达完全相同。

## 4. 推进实施

把设计结论转成清晰的修改范围和验收要点。小改动不需要长篇交接；跨页面或复杂任务才使用完整交接模板。

对没有后端支持的能力，明确区分“设计建议”“原型模拟”和“真实已实现”，不编造 API 或数据。

## 5. 按风险验证

优先验证本次修改影响的关键路径、重要异常和受影响的公共组件使用方。无需每次机械重跑所有场景。

报告实际验证了什么、没有验证什么，以及是否存在残余风险。

## 6. 里程碑收敛

在页面、模块、阶段完成或准备交接时，合并重要决策：保留一个当前有效结论，删除当前稿中的重复内容和无效过程；重要分歧保留必要理由；未决的高影响事项明确标出；稳定结论同步到项目原有事实源。

不要把每轮对话、每个视觉微调都变成正式决策记录。
