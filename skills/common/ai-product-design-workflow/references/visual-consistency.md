# 视觉一致性与设计复用

## 检查顺序

1. 阅读项目设计规范和前端规则；
2. 检查真实公共组件、主题和样式实现；
3. 检查 common 中的视觉与交互参考；
4. 对照已经验收的相邻页面；
5. 最后设计当前页面特有的组合方式。

文档描述预期规则，代码体现当前实现。如果两者不一致，应指出差异，不要默默选择对自己最方便的一方。

## 复用边界

- 基础控件和弹层：复用项目选定的组件库；
- Token/主题：使用项目唯一的维护来源，不重复硬编码；
- 跨页面模式：复用或扩展真实存在的共享 UI 能力；
- 业务模式：留在所属业务模块；
- 一次性页面布局：确有独特需求时允许局部样式。

静态 common HTML/CSS/JS 展示库可能只是设计参考，不一定是生产运行时组件库。除非项目明确允许，否则不要将演示脚本引入业务运行环境。

## 一致性检查

对照代表性页面检查：
- 页面标题和主操作的位置；
- 筛选区间距、应用/重置和高级筛选；
- 表格密度、表头、排序、复制和分页；
- 状态文案与语义颜色；
- 行操作和更多菜单；
- Drawer/Dialog 的标题、宽度、底部操作、关闭与焦点行为；
- 空、加载和错误反馈；
- 字体、间距、边框和响应式行为。

一致性意味着共享模式的表现和行为一致，不意味着不同任务的页面必须采用完全相同的布局。

## 克制设计

优先采用能够解决实际问题的最小改动。没有明确用户任务价值时，不增加装饰卡片、指标、标签页、状态徽标、筛选项或设置项。保持运营后台需要的信息密度。页面特例必须有明确理由，不能悄悄改变共享基线。
