# Skill 验收场景

以下场景用于抽查 Skill 是否具备良好判断力，不是每次任务都必须执行的流程，也不要求代理使用固定措辞或固定文档格式。

验收关注结果：是否理解用户目标、做出合理判断、避免重大错误、减少无意义的人为打断，并能适配不同项目。只检查与场景有关的资料，不要求无差别扫描所有文件。

## 场景 A：现有项目中原型与 PRD 不一致

产品负责人要求优化一个管理后台列表。PRD 定义业务状态和角色范围；当前原型多展示了几个后端状态，并重复放置一个操作。Common 有可复用的表格和 Drawer 模式。

通过表现：
- 能找到与本次修改有关的业务事实、规范和实现；
- 不把原型现状误认为已确认业务规则；
- 复用合适的公共模式，或说明现有模式为何不合适；
- 主动区分事实、建议和真正未决的问题；
- 不重复询问已有明确答案，也不擅自修改无关页面。

## 场景 B：业务规则缺失

用户要求展示“素材使用次数”并支持排序，但现有资料没有定义“使用”的统计口径，可能指任务尝试、成功成片、使用人数或发布次数。

通过表现：
- 识别不同口径会改变数据含义；
- 给出推荐及其业务原因；
- 只在确实无法合理推断时集中询问关键决策；
- 继续推进不依赖该定义的工作；
- 不把自己的建议伪装成用户确认。

## 场景 C：里程碑收敛

讨论中有重复结论、已否决方案和仍有争议的选项，用户要求准备实施交接。

通过表现：
- 当前有效结论清楚，不让旧方案干扰执行；
- 保留真正重要的分歧和未决风险；
- 交接信息与任务复杂度相称；
- 不为普通细节建立大量决策记录。

## 场景 D：在另一个产品中复用同一 Skill

一个新 SaaS 项目有不同术语、设计 Token 和组件库。

通过表现：
- 适配新项目，不带入其他项目的业务规则或 UI 假设；
- 优先复用该项目真实能力；
- 不创建重复 PRD 或组件库；
- 根据任务选择必要工作步骤，而不是机械执行全套流程。

## 场景 E：正式 PRD、长期评审文档与演进中原型并存

一个成熟产品同时存在 PRD、多轮评审和可运行原型。部分评审建议已确认，部分仍是建议，还有一些与 PRD 不一致。

通过表现：
- 能判断不同资料的职责和成熟度；
- 不认为 PRD 永远正确，也不把 review 全部视为已批准；
- 识别原型模拟行为与真实能力的区别；
- 对真正影响业务的数据/权限/流程差异给出推荐和影响；
- 不重复询问已确认的决策；
- 不为局部修改制造一份平行 PRD 或无必要的差异报告。

## 验收记录

实际运行时记录 PASS / NEEDS IMPROVEMENT / NOT RUN 和具体证据。场景用于检查判断质量，不应反过来成为限制模型思考方式的僵硬脚本。
